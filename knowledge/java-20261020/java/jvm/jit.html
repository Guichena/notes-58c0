字节码执行与动态编译

归属：Java → JVM → 执行引擎。本文以 HotSpot 21 的常见执行方式为主，区分 Java 语义、虚拟机实现和具体负载下的优化结果。类的生命周期、对象分配和诊断证据各有独立主题，这里只连接它们与代码执行的关系。

1. “编译还是解释”不是语言的单选标签

Java 源码通常先由 javac 编译为 class 文件。class 不只是字节码指令，还保存类型、字段、方法、常量池和属性等结构；它不是可以直接交给任意处理器执行的机器码。其他语言也可以生成符合要求的类文件。

运行时先要让类型可用，再执行方法。类加载、验证、链接与初始化解决“这是什么类型、引用如何关联、静态状态是否就绪”；执行引擎解决“方法的行为如何落实”。二者有关联，但不是同一个过程。

HotSpot 可以解释字节码，也可以执行 JIT 编译得到的本地机器码。解释器处理的是字节码语义，不是逐行重新读取 Java 源码，更不是规定每条字节码都先单独生成一小段机器码才能执行。因此，准确的描述是“源码编译为字节码，运行时可结合解释与动态编译”，而不是给 Java 永久贴上纯解释型或纯编译型标签。

这里的“先解释、热点后编译”是理解常见策略的入口，不是 JVM 规范要求所有方法必须遵守的固定时间表。具体虚拟机、执行模式和编译策略可以不同；不能从某个 HotSpot 配置推断所有 Java 运行环境。

2. JIT 的关键是让优化成本花在值得重复执行的代码上

JIT，即即时编译器，在运行过程中把选中的代码编译为目标平台机器码。它不仅改变指令形式，还可能利用运行时信息优化执行路径。

编译有成本：分析和生成代码消耗 CPU，生成结果占用 Code Cache，收集剖面和逐步形成较优代码也需要时间。如果一个方法只执行一次，花很大成本优化它，未必能从后续执行中收回收益。反过来，一个长时间反复执行的计算，即使编译较贵，也可能通过多次调用摊薄成本。

“热点”因此不是代码看起来复杂，也不等于某个业务接口最重要。调用频率、循环回边、类型剖面以及编译队列和运行时负载，都可能影响选择。不能背一个调用次数，便承诺达到该数值一定由某级编译器编译。

例如，启动时只用一次的配置解析与持续处理请求的解析路径，优化价值可能不同；但这只是解释成本模型，不是对某个实际系统的性能结论。启动阶段也可能有值得编译的热点，冷代码也不保证永远不会被编译。

3. 分层编译是动态接力，不是每个方法必经的流水线

HotSpot 21 常见的分层编译结合解释器、C1 的较快编译与剖面收集，以及 C2 的更深优化。运行时不必等所有代码完成高成本优化才开始提供服务；较快得到的执行版本还可以帮助收集进一步优化所需的信息。

各方法不必按同一顺序走完全部层级。有的方法始终不够热，有的跳过中间状态，有的后续需要重新编译。编译通常可与应用执行并行推进，结果安装后，后续调用能够进入相应的编译入口；其他代码仍可解释执行。编译线程同时也会竞争进程的 CPU 资源，并非没有业务成本。HotSpot 21 性能说明

一个方法可能只调用一次，却在内部循环很久。如果只能等下一次调用再使用机器码，就会错过最有价值的执行区间。OSR（栈上替换）允许运行时在合适的位置把正在执行的方法状态转换到编译版本，继续处理剩余循环。它描述的是执行状态切换，不是把对象分配到线程栈，也不意味着可以在任意指令处随意切换。

4. 优化的收益来自扩大分析范围，但优化也受预算约束

内联把被调用方法的逻辑纳入调用点，减少调用开销只是其中一部分价值。更重要的是，编译器可以看到跨方法的数据流，进而发现常量、无用分支、冗余计算或可以简化的对象操作。

在满足条件时，编译器可能进行常量传播与折叠、死代码消除、循环优化、边界检查优化和分配消除。但“源码具备某种形式”不等于“本次执行已采用某项优化”：调用形态、可见类型、内联机会、编译预算以及具体实现都影响结果。

内联也不是越多越好。过度展开会增加机器码体积，消耗编译预算，并可能增加指令缓存压力。短方法不保证内联，长方法也不能仅凭行数断言一定不会内联。讨论优化时，应说明成立条件，而不是把优化名称当成性能保证。

逃逸分析属于这种分析链条。它关注对象如何被使用，可为标量替换、分配消除或锁消除提供条件。一个只在局部使用的对象，不代表一定被改造成完整的栈对象；未能证明安全或未满足优化条件时，仍可能正常分配。对象表示与分配边界见《JVM对象分配与表示》，这里不重复其完整机制。HotSpot 逃逸分析说明

5. 推测优化必须保留回到正确语义的路径

运行时信息提供了静态编译时未必能确定的机会。例如，一个接口调用点在目前负载中总遇到同一种实现，编译器可能在相应检查或依赖保护下直接调用或内联目标，减少通用动态分派的成本。这类去虚拟化不是宣布其他实现永远不存在。

当后来出现不同接收者类型，或依赖的类层次条件发生变化时，运行时需要选择保守路径，必要时反优化，使旧的优化结果不再作为有效执行依据。反优化利用保留的状态信息重建可继续执行的状态；如果某些对象此前被消除，还可能需要重新物化。

因此，“机器码已经生成”不意味着它永远适用，“发生反优化”也不等于 JVM 算错了。保留检查、依赖和状态恢复机制，正是为了在运行环境变化时继续遵守程序语义。

真正需要警惕的是反复失效、重新编译与业务退化是否构成同一条证据链。一次事件、一次类型变化或一个编译日志名称，都不能单独证明它是延迟根因。诊断方法归入《JVM诊断证据与调优权衡》，而不是据此直接关闭某类优化。

6. 预热不是“所有第一次慢都由 JIT 造成”

第一次请求可能涉及类加载、静态初始化、连接建立、缓存填充、数据访问以及编译预热。即使稍后变快，也不能只凭时间顺序把收益全归给 JIT。

应分开两个问题：应用多快能够完成有用工作，以及运行一段时间后在代表性负载下表现如何。长时间服务可能更容易摊薄编译成本；生命周期很短的任务则可能在充分获益前已经退出。不过，业务持续时间并不是唯一条件，热点稳定性、资源配额和请求分布同样重要。

Code Cache 存放生成的本地代码等内容，不是 Java 对象堆。增加 Java 堆上限并不能等价解决所有执行引擎内存需求；编译 CPU、代码缓存和元数据应放入整个进程资源预算中理解，详见《JVM运行时区域与进程内存》。

在阅读性能结论时，还要问：比较的是冷启动还是稳态？输入是否代表真实负载？计算结果是否真的被使用？常量折叠、死代码消除或分配消除，可能让一段看似繁重的源码在实际执行中只剩很少工作。因此，单次循环耗时不能证明某类对象都在栈上，也不能从简单算术结果推出整个服务的吞吐收益。这里是评价证据的原则，不是要求运行实验。

7. 跨平台的是行为契约，不是同一份本地机器码

类文件和 JVM 行为契约提供可移植基础，各操作系统和 CPU 平台仍需要兼容实现。JIT 生成的机器码面向具体指令集和调用约定，不能把它当作可直接跨任意平台复用的 class 文件。

实现层可以复用类文件解析、类型管理、部分中间表示与优化逻辑，以及 GC、同步等通用协议。CPU 后端处理指令选择、寄存器约束、原子操作和机器码生成；操作系统适配层处理线程、虚拟内存、文件和等待唤醒；操作系统与 CPU 的组合层还要处理信号上下文、异常恢复等交叉问题。HotSpot 的共享代码和平台目录体现了这种分工，但分层接口比目录名称更重要。

例如，不同处理器可以用不同指令实现同样的 Java int 溢出语义。同步既要遵守互斥、重入和内存可见性要求，也可以采用不同的无竞争路径、原子操作或阻塞机制。不能声称每次 synchronized 都调用同一个操作系统互斥函数，也不能认为每条字节码都会进入内核。同步语义见《synchronized与Lock》及《volatile》，这里保留的是公共语义与平台实现的边界。

JVM 移植还涉及工具链、ABI、JNI、本地库和异常恢复等。应用层也可能依赖路径规则、字符编码或特定本地库；“有 JVM”并不保证所有外部依赖无需适配。解释器与 JIT 都必须服从语言与虚拟机的正确性要求，而不是为了速度改变可观察行为。

8. AOT 与 JIT 的比较必须先说清具体路线

AOT 泛指提前完成一些运行时工作，但不同产品提前做的事情并不相同。提前生成目标机器码，需要讨论部署目标以及动态加载、反射等能力的支持边界；提前保存类加载或链接结果，则不等于把整个应用转换成独立本地可执行文件。

例如 JDK 24 的提前类加载与链接属于后者，不应与各种 native-image 路线混称为同一功能。它也不自动取消运行时的 JIT。比较时要明确版本和产品，再讨论启动、稳态吞吐、内存、训练或构建成本，以及动态能力；不能脱离这些条件宣布 AOT 永远优于 JIT，或 JIT 必然提供更高峰值。JDK 24 提前类加载与链接

最终应串起一条因果链：规范化字节码让程序有共同执行入口，解释与分层编译控制启动和优化成本，运行时信息为优化提供条件，检查与反优化守住正确性，平台适配把同一语义落到不同硬件。性能收益属于具体负载下需要证据支持的结果，而不是这条链条自带的承诺。
