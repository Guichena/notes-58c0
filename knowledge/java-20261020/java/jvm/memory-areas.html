JVM 运行时区域与进程内存

理解 JVM 内存，需要同时回答三个不同的问题：程序执行需要哪些逻辑结构，具体虚拟机把它们放在哪里，整个进程最终消耗多少资源。这三层不能用一张“五个盒子”的图代替。

本文以 Java SE 21 的运行时模型、HotSpot 21 的实现为主要边界。历史永久代单独注明；讨论的是内存区域，不是 JMM 的可见性与 happens-before。两者的联系在于：共享对象的存储位置不能代替正确的发布与同步协议。

1. 先按职责分区，再问实际实现

程序计数器、JVM 栈和本地方法栈主要服务线程的执行状态；堆与方法区主要承载可被多个线程使用的对象和类结构。

“线程私有”描述执行状态的归属，不代表栈里引用的对象也私有。“线程共享”表示允许通过引用共享，不代表每个堆对象都被多个线程访问，更不代表访问自动线程安全。

方法区是规范概念。JVMS 在逻辑上将它视为堆的一部分，但不强制它采用普通对象堆的分配和回收方式。实际讨论 HotSpot 时，“Java 堆”通常专指对象堆，“元空间”则指类元数据相关的本地存储。两种语境必须分开，不能从规范的逻辑包含关系推导物理地址重叠。规范还单列运行时常量池来解释其职责；常用“五区”记法把它归入方法区，并不表示只有五种物理内存开销。规范依据：JVMS 21 §2.5

2. 一次方法调用需要保留什么

程序计数器描述线程当前执行的 JVM 指令位置，不是源代码行号，也不是“每个方法都有一个永久计数器”。执行 native 方法时，规范中它的值未定义；它不要求始终对应某个实体 CPU 寄存器。线程切换后能继续执行，是理解这份独立执行位置的直观方式，但操作系统保存的完整上下文远不止它。

一次 Java 方法调用在逻辑上产生栈帧。可以把栈帧理解为这一层调用的工作现场：

  • 局部变量表保存参数及局部值，包括基本值和引用；实例方法还需要接收者 this。
  • 操作数栈承接字节码运算的中间结果，不等于线程的整个调用栈。
  • 与当前类运行时常量池的联系支持字段访问、方法调用等动态链接。
  • 返回及异常传播需要恢复调用方的执行状态。

正常返回与异常退出都会按调用关系结束相应帧的生命。这里的“一调用一帧”是解释程序的逻辑模型：解释执行、JIT 编译和内联可能产生不同的物理表示；局部值也可能在寄存器中或被消除。局部变量槽位数、源代码变量数、实际栈字节数不是同一个量。

本地方法栈支持本地代码执行；native 调用不等于系统调用，也不保证每次都进入内核。HotSpot 可以让 Java 调用与本地调用使用相联系的线程栈设施，不应画成两块必须完全独立的连续地址区。规范中的帧与调用状态

3. 栈和堆的根本差别是生命周期，不是变量类型

方法调用结束时，执行现场可以按调用顺序撤销；对象却可能跨越这次调用继续存活。将二者分开管理，才能同时支持廉价的调用状态维护、返回对象、缓存以及跨线程传递。

设一个方法创建列表，并将它放进长期缓存。方法内的局部引用属于该线程的调用状态，列表及其元素通常属于堆对象；一旦缓存持有列表，方法返回并不会销毁列表。相反，如果所有有效保留路径都已消失，对象也不一定要等到源代码块的右花括号才具备回收条件。

因此，“基本类型都在栈，引用类型都在堆”是错误的：对象内部的 int 字段属于对象存储，局部变量表里也可以有引用。数组是对象，局部数组变量和数组内容不是一回事。

栈帧的进入退出通常不靠普通对象的垃圾回收流程维护，但 GC 仍需要识别执行状态中的活跃引用。不能把“不靠 GC 弹出栈帧”改写成“GC 完全不看栈”。对象是否真正分配、是否被标量替换，继续看《JVM对象分配与表示》，这里不重复对象头和分配路径。

也不能按“栈连续，堆不连续”直接推导速度。规范并不要求 JVM 栈连续；虚拟地址连续不等于物理页连续。HotSpot 的对象分配可以走很短的 TLAB 快路径，访问代价又受局部性、缓存、间接引用和同步影响。两者承担不同的生命周期要求，不存在脱离操作与实现的统一快慢排名。

4. 方法区、元空间、static 与常量池分别指什么

以 HotSpot 21 为例，一段类相关数据可以分成几层理解：

  1. 字段和方法的名称、描述符、修饰符、字节码等类相关结构，主要依托本地元数据存储。
  2. java.lang.Class 镜像本身是堆对象。static 字段的当前值与类镜像布局相关，不应将它们全部归入元空间。
  3. 引用型 static 字段保存引用，被引用的普通对象仍在 Java 堆。字段元数据、引用值、目标对象必须分开。
  4. JIT 生成的机器码涉及 Code Cache；一次执行中的局部值属于那次调用状态。每个实例不复制一份方法体，也不意味着一个方法永远只有一份不变的编译代码。

具体的 static 三层定位在《JVM对象分配与表示》的相关小节保留完整说明。本节负责将它放回整体内存地图，避免建立第二套相互冲突的定义。

“常量池”同样不是唯一一块存储：class 文件里的常量池描述符号与常量；运行时常量池是每类或接口的运行时结构；字符串驻留机制负责规范化字符串引用。它们有关联，但不能画成同一个字符串容器。现代 HotSpot 的 String 对象及内容数组在堆中，元数据里存在字符串相关符号，不等于对应 String 对象也在元空间。

驻留也不保证字符串永久存活。实际是否可回收，还取决于已加载类的关联、static 字段、缓存等保留路径；仅把一个局部变量设为 null 不能证明所有引用消失。完整字符串身份、intern 与拼接规则属于字符串主题，本章只保留位置和生命周期边界。

5. JDK 8 移除永久代，解决的是哪一层问题

JDK 8 的 HotSpot 移除了永久代，类元数据主要转向本地 Metaspace。这个变化不能概括成“方法区消失”，也不是把过去所有类相关内容一次性搬到堆外。历史演进中，字符串和静态数据的存储也要按具体 JDK 区分，不能将 JDK 7 及以前一概画成同一张图。

本地内存让类元数据不再受永久代那套容量管理方式限制，但本地内存并非无限，更不意味着绕过操作系统和容器预算。元空间增长仍可能碰到自身限额、相应类空间限额或进程资源边界。永久代也不是永远固定不变的一块容量；它有容量与上限管理，不能用“永久代固定，元空间无限”解释整个设计。

MetaspaceSize 的主要含义是初始元数据回收高水位，不是启动时必须占满的固定容量；MaxMetaspaceSize 表达相应使用上限，不是泄漏修复机制。这里只说明参数语义，不提供一套脱离负载的配置值。HotSpot 的元空间实现说明

动态生成类本身不是泄漏。关键是类及其加载器的生命周期：热更新后的旧加载器，如果还被长寿命线程、上下文加载器、注册表或缓存留住，其关联元数据也可能继续存活。卸载需要满足条件且依赖回收时机。设上限能限定一种失败边界，却不能替代解除不合理保留关系；把上限调大也只可能推迟失败。

6. 栈溢出、OOM 与系统终止不是同一种错误

先按“什么请求无法满足”分类，才知道为何堆还有空间也会失败。

  • StackOverflowError：调用所需栈深超过允许范围。无终止递归和过深调用链是典型原因；有限递归也可能超预算。它不是因为“所有堆对象塞满”。
  • 栈相关 OutOfMemoryError：规范允许动态扩展栈时，扩展申请无法满足，或新线程的初始栈无法创建。它与超过允许栈深是两个条件。本地方法栈的规范同样包含 SOE 与 OOM，不能只列 OOM。
  • Java heap space：对象堆分配无法满足。可能是泄漏，也可能是合法活集过大、单次大申请或短时并发峰值。
  • Metaspace / Compressed class space：相应类元数据资源不足。增加对象堆上限并不直接取消这些边界。
  • direct buffer memory：直接缓冲相关预算或资源不足。直接缓冲的堆上包装对象与本地内容分属不同预算；小视图也可能保留整块大缓冲。
  • unable to create native thread：还要考虑平台线程数量、本地内存、系统或容器任务数限制，并非一定是 Java 堆不足。
  • 系统或容器直接终止进程：可能根本没有 Java OOME 或堆转储。一个退出码也不能独立证明 OOM kill。

程序计数器应表述为“JVMS 没有为该区域规定 OOM 条件”，不是整个线程永远不会遭遇内存失败。将过深调用与创建/扩展资源不足区分，正是规范异常分类的意义。JVMS 栈异常边界

OOM 不等于泄漏。泄漏关注业务已不需要的资源为何仍被保留；OOM 关注分配为何失败。最后一次失败的分配位置也不一定是长期保留者。完整保留链分析、直接缓冲的租约/归还和故障恢复属于对应诊断主题，不能用一句“加堆”抹去差别。

7. 虚拟线程进一步说明逻辑区域不等于固定地址块

Java 21 虚拟线程仍有独立的逻辑调用状态，但它与平台线程不是“一对一独占同样大小本地栈”的关系。HotSpot 的虚拟线程栈状态可以存放于 Java 堆中的 stack chunk，并由载体线程承载执行。因此，线程私有是归属语义，不能机械推导所有私有状态都必须位于 Java 堆外。

堆中的栈块还要参与堆的资源管理，不能将其 GC 根语义完全照搬平台线程本地栈。这也不意味着无限创建虚拟线程毫无成本：每项任务持有的请求上下文、缓冲和待处理结果仍可能形成很大的活集。JEP 444 的栈与 GC 边界

8. 从区域知识推到整个进程的预算

Xmx 只约束 Java 堆，不是 JVM 进程总上限。类元数据、平台线程栈、Code Cache、直接缓冲、GC 辅助结构、JIT、本地库和映射等也会消耗资源。把堆配得更大，有时反而压缩线程与本地分配的余量。

还要区分三个观察口径：虚拟地址保留不等于已经提交；提交不等于所有页面当前驻留；RSS 也不等于 Java 堆已用。PSS 会按共享者分摊共享页面，而容器计费可能包含同组其他进程及被计费缓存。对象变得不可达、空间可被 JVM 复用、页面归还操作系统，是不同阶段。释放后 RSS 没立即下降，不足以单独证明泄漏。

对资料处理链路，预算应沿数据生命周期建立：原始字节、解码文本、解析树、分片、序列化副本分别在哪个进程，哪些阶段同时存活，再叠加并发任务和排队数据。入口单文件限额不是内存峰值；异步化缩短请求等待，也可能增加在途任务数。Java Host 与 Python Worker 若共用总资源上限，两边工作集必须一起考虑，Java 的堆转储不能解释 Python 的全部占用。

既有 NoteWeave 材料按 128MB 单文件能力设计，并记录单文件及整个 multipart 请求上限为 128MiB。这是材料中的设计条件，不代表已核验当前部署；请求封装也要占用总请求额度，不能把该数字直接换算成所需 Xmx。更一般的架构方向是有界并发、限制队列与缓冲、减少同时存活副本、阶段完成后解除保留，并预留峰值余量，而不是依靠一个更大的堆包办全部资源问题。

理解这条链条后，五区分类才有用：先定位逻辑职责，再对应具体实现，最后核对总资源与生命周期。内存区域解释“东西在哪里、为谁服务”，对象分配解释“如何得到存储”，垃圾回收解释“何时能够复用”，JMM 则解释“跨线程如何正确观察与访问”。
