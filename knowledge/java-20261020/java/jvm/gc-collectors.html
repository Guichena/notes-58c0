分代回收与收集器权衡

分代利用对象寿命差异组织工作，收集器则在暂停、吞吐、CPU、内存与实现复杂度之间取舍。先理解“回收什么、什么时候回收、工作放在哪里完成”，才能解释CMS、G1或低暂停收集器为何适合不同约束。

本文以HotSpot 21为主要机制边界；CMS使用JDK8历史语境。可达性、清除/复制/整理与SATB的完整解释见《GC可达性与并发回收》，这里不重复展开。

1. 分代利用的是寿命分布，不是对象大小分组

许多请求临时对象会很快死亡。若每次回收它们都扫描整个长期缓存，就反复处理大量活数据。将年轻对象集中，频繁收集较小、低存活率的集合，通常能以较少幸存者搬迁换回较多空间；长寿对象则减少接受这类高频检查。

这是经验假设，不是语言保证。老年代对象不一定更大，年轻对象也不一定短命。队列积压会让原本短期中间结果跨越多次收集；如果活集普遍长寿，分代收益就可能改变。

老年代也不固定采用一种算法：历史CMS常规老年代周期以清除为主，Parallel Old采用整理，G1对选中的老区疏散。高存活率说明整代复制可能昂贵，不说明老年代永远不能复制。

代之间并非两座隔离岛。老缓存可以指向年轻请求对象，年轻代收集必须找到这些外部入口。屏障、卡表、记忆集减少全老年代扫描，同时带来记录、处理和空间开销。收益要扣除这些维护成本。

2. Survivor 流转与晋升是有条件的策略

传统Serial、Parallel及历史ParNew的年轻代可用Eden、From、To理解：新对象通常在年轻代分配，收集时将仍须保留且适合继续年轻的对象复制到目标Survivor，达到晋升条件或Survivor容纳不下者尝试进入老年代；处理完成后回收原空间，From与To交换角色。

两个Survivor是交替角色，不要求对象先在S0待一次再在S1待一次。8∶1∶1只能在特定容量配置下作示意，不是全部收集器的恒定默认。G1用Region集合承担这些角色，不固定为三个连续地址段。

对象进入老年代至少区分年龄策略、容量压力和实现特定的大对象分配。年龄不是秒数，也不是每发生任意GC就加一。HotSpot21的年龄位可表示0至15并在上限饱和，晋升不依赖溢出；实际阈值可能低于配置上限。年龄表以各年龄幸存字节的累计量和目标Survivor容量决定策略，不是某一年龄超过“一半”就把所有对象一起搬走。

Survivor过小可能让中等寿命对象提前晋升，过大又占其他用途的预算，并可能增加重复复制。提高年龄可能减少过早晋升，也可能增加年轻代搬迁。要解释的是工作如何转移，而不是背“越大越好”。对象头年龄字段、大对象完整对齐尺寸与分配路径详见《JVM对象分配与表示》，此处不建立另一套阈值口径。

3. GC 不只在整个堆满了以后启动

TLAB不足可能换新TLAB或走缓冲外分配，不必GC。年轻代分配压力可能触发年轻代收集，而堆的其他部分仍空闲。并发周期还必须提前开始，因为回收期间应用继续分配；等彻底用尽才启动，往往来不及完成。

G1的自适应IHOP依据近期老年代分配、标记耗时和预留空间预测启动时机，历史CMS也要考虑并发完成前的空间需求。突发晋升、分配激增或CPU供给下降会打破原本足够的提前量。

元数据高水位也可能推动回收和类卸载，不能由此推断对象堆已满。System.gc()等显式请求如何处理，还受实现和选项影响，不保证总走一次相同Full路径；不用定时请求回收代替生命周期管理。

Young/Minor一般指年轻代收集；Major/Old的口径并不统一。应先明确收集器及事件含义，再讨论停顿。一次老年代并发周期不等于整堆STW，也不等于日志里每条记录都是一次暂停。

4. G1 固定区域大小，动态组织区域角色

G1将堆划成等字节大小的Region。一个进程启动选定粒度后，不会每轮随意改变单个Region尺寸；改变的是Eden、Survivor、Old、Humongous或空闲区域的角色与数量。提交更多同尺寸Region是堆扩容，不是放大每个Region。

以OpenJDK21 GA为界，自动选择与手工指定支持范围不能混为一谈：自动策略以约2048个区域为目标并在1至32 MiB内选择二的幂，手工支持范围更宽。这里不把范围当作推荐配置；具体构建和合法性检查仍需对应版本。小Region提供细粒度选集，也可能增加跨区关系和元数据；大Region改变疏散粒度及大对象门槛，未必更优。

G1仍然分代，只是不要求年轻代与老年代分别占据连续的大地址段。“区域化”不是“取消年龄和寿命分工”。保留、提交、已用和RSS的区别沿《JVM运行时区域与进程内存》理解。

5. 并发标记提供依据，Mixed 才逐批回收部分老区

G1通常经历多次Young-only暂停。需要新的老年代存活信息时，一次年轻代暂停承担Concurrent Start；之后相关根区域扫描与并发标记展开，SATB协助维护快照。Remark完成标记收尾和相应引用处理，后续准备与Cleanup等工作形成候选及阶段转换依据。

这些阶段不能逐个照抄CMS流程。完全没有须保留对象的区域可以在安全阶段归还，含活对象的普通老区不能因为“已标记完”就整区清空，仍须在适当时机疏散活对象及修正引用。

需要回收老区时，Mixed每次收年轻代，再加入部分老年代候选；候选或收益不足后回到Young-only。Mixed不是“整堆一次收完”，也不是每次Young都先启动一轮全局并发标记。

所谓Garbage First，应理解为在预测成本和回收收益之间选集。垃圾比例高的区域往往更划算，但复制量、根与跨区引用扫描、必须推进的工作及剩余暂停预算都会影响选择。Young-only不能随意跳过年轻代，只挑最脏老区；Mixed也有必须完成与可选工作之分。G1 的区域化与阶段说明

两个等大区域即使垃圾比例相近，外部引用数量不同也可能有不同扫描成本。只把每次老区选得更少，可能缩短单次暂停，却让回收长期追不上晋升。正确性和空间进展不能让位于一个漂亮的暂停数字。

6. G1 的暂停目标与空间余量都有边界

MaxGCPauseMillis是软目标。预测来自过去的存活率、扫描成本和CPU条件；活集突增、引用密集、CPU配额或调度变化、缺页等都可能使实际超出目标。并且根处理与引用修复等必要工作不能为了达标而省略。降低目标可能增加回收频率或减少吞吐，不是无代价降延迟。G1 暂停目标与调度约束

疏散需要目标空间。目标不足时，已搬迁对象和仍留原处对象必须保持一致的引用关系，恢复工作可能加长暂停；疏散失败本身不等于已经发生Full，只有空间仍无法满足等条件下才可能进入进一步兜底。HotSpot21的G1 Full采用并行整堆整理，不能叫作统一单线程Serial Old。

Humongous对象使用连续Region序列，最后一个区域可能有不能马上利用的尾部空间。即使总空闲区域数够，也可能缺少足够长的连续序列。它通常不走普通年龄晋升及每次普通疏散路径，存在标记后回收和符合条件的提前回收机制；也不能夸大成永远不移动。精确分配界限以完整对齐对象尺寸为准，见对象分配主题。

因此G1有整理能力，不等于完全没有空间浪费或连续性问题；Full整理也不能把合法活集压成零。如果活数据已超过容量，搬迁无法创造新内存。

7. CMS 是历史取舍，不是现代部署选项

JDK8背景下，CMS主要负责老年代，常与ParNew年轻代配合。初始标记和重新标记需要暂停；主要对象图追踪、预清理及常规清除尽量并发。常规路径不全面移动活对象，避免大量停顿搬迁，但留下空闲块碎片、浮动垃圾及并发CPU竞争。

碎片是布局问题；浮动垃圾是对象在本轮被保留后才失去入口的时间差。提前启动或加余量可以帮助并发及时完成，却不自动消除碎片。二者也都不应直接叫泄漏。

并发进度不足或无法满足老年代分配时，可能发生concurrent mode failure并进入前台处理。concurrent mode interruption可涉及显式或诊断请求打断周期，不能混为同一种失败。历史所谓“Serial Old后备”只是概括，具体前台压缩分支和配置有边界，不能推广成全部CMS Full或全部GC都是同一路径。

CMS在JDK9弃用、JDK14移除，HotSpot21不提供这个候选。保留它的价值是理解旧系统为何会付出碎片和失败恢复代价，而非把历史参数搬到新系统。CMS 移除记录

8. 收集器候选按机制区分，不按流行度投票

Serial以串行回收为特点，结构及开销相对简单，可作为小活集、有限CPU或小工具的候选，并非只能在物理单核运行。Parallel以暂停中的多GC线程工作为主，年轻代复制与老年代整理配合，常用于重视整体完成吞吐的负载；并行线程越多也不保证越快。

G1通过并发标记和分批停顿疏散取得平衡，不存在小于4GB就不能使用的统一门槛。ZGC和可用发行版中的Shenandoah把更多移动工作并发化，可作为严格暂停目标下的候选；它们仍需要屏障、CPU、内存余量和短暂停顿。

ZGC的有色指针与屏障帮助应用在对象并发重定位时找到正确目标，位编码与屏障分工随版本和分代模式变化。JDK21、22同时存在非分代与可选分代ZGC，不能从“选择了ZGC”直接推断已经分代；JDK23选择ZGC时默认分代，JDK24移除非分代。这个默认指ZGC内部模式，不是整个JDK默认收集器。JDK23版本记录、JDK24迁移说明。更晚版本开关生命周期仍归版本迁移主题，不用旧启动语法跨版本硬套。JDK21 分代ZGC说明

Shenandoah也进行并发疏散，但不是ZGC的另一个名称，屏障和版本演进各自不同；是否包含在所用厂商构建中需要确认。低暂停不等于零停顿，更不等于业务时延一定降低。

若分配速度超过回收速度，ZGC也可能出现allocation stall。它不是长STW，却仍增加请求延迟。并发GC与业务争用CPU时，即使暂停下降，排队仍可能增加。因此至少同时解释活集、分配突发、实际CPU供给和堆余量，不能只凭暂停图选择方案。

9. 把选择条件落回业务和资源预算

选型先明确版本与可用实现，再明确吞吐、尾延迟、内存和CPU约束。相同Xmx不等于相同总资源，堆外缓冲、线程栈、元数据及GC结构也在预算内。缓存长期保留大对象图与短命缓冲密集分配，即使堆相同，也会形成不同成本。

默认收集器只是环境中的选择规则，不是项目事实。JDK8常见HotSpot服务器配置与JDK9以后的相应服务器配置有不同默认，显式选项、厂商和资源环境仍会改变实际结果。构建文件的source/target也不能证明线上进程使用哪种GC。

资料异步流水线可作为机制推演：队列积压延长文档和中间结果寿命，可能增加幸存、晋升和活集；有界队列、缓冲和并发能从源头改变压力。Java Host与Python Worker分工不自动意味着总内存更少，也不能据此声称发生过某次生产GC优化或取得性能收益。

最终应能解释一条闭合的知识链：业务对象为何活这么久，回收器如何找到它们，本轮为何选这些区域，所需工作消耗什么资源，以及降低一种成本会把代价转到哪里。这里保留的是理解与决策边界，不提供运行实验、调参命令或未经验证的性能承诺。
