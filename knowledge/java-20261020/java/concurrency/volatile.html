volatile：从状态可见到安全发布

volatile 的作用，不是把一段代码变成“只能由一个线程执行”，而是为共享字段的读写建立明确的可见性和顺序关系。理解它，需要把三个问题分开：另一个线程能否正确观察状态，一组操作能否不可分割地完成，以及对象的初始化结果能否随引用一起交给读者。

本章按 Java 21 的语言语义解释，具体机器上的指令实现另作区分。重点是读懂并发关系，不要求运行代码。

1. 为什么共享变量不能只靠“已经改过了”

假设一个工作线程不断检查停止标志，另一个线程把标志从 false 改为 true。直觉上，两个线程访问同一个字段，写入以后，工作线程下一轮就应该读到新值。但普通字段并没有自动建立这次跨线程通信需要的同步关系。

CPU 缓存是理解问题的一条线索，却不是全部原因。编译器也可能在不违反单线程语义的前提下复用已读的值。Java 内存模型（JMM）规定的是一个线程的读取允许观察到哪些写入，而不是要求所有变量每次都从物理内存重新取值。

因此，不能用“写线程在时间上已经先运行了”“中间睡了一会儿”证明读取正确。对同一个 volatile 字段，写入与同步顺序中后续读取之间有规定的同步关系；这才是停止标志可以承担通信职责的理由。sleep 和 yield 本身不提供这种同步语义。规范核对：JLS §17.3、§17.4.5

这里的“可见”也不是实时调度承诺。工作线程仍须获得执行机会并再次检查标志；如果它卡在某个阻塞操作中，改标志不会自动把它唤醒。

2. 可见性不只关乎标志本身：沿一次发布理解 happens-before

设 data 初始为 0，ready 初始为 false。data 是普通字段，ready 是 volatile 字段。只有一个发布者，发布之后不再修改 data，也不把 ready 重置用于下一轮。

写线程依次做两件事：先把 data 写为 42，再把 ready 写为 true。

读线程先读取 ready；当它观察到这次发布的 true 后，再读取 data。

这时可以把保证拆成三段：

  1. 写线程内部，data 的写入在 ready 的发布之前。
  2. ready 的 volatile 写与读建立跨线程同步关系。
  3. 读线程内部，确认 ready 之后才读取 data。

程序顺序、同步关系和传递性连起来，data 的初始化结果就被发布给读线程。volatile 并非只保证“自身那个布尔值刷新了”，它还可以成为先前数据写入的发布点。

但这个结论有明确边界：

  • 如果先发布 ready，再写 data，后面的 data 写不在这条发布链之前。
  • 如果读者跳过 ready，直接读 data，就不能借用这条同步关系。
  • 如果发布之后还继续修改 data，那些新修改需要自己的同步安排。
  • 如果反复把 ready 改回 false 再改为 true，一个布尔值不足以表达“这到底是哪一轮数据”。需要另外设计版本或交接协议。

happens-before 不是把所有线程排成现实时间上的队列，而是用来证明特定读写之间应具备什么可见性和顺序。分析时要指出具体的发布动作和读取动作，不能只说“类里有 volatile”。

3. “禁止重排序”究竟禁止什么

编译器和处理器可能调整执行方式以提高效率，只要没有破坏必须遵守的语义。单线程中看不出差异的调整，放进缺少同步的多线程程序后，却可能影响另一个线程观察到的状态。

volatile 约束的是相关操作的可观察顺序，并不是让整个方法严格逐行执行、禁止一切优化。以上面的交接为例，发布前的数据写入不能以破坏发布保证的方式越过 volatile 写；读者确认发布后的数据读取，也不能以破坏保证的方式越过 volatile 读。

从实现角度看，编译器要限制某些代码移动，并为目标处理器选择合适的普通读写、屏障或带排序效果的指令。内存屏障是实现这些要求的机制，不应反过来代替语言语义。

所以，以下说法都过于绝对：每次 volatile 都固定插入四条屏障指令；每次都锁住总线；每次都立即写回 DRAM；读之前必定清空全部缓存。不同 CPU、编译器及优化情境可以采用不同实现，只要满足 Java 的保证。

release/acquire 可以帮助理解“发布之前的写”和“读取之后的操作”，但 Java volatile 还有同步顺序要求，不能把它无条件等同于其他语言或底层接口中的任意 acquire/release 组合。

4. 为什么 count++ 即使可见，仍然会丢更新

可见性回答“这次读取应观察到什么”，原子性回答“哪些动作必须作为一个不可分割的整体”。两者不是同一件事。

假设 count 是 volatile int，初始为 0。一次 count++ 包含读取、计算新值、写回三个逻辑动作。可能发生这样的交错：

  • A 读取 0。
  • B 也读取 0。
  • A 计算并写回 1。
  • B 根据自己先前读到的 0，也写回 1。

两次递增只留下了 1。每次单独读写都可以满足 volatile 的要求，整个读改写仍不是原子操作。这个反例不需要额外假设缓存失效，也不需要用指令重排来解释。

因此，“volatile 不保证原子性”更准确的说法是：它不能把复合操作变成原子操作。volatile 字段的单次读写本身有相应保证，包括 volatile long、double 的单次访问；不能把单次访问与读改写混为一谈。规范核对：JLS §17.7

要保护递增，可以用同一把锁覆盖整个读改写，或者用 AtomicInteger 的原子递增。若业务是“库存大于零才扣减”，需要保护的又是检查加扣减这一完整动作，不能只把扣减替换为原子操作便认为问题结束。

5. 与 synchronized 的差别，在于保护边界

volatile 修饰字段，建立字段读写的同步语义；synchronized 保护使用同一监视器的临界区，使参与者互斥执行，并通过释放与后续获取建立可见性关系。

对于一个仅由 false 变为 true 的停止标志，不需要把多步业务操作圈成临界区，volatile 可以清楚表达意图。对于余额检查后扣减、多个字段一起更新，则需要先找出完整的不变量，再决定用锁或合适的原子状态转换。

锁的保证也有条件。所有需要协调的访问必须遵守同一个协议：每次调用都创建一把新锁，不能协调不同调用；写线程加锁而读线程无同步地读取，也不能直接借用锁的发布保证。

不宜把 synchronized 一概称为“重量级而慢”，也不宜说 volatile 在任何场景下一定更快。锁是否发生竞争、临界区工作量、共享写入频率、运行时优化都会影响成本。首先比较它们能否表达需要的正确性，再讨论成本。volatile 不获取监视器，不等于围绕它构造的忙等循环没有开销。

6. 什么时候一个 volatile 字段就够用

一个实用判断是：更新是否依赖旧值，以及需要维护的规则是否跨越多个状态。

直接发布一个新状态，与先读旧状态再决定如何修改，具有不同的原子边界。两个线程都做 flag = true，可能完全符合“请求停止”的语义；两个线程都做“若当前未启动，则设为已启动并创建任务”，即使用 volatile，也可能创建两份任务。

因此，“直接赋值”和“不涉及其他变量”是有用的检查线索，不是脱离业务语义的万能充分条件。还要问多个写者相互覆盖是否允许，读者是否需要同一版本，是否存在检查后执行的动作。

多个字段属于同一版本时，发布整个快照

假设配置包含 revision 和 route。即使两个字段都声明为 volatile，写者先更新 revision、再更新 route，读者仍可能插在两次写之间，看到新版本号配旧路由。这是普通的交错，不需要重排序就能发生。

更自然的结构是把同版字段放进一个构造完成后不再变化的配置对象，再通过 volatile 根引用一次替换。读者只读取一次根引用，并从这个局部引用取出本次所需的字段。若每取一个字段都重新读取根引用，仍可能拼出两个版本。

这解决的是一致快照，不自动解决多写者的更新竞争。两个写者都基于旧快照计算新快照，后发布者仍可能覆盖先发布者的修改；此时需要锁或带旧版本检查的 CAS 协议。允许正在执行的请求继续使用旧快照，也不同于要求更新发生后旧请求绝不能提交，后者还需要提交点的版本检查。

7. 两个典型应用，把职责讲完整

停止标志：传递请求，不是强制终止

一个任务在工作片段之间检查 volatile stop；另一个线程把 stop 设为 true。这种设计表达的是合作停止：任务看到请求后，按自己的逻辑退出并清理资源。

关键前提是任务会重新检查标志，而且当前工作片段能够结束。标志不会自动中断网络读取，不会让等待锁的线程立刻获得锁，也不会执行清理代码。存在阻塞时，需要结合具体 API 的中断、超时或关闭机制。是否已经发出停止请求，与是否已经完成退出，是两个状态。

DCL 单例：一次初始化与安全发布是两件事

双重检查锁定的逻辑是：先在锁外查看 instance；若为空，进入同一把锁；在锁内再检查一次；仍为空才构造并发布对象。这里各部分有不同职责。

外层检查让已经完成初始化的访问走快路径。内层检查处理这样的竞争：A、B 都曾在锁外看到空，A 先获得锁并创建对象；B 随后获得锁时必须重新查看，不能沿用锁外的旧判断。volatile 引用则负责让快路径上的读者获得正确发布的对象状态。

为什么只有锁还不够？因为快路径的读者没有获取这把锁，不能直接依靠构造者释放锁时的同步关系。缺少合适发布方式时，不能仅凭引用非空就推定普通字段的初始化结果都已对该读者可见。

“分配内存、初始化、赋引用”有助于理解风险，但它是概念分解，不是每台机器固定存在的三条指令。未安全发布可能表现为读到未正确发布的字段状态，不能武断说必然出现空指针异常。

同样，volatile 只解决发布，不负责让后续的可变业务状态自动线程安全。单例中一个不断修改的计数器仍要单独协调。单例也通常只在定义它的类加载器范围内成立，不是分布式唯一实例。

并非所有单例都要采用 DCL。饿汉式和初始化持有者模式可以借助类初始化机制完成发布；选择时还要考虑延迟创建、初始化失败以及对象生命周期，而不是只背双重检查的形式。

8. 与 final、原子类和不可变对象的联系

final 主要限制字段再次赋值，并有特定的初始化安全语义；volatile 用于后续共享状态的发布和读取。一个 final 引用指向的集合仍可能变化，一个 volatile 引用指向的对象也不会因此变成不可变对象。

不可变快照让共享的内容保持稳定，volatile 根引用负责交接这个快照；原子类可以把特定更新表达为不可分割的状态转换；锁可以围住更复杂的一组操作。它们不是按“强弱”排成一条可随意替换的链，而是在不同边界上提供保证。

理解 volatile 最后要落到三个具体问题：哪次写发布了哪些状态，读者通过哪次读接收这些状态，还有哪些操作没有被这个关系覆盖。能把这条链说清楚，才不会把“可见”误当“互斥”，也不会把“对象已发布”误当“整个对象永远线程安全”。

9. 把volatile放回完整JMM：从哪个交接点获得保证

JMM是一套约束并发读写结果的规则，不是JVM堆、栈、方法区的空间划分，也不是某种CPU缓存拓扑。“主内存、线程工作内存、刷新和重新读取”的图可以辅助理解共享与观察差异，但不应逐一对应物理DRAM、L1缓存或某条固定指令。真正证明正确性时，仍回到程序顺序和具体同步关系。

原子性也不等于事务回滚。一个受锁保护的复合操作，可以相对于同样使用该锁的参与者不可分割地执行；但操作中途抛异常，不会因此撤销之前的字段修改。原子性同样不表示执行线程绝不被操作系统暂停，关键是别的参与者能否观察或介入被保护的中间状态。

可见性不是“某个固定毫秒内全体线程实时看到最新值”。有序性也不要求每条机器指令按源码次序执行。同步正确的程序允许实现优化，只要不破坏应有的可观察结果；happens-before提供的是这种结果与顺序的依据，而不是所有线程共享一张墙钟时间表。

生命周期也能建立交接关系

除了同一锁的释放/获取、同一volatile字段的写读，还有几类常用边：

  • 调用Thread.start之前的动作，可以沿启动关系发布给被启动线程。直接调用其run方法只是普通调用，不是启动了一个新线程。
  • 线程内的动作，在另一个线程成功检测到它已经终止之后具有相应可见性。例如等待其真正结束的join；带期限的join若仅因超时返回，不能据此声称线程已结束。
  • 中断操作与另一个线程成功检测到中断之间有同步关系，但中断请求仍不等于线程已经退出或资源已经清理。
  • 默认初始化、类初始化有各自的保证；它们不是后续任意可变状态都无需同步的理由。

start提供的是启动前到新线程的方向，不能反过来用它证明主线程已经取得子线程计算结果。要读结果，还应有对应的完成或结果交接。即使join确认线程结束，也只证明结束与相应可见性，不自动证明任务业务成功。

执行器、Future与阻塞队列，不是“隐形无同步”

提交任务之前的动作，可以通过执行器契约发布给任务；Future所代表计算的动作，与通过get取得结果之后的动作有相应先行发生关系。将对象放进BlockingQueue之前的动作，也能发布给随后取得该元素的线程。

这些工具因此可以承担跨线程交接，而不要求每个payload字段都单独声明volatile。需要检查的是接口是否确实完成了相应交接：提交被拒绝并没有启动任务，get超时也不是已经取回计算结果。

更重要的是，交接前的状态被正确发布，不代表交接后的双方可以继续无协调地修改同一个对象。生产者把可变缓冲放入队列后立即覆盖它，消费者仍可能读到变化；应移交所有权、复制内容或采用另外的同步协议。

三类保证不能替代业务不变量

正确同步、没有数据竞争的程序可以按顺序一致的方式理解，但每个字段分别同步，不等于多个业务动作组成事务。两个volatile字段各自读写正确，仍可能拼出不同版本；两个原子余额各自更新成功，也不证明转账总额始终不变。

分析时应先列出共享状态与业务规则，再用具体同步边证明读者看到什么、用原子边界证明哪些动作不能交错。这样，JMM、锁和原子类才是在回答同一个问题的不同层面，而不是三个可以互相替代的术语。
