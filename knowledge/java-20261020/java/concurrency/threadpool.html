线程池：任务怎样被接收、排队、执行与结束

线程池不只是复用线程的工具，也是接收工作、限制执行规模和处理过载的一套规则。一个任务从提交到结束，至少经过四个不同问题：能否接收，何时开始，结果由谁观察，资源怎样收回。

把它们连起来看，七个参数便不再是孤立名词：线程数控制执行者，队列容纳等待者，拒绝策略定义接不下时的结果，关闭机制结束整个执行域。本章围绕 Java 21 的 ThreadPoolExecutor 展开，定时执行器等不同实现另标边界。

1. 复用线程有什么收益，又没有承诺什么

对于传统平台线程，频繁创建和结束线程有运行时及操作系统开销。worker 执行一个任务之后继续取下一个任务，可以摊薄这些成本；集中管理也让执行规模、线程命名、任务统计和关闭责任更清楚。

复用不是重复调用同一个 Thread.start。线程启动以后，在自己的执行循环中不断取得任务并运行；一次业务任务结束，不代表这个线程结束。

“提高响应速度”是可能的收益，不是任务一提交就立即执行的承诺。线程可能尚未创建，池也可能已满；任务还可能在队列中等待。等待时间变长时，复用线程节省的启动成本并不能抵消排队延迟。

同样，线程池不自动保证任务可靠送达。任务仍在进程内存中时，机器故障可以让它消失；业务异常、拒绝、取消也需要另外的结果协议。需要持久受理、可恢复重试和幂等的工作，要把这些能力放在相应的消息或任务系统中，而不是把“放进池”当作已完成可靠交付。

2. 七个参数其实描述三组决策

执行规模：corePoolSize 与 maximumPoolSize

corePoolSize 是提交时优先补 worker 的阈值，不等于当前忙碌线程数，也不意味着构造线程池时已创建这么多线程。默认按需创建，可以预启动。

maximumPoolSize 是池内 worker 数的上限。达到 core 之后，普通提交路径先尝试排队；只有无法入队，才尝试继续增加 worker 到 max。因此，max 的效果离不开队列。一个几乎总能入队的队列，会让积压主要停留在队列里，而不是促使池不断扩到 max。

“核心线程”和“非核心线程”是理解容量与回收规则的方便称呼，不宜把它们想成每条线程终身不变的身份。回收判断结合当前 worker 数、超时策略和池状态进行。

等待与回收：workQueue、keepAliveTime、unit

workQueue 保存或交接待执行任务。它不仅影响占用多少内存，还决定任务先排队还是促使扩线程。

keepAliveTime 表达符合回收条件的空闲 worker 等待新任务多久，不是线程从出生开始的总寿命，更不是任务执行超时。默认主要针对超过核心规模的空闲线程；允许核心线程超时后，核心规模内的线程也可回收，并须满足正的 keepAliveTime 等参数约束。unit 规定这段时间的单位。

创建与接不下：ThreadFactory、RejectedExecutionHandler

ThreadFactory 决定新线程的名称、守护属性等创建细节。线程名能帮助区分业务执行域，但命名本身不提供可靠性；线程工厂创建失败还可能影响任务能否推进。

拒绝处理器定义不能接收任务时怎么办。不只是线程和队列饱和会触发拒绝，关闭后的新提交也会进入拒绝路径。

这些参数要联合理解：线程数不是全部资源上限，排队不是免费存储，拒绝也不是一个可以等系统故障时再补的末端异常。

3. 一次提交的主线与必须保留的重检

在池状态允许接收时，主线可以概括为：先尝试补核心 worker，再尝试入队；入队失败，再尝试按最大规模增加 worker；仍不能接收，则拒绝。

但源码逻辑不是毫无并发变化的一组静态判断。提交、worker 退出、池关闭可以同时发生。任务入队成功后还要重新检查池状态，必要时移除并拒绝；还要确保需要消费队列时有 worker。忽略这一步，就解释不了提交和关闭竞争，也解释不了核心数为零的池怎样开始处理已入队任务。

OpenJDK 用 ctl 联合管理运行状态与 worker 数，便于这些转换协调；并不是把队列容量和每个业务任务状态也全部编码进 ctl。

用七个任务理解“先排队，再扩容”

假设池起初为空，core=2、max=4、队列容量=2，采用显式拒绝策略；连续提交的任务在整个推演期间都不会完成，线程创建也成功。

  1. 第1、2个任务各自促成一个 worker。
  2. 第3、4个任务进入队列。
  3. 第5、6个任务因无法再入队，促使 worker 扩到4。
  4. 第7个任务无法再扩，触发拒绝。

这些前提不能省。如果任务已经完成、提交被 CallerRuns 拖慢，或线程创建失败，就不能机械套用这个数量结论。

还有一个容易忽略的结果：第5个任务可能被新 worker 直接接手，在队列中的第3个任务之前开始。FIFO 队列只规定队列内的出队顺序，不保证所有提交任务的全局开始顺序，更不保证完成顺序。

为什么不能只看“最大线程数30”

新任务到来时是否复用线程，取决于当前 worker 数、core、队列、空闲状态及池状态。worker 数仍低于 core 时，提交会优先尝试增加 worker，即便另一个 worker 刚好空闲；达到 core 后，任务更可能经队列交给现有 worker。空闲线程也可能已经超时退出。

因此，最大数只是一个上限，不能单独推导某一次提交的完整行为。提交策略与回收规则核对

4. 队列改变的不只是存储结构

ArrayBlockingQueue 是固定容量数组队列。容量明确，适合把等待任务数作为显式预算；但任务数相同，不代表所保留的字节数相同。

LinkedBlockingQueue 可以显式指定容量。省略容量时的上限非常大，通常被称为近似无界；不能把“链式”直接等同“必然无界”。链节点分配和锁组织与数组队列不同，但吞吐优劣取决于实际负载，不能凭数组或链表的名称下定论。

SynchronousQueue 不保存等待任务，执行的是直接交接。ThreadPoolExecutor 尝试把任务交给接收者；无法立即交接时，可能扩 worker 或拒绝。这里不是让提交者调用阻塞 put 一直等接收者。因此，队列 size 为零不等于没有执行压力。

队列越大，通常越晚触发扩容或拒绝，却可能积累更久的等待。把队列加长，是在延迟、内存和过载反馈之间做交换，不是在凭空增加处理能力。已经排队超过业务总期限的任务，即便最后执行，也可能失去价值。

优先队列和延迟队列还有自己的规则。优先级影响尚未开始任务的取出顺序，不会抢占已经运行的任务；到期只代表可以被调度，不保证立刻运行。它们也不自动提供严格积压上限。若 submit 包装了任务，队列真正看到的可能是 FutureTask，不能只让原始 Runnable 可比较就假定优先级生效。

5. 拒绝策略是一份结果合同

选择拒绝策略，首先要回答“调用者怎样知道接收失败、谁负责使结果终结”，之后才谈降级和重试。

AbortPolicy：把未接收变成显式失败

默认策略抛出 RejectedExecutionException。它让提交者有机会按业务选择快速失败、降级，或交给有边界的重试与持久接收流程。

异常被抛出不等于业务自动获得可靠性。若提交者只是吞掉异常，任务仍然丢失；若立即无限重试，又会把瞬时饱和放大成持续过载。失败观察与后续处置必须有拥有者。

CallerRunsPolicy：回压可能有用，但执行边界变了

池未关闭时，它让调用 execute 的线程直接运行任务；这个线程不一定是主线程，也可能是请求线程、事件循环或另一个池的 worker。执行耗时拖慢提交速度，是一种反馈机制。

但是它不是“任务绝不会丢”的策略：池关闭后会丢弃任务。也不能把池内 max 当作下游严格并发上限。若已有4个 worker 正在调用下游，另一个请求线程又以内联方式执行，实际就可能有第5个调用；多个提交者还可能进一步增加并发。

沿调用链看，还会出现三种影响：

  • 提交者若是事件循环，慢业务会阻塞它处理其他事件。
  • 提交者若持有业务锁，内联执行会扩大持锁范围，甚至引入依赖环。
  • 慢任务若已经在 submit 内运行，之后才调用 get(timeout)，这个等待期限覆盖不了先前的提交耗时。

ThreadLocal 上下文也应按真实执行作用域保存和恢复，不能假定任务一定运行在一条“干净的新线程”上。

DiscardPolicy 与 DiscardOldestPolicy：丢弃对象不等于结束句柄

DiscardPolicy 静默丢弃新任务。只在明确允许丢失、并且没有调用者依赖该任务完成的契约下才可讨论；“日志”也不是天然可丢，审计日志与普通采样埋点有不同要求。

DiscardOldestPolicy 移除工作队列队头，再重试当前提交。队头在优先队列里未必是提交时间最早的任务；策略必须与队列语义一起分析。

如果被丢弃的是 FutureTask，又没有取消或异常完成它，调用者持有的 Future 可能一直不结束。CallerRuns 在关闭后的丢弃也可能造成类似问题。处理任务接收的逻辑，必须同时考虑等待结果的人，不能仅记录“队列少了一个元素”。

自定义拒绝处理也不应进行无限阻塞、无限递归重提或无节制同步日志。需要不丢任务时，应明确持久化受理、幂等重试和失败回收，而不是只给内存池换一种 handler。

6. Executors 的风险在隐藏策略，不在方法名

newFixedThreadPool 和 newSingleThreadExecutor 限制了执行线程数量，但默认使用容量很大的工作队列。持续到达速度超过处理速度时，积压和闭包保留的对象可能先耗尽堆内存。

newCachedThreadPool 使用直接交接并允许非常大的线程规模。若任务长期阻塞或到达量失控，风险可能从队列堆积转成大量平台线程、线程栈和系统配额耗尽。

newScheduledThreadPool 管理延迟及周期任务，不能当成普通有界池来推导。它使用无界延迟队列，调高 maximumPoolSize 不会按“队列满了再扩线程”的普通模式发挥作用。定时触发、实际执行、周期失败和积压回收有各自边界。定时执行器契约核对

所以，工程上强调显式参数，是让容量与失败决策可见，而不是声称 Executors 在任何场景都不能使用。已由上层严格限制的小批量，与无限在线流量，风险不同。反过来，手写 ThreadPoolExecutor 却仍配置巨大队列和任意扩线程，也不会自动变得安全。

7. 从资源预算推导线程数，而不是记住一个公式

CPU 密集任务的执行能力主要受有效计算资源约束。可以从有效核心数附近估算，而不是把机器标称核心数当作每个业务池独占的预算。容器配额、同进程其他池、请求线程和GC都可能竞争这些资源。

I/O 密集任务常有大量等待，增加适当并发可以把等待重叠起来。但下游连接数、服务并发配额、调用速率、任务占用内存和尾延迟，可能比CPU更早成为约束。

常见估算式是：线程数约等于有效核心数 × 目标CPU利用率 ×（1 + 等待时间/计算时间）。它只是一个建立直觉的起点，并不是最优解定理。等待90ms、计算10ms时，比值是9，不是90/100；“CPU加1”“I/O乘2”也不能代替真实工作特征。

数量、速率、字节和期限是不同预算

线程数量约束同时执行的规模，速率约束单位时间内发出多少次操作。下游变快后，同样4个并发也可能产生更高QPS，因此并发闸门不能替代速率限制。

任务队列限制等待数量，但一个任务可能捕获几KB，也可能捕获大视频、请求体或大型结果集合。预算还需要考虑闭包保留对象、线程栈、结果缓冲和连接。即使池队列有界，提交者预先保存十万个Future，整体内存仍然可能很大。

在稳定条件下，可用“平均在途数量约等于到达速率乘平均停留时间”检查量级。单位要一致，平均值不能替代突发与尾部设计。若目标是限制排队等待，应分清总响应时间、实际执行时间和队列等待时间。

大批任务的正确直觉是窗口，不是一次全提交

假设有十万条数据要调用容量未知的服务。先保持一个有上限的在途窗口，回收一部分结果再补入新任务，比一开始创建全部任务和句柄更容易控制保留资源。

窗口之外还可能需要单独的下游许可与速率约束。响应变慢、429或过载反馈表示应减少压力，而不是立即启动更多重试。重试需有总期限、次数、退避以及副作用幂等条件；超时但仍未退出的调用也还在消耗资源。

资源耗尽不只有“队列太长”一种原因

积压任务可能保留大量堆对象；过多线程可能耗尽本地线程或栈资源；未消费结果、ThreadLocal残留、直接缓冲区和任务自身分配也可能造成压力。容器被系统因内存超限终止，甚至未必表现为Java堆OOM。

因此，增加最大堆或最大线程数不能普遍修复问题。需要对应地限制入口、队列、执行者、字节及下游占用，并使任务完成后真正解除资源保留。

8. 监控与动态调整，要看任务从哪里慢下来

poolSize 表达当前线程规模，activeCount 表达近似活跃执行者数量，二者不同；单看线程利用率，也分不清是在有效计算、等下游还是争锁。

一条有解释力的观察链应覆盖：提交与完成速率、排队深度和排队时间分位数、执行耗时、拒绝原因、任务成功与失败、取消后仍执行的工作、下游连接等待、CPU与GC。重点是完成了多少有效工作，而不是仅统计发出了多少请求。

动态调整 core/max 一般改变创建和空闲回收规则，不会自动删除已有队列任务，也不会立即杀死正在执行的线程。调整过程仍须保持 core 不大于 max：扩容先保证max容得下新core，缩容先把core降到合法范围。每一步应有明确原值与回退逻辑，不把“动态”理解成无约束修改。

标准阻塞队列没有一个通用的在线改容量接口。直接清空队列更不是正常缩容，它改变了任务受理契约，且可能留下永不结束的Future。

9. execute、submit 与异常到底落在哪里

execute 提交 Runnable，不返回该任务的结果句柄。直接运行的任务若有未捕获异常，可能导致该worker结束，并进入线程的未捕获异常处理机制；池可按状态和配置补位。这不等于整个JVM退出。

submit 通常把任务包装为 FutureTask，并返回Future。任务异常被保存在结果中，调用者需要通过get或明确的结果处理链观察。只提交不读取，不意味着任务没有失败，只意味着失败可能没有被任何人看见。

afterExecute 里的Throwable对submit任务可能为空，因为异常已由包装层捕获。因此只统计该参数，不能完整统计业务失败；ThreadFactory设置的未捕获异常处理器也不能替代Future结果观察。

还应分开三类事件：提交被拒绝，已接收任务执行失败，等待者等得太久。Future.get(timeout)限制的是本次等待，不自动停止计算，更不自动撤销已经发生的数据库或远端副作用。

10. 关闭是一个过程，不是一句“强制结束”

shutdown 停止接收新任务，允许已接收任务继续执行。它返回时，不代表这些任务已经结束。

shutdownNow 不再接收任务，尝试中断运行中的工作，并返回尚未开始的排队任务。名称中的Now不是安全强杀任意代码的承诺；任务如果不合作响应中断，仍可能继续运行。

池的拥有者应先停止上游提交，决定允许已有工作排空多久，再在必要时请求取消，并确认实际终止状态。awaitTermination 的等待和 isTerminated 的观察，比“已调用shutdown”更接近“池确实结束”的事实。关闭与终止契约核对

未开始的任务和等待结果的人，也必须收尾

shutdownNow返回的队列项不自动等于已经取消的调用者Future。直接submit形成的FutureTask，可以由拥有者明确取消；但CompletionService等结构可能还有包装层，不能假定返回项与外部句柄同型，随手强转。

更稳妥的职责划分是由提交者保存自己承诺给调用方的句柄，并在取消或关闭时让它们进入明确终态。任务不再排队，与等待者知道它不会执行，是两个动作。

句柄取消与资源释放可以有时间差

Future可能先进入取消状态，再向实际线程发出中断请求。此时任务的finally、连接归还等动作还未完成。若系统要求“资源已经回收”，还需要任务真实退出或释放的证据，不能仅看isCancelled。

总期限也不能通过每一步重新给足同样时间来实现。允许整次关闭最多等待一段时间，就应在后续等待中扣除已经用掉的预算。Java21的执行器close或自动关闭可能等待任务，不能把它视为所有超时路径上的立即返回手段。

关闭失败、任务失败和清理失败还要保留各自含义，避免后发生的清理异常盖掉最初故障。中断不是事务回滚，远端请求结果未知时仍需幂等、查询或补偿。

11. 业务隔离与任务依赖，把参数放回架构

CPU计算、慢外部调用、流式连接和短回调共用一个池，会让一种慢任务占住所有worker，影响原本很快的任务。按执行特征和故障影响划分执行域，能减少这种相互拖累；但拆池不能增加总CPU或下游容量，各池预算仍需合在一起看。

对于持续读取消息流再向客户端转发的桥接任务，长时间占用worker是工作形态，而不一定是异常。若这类任务放进大队列，少数核心worker可能被长期占满，后来任务一直排队，max迟迟发挥不了作用。直接交接可以改变接收与扩容路径，但扩到上限仍会拒绝，也不会自动提供足够的下游连接。

隔离还要沿整条链看：Servlet异步返回能释放初始请求线程，不代表后续向慢客户端写出完全不阻塞；应把派发、连接与长期桥接的容量分别说明。响应式适配也只有在源和下游共同参与背压时，才能真正约束积压。不能用一种执行模型的名称替代队列、取消与慢消费者策略。

定时维护任务同样属于业务正确性的一部分。daemon线程不会阻止进程退出，调用shutdown也不等于业务状态已经落盘；若租约续期失败，依赖租约的工作必须停止或转入失效处理，不能只是记录异常后继续假定拥有执行资格。连接回调与取消清理还应幂等，并辨别连接代际，防止旧任务的延迟回调误清理新的会话。这些协议细节由流式连接与租约主题继续展开。

也不要把真实数据依赖硬拆成并行。假设4个worker都在执行父任务，每个父任务提交同池子任务后同步等待，子任务需要worker才能运行，而worker全被等待者占着，即使没有监视器死锁，整个系统也可能卡住。

单纯增加到8个线程，只是把类似问题出现的门槛后移。应改用不占住worker等待的依赖编排，或让顺序步骤在同一任务内执行；确属不同资源的工作可以分开管理。虚拟线程能降低部分等待的平台线程占用，却不会自动归还父任务持有的数据库连接或信号量许可。

这里与ThreadLocal章衔接：任务从哪条线程提交、最后在哪条线程执行、何时结束，不应靠名称猜测。执行资源、请求上下文、结果句柄和业务资源是相关但不同的四层，只有把它们各自的拥有者和结束条件说清楚，线程池才真正成为可控的执行系统。
