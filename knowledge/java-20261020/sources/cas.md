# CAS与原子类：一次更新怎样成立，成立后又保证了什么

CAS把“当前值是否仍等于预期值”与“满足时写入新值”合为一次原子操作。它让竞争者能够先根据旧状态计算，再尝试提交，但它不负责替业务决定哪些状态必须一起更新，也不替业务管理重试和副作用。

理解CAS，应从更新契约走到整个算法：比较什么、失败怎么办、是否需要识别历史变化、哪些读取必须一致、成功后是否仍有其他工作可能失败。以下按Java21原子类的契约解释。

## 1. 比较与交换不可被拆开，计算过程却可能被打断

设共享值当前为V，线程预期它仍为A，想改成B。一次强CAS只有在比较时V等于A，才把它改成B，并报告成功；否则不完成这次写入。

它不同于普通的“先if判断，再赋值”：后者在检查与写入之间可能插入其他线程，CAS把这两个动作组成不可分割的提交步骤。但CAS之前读取旧值、计算新值的过程，不因此变成不可中断的临界区。

例如库存为1，甲乙都读到1，均想减到0。甲先成功提交1→0；乙再用预期1提交时失败，必须根据新状态重新判断，而不是继续认为自己已扣减成功。把库存放进AtomicInteger后先get判断、再set减一，仍然分成两个操作，不能自动防止这种竞争。

一次CAS不是一个循环。失败后重新读取、重算并再次尝试，是上层算法的选择；也可以有界重试、返回冲突或交给其他协调机制。若使用允许虚假失败的弱CAS接口，还不能仅凭一次失败断言值确实变化，必须按该接口契约组织逻辑。

原子类的比较交换和读写还各有内存效果。普通、acquire/release、volatile等访问模式不可仅凭“都是原子类的方法”混为一谈；使用弱一些的模式需要另行证明发布与观察关系。[AtomicInteger操作契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicInteger.html)

## 2. 低冲突时为什么有用，高冲突时为什么可能变差

短小更新在冲突不多时，可能一次读取、计算和提交就完成，不必围绕整个过程取得阻塞锁。CAS可以由运行时内建映射到目标平台的原子指令或指令序列，不能把某条x86指令当成所有CPU上的固定实现。

竞争集中到同一位置时，很多线程可能反复读取相似旧值，只有少数提交成功，其余重算。额外代价包括CPU消耗、缓存一致性竞争和重复计算，不只是“有无上下文切换”。多个变量即便逻辑上不同，若共用缓存行，也可能出现伪共享造成的争用。

CAS也不承诺业务线程不会被系统调度出去。更重要的是，“使用了CAS”不等于“算法是lock-free”。如果用CAS实现一个自旋锁，持有者暂停时，其他线程仍可能一直等它。lock-free讨论整体是否持续取得进展，wait-free还要求每个操作在有界步骤内完成；它们都不是单条原子指令的同义词。

因此选型不能只说“无锁一定快”。冲突低、重算便宜的更新适合考虑乐观提交；临界区长、冲突大或不能重复执行的操作，可能更适合锁、事务或明确的串行拥有者。任何重试方案都应交代失败与退出方式，而不是默认无限循环总能及时结束。

## 3. ABA：相同的当前值，不等于相同的历史

甲读取A后暂停。乙把共享值从A改成B，再改回A。甲恢复时只比较当前值，仍可能成功。CAS没有违反契约，因为当前值确实与预期相同；错误发生在甲把“当前相同”推导成“期间没有发生变化”。

ABA是否有害取决于业务是否依赖历史。例如某个操作只关心当前数值，值恢复后再次处理可能完全符合要求；若算法根据旧节点关系、代次或先前资格作决定，状态已经历变化却被当成未变化，就可能出错。

### 引用与版本必须是一份状态

AtomicStampedReference把引用与整数戳作为一对状态处理。提交时同时检查预期引用和预期戳，协议中的有效变化同时更新戳，才能区分“又回到同一个引用”的不同代次。

读取时也要获得一致的二元组。分别取引用、再取戳，中间可能发生另一次更新，拼出从未共同存在的组合。需要成对观察时，应使用一次返回引用并取得对应戳的接口。[引用与戳的成对契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicStampedReference.html)

版本戳不是无需设计的魔法。仍要规定谁递增、哪些变化必须递增、是否允许回绕、能否复用对象。随手加一个时间戳也不自动保证唯一代次，时间来源和相同时间值都可能影响协议。

### Markable与Stamped解决的状态需求不同

AtomicMarkableReference把引用与一个布尔标记组成原子状态，适合“是否逻辑删除”这种二态信息。一个布尔位不是任意长度的历史计数：引用A→B→A，标记false→true→false，旧的二元组仍可能重新匹配。

因此，不能把“带标记”直接等同“彻底解决ABA”。整数戳能表达更多代次，但同样受回绕和更新协议约束。两种工具保护的都是那一对状态，不会自动保护所指对象内部所有可变字段，也不会替底层对象复用或内存回收设计兜底。

## 4. 原子类要按保护边界分类，不只记名称

### 数值与布尔：一次方法调用的语义

AtomicInteger、AtomicLong、AtomicBoolean分别表达相应类型的原子状态。incrementAndGet返回更新后的值，getAndIncrement返回更新前的值，选择哪一个关系到调用者得到什么结果。

一个AtomicBoolean可以协调某种一次性状态转换，但不能自然累积多条消息；一个AtomicLong可以提供适合协议的原子序号更新，但序号溢出、重启与跨进程唯一性仍是另外的问题。

updateAndGet等函数式更新可能因竞争重复调用更新函数。这个函数应是无副作用的计算，不宜在里面扣款、发消息或修改外部对象。CAS最终只提交一次，不意味着提交前的函数只执行一次。

即使先完成CAS再发送消息，也会有“状态已变、消息发送失败”的空隙。因此进程内原子更新不能直接证明两个系统中的业务事务成功，可靠副作用需单独的协议。

### 数组：单元素原子，不是数组事务

AtomicIntegerArray、AtomicLongArray把相应操作的原子性落实到一个元素。它们不会把遍历所有元素自动变成一致快照，也不会把从索引0扣减、向索引1增加变成一次不可分割的转账。

多个位置共同维持不变量时，要么用同一锁保护整组操作，要么重新设计为一个可原子替换的聚合状态，不能仅把普通数组换成原子数组就宣布整体线程安全。

### 引用：替换入口，不是冻结内部对象

AtomicReference原子地管理根引用。把它指向一个可变Map后，在多个线程里随意修改Map内容，并不会因为根引用原子而安全。

一种适合整体配置的设计是：先构造完整不可变状态，再原子替换根引用。多个写者可以基于同一旧快照计算，提交失败者重读重算；读者只捕获一次根引用，再从同一快照取相关字段，避免跨版本拼接。

这不是同时CAS多个内存位置，而是把需要一起变化的信息建模成一个整体发布单元。复制与分配有成本，对象内部仍需保持不可变；若还有数据库、网络等外部副作用，根引用替换也不会替它们提供原子事务。

## 5. 字段更新器：更新已有字段，仍需统一访问协议

AtomicIntegerFieldUpdater操作目标对象已有的volatile int实例字段，而不是要求每个对象另持有一个AtomicInteger包装。大量同型节点共用一个更新器时，这种结构可能减少包装，但收益仍依对象布局、数量和维护成本，不能只凭少一个对象就断言更快。

AtomicLongFieldUpdater和AtomicReferenceFieldUpdater有相应类型约束；字段名称、volatile修饰、实例字段类型和访问权限必须符合要求。它不是对任意私有字段都无条件开放的绕过入口。

最容易出错的是混用：一部分线程通过更新器CAS，另一部分直接对字段做自增。volatile仍然没有把直接自增的读、算、写合成一步，更新器也不会替绕过协议的访问兜底。应封装相关读写，使修改遵循同一约定。[字段更新器的适用与原子性限制](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicIntegerFieldUpdater.html)

需要更精细访问模式时，可以转到VarHandle主题讨论，但不能因工具更底层就省略不变量证明。内部Unsafe也不应成为普通业务代码掩盖同步设计的捷径。

## 6. 热点计数的相关选择：不要为了吞吐换掉正确性

对于高频统计累加，既有热点计数主题中的LongAdder提供另一种思路：把更新分散到多个计数单元，而不是所有线程争一个全局位置，再在读取时汇总。

这种结构付出额外存储和求和成本。并发sum不是所有单元同一时刻的原子快照；没有并发更新时可以得到精确总量。余额、唯一序号、库存条件扣减和硬限额，不能不加区分地用它替换适合线性化更新的状态。

同样，reset或sumThenReset与并发写混用，不自动构成无损切分统计窗口的协议。分片为何减轻热点、Cell布局与伪共享的细节仍由热点计数主题展开；这里的选择标准是结果契约，而不是只看一个更高的吞吐数字。

## 7. 乐观与悲观描述策略，不是实现零件

悲观策略先取得互斥，再访问受保护状态；乐观策略先读取和计算，提交时验证冲突，失败则按协议重算或退出。synchronized、ReentrantLock常用于前一种策略，CAS和版本校验常用于后一种策略。

但锁内部也可能用CAS实现快速路径，所以看到CAS不能判断业务一定是乐观方案。数据库版本条件更新也不能仅凭“像CAS”就忽略事务隔离、影响行数和多行不变量，它有自己的执行环境与契约。

选择时，可以依次检查：需要原子提交的是一个值还是一组状态；是否必须识别历史；计算可否安全重做；失败者怎样结束；观察者需要实时一致结果还是可接受汇总统计。明确这些问题后，原子类、聚合快照、锁和事务才各有合适的位置。
