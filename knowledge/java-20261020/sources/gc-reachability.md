# GC 可达性与并发回收

垃圾回收需要解决三个不同的问题：哪些对象仍须保留，本轮处理哪些区域，以及怎样把可用空间交回分配器。可达性分析回答第一问，分代和 Region 选集回答第二问，清除、复制、整理回答第三问。具体收集器把这些机制组合起来，不能用一张名称清单代替因果关系。

以下以 Java SE 21 与 HotSpot 21 为主要边界；CMS 只用于历史机制对照。本文负责可达性、空间回收和并发正确性，具体代布局与收集器取舍见《分代回收与收集器权衡》。

## 1. 回收器判断的是可达性，不是业务价值

假设活动线程可达 A、B，A 又指向 C，B 指向 D，而 E 没有来自这张活图的入口。根追踪能够找到 A、B、C、D；E 则进入后续可回收性判断。重点不在于 E 有没有名字、存在多久，而在于程序是否还有有效访问路径。

把例子换成资料处理流水线：长期任务表仍保存已完成任务，任务又保存整份文档及解析结果。业务说“处理完成”，不会自动删除这条保留链。GC 继续保留这些对象并非失效；真正需要修复的是任务结束后的所有权与注销规则。

只将当前局部变量置空，不能消除缓存、监听器或 ThreadLocal 中的其他强路径。反过来，A 与 B 相互引用但没有外部入口，这个环也不必泄漏。朴素引用计数会被环内非零计数困住，根追踪则能识别整个不可达子图；具备循环检测的引用计数体系另当别论，不能说所有引用计数方案都无解。

找到不可达对象与立即重用内存是两回事。还要考虑收集范围、软弱虚引用及生命周期处理。对象失去强可达性，不是“这一行执行后内存立即减少”的保证。

## 2. 根应该落实到引用位置，而不是背永久名单

GC Root 更准确地说是追踪起点或根引用位置，口语里也把它指向的对象叫根对象。可以按来源理解：

- 活动执行状态：栈槽、操作数及寄存器中仍有效的引用。HotSpot 根据执行状态与引用位置映射识别它们，不是把所有看起来像地址的整数都当指针。
- JNI 登记的引用：局部引用和普通全局引用能保活对象；弱全局引用有不同语义。本地代码里的任意裸地址不会自动成为受保护的强根。
- 类、代码与运行时状态：存活类关联的 static 值、已解析对象引用、活动代码和 VM 内部引用可能形成保留链。

“static 是根”只是入口式概括。更具体的关系可能是存活加载器及类状态，经 Class 镜像中的静态缓存再到缓存对象。物理存储位置见《JVM运行时区域与进程内存》；不能再把 static 的当前值统一放入元空间，也不能把它叫作独立、永久、无法卸载的根。

词法作用域也不等于实际活跃区间。局部变量仍在源码作用域内，却可能已经不再被执行需要；反过来，对象离开创建它的方法后仍可能被其他位置保留。源码位置不足以单独判断回收时刻。

局部收集还有额外边界：本轮只收年轻代或少数 Region，范围外指入其中的引用仍必须被检查。这些外部入口不是新的永久根，却是本次追踪不可遗漏的条件。卡表与记忆集正是为减少这类扫描成本服务。

## 3. 常量、final、intern 都不等于永久存活

基本类型常量是数值，不天然指向包装对象。final 引用只限制重新赋值，不保证对象不可变，也不创造永久根身份。static final Object 引用一个新对象，与以常量表达式初始化的 final 基本类型或 String 常量变量，不是同一种语言概念。

运行时常量池也不是一篮子已经创建好的对象：符号信息、解析结果和真正保存对象引用的位置要分开。HotSpot 21 的已解析引用数组等结构可能强保留字符串，但这不能推导成所有常量池项都是永久对象根。编译期常量被内联到使用类后，使用类的关联同样可能保活字符串，不能只观察声明类。

常规 HotSpot 21 StringTable 的弱关联，不会让动态驻留字符串永久存活；已有类、代码、static 或业务缓存的强路径又可能继续保留它。CDS 归档字符串有独立的共享结构和保留路径，不能直接套用常规驻留表的弱关联结论。完整字符串身份和 intern 规则仍归字符串主题，本章只强调实际保留链。

加载器、类和静态对象相互成环不意味着能自保活。旧加载器被线程上下文、注册表或外部实例保留才是常见风险；满足卸载条件也不保证立即卸载。

## 4. 清除、复制、整理分别付出什么代价

**标记清除**先确定须保留对象，再将其余空间交给空闲结构。正常清除不搬活对象，省掉相关搬迁，却仍要追踪对象图、处理空间、维护空闲块。若空闲块为3、4、3 MiB，总计10 MiB也不一定能满足连续6 MiB申请；能否扩容或进入后备整理，还取决于具体实现。合并相邻空闲块不能跨越中间的活对象凭空制造连续空间。

**复制**将幸存者搬到目标空间并修正引用，原收集区域随后可复用。多条引用指向同一对象时，必须借助转发信息或等价协议，避免复制出多个独立身份。低存活率通常有利，因为大多数死对象不用搬；但成本还包含根、跨区入口、对象字段扫描和引用修正，不仅是复制字节。

“复制浪费一半空间”是等大双半区模型的结论，不是所有复制型收集器的定义。Eden加两个Survivor不等于全堆二等分，G1也不是永久空出半堆；它们仍要为幸存者准备目标空间和失败余量。没有固定半堆预留，不代表没有空间成本。

**标记整理**在确定活对象后安排新位置、修正引用并移动，使空闲空间更集中。经典滑动整理可将对象压向一端；实现的扫描次数、移动次序和并行分工不必相同。整理减少外部碎片，却不能消除对象对齐、区域尾部、预留或不可移动对象带来的所有浪费。

复制与整理也不是绝对互斥：把选中区域的幸存者疏散到紧凑目标区，本身就在完成局部整理。算法名称、一次阶段和整套收集器必须分层讨论。

## 5. 三色表示扫描进度，不表示对象的业务属性

白色是本轮尚未发现；灰色是已发现但出边尚未全部扫描；黑色是已发现且出边已扫描。黑对象可以指向灰对象，并不要求整个后代图都已处理完。颜色可由位图、队列等结构表达，不必真的写进对象头。

在静止图中，从根发现对象，逐个扫描灰对象并发现其后继，最后灰集合耗尽，才进一步判断未发现者。循环不会要求无限遍历，因为已发现状态能阻止无休止重复。

并发修改改变了前提。设 A 灰、C 黑、B 白，最初 A→B：应用先新增 C→B，再在扫描 A 前删除 A→B及其他尚待发现路径。若没有日志或补扫，之后扫描 A 找不到B，C又不会重扫，B仍可经C访问却漏标了。

这只是简化反例，不能把“两条边变化”当作全部并发GC的判定公式。临时局部引用、根变化、新对象分配及特殊引用访问，也需要完整协议覆盖。漏标可能误回收活对象，是正确性错误；保守多留垃圾一般是及时性和容量问题，两者不能混为一谈。

## 6. 增量更新与 SATB 各保住什么

增量更新侧重让变化后的新关系进入后续处理：若已扫描部分新增了可能遗漏的引用，需要记录有关变化或重新扫描。历史 CMS 通过脏卡、mod-union等机制和重新标记补足工作，不是每次写字段都精确读取三色并登记一条黑白边。

SATB侧重保住标记开始时的可达关系。G1在必要的引用覆盖前记录旧值，删除A→B后，B仍能通过日志成为待追踪工作。这个快照不是复制整个堆，而是依靠起始状态和变化记录维持逻辑视图。实际屏障有活动期、空值和初始化等过滤，新分配对象也有配套规则。[G1 的 SATB 机制](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

同一反例中，增量更新让C的新关系有机会补扫，SATB则保留A被删除的旧目标。两种思路都不能遗漏仍须使用的对象，也都可能保守多留一些数据。

已标记对象后来失去最后入口，可能形成浮动垃圾。本轮暂留它不等于泄漏，也不能根据一次引用删除就立刻把对象改白：其他路径及并发扫描仍可能存在。后续周期能重新判断，但没有“下一次某个时刻一定释放”的业务时限。并发期间应用仍分配，浮动垃圾又暂占空间，所以并发回收必须有时间和容量余量。

## 7. 四种经常混淆的协调机制

SATB日志处理时间上的图变化；卡表和记忆集处理空间上的外部指入关系。卡表常以粗粒度记录可能改变的位置，记忆集组织指入某代或Region的候选位置，扫描时还需找真实引用。G1写前SATB与写后脏卡维护可以同时存在，不能互相替代。

GC屏障是引用访问附近的回收器协作逻辑。JMM内存屏障服务于线程可见性和顺序，两者不等同；应用不能借GC自动生成的写屏障获得volatile或锁的发布保证。

安全点解决的是能否安全识别线程执行状态等协调问题。引用位置映射帮助区分栈槽或寄存器中的值；到达安全点的等待与到达后的GC工作也要分开。初始暂停并不统一等于“递归扫描整个堆”，也不保证恒定时间：G1的Concurrent Start通常搭载年轻代疏散，历史CMS初始标记则有不同职责。

并行意味着多个GC工作者同时工作；并发意味着GC与应用的执行在时间上重叠；STW表示相关应用执行暂停。并行GC可以STW，并发GC也有暂停阶段。低停顿是在正确性约束下重分配工作，不是让CPU、屏障、元数据和扫描成本消失。

## 8. 可回收性与资源释放期限分开设计

软、弱、虚引用改变特定保留关系，不会消除另一路强引用。引用被清除、包装入队、对象空间复用以及外部资源释放，不是同一事件；ReferenceQueue中收到的是包装对象，而且手动入队不能证明GC已释放目标。

文件、连接和本地资源需要明确的关闭或归还协议。Cleaner可作后备，不能提供业务期限内必执行承诺，清理状态也不能反向强持有被清理对象。完整Reference API、弱容器、Cleaner和reachabilityFence仍保留在引用与资源生命周期主题，不把本章扩成API手册。

同理，System.gc()是回收请求，不承诺收回指定对象、固定字节数或按某时刻清除引用。程序正确性、锁释放、连接归还和任务结束都不应等待这个请求兑现。
