# AQS：把状态获取、排队等待和条件通知连起来

AQS（AbstractQueuedSynchronizer）不是一把具体的锁，而是构造锁和同步器的框架。理解它，关键不是记住“volatile、CAS、双向队列”三个词，而是分清两个职责：谁定义资源何时可用，谁组织暂时不能继续的线程。

子类解释同步状态，并实现获取、释放等规则；框架处理竞争失败后的入队、重试、停放、唤醒和取消。因此同一套基础设施可以支撑 ReentrantLock、Semaphore、CountDownLatch 等不同契约。本章按 Java 21 的公开契约解释，不把某一旧版源码的字段名当成永久接口。

## 1. state 表达什么，由同步器决定

一个同步器实例有一份同步状态，不是每个等待线程各有一份。竞争这个实例的线程共同观察它；等待节点另外保存线程、等待状态和前后关联。

- ReentrantLock 用 state 表示持有层数，0表示空闲，正数表示同一持有者重入了多少层。它还需要知道持有者是谁。
- Semaphore 用状态表达许可余额。取得许可与归还许可改变余额，不要求许可一定由同一线程归还。
- CountDownLatch 用状态表达距离打开门闩还剩多少次倒数。到零后永久开放，不是取得一次就消耗一个通行名额。

所以，state 大于1不能泛化成“多把锁”，共享模式也不必然意味着“有几个资源就放几个人”。必须先解释具体同步器的不变量。

AQS提供具有相应内存语义的状态读取、写入与CAS操作。CAS适合多个竞争者同时尝试从空闲变为占有；但不能说每次状态修改都必须CAS。可重入锁中，已经持锁的线程更新自己的重入层数，以及合法持有者释放锁，有不同的竞争条件。安全性来自整个协议，不是每一行都出现原子指令。

这也衔接JMM：volatile不能把“检查持有者、修改计数、发布空闲”自动拼成完整业务原子操作；锁的释放和后续成功获取才共同承担保护数据的可见性关系。只复制一个volatile计数器，并没有实现一把锁。

## 2. 独占获取：等待的是再次尝试的机会

以互斥锁为例，当前线程先按具体锁的规则尝试获取。成功就进入临界区；失败则由AQS组织等待，必要时建立节点并加入同步队列。

入队之后不是所有线程持续空转争抢。框架依据前驱、节点状态和当前资源状态决定何时再次尝试，不能推进时使用停放机制减少空耗。释放方让可推进的等待者获得重新运行的机会，醒来的线程仍须重新取得同步状态。

假设A持锁，B排队，C随后到来：A释放之后，B被唤醒，并不意味着锁已经划给B。非公平策略下，C可能在B真正恢复执行之前先取得空闲锁。B会再次检查，必要时继续等待。这正是“通知”和“授予资源”不能混为一谈的原因。

队头通常承担队列推进的基点作用，不应把它直接画成“永远正在等待的第一个业务线程”。成功获取后节点角色会变化；取消、超时和中断还可能使原来的后继不再有资格等待。应说推进合适的后继，而不是永远唤醒物理链表紧挨着的那个节点。

### 为什么需要重试、双向关联和取消处理

获取失败与释放可能并发发生；加入队列、准备停放和前驱释放也可能交错。框架需要协调这些步骤，避免出现资源已经释放、等待者却错过通知而永远停着的情况。仅仅“把线程放进链表，然后park”并不够。

前驱关联有助于判断排队位置，前后关联也参与取消节点的跳过、清理与后继推进。取消的前驱可能不会再承担原来的通知责任，因此不能只依赖每个业务线程手工唤醒下一个线程。

传统CLH自旋锁与AQS的同步队列有历史联系，但AQS不是照搬一个无限自旋的CLH锁。旧资料中的waitStatus、SIGNAL等名字有版本背景；理解等待状态的用途，比把旧节点字段表当作Java21固定布局更重要。

重试也不能解释成“先固定自旋几次，几次失败就证明持锁时间很长”。获取路径可以在停放前多次尝试，但具体策略随实现变化。短暂重试可能省去调度成本，长期竞争则需要避免持续浪费CPU。[AQS获取与排队契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/AbstractQueuedSynchronizer.html)

## 3. 重入：同一持有者的层数，不是放松互斥

设A第一次获得锁，持有层数为1；A在临界区内再次调用需要同一把锁的方法，识别到自己已经是持有者，层数变为2。B不能因为看到正数就把计数也加一，它不是持有者。

A退出内层时，层数从2降到1，B仍然不能进入。只有最外层释放使计数归零，持有关系解除，其他线程才有机会获取。每次释放还要验证调用者确实持有锁；计数溢出同样需要处理，不能无界加一。

这说明重入协议至少包含持有者、层数、获取资格和完全释放时的发布顺序。若用synchronized构造教学实现，就应由同一监视器保护这组状态；若基于AQS，就遵循其状态与获取释放协议。不能从两套实现各摘一半，拼成未经证明的锁。

可重入只解决同一线程再次取得同一把锁的问题。A持甲等乙、B持乙等甲，仍会死锁。多个资源应采用稳定的获取顺序；期限和回退可以改善故障响应，但无休止的失败重试仍可能形成活锁。

## 4. 公平性来自准入规则，不来自FIFO三个字

队列按FIFO组织等待，不等于新线程一定先入队再争抢。非公平锁允许新到线程在某些路径尝试取得当前空闲状态；公平获取通常先判断是否已有排队前驱，再决定能否取得。

公平策略减少插队，往往使等待更可预测，但它不保证操作系统一定先调度谁，也不保证谁先完成业务。无参数tryLock即使面对公平ReentrantLock，仍可以直接争抢；带期限的tryLock有相应的公平行为。判断是否满足公平要求时，必须同时看构造策略和所用API。[ReentrantLock公平策略边界](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html)

公平与吞吐的差异也不只是“多判断一次队列”。按等待顺序交接可能需要恢复被停放的线程；非公平路径可能让已经在运行的线程先完成一次短临界区，避免某些交接空隙。代价还包括调度、竞争与工作负载，不能承诺某一种策略永远更快。

如果业务要求严格轮流执行ABC，公平锁仍然不够。应把“轮到谁”写进业务状态，并按该条件等待。公平性是锁竞争策略，轮次是业务协议。

## 5. 共享模式：一次成功之后，别人是否还能继续

共享模式允许多个获取者在状态规则满足时通过，但不要求所有人同时成功。AQS的共享尝试返回值区分失败、成功但不能保证后继还能取得，以及成功且后续仍可能取得。这个返回结果不应与state本身混为一谈。

### Semaphore：先计算候选余额，再决定能否提交

假设有3个许可，每个任务需要1个。获取者读取当前余额，计算扣除后的候选值；候选值不够时获取失败并等待，够用时才尝试原子提交这次扣减。不能把它理解成先把真实state减成负数，再让所有失败者各欠一个许可。

CAS失败可能意味着别的线程已改变余额，应按新状态重新判断。归还许可后，等待者重新竞争；共享传播让更多符合条件的等待者有机会继续，而不是无条件把所有线程放行。一次申请多个许可、不同申请量或公平规则，会进一步影响谁能推进。

许可不是消息，也不绑定线程所有权。只有确实获取成功，才应按协议归还；未获取就release，会把可用额度凭空增加。一个二元信号量并不是带持有者检查的ReentrantLock。并发许可也不是每秒请求限流，下游变快时同样的许可数可以产生更高QPS。[Semaphore许可与所有权契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/Semaphore.html)

### CountDownLatch：等待事件，不是借用资源

Latch的倒数从3到2到1再到0，表示三次被约定的完成事件已经报告。三次事件可以由三个任务产生，也可以按明确协议由其他安排产生，不能把计数机械等同于线程数量。

await在计数非零时等待，到零后当前及后来的等待者都可通过。它是一次性门闩，不能通过release把“名额”补回去，也不能reset成下一轮。

把countDown放在任务的finally里可以报告任务已经结束，却不证明任务成功。错误信息和结果必须另行收集；若工作尚未被线程池接收就遭拒绝，还要由拥有者处理对应完成责任，否则等待者可能永远等一个根本不会执行的任务。

多个阶段重复会合应查看CyclicBarrier或Phaser的契约，而不是强行复用同一个Latch。不同工具可能组合锁和条件等机制，不应仅因都在JUC就称它们全是直接的AQS子类。

## 6. Condition：先等条件，再等重新拿到锁

AQS的Condition支持是有前提的：同步器要支持相应的独占持有检查、完全释放以及恢复保存的持有状态。不是所有基于AQS的共享同步器都自动拥有可用的Condition。

以有界队列为例，消费者持锁发现队列为空，不能一直占着锁等生产者，因为生产者也需要这把锁放入元素。await会保存相关持有状态、释放锁，并进入条件等待。生产者放入元素后signal，消费者成为重新竞争锁的候选者；等它真正重新拿到锁，恢复持有状态后，才从await继续。

这里有两种不同的等待：条件队列等业务谓词变化，同步队列等取得锁的资格。signal不是直接把锁交出去，发出signal的线程仍然持锁，直到它自己释放。

消费者恢复后仍必须循环检查“队列非空”。一方面可能虚假唤醒，另一方面被通知后别的消费者也可能先取走元素。通知只是提醒重新检查，条件本身必须存放在受保护的共享状态中。

同一把ReentrantLock可以建立notEmpty与notFull等多个Condition，让生产者、消费者等待不同谓词，减少无关唤醒。相应状态的检查、修改和通知仍应遵守同一锁协议；只给通知动作加锁，却在锁外任意改变队列，无法补全正确性。

## 7. 中断、超时和释放属于同一生命周期

lock、lockInterruptibly和限时tryLock表达不同的获取契约。lock不会通过抛InterruptedException结束获取；可中断和限时路径则允许调用者结束自己的等待，框架也须维护取消后的队列推进。

获取失败或抛出中断异常时，没有取得锁，不能在一个无条件finally里unlock。只有成功获取后，才进入保证释放的业务作用域。获得锁之后发生业务异常，释放锁也不意味着业务修改自动回滚。

等待节点退出、线程重新可运行、线程获得资源、业务操作完成，是四个不同事件。超时只结束当前获取尝试，不等于别人的临界区停止；唤醒只提供推进机会，不是完成凭证。这与线程池中“Future取消不等于实际资源已经释放”是同一种生命周期区分。

## 8. 怎样选择，而不是给工具排高低

简单互斥可优先采用边界清楚、容易正确释放的结构。需要可中断获取、限时尝试、多条件队列或可选公平策略时，显式锁提供更直接的控制；需要许可余额或一次性完成事件时，使用对应同步器，而不是把所有等待都写成锁竞争。

synchronized本身也具有互斥、重入和可见性语义。它的性能依赖目标JDK、竞争程度、临界区长度和运行环境；不能把“AQS在高并发一定更快”作为结论，更不能把灵活性等同于性能证明。

同样，AQS内部使用CAS，不代表基于它的锁是lock-free算法。持有者暂停时，其他线程仍可能无法进入；框架还会停放等待者。底层采用原子指令与上层是否阻塞，是两个不同层次。

阅读一个同步器时，可以沿四个问题建立完整解释：状态代表什么，谁有资格改变它，失败者怎样等待和退出，释放之后谁能继续。再把它连接到JMM、取消、资源所有权与业务不变量，才真正理解了同步框架，而不是只记住其零件名称。
