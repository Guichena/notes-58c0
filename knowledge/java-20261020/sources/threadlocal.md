# ThreadLocal：线程绑定、请求边界与上下文传递

ThreadLocal 解决的是“同一线程中的多层调用怎样取得当前上下文”，不是“多个线程怎样共同修改一个对象”。它把值绑定到当前线程，让相同的访问入口在不同线程上取得各自的绑定。

理解它，可以沿一条线展开：值放在哪里，为什么能隔离绑定，为什么线程池复用会留下旧数据，以及任务跨线程后应怎样重新建立并结束这个绑定。本章以 Java 21 为语义基线；涉及 ThreadLocalMap 的部分明确指 OpenJDK 21 实现，不把内部结构当成所有 Java 实现必须遵守的 API。

## 1. “每线程一份”究竟是什么意思

假设应用用同一个 ThreadLocal 保存用户上下文。线程 A 设置用户甲，线程 B 设置用户乙；两者调用同一个 ThreadLocal 的 get，获得的仍是各自线程上的值。隔离的关键不是创建了两份 ThreadLocal，而是访问发生在哪个线程。

不过，“每线程一份变量”不等于“自动复制一份对象”。如果 A、B 都把同一个可变 List 引用放入各自绑定，两个线程最终仍在修改同一个 List。ThreadLocal 没有为列表加锁，也没有深复制其中元素。

同理，方法中的局部引用只属于当前调用，不代表它指向的对象不会共享。安全性取决于对象是否真正由一个线程独占，而不是变量恰好写在方法里。

### 为什么不用方法参数

如果数据只在一个方法内部使用，局部变量最直接。如果调用关系明确，显式参数也更容易看出依赖、控制生命周期，并理解异步传递。

ThreadLocal 的便利在于同一执行线程上的多层方法不必逐层增加参数。例如入口已经完成身份验证，Service 和日志组件可以读取当前用户或追踪信息。代价是依赖变得隐式：单看方法签名，不知道它需要入口事先安装什么状态，也不知道缺少上下文时应如何处理。

所以它更适合作为有明确进入和退出边界的上下文载体，而不是把任意业务变量放进一个“到处都能取”的隐藏容器。

## 2. 值存在 Thread 的 Map 中，ThreadLocal 是绑定的键

在 OpenJDK 21 的实现里，一个线程拥有自己的 ThreadLocalMap。同一个线程可能需要用户身份、追踪信息、格式化器等多种绑定，具体的 ThreadLocal 对象用来区分这些绑定。

set 的逻辑是取得当前线程的 Map，再为当前 ThreadLocal 保存值；get 则在当前线程的 Map 中查找这个键。Map 已经归属于某条线程，所以没有必要再用线程 ID 作为键。

可以想象两张表：A 的表里，同一个上下文键指向用户甲；B 的表里，这个键指向用户乙。键相同，所属的表不同，值也就可以不同。ThreadLocal 对象更像访问约定，不是把所有线程的业务值集中存放在自己身上的仓库。

如果当前线程还没有这个绑定，get 会按初始化规则取得初始值。默认初值是 null，也可指定初始化方式。remove 移除的是当前线程、当前 ThreadLocal 对应的值；以后再 get，可能重新触发初始化。它不是“清除所有线程的这个变量”。[API 语义核对](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ThreadLocal.html)

### ThreadLocalMap 为什么不用普通 HashMap 的碰撞结构

OpenJDK 的 ThreadLocalMap 使用数组和线性探测：一个键的起始槽位被占用时，继续向后寻找匹配键或可用位置，越过数组末尾后回到开头。它与 HashMap 常见的桶内链表、树结构不同。

这也解释了为什么删除不是简单把一个槽置空。假设两个键从同一位置开始查找，第二个因碰撞被放到后面；若前面的槽直接变成查找终点，后面的键就可能被误判为不存在。清理时需要整理相关探测路径。

已有知识中的哈希增量用于改善二次幂容量下的分散，不代表永远没有碰撞，更不是对业务对象的同步保护。阈值约为容量的三分之二，也不等于一到阈值便立即扩容：实现会先尝试清理失效项，再根据剩余数量决定是否扩大数组。HashMap 的 0.75 是常见默认负载因子，同样不该误当固定不可变的定律。[OpenJDK 21 实现核对](https://github.com/openjdk/jdk/blob/jdk-21%2B35/src/java.base/share/classes/java/lang/ThreadLocal.java)

## 3. 弱引用只放开了键，不会顺带释放值

ThreadLocalMap 的 Entry 对 ThreadLocal 键持弱引用，对 value 通常持强引用。假设某个 ThreadLocal 已没有其他强引用，GC 可以清除这个弱键，但仍存活的线程还可能通过自己的 Map 和 Entry 保留 value。

因此，键已失效与值已释放不是一回事。此时可能出现一个业务上已无法正常取回、却仍被内部结构保留的值。

把键做成弱引用的意义，是避免 Map 一直强行延长无用 ThreadLocal 对象本身的寿命；它不是完整的资源清理方案。如果键也为强引用，存活线程的 Map 还会把键一起保留下来，问题并不会更好。

也不能说这些值“永远不会回收”。后续有关操作可能清理失效项，线程终止后也可能不再保留它们。真正的风险是：请求已经不需要对象，但它可能继续随长寿命线程保留，释放时间没有对齐业务生命周期。

### 为什么不能等下次 get 或 GC 自动收尾

实现会在一些查找、插入和移除路径中处理失效项，但不是每次操作都扫描全表。一次 get 若直接命中目标位置，就不代表其他槽位上的陈旧对象也被清掉。

GC 处理可达性，不知道“这个请求已经结束”；Map 的顺带清理也不知道业务希望在哪个时间点释放绑定。因此，清理责任必须由拥有请求或任务作用域的代码承担，不能寄希望于未来某次访问碰巧触发扫描。

## 4. 在线程池中，数据串用与内存滞留是两类风险

线程池最重要的变化是：任务结束了，执行它的线程通常还会继续处理后续任务。

请求 A 在 worker 上安装用户甲的信息，结束时没有清理。worker 接着处理请求 B。如果 B 的某条路径没有正确安装自己的上下文，却直接读取绑定，就可能读到甲。即使 B 从不读取这个值，甲的大对象也可能继续被保留。

前者是上下文串用，可能影响身份或租户判断；后者是超出需要的内存保留。它们可以同时发生，但不能只用“弱引用键是否被GC”来解释。

### static final 为什么不是防泄漏方案

把 ThreadLocal 声明为 static final，可以稳定访问键，避免每次调用都创建新的键。这不等于请求值被自动清理。只要类和键仍可达，键可能一直不失效，旧值反而仍能通过 get 正常读到。

因此，“没有 null 键”不等于“没有残留问题”。真正需要检查的是：这一份值应该活到什么时候，谁在边界结束时移除或恢复它。

set(null) 也不等同于 remove。前者建立或保留一个值为 null 的绑定，后者移除绑定，后续 get 的初始化语义不同。若值是连接等资源，remove 只解除绑定，不自动完成资源关闭、事务结束或归还连接池；这些动作要由资源的拥有者负责。

## 5. 清理的完整规则：顶层移除，嵌套恢复

对于没有外层上下文的顶层请求，一个基本结构是：进入时安装本次上下文，执行业务，正常或异常退出时在 finally 中移除。清理应发生在持有该绑定的执行线程上；换到另一个线程调用 remove，清不到原 worker 的值。

但可复用的组件不能简单规定“finally 一律 remove”。考虑外层任务已经绑定用户甲，内层临时安装另一份上下文，退出后外层还要继续执行。如果内层直接移除，就把外层原本正确的绑定也破坏了。

更通用的规则是：

1. 进入作用域时保存执行线程原有的绑定状态。
2. 安装当前作用域需要的值。
3. 执行当前工作。
4. 退出时恢复原来的绑定；原先没有绑定，才移除。

这里要区分“没有绑定”与“绑定值恰好为 null”。普通 ThreadLocal 的 get 还可能触发初始化，因此完整的作用域封装需要自己定义如何表示缺省状态，不能把任何 null 都草率当作不存在。

线程池的 CallerRunsPolicy 使这个问题尤其直观：池饱和后，一个提交的任务可能直接在提交者线程执行。提交者不一定是空白 worker，它可能仍处于外层请求之中。保存与恢复的对象应该是真正执行任务时的线程状态，而不是提交时猜测的某个 worker 状态。

finally 解决的是正常栈展开下的清理，不是任何情况下都必定完成的承诺。永不退出的任务、进程被终止，以及前一项清理抛异常，都需要分别理解。多项清理互相独立时，不能让资源释放的异常跳过上下文恢复。

## 6. 父子线程继承，不等于线程池任务传播

普通 ThreadLocal 不会自动把父线程的绑定传给新线程。InheritableThreadLocal 提供的是另一种机制：通常在创建子线程时，形成继承初值，而不是在每次提交任务时捕获提交者状态。

如果线程池的 worker 早已存在，新请求提交任务并不会重新创建该线程，自然不能依赖“创建时继承”传递本次请求。更隐蔽的情况是，worker 恰好在某个请求期间被创建，继承了当时的值，随后又被其他请求复用，留下过时上下文。

继承也不等于深复制。默认 childValue 返回父值本身，若它是可变对象引用，父子线程可能仍然共享对象内容；而线程创建方式也可以选择不接收继承值。[继承时机与默认行为核对](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/InheritableThreadLocal.html)

### 异步传播要跟着任务，而不是猜测线程血缘

一条清晰的传播链是：提交任务时捕获本次必要的不可变上下文；任务真正执行时保存执行线程旧状态，再安装捕获值；任务结束时恢复旧状态。

这把“捕获哪次请求”与“在哪条线程上使用”分开了。捕获的也不应是一个随时会被父任务修改的共享 Map，否则只是传播了引用，仍然没有隔离状态。

TransmittableThreadLocal 等工具可以帮助实现支持路径上的传播，但不能只换类名便假定任意线程池、回调和框架都被覆盖。关键仍是捕获、安装、恢复三个边界。对于显式参数就足够的调用，直接传必要值往往更容易理解；对于响应式处理，也不能把一个逻辑请求永远绑定到固定线程的假设带过去。

## 7. 四类使用场景，各自有什么边界

### 用户上下文：便于访问，不负责证明身份

同一线程内的入口、Service、DAO 读取当前用户，是 ThreadLocal 的典型用途。入口应先取得可信认证结果，再建立绑定；结束时由拥有者清理。

如果网关通过请求头向下游传递身份，下游还需要明确哪些来源可信、怎样防止外部调用伪造相同字段。把一个 userId 存进 ThreadLocal 不会让它自动变成经过认证的身份。跨服务传输和服务内线程绑定是两层不同职责。

这个过程是架构示例，不应写成学习者已经做过的真实项目经历。

### 数据库连接：表达同线程事务范围，不等于任意共享连接

在传统的线程绑定事务模型中，一组 DAO 调用可能需要使用同一个事务所持有的连接。ThreadLocal 可以作为定位这个资源的载体，但连接的取得、事务提交或回滚、资源释放仍属于事务管理职责。

不能把它理解成“每个线程永久占一个数据库连接”，也不能把连接引用随日志上下文一起复制到异步线程。拿到了相同引用，不代表拥有跨线程并发使用该连接的权利，更不代表事务边界被自动传播。

### SimpleDateFormat：隔离可变实例，也要考虑保留成本

每个线程真正持有独立的 SimpleDateFormat，可以避免多个线程同时修改同一实例。若初始化逻辑始终返回一个共享对象，ThreadLocal 并不能补救。

对象复用可能减少分配，也会增加每线程长期保留的状态。几百条长期线程分别保存大对象，与少量短寿命线程的成本完全不同。已有笔记中的 DateTimeFormatter 是另一条思路：使用不可变、线程安全的格式化器，同时核对格式符、时区、Locale 与解析语义，而非只机械替换类名。

### TraceId：跨方法、跨线程、跨进程分别处理

同一线程里把 TraceId 放进日志上下文，可以减少显式传参。异步任务需要相应的上下文传播，网络调用则需要通过约定的传播载体注入和提取。ThreadLocal 本身不会把值穿过网络带到另一服务。

追踪标识用于关联事件，不是权限证明。日志上下文被成功复制，也不意味着数据库事务、用户权限和所有业务状态都应一起复制。

## 8. 用生命周期把这些知识连起来

ThreadLocal 的核心不是“省略参数”，而是一次有边界的绑定：由谁创建，谁能读取，什么时候跨线程，什么时候恢复或结束。

如果线程与任务具有不同寿命，就要显式处理残留；如果多个线程拿到同一个可变对象，就还需要对象所有权或同步；如果出现嵌套调用，就不能只清空而不恢复；如果跨线程或跨进程，就必须重新说明传播机制。

与 volatile 对照也很清楚：volatile 为共享字段建立可见性和顺序关系，ThreadLocal 选择的是把绑定按线程分开。前者不自动提供复合操作互斥，后者不自动复制对象。只有先看清共享的究竟是什么，才能判断是否真正消除了并发问题。
