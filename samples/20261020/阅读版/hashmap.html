HashMap：从一次查找到碰撞、扩容与并发边界

HashMap 是按键保存和查找值的哈希表：先用哈希缩小查找范围，再用键的相等关系确认目标。它适合不要求顺序的键值索引，但不能把“通常查得快”理解为任何输入下都恒定耗时，也不能直接拿来承接无同步的并发读写。

样稿版本：2026-10-20。 本文是独立学习样稿，不是线上页面更新。题型为 Java 集合原理与使用边界；API 依据 Java SE 21，实现依据 OpenJDK jdk-21+35 的 HashMap。后续更新版、其他厂商实现和其他语言的哈希表不能直接套用源码结论。

1. 30—60 秒口述

“HashMap 用哈希值定位桶，在桶里确认键是否相等，所以碰撞不等于覆盖，只有同一个逻辑键再次 put 才会替换原值。OpenJDK 21 的桶通常使用链表，碰撞严重且满足容量条件时会转为红黑树；扩容则重新分配桶，把原有映射迁移过去。使用上，我会保证键的 equals 和 hashCode 一致且入表后稳定，注意它不保证遍历顺序，也不提供并发安全。性能要结合哈希分布、扩容和业务访问模式讨论，不能只背一句 O(1)。”

2. 标准层：沿一次 put / get 讲机制

先分清三个“相同”

  • 相等的键：由键的相等契约决定，是同一个逻辑键。
  • 相同的 hashCode：可能只是碰撞，并不证明键相等。
  • 落入同一桶：即使完整哈希不同，也可能因为桶数量有限而发生。

equals 相等的对象必须有相同的 hashCode；反过来不成立。因此自定义键重写 equals 时，一般也要相应重写 hashCode。HashMap 不是“只要地址不同就存两份”，也不是“哈希一样就覆盖”。依据：Object 的相等与哈希契约

路径一：定位桶，再确认键

在本文核对的实现中，非空键的 hashCode 会经过高低位混合，再与容量掩码计算桶下标。桶为空就可以直接放入；桶非空则沿链表或树查找。找到相等键时更新值；没找到才新增映射。get 沿相同定位路径查找，但不新增节点。实现依据：hash、getNode、putVal

直觉上，桶相当于“先找对抽屉”，相等判断相当于“再核对文件编号”。抽屉里有多份文件是正常情况，不能看到抽屉相同就覆盖第一份。

路径二：区分容量、元素数与装载因子

容量是桶数；size 是映射数；装载因子影响何时为更多映射腾出空间，不是“已有多少个桶非空”。默认装载因子为 0.75。更稀疏通常耗费更多空间；更拥挤会增加碰撞风险。把初始容量设得特别大也不是免费优化，完整遍历还需要扫描桶。依据：HashMap 类说明

设想仅有 100 条学习笔记，却预留了数百万个桶。即使查一个编号很快，定期导出全部内容时仍要面对大量空桶。这是“单次查找”和“全量遍历”不能混为一谈的原因，不是实测性能数字。

路径三：扩容不是简单复制数组

在该实现的普通扩容路径中，容量翻倍；迁移使用节点中保存的哈希，将旧桶拆成“原位置”和“原位置加旧容量”两组，不要求逐项重新调用键的 hashCode。新增映射超过阈值会触发扩容；小容量下碰撞过多也可能先扩容而不是树化。实现依据：resize、treeifyBin

下面用具体数字自行推演，而不是只记“扩容两倍”：容量为 4 时，哈希 1 和 5 的下标都为 1；容量变成 8 后，它们分别去 1 和 5。原来冲突的两项因此分开。若所有键的完整哈希都一样，增加桶数并不能把它们分散开。

3. 原创例子：学习笔记索引

场景是“按主题键查询整理状态”，不涉及真实用户数据。用不可变 record 表示测试键，故意指定哈希来观察碰撞：

record Key(String id, int hash) {
    @Override public int hashCode() { return hash; }
}

这里 record 的相等关系包含 id 和 hash；这是用于控制实验输入的键，不是建议业务系统把“人工哈希”作为业务身份。

依次执行：

  1. 写入 Key("Java", 1) → "draft"。
  2. 写入 Key("SQL", 17) → "ready"。容量为 16 时，两项都落入下标 1，但它们不是同一个键，所以 size 为 2。
  3. 用一个新建的 Key("Java", 1) 写入 "checked"。虽然不是同一对象，它与原键相等，因此旧值被替换，size 仍为 2。
  4. 查询 Key("SQL", 17)，仍能得到 "ready"。碰撞没有使这份笔记丢失。

应该从轨迹得出什么？ 哈希解决的是候选范围，equals 解决的是身份；对象新旧不是逻辑键新旧。完整运行代码见同目录 HashMapProbe.java，不是要求读者补齐的伪代码。

再看一个反例：如果键用可变字段 id 参与相等和哈希，插入后把 id 从 1 改成 2，就可能在新位置找不到旧节点。Map 契约本来就没有为“入表后改变了键的相等关系”提供正常行为保证，不应该写依赖这种结果的业务代码。优先使用不可变键，或把稳定的业务编号作为键。依据：Map 可变键警告

4. 易错边界：背数字之前先说适用条件

树化不是“第八个元素必变树”

以下只针对所核对源码及普通 put 路径：树化相关常量为 8，最低表容量为 64；已有 8 个节点的链表再追加不同键，即第 9 个节点时才走到树化请求。容量不足则先扩容。扩容拆分树桶时，某侧节点数不超过 6 会退回链表；普通删除路径还有树形判断，不能归纳成“任何时候剩 6 个必退化”。实现依据：putVal、treeifyBin、TreeNode.split、removeTreeNode

这些数字是理解实现的线索，不应成为业务正确性的前提。尤其不要把一个插入入口的计数条件推广到所有 compute / merge 路径。

红黑树不等于任意键都保证对数查找

树高受约束，不代表每次查找都能只走一个方向。源码在哈希相同且无法用合适的比较关系区分键时，可能搜索两侧子树。因此不能承诺“只要树化，所有恶意碰撞输入下都 O(log n)”。这是对源码分支的分析，不是本次运行得到的性能曲线。实现依据：TreeNode.find

复杂度怎样说才稳妥？ 在键的哈希与相等判断为常数成本、散列分布良好的前提下，查找通常按期望 O(1) 分析；插入还要考虑扩容后的均摊成本。若 N 为映射数、C 为容量，全量遍历为 O(C+N)；链式碰撞桶长度为 B 时，查找可到 O(B)。极端碰撞不能凭树化排除线性查找，且用户自定义 hashCode / equals 本身也可能昂贵。性能前提：HashMap API

null、顺序与线程安全分别回答

  • HashMap 允许一个 null 键及多个 null 值。get 返回 null 可能是没有映射，也可能是值确实为 null；需要区分时用 containsKey。它不保证遍历顺序，包括“不变更时看起来稳定”也不应当作插入顺序契约。依据：HashMap API
  • 需要插入顺序或访问顺序时，研究 LinkedHashMap 的对应模式；需要按键排序或范围查询时，研究 TreeMap。顺序要求不同，不能用“都能存键值”代替选型。LinkedHashMap；TreeMap
  • HashMap 没有提供并发读写同步。fail-fast 是尽力发现修改错误，不是锁，也不保证总会抛异常。不能把“没抛异常”当作线程安全证据。依据：HashMap 并发与迭代说明
  • 若选择 synchronizedMap 包装，访问应统一经过包装对象，遍历其视图时还要按文档在 map 上同步。若选择 ConcurrentHashMap，可使用其原子更新 API，但它不接受 null，且多次独立方法调用不会自动成为一次业务事务。Collections.synchronizedMap；[ConcurrentHashMap](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)

5. 四个追问，带可继续讲的答案

Q1：只重写 equals，不重写 hashCode，哪里会出问题？

两个逻辑相等的实例可能产生不同哈希，查询定位和候选过滤就可能绕开已存键，出现查不到或看似重复的逻辑键。问题是键类违反相等/哈希契约，不是 HashMap 应该全表扫描替你修复。做法是让两者基于同一组稳定身份字段，并测试“相等的新实例能够找到旧值”。Object 契约

Q2：预计放 1,000 项，new HashMap<>(1000) 就不会扩容吗？

不要把构造器的初始容量参数当成预期映射数。以默认装载因子思考时，需要为 1,000 个映射留出负载空间，而不是只准备 1,000 个桶。Java 19 起可用 HashMap.newHashMap(1000) 表达“预计 1,000 个映射”，在本文的 Java 21 API 中可用；更早版本需自行估算容量，并考虑实现取整。即使预留充足，也不要进一步承诺任意碰撞输入绝不发生内部调整。HashMap 构造器与 newHashMap

Q3：两个线程都执行“没有就新增”，换 ConcurrentHashMap 就够了吗？

仅把容器替换掉，而仍写成 containsKey → put 两步，两个线程仍可能同时判定不存在。若需求是同一个键的原子初始化，可按 ConcurrentHashMap 的契约选择 putIfAbsent 或 computeIfAbsent；不要在计算函数里塞很慢的网络请求后假定没有竞争影响。若需求是跨多个键保持业务一致性，还要另外设计协调机制。容器级线程安全与业务流程原子性是两个问题。ConcurrentHashMap 原子更新方法

Q4：压测发现查找变慢，是否直接调低装载因子？

不能先把原因归给装载因子。先看样本的键分布、equals/hashCode 成本、扩容是否集中发生，以及耗时测的是单次查找还是全量遍历。分布差可能要改键设计；增长可预测时可以合理预分配；若测的是遍历，过大容量还可能更差。此处是排查方案，不是已经定位过的故障，也没有宣称任何提升比例。

完整可运行验证代码

以下程序与随附源文件一致，可直接保存为 HashMapProbe.java 运行。

import java.lang.reflect.Field;
import java.util.HashMap;
import java.util.Objects;

// Original learning probe. Reflection is used only to inspect JDK internals in a local test.
public class HashMapProbe {
    record Key(String id, int hash) {
        @Override public int hashCode() { return hash; }
    }
    static final class MutableKey {
        int id;
        MutableKey(int id) { this.id = id; }
        @Override public int hashCode() { return id; }
        @Override public boolean equals(Object other) {
            return other instanceof MutableKey k && id == k.id;
        }
    }
    static void expect(Object actual, Object expected, String name) {
        if (!Objects.equals(actual, expected))
            throw new AssertionError(name + ": " + actual + " != " + expected);
        System.out.println("PASS " + name + " = " + actual);
    }
    static Object[] table(HashMap<?, ?> map) throws Exception {
        Field f = HashMap.class.getDeclaredField("table");
        f.setAccessible(true);
        return (Object[]) f.get(map);
    }
    static String binKind(HashMap<?, ?> map, int bucket) throws Exception {
        return table(map)[bucket].getClass().getSimpleName();
    }
    public static void main(String[] args) throws Exception {
        HashMap<Key, String> notes = new HashMap<>(16);
        Key a = new Key("Java", 1), b = new Key("SQL", 17);
        expect(notes.get(a), null, "empty lookup");
        notes.put(a, "draft");
        notes.put(b, "ready");
        expect(notes.put(new Key("Java", 1), "checked"), "draft", "equal key replaces");
        expect(notes.size(), 2, "collision is not equality");
        expect(notes.get(b), "ready", "colliding key remains retrievable");
        notes.put(null, "unknown topic");
        notes.put(null, "renamed topic");
        expect(notes.get(null), "renamed topic", "one null key");
        notes.put(new Key("RAG", 33), null);
        expect(notes.containsKey(new Key("RAG", 33)), true, "explicit null value is present");
        expect(notes.containsKey(new Key("missing", 49)), false, "absent colliding key");

        HashMap<Integer, Integer> small = new HashMap<>(4);
        expect(table(small), null, "lazy allocation");
        for (int k : new int[]{1, 5, 2}) small.put(k, k);
        expect(table(small).length, 4, "capacity at three mappings");
        small.put(3, 3);
        expect(table(small).length, 8, "capacity after fourth mapping");
        expect(((java.util.Map.Entry<?, ?>) table(small)[1]).getKey(), 1, "hash 1 stays");
        expect(((java.util.Map.Entry<?, ?>) table(small)[5]).getKey(), 5, "hash 5 moves");

        HashMap<Key, Integer> collisions = new HashMap<>(64);
        for (int i = 0; i < 8; i++) collisions.put(new Key("k" + i, 7), i);
        expect(binKind(collisions, 7), "Node", "ordinary put at eight nodes");
        collisions.put(new Key("k8", 7), 8);
        expect(binKind(collisions, 7), "TreeNode", "ordinary put at ninth node");
        expect(collisions.get(new Key("k8", 7)), 8, "equal distinct key in tree bin");

        HashMap<MutableKey, String> unsafe = new HashMap<>();
        MutableKey key = new MutableKey(1);
        unsafe.put(key, "value");
        key.id = 2;
        expect(unsafe.get(key), null, "mutation pitfall on this runtime, not API guarantee");
        expect(unsafe.size(), 1, "entry still occupies storage");
        System.out.println("All 17 checks passed.");
    }
}
