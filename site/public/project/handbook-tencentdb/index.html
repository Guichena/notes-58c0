01一、信息缺口门控替代关键词触发（核心改造一：压降高误调用）

对应简历关键词针对关键词触发误调用率高，参与 Proxy 系统提示词注入优化，以信息缺口门控替代关键词触发。Codex CLI 上，误调用率由 87.14% 降至 31.94%。

先懂再背1.0 设计推演速懂（先懂再背）

先拆简历原句 & 点破易踩坑：

先认清整套系统的位置：开发者不改 Codex CLI / Claude Code 一行源码，只把 API Base URL 指向无状态透明代理 MemoryProxy（8 阶段流水线，你独立负责第 4 阶段系统提示词注入与 test1k 评测），模型需要查团队资产时借宿主原生 Shell + curl 调 Bridge 网关。

  • 易踩坑预警 1（核心认知转折）：原版误调用率高达 87.14%（122/140），根本原因不是模型笨，而是原版把“主题相关（词面重合）”当成了调用条件！编码时用户问“按规范改命名”，哪怕答案已经贴在当前窗口里，关键词触发器照样逼它调接口。改造的本质是把触发条件从“关键词重合”切换为“当前窗口是否缺少作答证据（信息缺口）”。
  • 易踩坑预警 2（主动交代权衡）：门控收紧把误调用 FCR 净压降 55.20pp（87.14% → 31.94%），伴随正例发出率 ECR 由 96.08%（98/102） 回落至 77.88%（81/104）（-18.20pp），这是召回换精度的工程权衡，汇报时必须主动说透。

车祸现场推演：每一步为什么被迫这么设计？

  1. 车祸 1（单向正向强制句 + 关键词重合 → 窗口已有答案仍 87.14% 狂调接口）→ 主模型全局三步门控 + 成对正负边界
    • 不加它怎么炸：原版每个工具段落各自堆砌“遇到规范/命名/配置务必调用 XXX”且没有拒识出口。结果就像 Unity 命名规范的正负配对题——两题提问逐字节一模一样，负例窗口里明明已经贴出了 Forest Spirit / Evil Spirits 正文，原版仍 87.14% 触发远程检索。
    • 怎么设计：在全部工具卡之前抽离全局三步信息缺口门控，第一步先给显式拒识出口（明确“单凭关键词重合不构成调用理由”），并在每张工具卡成对写明「适用条件 + 避开条件」；同时死锁两条防漏调硬边界（L2 路径摘要 ≠ 正文、Skill 名称简述 ≠ 正文），防止模型扫一眼目录就自以为够用而瞎编。
  2. 车祸 2（为什么不在 Proxy 前置挂一个 Embedding 路由器或 7B 小模型硬拦截？）→ 视野与延迟的双重死结
    • 不加它/硬上它怎么炸：
      • Embedding 向量路由：算的还是“问题和工具的主题相似度”，根本判断不了当前窗口里有没有答案，在 109 条同主题外队干扰和 464 条窗口已给 Pair 上全军覆没；
      • 前置 7B 小模型分类器：如果只传最后一句提问，一样看不到窗口里的代码和历史；如果把几万 Token 本地代码全传给小模型，每轮白多一跳长上下文 Prefill 延迟与成本，而且小模型看不到主模型同轮第 2、3 步刚拿回来的工具 Observation！
    • 怎么设计：直接复用已经握有完整代码窗口与实时工具返回的主模型做门控，零额外网络往返延迟、视野最全。
  3. 车祸 3（为什么不走标准 Function Calling / MCP 而让模型拼 Shell + curl？）→ 透明代理零侵入的最大公约数
    • 不加它怎么炸：透明代理承诺“多种第三方 CLI 只改一行 Base URL 即用”。如果 Proxy 擅自在请求体里塞自定义 tools 函数声明，上游模型吐出自定义 tool_call 后，客户端本地根本没注册对应处理函数，当场报错中断会话！
    • 怎么设计：所有编码终端 CLI 都原生自带 Shell 工具，让模型借原生 Shell + curl 打向既有 Bridge 网关（由 Bridge 代填后端鉴权凭据）是零客户端改造的通用解法；正因无原生 Schema，才引出了下一章的「运行时契约三层编译工具卡」。

    • 不加它怎么炸：项目早期每轮自动召回记忆拼进用户消息前缀，结果每次都改动前缀把上游 Prefix Cache 打碎，延迟和算力反而暴涨才下线；如果按每轮 Query 动态只塞 1~2 张工具卡，会在十几轮编码对话里把前 500 Token 改来改去，重蹈整段源码重算覆辙。

    • S（背景与痛点）：原版手写 Markdown 在三类工具间重复堆砌协议，未开启的写卡片也照塞（均值 3,518.0 Token），服务端改参极易漂移；相邻工具边界模糊，多跳读附件常手猜路径或跨响应混拼版本号报 4xx，发出后的首步命中率仅 27.55%。
    • T（技术目标）：消除说明与源码漂移，压缩冗余并保证十几轮编码对话里静态前缀逐字节恒定以护住 Prefix Cache，同时把首步选型与多跳参数绑定拉上来。
    • A（核心做法与钩子）：设计了三层解耦编译器：
      • ① 底层 Runtime Contract：对齐服务端源码登记路径、必填/禁用参数与请求头；
      • ② 中层 Strategy IR：声明成对适用避开、相邻工具区分、同次成功响应参数强绑定及唯一共享 HTTP 协议；
      • ③ 顶层 Capability Pruning + 五段装配：按会话剔除未启用家族与写卡，前三段静态置顶缓存、后两段动态置底，配套 7 个文件共 183 项单测（含故意删改限制词必报错的负向断言）护航。
    • R（量化结果与边界）：同批 250 条工具说明从 3,518.0 降至 2,567.5 Token（压缩 27.02%）；条件首步命中率 27.55%（27/98）→ 74.07%（60/81），全量口径同步从 26.47%（27/102）→ 57.69%（60/104）（命中题数 27 → 60，证伪缩分母刷分）。

  • 固定五段 Prefix Cache 装配与 183 项单测负向断言：受 Transformer 单向因果掩码（Causal Mask）限制，仅从第 0 个 Token 起字节一致的前缀可复用 KV Cache。我固定按 [1] 共享协议与停止规则、[2] 信息缺口门控、[3] 能力说明加稀疏工具卡与静态指引、[4] 会话地址与请求头绑定、[5] 运行时动态资产（Skill 目录、L3、L2 目录）拼装。前 3 段静态前缀置顶并按 模板版本 + 会话能力签名 做进程内缓存，后 2 段动态置底（此设计在架构上创造了 Prefix Cache 命中前提，未直读闭源服务商内部缓存计数器）。配套 7 个测试文件共 183 项单测与负向断言，具体校验项见 2.3 Q2。

高频追问2.3 面试官高频连环追问与脱稿答辩（Q1–Q3）

Q1 ★★★（Prefix Cache 经济学拷问）：既然要省 Token，每轮按用户 Query 动态检索只塞最相关的 1～2 张工具卡能省 80%，为什么只压缩 27.02% 做会话级固定装配？

面试官发问：「工具说明压完还有 2567 Token，如果在 Proxy 里按每轮用户问题做一次毫秒级向量匹配，只把最相关的那张工具卡塞进系统提示词，单轮岂不是能压到 500 Token 以内？为什么不做逐轮动态裁剪？」
  • 脱稿答辩：

    「核心是权衡单轮字面节省与多轮几万 Token 代码窗口的前缀缓存复用。

    ① 逐轮换卡会击穿整段代码上下文缓存：编码 Agent 修跨文件缺陷常连发 10～20 轮调用，窗口里挂着几万 Token 仓库源码与历史轨迹，推理引擎按块级前缀哈希匹配 KV Cache 且受单向因果掩码限制，一旦排在最前面的系统提示词在第 500 个 Token 处因逐轮换卡发生字节变动，紧随其后的几万 Token 源码缓存就会整段失效重算，导致首字延迟与真实算力反升，项目早期每轮自动召回记忆拼入前缀正是踩了这个坑才下线。

    ② 会话级裁剪兼顾瘦身与前缀恒定：按会话能力裁剪并把前三段静态前缀置顶，进程缓存键绑定模板版本加会话能力签名，既一次性削减 27.02% 常驻冗余，又保证同会话十几轮交互间静态前缀逐字节恒定（因上游闭源服务未暴露缓存命中计数器，实验只实测汇报 Token 降幅，不虚报缓存命中率与首字延迟）。」

Q2 ★★（编译器工程落地拷问）：按运行时契约生成工具卡在代码里具体输入输出是什么？压缩文案时怎么证明没把关键安全约束删丢？

面试官发问：「具体讲讲按运行时契约生成工具卡在代码里是怎么落地的，输入是什么、输出是什么？把长散文压成稀疏卡片时，怎么防止不小心漏掉某个重要限制导致线上调不通？」
  • 脱稿答辩：

    「我将原本混在长散文里的说明拆成了三层结构化管线加自动化测试护栏。

    ① 三层结构化输入与渲染输出：底层运行时契约字典对齐服务端源码，录入接口 HTTP 方法、路径、必填与禁用参数、必需请求头及返回类型，中层策略表示按槽位填入成对适用避开条件、相邻工具区分及跨步参数来源（例如强制读 Skill 附件的标识、版本号、路径取自同一次业务码成功的查看响应，且知识库接口外层成功但内层错误布尔标记为真时仍按失败读取错误文本），顶层按会话能力裁剪后套用固定五段模板渲染输出。

    ② 183 项自动化单测与负向断言防退化：合入提交配套 7 个测试文件共 183 项单测，除参数对齐校验与共享协议单次出现断言外，我专门编写了故意删改版本号绑定、禁用参数等关键限制词并断言校验器必报错拦截的负向断言测试，从工程上保证只删冗余表述、不丢安全约束。」

Q3 ★★（读写安全与仓库级规则竞争拷问）：只靠提示词裁剪藏起写工具卡安全吗？透明代理注入会不会和仓库自带的 .claude/ 或 AGENTS.md 冲突？

面试官发问：「只读模式下只是没在提示词里渲染写操作卡片，如果模型遇到提示注入或幻觉自己拼了一条写接口 curl 怎么办？另外如果用户代码仓库里自带了 .claude/ 配置，会和注入的门控冲突吗？」
  • 脱稿答辩：

    「这两点分别对应服务端账号归属核验与宿主规则优先级竞争。

    ① 安全边界由服务端网关强制把关：提示词裁剪和门控只负责省 Token 与减轻注意力负担，提示词裁剪不当作安全防线。宿主 CLI 本地不持后端存储凭据，所有 curl 请求均经 Bridge 转发 MemoryCore，服务端按会话令牌校验账号归属和读写范围，只读会话即便手拼写请求也会被网关返回 403。

    ② 二分切片实测印证仓库自带规则竞争：我在辅组 Claude Code CLI 跑前 250 条对照时做过二分切片排查（174 + 76 = 250），不含 .claude/ 的 174 条样本误调用正常大降 19.42 个百分点，而在 3 个自带 .claude/ 目录的仓库共 76 条样本上误调用仅降 2.44 个百分点、完成率反降 5.71 个百分点，清晰揭示宿主自动加载的仓库级指令会与代理注入规则争夺优先级。」

    • R（量化结果与边界）：冻结覆盖 39 个仓库、1,140 条正负样本（464 正 + 676 负） 的 test1k 基准，扫描零违规；并主动明确受 CLI 耗时限制先顺序截取前 250 条做固定子集回归、且 Knowledge 正例数为 0。

  2. 辛普森效应拆账变亮点：把 Overcall = ECR - Strict 拆两半——未完链盲目乱调已暴降超三分之二（70.59% → 22.12%）；完链内部多调由 10/26 变为 38/58 是因为 V4 新救活的 +32 条多为两跳/三跳难例（难度分布偏移），编码模型改代码前习惯求稳多查一步，精准暴露纯提示词的停止上限。
  3. 严守消融与改造边界：如实交代 Baseline vs V4 是版本整体对照、未做单变量消融（给出机理映射与五组消融设计）；剩余未完成 46 条 = 23 漏调 + 21 首步错 + 2 绑参失败，压降完链求稳多查是下一步规划，下沉到 Bridge 网关做等价请求幂等短路或注 sufficiency=complete 响应头，明确当前尚未改 Bridge。

  • 30 秒速答（先抛结论 + 拆三步 + 抛钩子）：

    「真实终端里模型既跑本地 cat/grep、又常只在文本里打印示例 curl，用大模型裁判还容易放过负例乱调。

    我独立部署 Baseline 和 V4 两版代理跑真实 Codex CLI，在线只拦打到执行器 TDAI 的真实 HTTP 请求，离线按 5 种合法跳步变体和同次响应参数血缘五级漏斗算分。

  • 90 秒完整 STAR：
    • S（背景与痛点）：真实终端交互里混杂大量本地命令和未执行的文本 curl；同时合法调用有等价跳步变体，死板串匹配会误杀合规直读，而 LLM-as-a-Judge 只看最终回答又会掩盖负例多调远程接口或跨版拼错参数的问题。
    • T（技术目标）：在真实 Codex CLI 下剥离本地命令与超时噪声，建一套兼容合法跳步、严验跨步参数血缘且 100% 可复现的确定性评测框架。
    • A（核心做法与钩子）：
      • ① 受控隔离环境：Baseline 与 V4 固定提交独立部署，锁定 Codex CLI + gpt-5.6-luna 跑前 250 条（超时独立分账：242 vs 248）；
      • ② 在线精确拦截：只录经宿主 Shell 实际打到 TDAI 执行器的 HTTP 请求，自动剥离本地命令与文本示例 curl；
      • ③ 离线五级确定性漏斗：依次校验是否发出、允许首步集、必要节点与前置顺序（5 种合法变体）、同次成功响应参数血缘，以及是否零多余请求。
    • R（量化结果与边界）：全部有效正例的必要链完成率 Complete 从 25.49%（26/102） 升至 55.77%（58/104），未完链盲目乱调暴降超三分之二（70.59% → 22.12%），并精准定位出完链后求稳复核 38/58 的控制上限（未做单变量消融，下一步规划下沉 Bridge 网关短路，当前尚未改 Bridge）。

核心机制4.2 关键方案选型对比表与核心契约记忆桩

  • 三条防测量污染规则与全量核心指标公式卡片：锁定 Codex CLI + gpt-5.6-luna 跑前 250 条（并发 5，单条超时 8min）。① Gold 标签离线文件独立存放隔离。② 仅统计经宿主 Shell 真实打到执行器 TDAI 接口的请求（文本打印 curl 不计）。③ 超时独立分账，Baseline 为 n=242（102 正 + 140 负，另 8 超时），V4 为 n=248（104 正 + 144 负，另 2 超时）。核心指标公式与数值锚定如下：
    • 误调用率 FCR：发出请求的负例数除以有效负例数，由 87.14% (122/140) 降至 31.94% (46/144)（-55.20pp）。
    • 正例发出率 ECR：发出请求的正例数除以有效正例数，由 96.08% (98/102) 回落至 77.88% (81/104)（-18.20pp）。
    • 条件首步命中率 TSR_cond：首步命中的正例数除以已发请求的正例数，27.55% (27/98) → 74.07% (60/81)（+46.52pp），汇报时同步给出全量口径 TSR_all：26.47% (27/102) → 57.69% (60/104)（+31.22pp）。
    • 必要链完成率 Complete（即配图中的 CCR，Chain Completion Rate）：必要节点与参数绑定均完成的正例数除以全部有效正例数（含单步与多步，不限于多步样本），25.49% (26/102) → 55.77% (58/104)（+30.28pp）。通用 DAG 偏序评分器属扩展设计，实际落盘跑通采用固定 Gold 合法路径变体加参数绑定检查。
    • 零多余完成率 Strict 与多余发出率 Overcall（Overcall = ECR - Strict）：Strict 为 15.69% (16/102) → 19.23% (20/104)。Overcall 为 80.39% (82/102) → 58.65% (61/104)（-21.74pp），精确拆解为「未完链盲目乱调 72/102 (70.59%) → 23/104 (22.12%)」与「完链后求稳复核 10/102 (9.80%) → 38/104 (36.54%)」两块。
  • 两项深水区实验洞察：① 完链难度偏移（辛普森效应）与停止规则瓶颈：未完链盲目乱调已被三层编译与门控净砍超三分之二，而完链内部多调由 10/26 变为 38/58（Strict/Complete 由 61.5% 变为 34.5%）源于 V4 新救活的 +32 条集中在两跳/三跳复杂链路，编码模型改代码前习惯求稳多查一步确认（深挖与网关演进见 4.3 Q3）。② 仓库级规则竞争：辅组 Claude Code CLI + deepseek-v4-flash 前 250 条整体 FCR 降 14.58pp（65.97% → 51.39%）、Complete 持平 37.74%。其中无 .claude/ 的 174 条正常改善，含 .claude/ 的 76 条存在指令优先级争夺（二分切片细节见 2.3 Q3）。

高频追问4.3 面试官高频连环追问与脱稿答辩（Q1–Q3）

Q1 ★★（判分器选型与噪声剥离拷问）：为什么不用 LLM-as-a-Judge 直接评最终回答，而坚持写确定性轨迹规则判分？遇到跳步调用或光打印 curl 不执行怎么处理？

面试官发问：「为什么不用大模型直接对比最终回答和标准答案打分，连端到端问答质量一起测？用确定性规则判轨迹，万一模型换了种合法调用顺序怎么办？」
  • 脱稿答辩：

    「工具调用优化的核心靶点是过程行为精准。

    ① 规避结果正确掩盖过程乱调：若一条负例答案就在当前窗口里，模型却白调了三趟远程接口才给出正确回答，只评最终文本会将其判为通过，直接掩盖 87.14% 的高误调用，且裁判模型有采样随机性，难以逐字核验读附件传入的版本号是否严格取自上一步成功响应。

    ② 执行器 HTTP 拦截去噪加 5 种合法变体兼容跳步：在线采集只录经宿主 Shell 真实打到执行器 TDAI 接口的 HTTP 请求，滤除本地文件查看命令与未执行的文本 curl，离线评分围绕 8/240 两层可见性预置 5 种合法路径变体，按允许首步集、必要节点、前置顺序与同次响应参数血缘逐级核验，既兼容最小跳步又严卡跨版拼参。」

Q2 ★★★（单因素消融归因拷问）：四个指标大幅改善里，信息缺口门控和运行时契约工具卡各自独立贡献了多少个百分点？做过单变量消融吗？

面试官发问：「误调用降了 55 个点、必要链完成率翻倍到 55.77%，能拆清楚这里面多少是门控的功劳、多少是工具卡重构的功劳吗？」
  • 脱稿答辩：

    「我严守归因边界不虚报单项拆分，但能讲清机理映射与补做方案。

    ① 如实说明版本整体对照边界：本次实验是 Baseline 与 V4 两个独立部署服务版本的整体受控对照，V4 同时合入了信息缺口门控、运行时契约工具卡与固定五段装配，当时未跑单变量消融实验，前文全量首步命中率等于正例发出率乘条件首步命中率只是分母约分的代数恒等式，不能当作因果拆解。

    ② 机理映射与五组消融设计：机理上门控加避开条件主攻压降负例误调用，相邻工具区分加参数绑定主攻提准首步命中与必要链完成率，共享协议抽离加会话裁剪直接对应 27.02% 常驻 Token 压缩。若补做严格消融，应锁定同版底座代码和同批样本跑『原版、仅门控、仅工具卡、仅五段布局、全组合』五组对照，预算受限时优先单跑仅门控组验证主护栏收益。」

Q3 ★★★（剩余 Bad Case 拆桶与下一代演进拷问）：优化后为什么还剩 31.94% 误调用和 44.23% 未完成正例？为什么 Complete 翻倍但 Strict 几乎没涨，下一步怎么突破？

面试官发问：「数据里误调用还剩 31.94%（46/144），必要链完成率 55.77% 说明还有约 44% 没完成，而且 Strict 只从 15.69% 升到 19.23%。如果继续往下把误调用压到 10% 以内，瓶颈在哪、怎么改？」
  • 脱稿答辩：

    「我把剩余错例和 Overcall = ECR - Strict 做了精确代数拆解。

    ① 故障拆桶与未完链乱调大降：负例剩余 46/144（31.94%） 集中在模型对窗口旧结论时效性不放心求稳复核及同主题外队规范干扰场景下的探索惯性，正例未完成 46/104（44.23%） 拆为 23 条隐晦缺口漏调 + 21 条首步相邻工具选错 + 2 条附件参数绑定失败。而多余发出率 Overcall 由『未完链无效乱试』与『完链后求稳复核』两块构成，V4 已将未完链盲目乱调从 72/102（70.59%） 压降至 23/104（22.12%）（净砍超三分之二）。

    ② 辛普森效应解释剪刀差并推进网关硬协同：完链内部多调由 10/26 变为 38/58（Strict/Complete 从 61.5% 变为 34.5%）源于完链样本难度分布偏移（辛普森效应）——Baseline 跑通的 26 条多为首轮目录可见的 1 跳直读，V4 新救活的 +32 条集中在两跳与三跳复杂链路，编码模型改代码前常求稳多查一步确认。这恰恰证明选型与参数绑定靠三层编译可解。抑制防御性二次确认是下一步规划，要下沉到 Bridge 网关做同会话等价请求幂等短路，或在完整响应头注入 sufficiency=complete 硬收敛信号，目前尚未改 Bridge。当前实验只定位到纯提示词停不住完链后的求稳多查。」
