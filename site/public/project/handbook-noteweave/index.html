01一、以 Table-as-State 为核心的 Deep Research Agent（职责 1）

简历原文设计以 Table-as-State 为核心的 Deep Research Agent：针对多轮检索上下文膨胀、维度漏查与证据冲突，前置探路构建 「研究对象 × 待验证字段」状态表，按对象隔离上下文并行取证；分层 Verifier 剥离推理链校验，按缺口 Replan、遇冲突独立反证；写表侧统一锁序，以 Redis ZSET 租约管理槽位、Fencing Token 拒绝过期写回，离线评测中有效单元完成率由 67% 提升至 83%。

车祸现场推演：每一步为什么被迫这么设计？

  1. 车祸 1（普通 ReAct 上下文爆炸 + 模型自审顺着圆谎）→ 状态表外置 + 剥离推理双层 Verifier
    • 不加它怎么炸：把几十篇网页塞进一个对话窗口，模型中段注意力衰减必然漏查维度。如果让同一个模型带着刚才的“思考草稿”自审，它会顺着前面的自圆其说直接附和放行，搜出冲突时又容易原地翻回同一批二手转载文章。
    • 怎么设计：
      • 克制架构（1 主 + N 子）：只有 1 个 Lead Agent 读状态表摘要做规划，N 个同构 Subagent 按行（≤5 列）独立短上下文取证，其余收口、核验、反查、成文全是确定性流水线步骤。
      • 执行状态与研究状态物理拆开：接口限流/崩溃/超时只原卡重派（≤2 次），不改检索词、不扣单格 3 次补查配额。
      • 剥离推理 + 失败分支警示 + 域名黑名单：规则层先零成本卡死偏移量、资料有效版本与量纲，再剥掉推理草稿交异构模型核验。驳回时在单元格附带一行结构化 failed_branch_hints（上限 3 条，仅研究层驳回写入、执行层限流/崩溃不写），防下波无状态子任务重复搜同一批死胡同。同前提冲突则拉黑旧主域名派 1 次独立反证，仍分歧就标为证据冲突终态并列披露。
    • 为什么不用 LangGraph：LangGraph 管的是节点跳转控制流，全局状态是整体内存对象。跨进程多 Worker 并发改不同格子并拦住慢节点迟到写回，仍需自建数据库行锁与令牌校验。
  2. 车祸 2（多 Worker 并发回调撞上 Replan/回收引发 InnoDB 死锁，或主记录全程 X 锁 把 8 路写回串行化）→ 第一道防线：精细化统一单向锁序
    • 不加它怎么炸：Worker 写回先锁研究格再锁主记录，而 Replan/超时回收先锁主记录再锁研究格，反向加锁直接闭环死锁。反过来如果写回时盲目给 RESEARCH_MAIN 加排他 X 锁，又会把 8 路本应并发写不同格子的回调强行串行在主记录单行上。且若事务里留着大模型调用，持锁几十秒直接拖垮数据库。
    • 怎么设计：所有抓网页、检索、模型核验全放事务外。事务内仅保留毫秒级落库，全系统写状态表严格遵循唯一单向顺序：研究主记录（写回只读 plan_version 加 FOR SHARE 共享锁，仅 Replan 升版加 X 锁。发号走独立微事务毫秒释放）→ 子任务 (X锁) → 目标研究格 (聚簇主键升序 X锁) → 引用资料表 (主键升序 S锁复核有效态与版本)。这样既精准破坏死锁的“循环等待”条件，又让 8 路 Subagent 回调在主记录共享锁上彼此完全并发、只与低频 Replan 互斥！事务外先剔除大模型编造的不存在幻觉资料 ID（防 RR 隔离级别锁住页尾 supremum 阻塞新文档插入），主键等值点查退化为 LOCK_REC_NOT_GAP 单行锁。
  3. 车祸 3（Python Worker OOM 被强杀导致并发槽位永久泄漏 + 快慢任务互抢）→ 第二道防线：Redis ZSET 调研独立 8 槽租约
    • 不加它怎么炸：第一版用 Redis INCR / DECR 计数限流，Worker 解析大网页 OOM 被 SIGKILL 强杀，finally 里的 DECR 没跑，工作区调研池 8 个槽位逐步被泄漏卡死。若再与 2～6 分钟的重型产物生成混用一个池子，后台批量视频转讲义一提交就把交互式深度研究卡死在外面。
    • 怎么设计：每个工作区为深度研究独立建一个 ZSET（nw:slots:research:wsId 限 8 槽，刚好饱和 DEEP 8×8 首波 8 行全并行。与重型产物池 nw:slots:artifact:wsId 8 槽做快慢舱壁隔离，且不加 {wsId} Hash Tag 防 Redis Cluster 热点倾斜），member = lease_token，score = 过期时间戳 (300s)（取 Redis 服务端 TIME 防时钟偏差）。申请槽位用一段 Lua 原子执行：ZREMRANGEBYSCORE 清过期 → ZCARD 判 < 8（同令牌幂等刷新）→ ZADD 占槽。正常运行每 60 秒的心跳接口先续 MySQL SUB_TASK 运行租约、成功后再用 Lua 续期 Redis ZSET（先 ZSCORE 确认未过期再用 ZADD XX 更新，防被回收后抢回，也避免 Redis 续着槽不放而 DB 已超时重派的脑裂窗口）。就算 Worker 暴毙，300 秒后自动回收。
  4. 车祸 4（租约到期重派后，僵尸节点醒来覆盖新结论）→ 第三道防线：Fencing Token + 两支释槽
    • 不加它怎么炸：Worker A 发生长 GC 或容器挂起超过 300 秒，看门狗和业务线程一起冻住，租约过期。主控重派给 Worker B，B 写回新结论。随后 A 醒来把旧半成品发回来，直接覆盖 B。（这就是为什么 Redisson 看门狗和 Redlock 多数派都挡不住进程停顿，Redis 只管并发数量，正确性必须交存储端验令牌。）
    • 怎么设计：
      • 研究主记录全局递增发号：每次派发/重派/Replan 在 MySQL 研究主记录上原子 +1 发 fencing_token（不在 Redis INCR 防主从切换回退）。
      • 落库“三验”口诀（领号 ≠ 刷卡落座）：① 子任务仍是 RUNNING 且持有令牌相等。② 计划版本未变且格未归档。③ 传入令牌 > 该格最后写入令牌水位（并共享锁复核引用资料未撤回/未升版）。缺①只验③的话，B 刚领 6 号还没写库（水位仍为 0）时，被作废的 A 拿 5 号醒来仍会趁虚而入。
      • 两支分流释槽：① 超时僵尸分支（条件①失败）：整事务回滚且严禁调 Redis ZREM（防误删 B 的有效槽）。② 当值合法分支（条件①通过）：逐格独立裁决（归档格跳过、资料变更格置待重验且不扣 3 次配额、合规格推进水位），就算计划已升版也结清子任务并单次 ZREM 立即释槽，消除 300 秒槽位泄漏。

      「核心思路是把深度研究的进度从模型对话窗口搬进数据库状态表，系统性解决多轮检索上下文膨胀、维度漏查和证据冲突。

      ① 先多视角探路，建一张『研究对象 × 待验证字段』的状态表，按对象拆独立短上下文并行取证。

      ② 校验层物理剥离取证推理链，用规则加异构小模型核验，缺口改词补查、冲突拉黑旧域名独立反证，最后拔掉搜索工具按表成文。

      这块分认知验证闭环和并发写表三道防线两条线，更想先听哪一块展开？」

    • 背景（S）：做复杂技术调研时，需要交叉核实工作区私有资料与公网信源。自由 ReAct 连续检索十几轮后容易上下文膨胀、漏查对比维度。同一模型带着推理草稿自审容易顺着前文自圆其说，写作阶段也容易凭预训练印象补编数据。
    • 任务（T）：把研究进度外置成显式状态表，隔离取证和核验上下文，跑通缺口补查、冲突反证和并发安全写回的闭环。
    • 做法（A）：
      • ① 探路建表与独立取证：先多视角探路摸清真实对象与验收口径，一次锁定档位建最多 8×8 状态表。按对象打包在独立短上下文取证，原文写进外部证据库、用完销毁几十 K 网页正文。
      • ② 剥离推理校验与无工具成文：第一层规则硬查偏移量、资料版本与量纲，第二层物理丢弃推理草稿交异构小模型验前提。缺口改词补查或拆格判环，同前提冲突拉黑旧域名派 1 次独立反证，成文前反查后物理拔掉搜索工具按表写作。
      • ③ 并发写回三道防线：Redis ZSET 调研独立池控工作区 8 槽（与产物池 8 槽舱壁隔离），MySQL 短事务单向升序加锁，三验令牌、计划版本、写入水位和资料版本，并区分超时僵尸回滚（禁碰槽位）与当值结清单次释槽。
    • 结果（R）：在 20 道冻结公开技术研究题的离线评测中，有效单元完成率从 67%（94/140）提升到了 83%（120/145）。

核心机制1.2 核心架构与设计权衡

  • 1. 克制智能体边界与状态证据双外置
    • 架构设计：按「是否需要多步自主调工具」和「是否需要独立窗口隔离搜索噪声」划界，全链路只设 1 个主控 Lead Agent（只读状态表摘要与线索池，输出结构化规划与重规划动作）加 N 个同构 Research Subagent（通过不同任务卡切换探路、按对象深挖、独立反证三种模式），其余问题收口、分层核验、成文前反查和无工具成文全部做成确定性流水线步骤。Spring Boot 集中管控状态表、并发准入与事务写回，Python 无状态承载检索阅读与模型推理。
    • 为什么这么分：拒绝凑角色式的多智能体对话链，消除多层自然语言传话失真与无谓同步开销。同时把执行状态（子任务运行层）与研究状态（状态表单元层）物理拆开——接口限流、进程崩溃或租约到期只触发原任务卡重派（最多 2 次），不会改歪原本正确的检索词，也不扣减单格 3 次补查配额。
  • 2. 前置探路与两步弹性定级（上限 8×8，活跃格 ≤48）
    • 架构设计：所有问题走同一条六阶段主链（问题收口 → 多视角前置探路 → 合并建表与锁定档位 → 波次深挖核验与重规划 → 成文前反查 → 无工具成文）。探路前先按是否点名对象及候选集是否封闭确定探路路数（1～4 路），探路子任务先宽后窄摸底且候选必须绑定逐字原文片段，按独立主域名数与是否命中工作区资料客观预排权重。主控单次调用完成同义合并、定行定列与每列验收口径后，按实际对象规模与探路重合度一次锁定 QUICK（1×4）/ STANDARD（6×6）/ DEEP（8×8） 档位整场不变。
    • 设计权衡：开放课题先摸清真实流派再建表可消除预训练盲拆漏项，看到实际对象数量后再定档则让简单对比轻量收敛、复杂综述算力充足且离线评测可复现。
  • 3. 按对象分包独立上下文取证与制品旁路交接
    • 架构设计：将同一研究对象（同一行）的待查字段打包成一张深挖卡（单卡不超过 5 列，超 5 列或源码机制与商业报价等来源跨度大时拆成最多 2 张卡），在独立短上下文内遵循「工作区资料优先、公网信源补充」共享一次长文档阅读，提取阶段按列逐一独立输出，连续 2 步无新独立来源即提前早停。命中的原文片段与偏移量直接写入不可变证据库（同场网页快照按网址共享免重抓），任务结束直接销毁本地几十 K 网页正文上下文，向主控只回传轻量候选、适用前提、证据编号与最多 2 条表外线索。
    • 设计权衡：既避免一格派一卡把百页官方手册重复读五遍，又防止几十篇网页塞进主控窗口引发中段注意力衰减。
  • 4. 剥离推理的分层 Verifier 与屏蔽旧域名的独立反证
    • 架构设计：第一层确定性规则零模型开销快筛证据存在、偏移量截取逐字一致、工作区资料处于有效态且匹配当前版本、内置单位词表同量纲换算无矛盾（生僻单位放行交下一层）。第二层物理剥离取证子任务的推理思考草稿，只把单格验收口径、候选结论和原文片段交给异构模型家族的轻量模型（如 GLM-4-9B）核验支持度并比对适用前提：前提无交集按版本分档并存直接采纳，缺前提打回证据缺口补核版本，同前提结论正面相悖则标为待反证。下一波主控派发独立反证卡（每格上限 1 次，独立于 3 次补查配额），强制注入已用文档与主域名黑名单搜寻独立第三方权威来源，仅当第三方支持一手方且另一方为社区二手时采纳，否则定格为证据冲突终态并列披露。
    • 设计权衡：剥离推理链阻断了核验模型顺着前置自圆其说附和放行，域名黑名单则防止冲突复核又翻回同一批转载网文原地打转。
  • 5. 波次等待窗口、局部 Replan 与拆格拓扑判环
    • 架构设计：每波设 3/5 分钟等待窗口，到点后主控不等慢长尾直接审视已返回单元推进下一波，已采纳格原地锁定，仅对缺口格按打回原因改写检索词定向补查（上限 3 次，跳过近似旧词）。同时吸收 EMNLP 2026 MAGE 的执行状态管理与跨分支提示思想，为研究单元格增加轻量有界 JSON 字段 failed_branch_hints（死胡同警示，上限 ≤3 条）——每轮仅在 Verifier 规则或语义驳回时追加 1 行结构化记录（已试方向/低质信源特征、驳回归因、下波规避指令），随补查任务卡注入新 Subagent 剪枝无效分支并省 Token（执行层 429/超时/OOM 重派不写入，防瞬时故障误杀好方向）。表外线索池中满足「候选集未封闭且覆盖至少 2 个独立主域名」的新对象可动态加行，影响必答格的隐藏前提可受控扩列（整场最多 2 次）。发现单元粒度过粗（如区分社区版与企业版）时，归档原父格移出分母，新建待核实子格从头核验（严禁直接复制父格通过态），新增跨格依赖前置在内存先跑 Kahn 入度拓扑排序（顺带产出可执行并行波次）。仅当出队数 < 总节点数 检出有环时，才按需对残余子图跑一次三色 DFS 抽出精确环边打回拆解（避免把被环卡住入度的正常下游汇总列一并误伤）。
  • 6. 成文前反查、无工具成文与逐句引用精度核对
    • 架构设计：阶段 4 全档位做必答点规则反查，DEEP 档另生成几百 Token 论证提纲暴露跨行支撑缺口（最多补查 1 轮后冻结状态表，提纲直接复用为成文骨架）。阶段 5 物理拔除一切检索与联网工具，只读冻结状态表与关联原文成文：跨行结论至少引用 2 个已采纳格，含「最高、最低、优于」等比较级表述必须覆盖所有参与比较的行否则自动降级为分行客观陈述，随后经规则核对数字、版本号与日期精度不超原文（如原文只写年份严禁出现月份），再由轻量模型核对正负极性。
  • 7. 工作区独立 ZSET 租约准入、单向升序锁（主记录 S 锁并发）与 Fencing Token 两支释槽

点击展开：本章高频底层原理与指标公式速查（微平均 vs 宏平均 / Kahn+三色DFS / Fencing Token vs Redlock / MVCC ReadView / Redis ZSET / MAGE 失败分支警示）
  1. 微平均（Micro-average）vs 宏平均（Macro-average）：
    • 计算公式：微平均把所有题目的格子汇总后统一相除：有效单元完成率 = (Σ 各题有效格数) / (Σ 各题活跃规划格数) = 120 / 145 = 82.76% ≈ 83%（改造前 94 / 140 = 67.14% ≈ 67%）。宏平均则是先算每道题各自的完成率再求算术平均。
    • 为什么选微平均：QUICK 简单题只有 4 格、DEEP 复杂题可达 20+ 格，宏平均会让 4 格题和 20 格题权重相同导致指标虚高。微平均按每个研究格等权计分，更真实反映难题覆盖度。
  2. Kahn 入度拓扑排序 + 三色 DFS 判环：
    • 原理：先统计每个研究格子的前置依赖入度，将入度为 0 的节点入队逐波弹出并把邻居入度减 1（顺带得到可直接并行派发的波次序列）。若最终出队节点数 < 总结点数，说明图中必存在依赖环。此时仅对残余子图跑一次三色 DFS（白=未访问、灰=当前递归栈中、黑=已完成），一旦沿边撞到灰色节点即精准抽出环路边打回拆解，不会把被环卡住入度的正常下游汇总格一并误杀。
  3. Fencing Token（单调防护令牌）vs Redisson 看门狗 / Redlock：
    • 本质痛点：客户端分布式锁强依赖「进程无长停顿」假设。一旦 Worker 遭遇长达数百秒的 Full GC 或容器暂停，续租看门狗线程一起冻结，锁超时易主给节点 B。随后节点 A 醒来不知锁已失效仍继续写库覆盖 B（哪怕 Redlock 多数派也挡不住客户端停顿）。
    • 解法：每次拿锁/派发由存储侧签发全局严格单调递增的整数令牌（如 5、6），目标库 MySQL 在写回 UPDATE 条件中强制校验令牌匹配与水位推进，不再依赖时钟与进程无停顿假设。
  4. MVCC ReadView（快照读 vs 当前读）与 S / X 锁矩阵：
    • InnoDB 默认 REPEATABLE READ 下，普通 SELECT 走 ReadView 快照读（事务首次读固定视图），看不到并发事务已提交的新令牌会引发丢失更新。UPDATE、SELECT ... FOR SHARE（共享 S 锁）、SELECT ... FOR UPDATE（排他 X 锁）走当前读，读最新已提交版本并加锁。S 与 S 兼容、与 X 互斥，故 8 路并发写回对主记录降为 FOR SHARE 可互不阻塞并发执行，仅低频 Replan 加 X 锁互斥。
  5. Redis ZSET 底层编码（listpack vs dict + skiplist）：
    • 当成员数 ≤ 128 且单成员长度 ≤ 64 B 时采用紧凑连续内存 listpack（无指针碎片，本项目调研/产物独立池各仅 8 槽稳定命中 listpack）。超阈值自动转为 dict（哈希表 O(1) 按成员查 score）+ skiplist（多层概率跳表，按 score 范围查询 ZRANGEBYSCORE 平均 O(log N + M)）。
  6. 单元格死胡同警示（Failed Branch Hint / 负向诊断提示，吸收 EMNLP 2026 MAGE 思想）：
    • 论文出处：EMNLP 2026 MAGE（Beyond Semantic Organization: Memory as Execution State Management for Long-Horizon Agents, arXiv:2606.06090）提出把 Agent 记忆从被动语义检索升级为执行状态管理，在 Revise 回退重开新分支时向新分支注入先前失败分支的精简提示，避免重复探索死胡同。
    • 本项目极低成本落地：无需引入重型树记忆引擎，只需在 MySQL 状态表单元格上挂一个上限 ≤ 3 条的 JSON 数组字段 failed_branch_hints（单条 1 行：{"tried": "...", "fail_reason": "...", "avoid": "..."}）。只在 Verifier 规则/语义驳回时写入（执行层 429/超时/OOM 重派不写，防误杀好方向），随补查任务卡注入下波无状态 Subagent，相比 Reflexion 在长对话里堆叠文字反思更紧凑省 Token。
    • 面试口径边界：坦诚该字段作为单元格局部重规划的轻量演进/结构化补强纳入设计，未针对单字段做独立消融实验，不单独虚报额外百分点。

    • 不加它怎么炸：固定长度切块会把代码、表格和章首前提拦腰截断。纯向量能懂同义改写，却经常把 ERR_4031 和 ERR_4032 这类错误码搞混（专有名词 Recall@10 仅 0.48）。如果精读问题也去全库捞 6 块碎片，东拼西凑完全读不连贯。
    • 怎么设计：
      • QA：定制分词 BM25 补齐精确词（专有名词 0.48 → 0.93），与向量互补。因 BM25 分数无上界而余弦值在 0~1，用只看排名的 RRF(k=60) 免调权重融合取 30 条，再交昂贵但精准的交叉编码器精排取前 6（单轮 20 题 Recall@10 0.66 → 0.87，MRR 0.51 → 0.78）。
      • Note：先定位资料和小节，再沿章节树扩成连续原文窗口（比“按资料对切片得分求和”更好，避免偏向长文档）。
      • Wiki：为什么不上全局 GraphRAG？因为全量抽实体关系贵，且用户删一份资料时很难反推知识图谱里哪些边该删。有界一跳 + 段落来源回链删资料只需局部重算关联页。
  2. 车祸 2（用户刚删完资料立刻提问，ES 仍召回旧切片。或废片把 Top-50 占满导致答不出）→ Redis 到期墓碑 + 删净缩期 60s + MySQL 主库复核
    • 不加它怎么炸：
      • 方案 A（删资料时同步删 ES 并调 refresh=true 强刷）：制造大量微型碎段拖垮集群，且跨 MySQL/ES 难以事务回滚。
      • 方案 B（只在读侧拿结果去查 MySQL 过滤）：废切片会把 ES 向量 kNN 粗召回名额全占光，有效结果被挤出 Top-50，过滤后直接变空返回“未找到证据”。
    • 怎么设计（写侧 + 清理侧 + 读侧三端协同）：
      • 写侧（防 ABA + 24h 保底墓碑 + 同分区保序事件）：撤回、重传或恢复启用一律递增新 proc_version（旧版本不再复用）。本地事务改状态写极简待投递事件发往 与阶段 4 建索引共用的按 docId 分区 ES 同步 Topic（同文档 UPSERT_INDEX 与 DELETE_INDEX 在单分区内严格 FIFO 串行，从因果顺序根源消灭“删跑在迟到建索引之前”的乱序幽灵切片），并向工作区墓碑 ZSET（nw:tombstone:wsId）写入 member = docId:oldVer, score = now + 24h，顺带清本机缓存并经 Pub/Sub 广播失效各机 1s Caffeine 缓存。
      • 清理侧（同分区串行删净 + 缩期 60s）：ES 同步消费者按 docId 单分区串行消费，无需脆弱的 sleep 2s 盲等。收到 DELETE_INDEX 执行 delete_by_query，只有确认 failures 为空、删净 < target_ver 旧切片后，才经 Lua 将对应墓碑缩期到 min(oldScore, now + 60s)，精准覆盖 1s refresh 和 index.gc_deletes=60s 窗口（异常慢旧写靠写前查主库 + version_type=external_gte 与读侧主库复核双端挡死）。
      • 读侧（前置下推 + 1,024 故障/压测降级熔断水位 + 主库终审）：读路径 ZRANGEBYSCORE key now +inf 拉有效墓碑（常态 ES 几秒删净缩期，单工作区通常仅个位数～几十条）：
        • ≤ 1,024 条：同时下推到 BM25 的 bool.must_not 和向量的 knn.filter（在 HNSW 遍历时提前跳过废片，不占名额）。
        • > 1,024 条（面向批量删库压测或 ES 清理消费积压故障演练的降级熔断水位：虽未触及 ES 65,536 硬上限，但实测超 1,024 时查询序列化与预过滤位图延迟抬升）：切 1 秒本地 Caffeine 短缓存 + 扩窗召回 + 内存 HashSet 过滤并触发积压告警。
        • 主库终审：精排 Top-6 提取去重 docId，按聚簇主键 IN 批量直查 MySQL 主库（不走从库防主从延迟，耗时仅 1~2ms）核验 status='ACTIVE' 且 proc_version == current_version。若剔除后结果被刚删长文挤空，立即绕过本地缓存重拉墓碑扩窗补检一次。
  3. 车祸 3（Wiki 更新时的 Cache-Aside 并发慢读，把旧 V3 填回缓存复活）→ 单调版本指针（读写双端 Lua）+ 不可变版本 Key
    • 不加它怎么炸：缓存未命中时，慢读线程 A 查库拿到旧版 V3 后卡住。期间写线程 B 把库更新为 V4 并删掉缓存。随后慢读线程 A 醒来把 V3 写回 Redis——缓存里 V3 复活，直到过期前所有人读到的都是脏页！（延迟双删的休眠时间估不准，加读写锁又让读请求排队阻塞。）
    • 怎么设计：把缓存拆成两把无 {} Hash Tag 的单键：
      • 版本指针 Key（wiki:ver:wsId:pageId，TTL 10min。仅从未存在的非法 ID 写 -1 短 TTL 防穿透，合法页面下线时照常升版写下线标记而不覆写 -1）。
      • 不可变正文 Key（wiki:page:wsId:pageId:v{ver}，TTL 1h，内存满按 volatile-lfu 淘汰）。
      • 写流程 & 读未命中回填统一走同一段 3 行 Lua 单调高水位写：写流程先写新正文 :v4，再经 Lua（仅 newVer > curVer 才覆盖）推进指针。读未命中回源 DB 后回填指针也必须走同一段 Lua 单调写（不能用普通 SET！），防止 10min 指针自然过期瞬间，慢读 A 回填 3 把写线程 B 刚推高的 4 倒退覆盖！指针自然过期瞬间的热页并发回源再配本地 SingleFlight 合并防击穿。
      • 读流程：先读指针拿到版本号 4，再读 :v4。就算慢读线程 A 晚到回填，既改不动高水位指针 4，正文也只会落进废弃旧键 :v3，把覆盖写变成异键隔离，不阻塞读且不让旧值复活。

  • 面试官主问：「第二条写了 QA、Note、Wiki 三种知识链路以及资料撤销后的一致性处理，具体是怎么设计的？」：
    • 约 1 分钟速答（先抛结论 + 拆三步 + 抛钩子）：

      「核心思路是一份资料只切一次、建一套章节树底座，召回组装按任务分叉，再把删改窗口期的两类脏数据堵死。

      ① 业务侧用策略模式分出三条链路：QA 跑 BM25 加向量双路 RRF 和精排，Note 扩连续原文窗口，Wiki 做有界一跳和来源回链。

      ② 撤回防 ES 脏召回，靠 Redis 到期墓碑前置过滤加 MySQL 主库主键批量复核。

      ③ Wiki 缓存防慢读旧值复活，靠单调版本指针配不可变版本 Key 隔离写回。单轮 20 题 Recall@10 从 0.66 提到了 0.87。

      这块分三粒度检索设计和撤销/缓存一致性两块，更想先细聊哪一块？」

    • 背景（S）：真实资料研究包含精准查码、章节精读与跨文档 Wiki 沉淀三类不同诉求，传统固定切块加纯向量不仅会截断章首前提和表头，还容易混淆相似报错码。同时用户高频删改旧版草稿、重传正式版后立刻提问，ES 异步清理滞后与 Cache-Aside 并发慢读还会引发脏召回和缓存旧页复活。
    • 任务（T）：基于统一章节树底座定制三类证据粒度，阻断资料删改窗口期的脏召回与缓存旧值复活。
    • 做法（A）：
      • ① 三粒度策略分叉：保留章节树和跨页父表头，QA 走定制分词 BM25 加向量经 RRF 与交叉编码器精排，Note 先定资料小节再扩连续窗口，Wiki 走 BM25F 有界一跳扩展并记段落来源血缘。
      • ② 撤回三端防脏召回：本地事务改状态、升版本号（防 ABA）并写待投递事件发 Kafka 清旧片。同时写 24 小时 Redis 墓碑并经 Pub/Sub 失效各机 1 秒本地缓存，确认 ES 删净旧片后再缩期至 60 秒。读侧下推墓碑（常态仅个位数～几十条，1,024 为故障/压测降级熔断水位，超水位切 1 秒本地缓存扩窗过滤）并回 MySQL 主库复核。
      • ③ 版本化 Key 防旧值复活：Wiki 拆成单调版本指针配 :v3/:v4 不可变正文键，先写新正文再 Lua 推指针，慢读晚到也盖不到新版本。
    • 结果（R）：单轮 20 题 Recall@10 从 0.66 升至 0.87（MRR 0.51 → 0.78）。这次并发撤回重传压测里没有观测到脏召回或旧值复活。

核心机制2.2 核心技术点

  • 1. 切片底座
    • 怎么用：解析后还原章节树，切片按章节边界切，单块目标长度约 500 字，代码块和表格不从中间切断，跨页表格切开的子块都拼上父表头。每个切片记录文档 ID、处理版本号、章节路径、章节内顺序号，以及「文档 ID 加版本号」的组合字段，方便按版本过滤。切片正文和向量写 ES，章节树、切片状态和处理版本号存 MySQL。
    • 对比：固定长度切片实现简单，但会把表格、代码和章首前提切散。语义切分效果好，但每次都要算相邻句子的相似度，成本高。按文档结构切是两者的折中。
  • 2. ES 索引设计
    • 怎么用：统一采用共享物理索引 noteweave-chunk（生产目标 3 主 × 1 副，个人测试 replica=0），通过读写别名 noteweave-chunk-read / noteweave-chunk-write 访问（改 Mapping 或重建索引时双写切别名，业务无感知），所有检索强制携带 workspace_id（keyword 字段）精确过滤。不按工作区建独立索引（校级几百上千个工作区会瞬间打穿 ES max_shards_per_node=1000 硬上限引发分片爆炸与 HNSW 堆 OOM。中小工作区可选按 routing=workspace_id 路由单分片降扇出，同时监控大工作区防数据倾斜）。正文字段配自定义分析器，英文和符号用 word_delimiter_graph 保留子词（索引端配 flatten_graph），比如 ERR_4031 拆成 ERR 和 4031 同时保留原词，中文用 cjk_bigram 二元切词。向量字段是 1024 维的 dense_vector，用 HNSW 索引，m 取 16、ef_construction 取 100，相似度用余弦。
    • 参数怎么定：m 是每个节点的邻居数，越大召回越高、内存越大。ef_construction 是建图时的候选数，越大图质量越好、建索引越慢。这两个是常用的默认组合，资料规模不大时够用。
    • 为什么用别名：分析器或映射改了必须重建索引，切换别名就不用停机。
  • 3. 双路召回、RRF 与重排
    • 怎么用：BM25 和向量两路用 CompletableFuture 并行发出，向量路 k 取 50、num_candidates 取 100，BM25 路取前 50。两路结果按切片 ID 合并，用 RRF 计算得分，k 取 60。融合后取前 30 交给交叉编码器重排，取前 6 进入证据预算。
    • 参数怎么定：num_candidates 是 HNSW 每个分片上搜索时保留的候选数，越大召回越高、越慢，一般取 k 的两三倍，我这里取了 2 倍。重排只取 30 条，因为交叉编码器要把问题和每条切片拼在一起逐条推理，耗时和条数成正比。
    • 对比：ES 8.x 自带 RRF 检索，但混合检索的打分细节不好控制，我在应用层融合，方便调试每一路的命中。
  • 4. Note 的连续原文窗口
    • 怎么用：先在资料和小节级别召回，定位最相关的文档和章节，再按章节内顺序号取命中块前后各 2 块，拼成连续窗口，补上章首前提和父表头。章节树的查询走「文档 ID、章节路径、顺序号」联合索引，是等值加范围查询。
  • 5. Wiki 检索与一跳扩展
    • 怎么用：Wiki 页用 BM25F 对标题、摘要、正文分字段加权，标题权重最高。取得分最高的 3 个种子页，沿页面关系各扩展一跳，扩展页总数不超过 6 个，按关系强度排序。每段内容记录来源资料 ID，删除资料时按来源回链找到受影响的页面局部重算。
  • 6. Redis 到期墓碑、删净缩期 60s 与 > 1,024 故障/压测降级熔断水位
    • 怎么用：单工作区一个墓碑 ZSET（nw:tombstone:wsId），成员 docId:oldVer、score 存到期毫秒时间戳（撤回写 now + 24h 保底，顺带清本机缓存并经既有 Pub/Sub 广播失效各实例本地 1s Caffeine 缓存，读路径 ZRANGEBYSCORE key now +inf 纯读，后台定期清过期项）。常态单工作区有效墓碑仅个位数～几十条。1,024 是面向批量删库压测或 ES 清理消费积压故障演练的降级熔断水位（虽未触及 ES index.max_terms_count=65536 硬上限，但实测超 1,024 时查询序列化与 knn.filter 位图构建延迟抬升）：不超过 1,024 条双路下推 bool.must_not 与 knn.filter，超 1,024 条改走 1 秒 本地 Caffeine 短缓存配扩窗召回与内存 HashSet 过滤并告警，若主库复核剔除后有效结果被刚撤回长文挤占为空，立即绕过本地缓存重拉墓碑扩窗补检一次。仅当 delete_by_query 返回 failures 为空、确认删净 < target_ver 旧切片后，才经 Lua 对 < target_ver 墓碑成员缩期至 min(oldScore, now + 60s) 覆盖 1s refresh 与 index.gc_deletes=60s 窗口。
    • 为什么向量路也要过滤：kNN 先取近邻再过滤的话，废切片会占掉候选名额，有效结果反而被挤出去。
  • 7. MySQL 主库复核与慢旧写双端拦截
    • 怎么用：精排后的 Top-6 候选提取去重资料 ID 按聚簇主键 IN 批量查 MySQL 主库，同时确认 status='ACTIVE' 且切片 proc_version == current_version。重传缩页或卡顿超 60s 的慢旧写靠写 ES 前查主库当前版本加 external_gte 拒旧写与读侧主库复核版本双端拦截。
    • 为什么走主库：从库复制有延迟，刚撤回的资料在从库上可能还显示有效。
  • 8. 写侧待投递事件、防 ABA 升版与同 docId 分区建删保序
    • 怎么用：撤回、重传或恢复启用均递增分配新 proc_version（已撤回的旧版本号不再复用），同事务更新资料状态并写入极简同库待投递事件记录，提交后异步发往与阶段 4 建索引共用的 ES 同步 Kafka Topic（按 docId 分区，区分 UPSERT_INDEX 与 DELETE_INDEX 事件，异常由后台扫未投递记录幂等补发）。同一文档的建索引与删索引在单分区内严格 FIFO 串行执行，从因果保序根源消灭“删跑在迟到建索引之前”的幽灵切片竞态（无需脆弱的 sleep 2s 盲等）。仅当 delete_by_query 返回 failures 为空、确认已删净 < target_ver 旧切片后，才通过 Lua 对 < target_ver 墓碑成员执行 min(oldScore, now + 60s) 缩期（临近 24 小时保底期先顺延）。新版本写入带 version_type=external_gte 拒迟到旧写。
  • 9. 版本化 Key 缓存（读写双端 Lua 单调高水位 + SingleFlight）
    • 怎么用：每个 Wiki 页拆成无 {} Hash Tag 的两把单键——版本指针键 wiki:ver:wsId:pageId（TTL 10min）与不可变正文键 wiki:page:wsId:pageId:v{ver}（TTL 1h，内存满配 volatile-lfu 淘汰并支持 --hotkeys 频次统计）。更新写入与读未命中回填版本指针均强制走同一段 3 行 Lua 单调高水位脚本（仅 newVer > curVer 才覆盖）：写侧先写新正文 :v4 再推高指针。读侧未命中回源 DB 后回填指针也走同一段 Lua，避免 10min 过期瞬间慢读拿旧 V3 普通 SET 把已推进的 V4 指针倒退覆盖。仅从未存在过的非法 ID 在指针缺失时写 -1 短 TTL 防穿透。合法页面下线时照常升版写下线标记，不覆写 -1。热点页指针 10min 自然过期瞬间通过本地 SingleFlight 合并回源防击穿。
    • 对比：延迟双删的休眠时间要大于一次慢读，估不准。读写锁会让读请求排队。版本化 Key 读写都不阻塞，代价是旧版本正文会占一段时间内存。
  • 10. 策略注册表
    • 怎么用：QA、Note、Wiki 三种模式各是一个策略类，实现同一个接口。Spring 把所有实现注入成一个列表，启动时按模式放进不可变的 Map。请求进来按模式取策略，默认走 QA。
    • 延伸：这是策略模式加简单工厂，新增模式只加一个类，符合开闭原则。
  • 11. Note 的资料级召回怎么做
    • 怎么做：每份资料入库时额外生成两类索引项，一是资料级摘要，二是每个小节的标题加首段。Note 模式先在这两类索引项上做混合检索，选出最相关的一两份资料和其中的几个小节，再在这些小节里按切片检索定位命中块，最后按章节树扩成连续窗口。
    • 为什么：精读的问题往往针对某一份资料的某一部分，直接在全库切片里检索，结果会散落在多份资料里，拼不成连续的原文。先定资料、再定小节，证据更集中。
    • 对比：也可以把切片得分按资料聚合（取最高分或求和）来选资料，实现简单，但长文档切片多，求和会偏向长文档，取最高分又容易被一个偶然命中的切片带偏。
  • 12. Wiki 页怎么生成和维护
    • 怎么做：资料入库后经 Kafka 异步触发 Wiki 更新，模型从新资料里抽出主题，和已有 Wiki 页按标题和向量相似度匹配，命中就增量更新这一页，没命中就新建。每一段 Wiki 内容记录来源资料 ID 和切片 ID。页面之间的关系有两种来源，一是两页共享来源资料，二是正文里显式提到另一页的主题，关系带强度分。删除资料时，按来源回链找到受影响的段落，删掉只来自这份资料的内容，其他段落保留，再更新版本指针。
    • 为什么有界一跳：关系图随资料增多会越来越密，多跳扩展会把不相关的页面带进来，一跳加数量上限能控制上下文规模。
点击展开：本章检索算法、ES 内核与评估指标公式速查（BM25 / BM25F / HNSW / RRF / Cross-Encoder / Lucene FST+.liv / Recall@10 · MRR · nDCG@10 / SingleFlight / W-TinyLFU）
  1. BM25（Best Matching 25）与 BM25F 原理和公式：
    • 公式：BM25(Q, D) = Σ IDF(q) × [ f(q, D) · (k1 + 1) ] / [ f(q, D) + k1 · (1 - b + b · |D| / avgdl) ]，其中 IDF(q) = ln( (N - n(q) + 0.5) / (n(q) + 0.5) + 1 )。
    • 为什么比 TF-IDF 强（三大设计）：① 词频饱和度 k1（默认 1.2），同一个词在文档里出现 1 次→5 次提分明显，但出现 50 次不会像 TF-IDF 那样线性刷到天际，而是平滑趋近上界。② 文档长度归一化 b（默认 0.75），文档长度 |D| 越远超平均长度 avgdl，分母越大，惩罚啰嗦长文靠篇幅偶然撞词。③ 逆文档频率 IDF，全库越稀有的报错码/专有名词（n(q) 越小）权重越高。
    • BM25F（多字段加权）：Wiki 检索对「标题 3 / 摘要 2 / 正文 1」先按字段权重折算合并为伪词频再统一套一次词频饱和，避免把三个字段分别算 BM25 再相加导致同一词被重复记分。
  2. HNSW（Hierarchical Navigable Small World，分层可导航小世界图）：
    • 是什么：把跳表（Skip List）的分层跳跃思想搬到高维向量近邻图——顶层图节点极稀疏、连着长距离高速边，检索时从顶层入口贪心往离 Query 向量最近的邻居大步跳，每层走到局部极小就下沉一层，直到最底层（第 0 层，含全量节点）做精细近邻搜索，平均耗时近似 O(log N)。
    • 三大参数：m = 16（每个节点最多连 16 条双向边，越大召回越高但内存与建图开销线性涨），ef_construction = 100（建图插入节点时动态维护的候选列表大小，决定图拓扑质量），num_candidates = 100（检索期每个分片保留的动态候选宽，通常取 2×k）。
    • 为什么必须用 knn.filter 预过滤：先取近邻再过滤（Post-filtering）会让刚撤回的废切片占满 50 个名额导致过滤后结果为空。把墓碑塞进 knn.filter 是在图遍历期间实时跳过不合规节点，保证凑足 k 个有效近邻。
  3. RRF（Reciprocal Rank Fusion，倒数秩融合）公式与为什么不用分数加权：
    • 公式：RRF(d) = Σ 1 / (k + rank_r(d))（平滑常数 k = 60，rank_r(d) 为切片 d 在第 r 路召回中的正整数名次，从 1 开始）。
    • 例：切片 A 在 BM25 排第 1、向量排第 3，则 RRF(A) = 1/61 + 1/63 ≈ 0.0323。切片 B 仅向量排第 1、BM25 未命中，则 RRF(B) = 1/61 ≈ 0.0164，天然奖励多路共识候选。
    • 为什么拒绝线性加权 / Min-Max 归一化：BM25 区间 [0, +∞) 无上界（撞上稀有高 IDF 词可飙到 30+），做 Min-Max 会把其他正常的 8 分、9 分全压扁到 0.2 以下。而 bge-m3 余弦分数挤在 [0.65, 0.85] 窄区间。RRF 只看序数名次、不依赖原始分值大小，免调权重且对离群高分免疫。
  4. Cross-Encoder（精排）vs Bi-Encoder（双塔粗召回）：
    • Bi-Encoder（如 bge-m3）：Query 与文档切片独立编码成向量再算余弦，文档向量可离线算好建 HNSW 索引毫秒级扫全库，但丢失了词与词之间的细粒度交互。
    • Cross-Encoder（如 bge-reranker-v2-m3）：把 [CLS] Query [SEP] Chunk [SEP] 拼成一条序列过 Transformer 全层自注意力，逐字交互比对限定词，精度高，但无法离线建索引、耗时与候选条数线性正比，所以只能放在漏斗末端排 Top-30 → Top-6。
  5. 离线检索三大指标公式与本项目落盘口径（Recall@10 / MRR / nDCG@10 vs Hit@6）：
    • 本项目命中判定统一口径（不绑死切片 ID）：见下节评测设计，每道题人工预埋若干要点、每个要点给一组词项，只要返回证据的标题加摘录包含整组词项即算命中该要点，改了切片策略后评测集仍能直接复用。
    • Recall@K（召回率，如 Recall@10）：前 K 条结果覆盖了该题多少比例的预埋要点。公式：Recall@K = |Top-K 覆盖的预埋要点数| / |该题全部预埋要点数|（多题取均值）。例：某题有 4 条要点，前 10 覆盖 3 条即 0.75。只看要点找得全不全，不关心排第 1 还是第 10（本项目 0.66 → 0.87）。
    • MRR（Mean Reciprocal Rank，平均倒数排名）：只看第一条命中预埋要点的证据排在第几位。公式：MRR = (1 / |Q|) × Σ (1 / rank_first_i)。例：第 1 位命中得 1.0、第 2 位得 0.5、第 5 位得 0.2、未命中得 0。最灵敏反映 Cross-Encoder 精排把关键证据顶到前排的效果（本项目 0.51 → 0.78）。
    • nDCG@K（Normalized Discounted Cumulative Gain，归一化折损累计增益，如 nDCG@10）：通用 IR 公式为 DCG@K = Σ_{i=1..K} (2^{rel_i} - 1) / log2(i + 1)、nDCG@K = DCG@K / IDCG@K（越靠后按 log2(i + 1) 折损）。本项目落盘口径：不手工打多档 rel，而是按每条证据新覆盖的未命中要点计增益（已命中的要点不再重复记分，避免重复切片把分数抬高），再除以理想排序 IDCG@10 归一到 [0, 1]（本项目 0.57 → 0.80）。
    • 与制造业 Hit@6 的区别：Hit@K 是二值命中率（前 K 只要至少命中 1 条核心规程该题即记 1，否则 0），适合「找到关键故障规程即可排查」的工业诊断场景。Recall@10 看多条要点找全比例，MRR 看首位命中，nDCG@10 看去重后的整体排序质量。
  6. Lucene 倒排内核 & 缓存组件原理：
    • Lucene 倒排：词典前缀后缀压缩成 FST（Finite State Transducer）常驻内存定位倒排表。倒排表用差值压缩 + Roaring Bitmap 咆哮位图做极速布尔求交。段（Segment）不可变，写入先进 Buffer + translog，默认每 1s refresh 进 OS PageCache 可搜，删除只在 .liv 存活位图打标并保留 index.gc_deletes=60s 待后台 Merge 回收。
    • SingleFlight：同一进程内对相同 Key 的并发回源请求合并为 1 次查库，其余协程/线程等待共享结果，消除热点 Key 过期瞬间的缓存击穿。
    • Caffeine W-TinyLFU & Redis volatile-lfu：Caffeine 用 4-bit Count-Min Sketch 频率草图准入（新条目访问频次高于待淘汰老条目才进主缓存，防冷数据扫描污染）。Redis volatile-lfu 优先淘汰带 TTL 且近期频次最低的键（Morris 概率计数器递增并随时间衰减）。

高频追问2.3 高频追问

  • 追问 1（三粒度策略与双路融合漏斗） ★★★：「为什么要分三种模式又共用一套索引？为什么用 RRF 加 Rerank 漏斗，Wiki 为什么不用 GraphRAG？」

    「① 共用一套切片底座只在召回组装阶段按策略模式分叉（新增模式只加策略类符合开闭原则，入口由用户选模式、会话内细分意图搭在查询改写里输出），这样资料只处理一次、撤销一致性也只维护一份。

    ② QA 里向量与 BM25 互补，因 BM25 无上界而向量余弦区间窄，RRF 只看排名免调权重，双塔模型能离线算向量建 HNSW 图粗筛，交叉编码器全注意力交互精度高但没法建索引，只能放漏斗最末排少量候选。

    ③ Wiki 没上 GraphRAG 是因为全量抽实体关系构建贵，且删一份资料很难反推图里哪些边该删，有界一跳加段落来源回链删资料时只需局部重算关联页。」

    • → 触发八股（倒排索引 vs B+ 树 与 HNSW 近邻图） ★★：B+ 树 按键有序适合等值和范围查询，但左模糊 LIKE '%词' 用不上索引，ES 倒排索引词典用 FST 压缩、倒排表用差值编码并用 BM25 打分。HNSW 逐层贪心下沉，带过滤须在遍历图时跳过不合规节点防结果滤空（规模全库检索用 HNSW，而实习项目预过滤后仅剩两三千条直接精确算距离即可）。
  • 追问 2（删资料三种方案取舍与缩期细节） ★★★：「资料删了为什么还能搜到？为什么不直接调 ES refresh=true 强刷，也不只在读侧查 MySQL 过滤？」

    「① 删时同步清 ES 并强刷会造大量微型碎段且跨库难回滚，只在读侧查 MySQL 过滤又会让废切片占空粗召回名额。

    ② 所以我拆成三端协同：撤回、重传或恢复启用一律递增新版本号防 ABA，写 24 小时墓碑时清本机缓存并经 Pub/Sub 广播失效各实例本地 1 秒缓存。同时把阶段 4 建索引与撤回删索引收口到同一个按 docId 分区的 ES 同步 Topic（同文档建删严格 FIFO 串行，根治迟到写幽灵切片，免去盲等 2 秒），确认 delete_by_query failures 为空删净旧切片后经 Lua 缩期至 60 秒覆盖刷段与版本回收窗口（慢旧写再由 external_gte 与主库复核双端拦截）。

    ③ 常态单工作区有效墓碑仅个位数～几十条，1,024 是面向批量删库压测或 ES 清理消费积压故障演练的降级熔断水位（虽未触及 ES 65,536 硬上限但超 1,024 序列化与预过滤位图延迟抬升），超水位切 1 秒本地 Caffeine 短缓存配扩窗内存 HashSet 过滤并告警，若主库复核剔除后有效结果被挤占为空则立即绕过本地缓存重拉墓碑扩窗补检一次。」

    • → 触发八股（ES 近实时、Kafka 单分区因果保序、Redis 持久化与主从延迟聚簇点查） ★★：ES 写入先进内存缓冲和 translog、默认每秒 refresh 生新段才可见，删除仅置 .liv 位图并保留 index.gc_deletes=60s。同一文档的写/删同进按 docId 分区的单分区即可严格保序（扩分区须低峰排空防破坏顺序）。Redis 混合持久化或主从切换仍有秒级丢失窗口，故墓碑只做前置保名额，终审放显式直连的 MySQL 主库聚簇主键 IN 点查免回表。

简历原文设计 Context 编译与长期 Memory 机制：针对长会话 Token 膨胀与自动记忆污染事实问题，分层编译 Topic-aware Window、会话持续约束与增量摘要，摘要经 Kafka 异步生成、滞后时按覆盖范围补齐原文，编译结果按版本缓存于 Redis；经「候选提取—门控晋升」沉淀长期 Memory，限定于表达参数控制并与资料 Evidence 事实层隔离。相比全量历史回放，平均输入 Token 降低 34%，关键事实检查通过率 92%。

先拆简历原句 & 点破易踩坑：

这条职责的核心哲学只有三句话：事实每轮重检资料（Evidence）、会话历史只用来解指代和续话题、跨会话长期记忆只管“怎么表达”不碰业务事实。

车祸现场推演：每一步为什么被迫这么设计？

  1. 车祸 1（全量历史 Token 爆棚 + 20 轮截断丢首轮数字。滑窗切回旧话题直接断片。单做意图分类又拖慢首字）→ 约束解码流式 JSON {i,r,d,s} 搭车路由 + 出处回放
    • 不加它怎么炸：用户聊 A 话题 10 轮、插聊 B 话题 10 轮、再回头问 A 话题“刚才那个方案的延迟是多少”。全量塞满 16k 截断后首轮数字没了。固定滑窗只留最近几轮也会丢掉 A 话题。若单独调一个分类器判意图+话题，又白白多一轮串行网络延迟。而靠纯文本自由格式吐四行又极易因小模型多吐前缀客套话或丢换行导致解析失败。
    • 怎么设计：追问本来就要调小模型改写成独立查询 s，直接让 Qwen2.5-7B 走 Structured Output（Guided Decoding / FSM 约束解码）按固定键序流式吐出极简 JSON {"i":...,"r":...,"d":...,"s":"..."}（只喂最近 4 轮短摘 + 话题标题行压薄 Prefill 守住 400ms 延迟预算）：后端流式状态机读到第 1 键 i 发现不用检索立刻短路，读到 r 立刻并行拉摘要和缓存，读到 d=0 甚至不等 s 就能启动历史装配（超时或异常兜底退回问答，话题切分回退词项 IDF + 余弦相似度）。每个话题的摘要按四小节记录且每条要点标着来源消息序号，d=1 时精准按序号把当年那组问答整组捞回来（≤3 组）。
  2. 车祸 2（每轮重拼 Prompt 打碎推理引擎 Prefix KV Cache。摘要滞后丢最新对话）→ 置顶前 3 段 + 4~6 条步长异步摘要 + 独立指纹缓存
    • 不加它怎么炸：大模型推理引擎按前缀块哈希复用 KV Cache，前面改一个字后面全白算！如果每聊 1 轮就重写一次摘要、或者把每轮都会变的新消息/时间戳放前面，前缀缓存每轮全炸。而如果为了稳住前缀干脆滞后摘要，用户刚说的话模型又看不见。
    • 怎么设计：
      • 步长攒批 + 动态尾部补齐：未覆盖问答攒够 4~6 条才发 Kafka（按 sessionId 分区保序，防乱序覆盖）生成不可变新版摘要。窗口期或消费滞后 ≤8 条时，从 MySQL 拉未覆盖序号范围的原文直接补在第 4 段动态尾部（超 8 条展开当前话题段）。这样同话题连续 2~3 轮追问里，前 3 段 2,900 Token 逐字不变，既不丢最新话又守住前缀缓存！
      • 第 2 段与第 6 段缓存解耦：会话约束只按 (session_id, constraint_ver) 缓存，长期记忆只按 (user_id, scope, active_mem_ver_set) 缓存（TTL 180s + 0~30s 抖动防雪崩），谁变切谁，互不连带失效。
  3. 车祸 3（像 MemGPT 让模型自动记业务事实，导致跨会话“昨天的错误讨论污染今天的资料”）→ 8 槽受限程序性记忆 + 四道门控
    • 不加它怎么炸：用户第一天整理论文对比表聊出个草稿数字，第三天新开会话扩写，如果自动记忆把第一天的对话结论带过来，就绕过了资料 Evidence 污染事实。
    • 怎么设计：长期记忆物理限定只存 8 个表达槽位（语言、篇幅、风格、约束、结构、表格、术语、交互方式），(user_id, slot, scope) 唯一约束（全局填固定哨兵 GLOBAL 避免 MySQL NULL 唯一键失效）。抽取时输入包数据围栏、剔除外部文档块、夹带业务实体数值整批作废。必须同时通过置信度、效用、风险、适用范围四道门控才自动生效（有冲突转待确认），并按固定公式静态排序编译放第 6 段紧贴问题（靠近生成位置遵循效果最好，优先级：当轮临时要求 > 会话持续约束 > 长期记忆）。

    • 约 1 分钟速答（先抛结论 + 拆三步 + 抛钩子）：

      「我定了一条硬规矩：事实每轮重检资料，历史只管解指代，跨会话长期记忆只存表达偏好、不碰业务事实。

      ① 借查询改写小模型流式搭车输出意图和话题，零新增串行调用。把稳定的前 3 段置顶，早期细节按摘要标注序号捞原文。

      ② 话题摘要攒够 4~6 条步长再经 Kafka 异步升版，窗口期把滞后原文补在动态尾部，兼顾前缀缓存。

      ③ 长期记忆只开 8 个表达槽位过四道门控，和会话约束分开按独立指纹缓存。最终平均输入 Token 降了 34%，关键事实通过率 92%（基线全量回放 89%）。

      这块想先看七段编译怎么护住前缀缓存，还是长期记忆怎么防污染事实？」

    • 背景（S）：深度研究中的单次会话常持续二三十轮，并在三五个子话题间来回切换。全量历史回放会让输入 Token 随轮次线性膨胀，超过 16k 预算从头部截断后还会丢掉首轮关键数字。固定滑窗切回旧话题容易断片。而像 MemGPT 那样自动将对话提炼为业务事实记忆，容易把前一天未经核实的讨论带入新会话污染资料证据。
    • 任务（T）：在不增加额外串行模型调用的前提下，压低输入 Token、保住跨轮约束与早期细节，并把跨会话记忆和事实层物理隔离。
    • 做法（A）：
      • ① 流式路由与七段装配：改写小模型走 Guided Decoding 约束解码按固定键序流式输出极简 JSON {i,r,d,s}，读到意图就分流。前 3 段（指令、会话约束、不可变摘要共 2,900 Token）集中置顶，后 4 段向核心资料 Evidence（5,400）倾斜并放最多 3 组出处回放与保底原文、长期记忆与当前问题，并落 MySQL 冻结快照保证可复现。
      • ② 步长异步摘要与尾部补齐：未覆盖消息攒够 4~6 条才发 Kafka（按 sessionId 分区保序）生成不可变新版，攒批和滞后期间按序号补原文在第 4 段，让同话题连续 2~3 轮前 3 段逐字不变。
      • ③ 受限记忆与独立指纹缓存：长期记忆仅抽 8 个表达槽过四道门控静态编译，第 2 段约束和第 6 段记忆按各自指纹独立缓存于 Redis，互不连带失效。
    • 结果（R）：同在 16k 预算下对比全量回放，主模型平均输入 Token 降了 34%（9,860 → 6,510），250 个关键事实检查点通过率 92%（230/250，基线 222/250 约 89%）。

核心机制3.2 核心技术点

  • 1. 三类信息的边界
    • 怎么用：资料片段存 ES 和 MySQL，每轮按独立查询重新检索，是事实的唯一来源。消息原文和话题摘要存 MySQL，只在会话内帮助理解追问。持续约束存 MySQL，会话内每轮都带。长期记忆存 MySQL，编译结果缓存在 Redis，跨会话只影响表达方式。
    • 为什么：边界清楚，才能保证跨会话不会把未经核实的对话结论当成事实。
  • 2. 意图和话题判断合并进查询改写（Guided Decoding 固定键序 JSON）
    • 怎么用：改写模型输入压薄为最近 4 轮短摘与最多 8 个已有话题标题行（最近 3 个附简短结论，守住 < 400ms 延迟预算），走 Structured Output（Guided Decoding / FSM 约束解码） 按固定键序流式输出极简 JSON {"i":...,"r":...,"d":...,"s":"..."}（避免 7B 小模型多吐前缀客套话或丢换行导致解析崩溃）。i 是意图，取资料问答、只改表达、设定约束、超出范围四个值之一。r 是目标话题编号或新开话题。d 表示是否需要早先细节。s 是补全主语后的独立查询。后端流式状态机边收边解析，读到 i 属非检索三类直接分流，资料问答读到 r 先并行拉取话题摘要与控制块，读完前三键若 d 为 0 即无需等 s 做原文回放，d 为 1 时再等 s 做两级定位回放。模型输出的话题不存在或超时，就按词项 IDF 覆盖度和话题向量余弦相似度切分，用户明确说回到、改聊、更正时优先按规则判断。规则切分里不确定的边界每 30 秒批量交给模型复核。
    • 意图怎么处理：资料问答走正常检索和编译。只改表达不重新检索，按上一轮冻结快照里的切片 ID 取回原文并做主库复核，只重新生成。设定约束在回答前就同步写进会话约束表、推进指纹，当轮就生效，不用等回答后的抽取。超出范围直接拒识。意图不合法、超时或拿不准都退回资料问答。一句话里既改格式又要新信息，比如改成表格并补上 B 的数据，按资料问答处理，格式要求跟着问题走。
    • 意图和话题的区别：话题回答接着哪条线聊，意图回答要系统做什么。回到旧话题并把表改短，话题是旧话题，意图是只改表达。
    • 为什么合并：追问常省略主语，本来就要调用模型改写成独立查询，意图和话题判断搭车不增加调用次数。i 放最前面，判成不检索的类别时，后端读到第一个字段就能跳过检索。
    • 对比：单独用一个分类模型判断话题，多一次调用，首字延迟变长。只用向量相似度切分，对省略主语和隔几轮回到旧话题判断不准。
  • 3. 预算与选取
    • 怎么用：单轮输入预算按 16k（满额 16,384）切分：稳定前缀前 3 段维持 2,900 Token 不动（系统指令 1,200、会话持续约束 200、话题摘要 1,500），动态尾部向“以资料为中心”倾斜——出处回放 1,500、最近原文与滞后补齐段 3,800、资料片段 Evidence 5,400（充足支撑 QA Top-6 与 Note 连续章节窗口）、长期记忆表达方式 200、当前问题与生成余量 2,584。最近原文保留 2 到 8 条，累计不超过 3,800 Token。目标话题展开四小节摘要，其他话题只带已定结论。摘要滞后补原文分两种情况并统一放在第 4 段动态尾部：当前话题的摘要落后 8 条以内，按未覆盖序号范围把这几条原文补齐。回到旧话题时，那一段摘要还没覆盖到的段尾原文最多带 4 条。需要早期细节时，先用独立查询在目标话题摘要的要点里做词项匹配，找到最相关的要点，再按要点上标注的消息序号取回整组问答，最多 3 组，合计不超过 1,500 Token。
    • 为什么最近原文无论属于哪个话题都保留：话题判断偶尔会错，刚说过的内容必须保留以防指代断档。
  • 4. 冻结快照
    • 怎么用：每轮规划结果写进 MySQL 的快照表，按用户消息序号作为键，记录每项内容入选或被排除的原因。重试和重新生成都读同一份快照。
    • 为什么：输入可复现，回答有问题时能追溯当时模型看到了什么，排查不用靠猜。
  • 5. 编译顺序与前缀缓存
    • 怎么用：固定分七段，前 3 段置顶系统指令与工具定义、会话持续约束、各话题不可变的摘要和结论（稳定前缀合计 2,900 Token），后 4 段依次放两级回放与最近保底原文、资料片段、长期记忆表达方式、当前问题。前缀里不放时间戳和随机 ID，工具列表和字段顺序固定。
    • 为什么：推理服务按块哈希复用逐字相同前缀对应的 Prefix KV Cache，稳定内容置顶配合摘要按步长触发，在架构上减少重复预填充算力与输入成本（实测输入 Token 降 34%，TTFT 未做同口径对照）。表达方式放在问题前面，离生成位置近，遵循效果更好。
  • 6. 增量话题摘要（按 4～6 条步长经 Kafka 异步触发）
    • 怎么用：回答结束后检查目标话题未覆盖消息数，攒够 4～6 条未覆盖问答步长才往 3 分区摘要主题（分区键为会话 ID，同会话严格按顺序处理）投递任务，读上一版摘要和新增消息生成不可变新版，记录覆盖的消息终点序号。摘要按目标、已定结论、关键数字与清单、未决问题四个小节输出，每条要点标注来源消息序号。步长攒批窗口期内未覆盖的消息直接靠第 4 段按序号范围补齐原文（落后 8 条以内补段尾，落后更多直接展开当前话题段原文），使同话题连续 2～3 轮追问（4～6 条消息）期间前 3 段 2,900 Token 逐字恒定命中 Prefix KV Cache。
    • 消费参数：关闭自动提交，摘要写库成功后再手动提交位点。单条摘要要调模型，max.poll.records 设得很小，避免一批处理超过 max.poll.interval.ms。
    • 对比：每轮同步重写全量摘要既拖慢回答、累积误差，又会每轮刷掉第 3 段前缀缓存。用 Redis 队列做异步，没有分区有序和位点回放的能力。
  • 7. 分离第 2 段与第 6 段的独立状态指纹缓存
    • 怎么用：第 2 段（会话持续约束控制块，仅对 (session_id, constraint_ver) 算哈希）与第 6 段（长期记忆表达控制块，独立对 (user_id, scope, active_mem_ver_set) 算哈希）各自独立缓存在 Redis，均不含话题摘要版本号，几百字节，过期时间 180 秒加 0 到 30 秒的随机抖动。任一侧状态变了只切对应那一侧的新指纹键，互不连带失效。
    • 为什么加抖动：大量活跃会话如果在同一秒过期，会同时回源数据库重新编译。
  • 8. 长期记忆的写入
    • 怎么用：回答结束后经 Kafka 异步抽取。先用一个短分类判断用户这条消息里有没有对回答方式的要求或反馈，有才做结构化抽取。槽位限定 8 个：语言、篇幅、风格、约束、结构、表格、术语、交互方式。主表按用户 ID、槽位、适用范围建三列唯一约束，全局偏好填固定哨兵值 GLOBAL 避免 NULL 唯一键失效并支持 QA、NOTE 分模式差异化配置。用户消息包在数据围栏里，外部文档块全部剔除，输出不符合 Schema 或夹带业务实体数值就整批作废。
    • 冲突检测：同一用户全局加当前模式生效记忆最多仅 8 个表达槽位（总计不足 250 字），不杀鸡用牛刀额外维护记忆向量库——同槽直接比对取值和方向，跨槽冲突检测直接将该用户全部 ≤8 条生效记忆一次性拼进 Prompt 交 7B 模型做全量一致性判定（无需维护向量库，全量直判跨槽语义矛盾、不靠 Top-K 截断）。
    • 门控：证据置信度、预期效用、风险、适用范围四项全部通过才自动生效，有冲突或冲突检查没跑成就转待确认。确认后旧记忆标为已替代并记录失效时间，历史版本保留。
  • 9. 长期记忆的静态编译与反馈
    • 怎么用：(user_id, slot, scope) 唯一约束下仅 8 个表达槽位（其中 术语 槽存「技术术语保留英文原文不硬译」等通用表达规范，具体业务词汇归资料 Evidence），当前模式专属 scope 优先覆盖 GLOBAL，不按当前问题相关度动态筛选，统一按 置信度 × 效用 × 新近度 除以篇幅静态排序装入 200 Token 预算并与会话约束去重，保证同一记忆版本集编译文本逐字确定。每次回答记录注入了哪些记忆版本，点赞点踩、重新生成、下一轮追问都记到这些记忆上，负反馈多或效用持续偏低的退回待确认。
    • 对比：MemGPT 让模型自己决定记什么、删什么，灵活但不可控。我让模型只负责抽取候选，晋升由规则门控决定。
  • 10. 会话持续约束
    • 是什么：用户在会话里明确提出、希望后面一直遵守的要求，比如术语保留英文、回答控制在三段以内、只用我上传的资料。它只在当前会话内有效，和跨会话的长期记忆分开存。
    • 怎么做：分两条路写入。查询改写把这一轮的意图判成设定约束时，回答前就同步写进会话的约束表并推进指纹，当轮就生效。没被判成设定约束的，回答结束后用一个轻量抽取再判一次用户这条消息里有没有持续性要求，有就补写进约束表，推进指纹，下一轮编译时生效。同一类约束新的覆盖旧的，用户说取消就失效。当轮的临时要求本身就在问题里，模型直接能看到，不依赖抽取。约束表是整表快照，每轮都完整带上，放在置顶前缀第 2 段会话持续约束这一节。
    • 为什么和长期记忆分开：会话约束是用户明确说出来的，当场就该生效，不需要门控。长期记忆是从多次对话里推断出来的，要经过门控才能跨会话生效。两者的可信度和生效速度不同。
    • 优先级：当轮临时要求高于会话持续约束，会话持续约束高于长期记忆，冲突时按这个顺序。
点击展开：本章上下文与记忆核心机制公式速查（Guided Decoding FSM / Prefix KV Cache 因果掩码 / IDF+余弦退路 / Beta(α,β) 后验平滑 / EMA 指数移动平均）
  1. Guided Decoding（受限解码 / Structured Output）底层原理：
    • 原理：推理引擎（如 vLLM 集成 outlines / xgrammar）把 JSON Schema 或文法离线编译为有限状态机（FSM）。在自回归每一步生成下一个 Token 前，根据当前所处状态算出允许接续的合法词表子集掩码（Token Mask），将所有破坏括号闭合、键序错乱或类型非法的词元 logits 直接置为 -∞（Softmax 后概率归零）。
    • 能力边界：只保证输出符合语法结构，不管内容事实真假——所以仍需配合 64字符/400ms 超时护栏、finish_reason != 'length' 截断检查与后置代码规则核验。
  2. Prefix KV Cache（前缀缓存）与单向因果掩码（Causal Mask）：
    • 自回归模型中第 t 个 Token 的 Key/Value 严格依赖前 0..t-1 的精确序列。推理引擎对 PagedAttention 物理块（如每 16/32 Token 一块）计算包含前序全部块在内的级联块哈希（Block Hash）。只要最前面哪怕改动 1 个字节，从该块往后的整段历史 KV Cache 都会哈希失配作废，被迫重跑 O(N²) Prefill。这就是为什么要把前 3 段 2,900 Token 置顶并攒够 4～6 条才异步升版摘要。
  3. 异常退路：IDF + 余弦相似度 规则回退：
    • 当查询改写小模型超 400ms 或异常时，用 IDF（逆文档频率） 抓用户问题里最稀有的专有词与各话题历史词项重合度，叠加句向量余弦相似度定位目标话题并做原文回放，保证不挂起也不乱丢上下文。
  4. Beta(α, β) 后验平滑置信度（生效后的小样本反馈修正，注意区分准入门控）：
    • 分工边界（避免与晋升门控混为一谈）：记忆能否生效由四项门控（证据置信度、预期效用、风险 < 0.70、适用范围）和无冲突把关——用户明确表述且四项全过直接生效，一次性随口要求被置信度与适用范围拦在待确认。Beta(α, β) 用在生效之后的使用反馈置信度更新与编译排序（置信度 × 效用 × 新近度 / 篇幅）。
    • 公式与直觉：后验均值 p̂ = α / (α + β)，α 和 β 带初始先验值，生效后每次正反馈 α ← α + 1、负反馈 β ← β + 1。如果直接算好评率，一条记忆只用过 1 次被点赞就是满分，和用过 100 次、90 次好评相比并不可靠。引入 Beta 初始先验后，小样本阶段均值会向先验靠拢，用得多、反馈稳的记忆置信度才真正走高。
  5. EMA（Exponential Moving Average，指数移动平均）效用更新：
    • 公式：u_t = 0.75 × u_{t-1} + 0.25 × y_t（近期反馈权重大，又不会被单次偶发波动带偏）。
    • 退回机制：当触发单次明确负反馈、累计两次不良表现，或使用不少于 3 次且效用跌破 0.40 时，自动把该记忆退回 PENDING_CONFIRM 并移出自动注入池，须用户重新确认才能再生效。

高频追问3.3 高频追问

  • 追问 1（编译顺序与 Prefix KV Cache） ★★★：「分层编译为什么定这个先后顺序？对推理成本和指令遵循有什么影响？」

    「① 主要权衡前缀缓存命中率和末尾指令遵循两件事，推理服务（如 vLLM 按块哈希匹配和商业 API 提示缓存）会复用逐字相同前缀的 KV Cache，中间改一个字后面全失效。

    ② 所以把最稳定的系统指令与固定顺序工具定义、独立指纹缓存的会话持续约束、以及按 4 至 6 条步长才异步升版的不可变话题摘要集中置顶在前 3 段（共 2,900 Token），把每轮可能变的两级回放和最近保底原文移到第 4 段动态尾部并标注所属话题和消息序号，使同话题连续 2 至 3 轮追问（4 至 6 条消息）期间前 3 段逐字恒定命中缓存，在架构上减少重复预填充算力与输入成本（实测输入 Token 降 34%，TTFT 未做同口径对照）。

    ③ 每轮变化的资料片段放第 5 段，只有几行的长期记忆表达块静态编译后紧贴当前问题放第 6 段，重算代价极小，换来靠近生成位置的遵循效果。」

    • → 触发 Agent 考点（Context Engineering 四类手段） ★★：写出去（中间状态外置落表，如研究状态表与摘要表）、选进来（按话题与序号回放按需选取）、压缩（不可变话题摘要替原文）、隔离（按对象分包的研究子任务独立上下文），本项目把四类手段组合成了统一流水线。
  • 追问 2（步长异步不可变摘要与分区保序） ★★：「增量摘要为什么按步长做成不可变版本放 Kafka 异步跑？追问太快摘要滞后怎么办？积压能直接扩分区吗？」

    「每轮重写全量摘要既累积丢数字误差、同步拖慢回答，又会每轮改写第 3 段冲刷前缀缓存。改成未覆盖消息攒够 4 至 6 条步长经 Kafka 在上一版基础上只读新增消息生成不可变新版（记覆盖序号终点与固定四小节），步长窗口期或消费滞后在 8 条以内时直接从 MySQL 拉未覆盖范围原文补在第 4 段尾部，超过 8 条直接展开当前话题段原文（持续约束不走摘要队列：意图判成设定约束的当轮同步推第 2 段指纹即生效，回答后补抽的下一轮生效）。」

  • 追问 3（Redis 缓存边界与长期记忆防污染） ★★★：「为什么不用 Redis List 存最近会话消息？长期记忆为什么不学 MemGPT 让模型自己读写业务事实？」

    • → 触发八股与 Agent 考点（Redis 为什么快 + 记忆分类与门控治理） ★★：Redis 快在纯内存、单线程执行省锁与切换开销、IO 多路复用（6.0 后网络读写解析多线程但命令执行仍单线程，大 Key 排障见实习项目）。Agent 长期记忆分语义、情景、程序性三类，本项目只做受四道门控管制的程序性记忆。
  • 追问 4（前缀缓存的反问） ★★★：「全量历史回放是只追加的，本来就最容易命中前缀缓存。你每轮都重新编译，会不会反而更慢？」

    「① 全量回放初期前缀确实最稳定，但它有两个硬伤：一是输入长度随轮数线性增长，注意力计算和显存仍随长度涨，二三十轮超出窗口从最早消息一截断，整条前缀立刻全盘失效，二是长历史混杂旧说法稀释注意力。

    ② 我的编译方案里，前 3 段 2,900 Token 集中置顶，第 2 段与第 6 段缓存解耦，且增量摘要攒够 4 至 6 条未覆盖步长才异步升版，因此在同话题连续 2 至 3 轮追问（4 至 6 条消息）期间前 3 段逐字恒定不变，变的只是第 4 段往后的动态尾部。

    ③ 所以这套顺序既给前缀缓存留出了稳定复用窗口，又把单轮输入控制在固定预算内，34% 的 Token 降幅是实测的，首字延迟未做同口径对照，不会拿它当结论讲。」

  • 追问 5（质量有没有换掉） ★★：「Token 降了 34%，事实通过率是不是拿质量换的？92% 的基线是多少？」

  • 追问 6（为什么是 16k） ★：「模型支持 32k 甚至更长，为什么只给 16k？」

04四、搭建异步资料处理与流式回答链路（职责 4）

简历原文搭建异步资料处理与流式回答链路：针对大文件同步解析阻塞与流式回答断连问题，将解析、切片、向量化和索引拆为 Kafka 分阶段任务并按处理版本幂等推进，通过流式读取支持 128 MB 单文件异步接入；回答侧以幂等 Turn + Redis Stream 中转 SSE 解耦生成与连接，对 Stream 按条数裁剪，控制内存增长，支持基于 Last-Event-ID 的跨实例断线续读。

先懂再背4.0 设计推演速懂（先懂再背）

先拆简历原句 & 点破易踩坑：

这条职责是两条彼此清晰的前后端核心链路：

  • 链路一（大文件入库）：解决 128 MB 单文件上传阻塞和 512MB 小堆 OOM —— 分片直传 MinIO + 同步回调 Range 4 KB 验魔数（业务机 0 MB 穿境）+ 异步阶段 1 8 KB 流式读取算 SHA-256 与 15 页微批解析 + Kafka 四阶段版本幂等推进 + 批次条件更新汇聚。
  • 链路二（AI 流式回答续读）：解决生成绑死 HTTP 连接、断网/切网关丢字 —— 幂等 Turn + Redis Stream 50ms 微批中转（网关固定 4 路分片 XREAD 多 Key 多路复用扇出，防 Lettuce 连接池打爆）+ MySQL 5 秒检查点 + 基于 Last-Event-ID 的 64 位整数比对无缝续读。
  • 易踩坑预警：断线重连判断游标有没有被 Stream 裁掉时，不能直接调 XREAD（游标被裁时 Redis 会静默从现存首条跳读漏字），也不能用字符串字典序比较 ID（"9-0" > "10-0" 会直接误判），必须拆出 - 前的 64 位整数做数值比对！

车祸现场推演：每一步为什么被迫这么设计？

  1. 车祸 1（512MB 堆整包读 128MB 爆 Full GC + Java 同步回拉 128MB 吃爆带宽与超时）→ 分片直传 + 4KB Range 嗅探 + 阶段 1 异步 8KB 流式读取
    • 不加它怎么炸：在 -Xms512m -Xmx512m 受限堆下，直接 getBytes() 读 128MB 远超 G1 半个 Region 大小，直接作为巨型对象塞进连续老年代，8 路并发必爆 Full GC/OOM。如果同步上传回调里由 Java 把整个 128 MB 从 MinIO 拉回来算 SHA-256，既让 128 MB 带宽倒灌业务机又容易触发接口超时。如果整个解析+切片+向量化+写 ES 揉成一步，不仅无法各自扩缩容，向量化限流报错还得重头 OCR。
    • 怎么设计：前端 8MB 分片直传 MinIO 合并（支持 S3 原生分片校验）。Java 同步回调只用 Range: bytes=0-4095 读前 4 KB 验魔数（毫秒返回，0 MB 大文件穿境）。全文件 SHA-256 复算下沉到异步消费阶段 1 通过 8 KB 缓冲流式读取 MinIO 对象流边校验边做 15 页微批流式 OCR（全程常数堆内存，8 路并发 0 巨型对象 Full GC）。拆成四阶段 Kafka（消息体只传 MinIO 指针，向量化单独 6 分区按 docId + batchNo 打散提速，阶段 4 与撤回删索引共用按 docId 分区的 ES 同步 Topic 保序）。
  2. 车祸 2（Kafka 重复消费导致向量化完成批数多加，提前触发建索引）→ 批次明细表条件更新汇聚
    • 不加它怎么炸：向量化某批次消费重复投递，如果直接给主表 done_batches + 1，实际还没跑完就触发了建索引，丢掉后面批次的切片。如果改用布隆过滤器去重，一旦发生假阳性把真实批次当成重复丢掉，完成批数永远少 1，整篇文档永久卡死！
    • 怎么设计：向量化前先往批次明细表插满每批一行（待处理），每批结束在同事务里做条件更新 待处理 → 已完成，只有影响行数等于 1 时才给主表完成批数 +1，等于总批数时才发建索引事件。建索引带 version_type=external_gte 既允许同版本重放又拒旧版本。
  3. 车祸 3（SSE 绑死单连接断网白算 + Stream 内存无限涨 + 长时间断网漏字）→ POST/GET 解耦 + Stream 裁剪与 5s 检查点双保险
    • 不加它怎么炸：直接在一个 POST 请求里同步流式写 SSE，用户刷新、切网关或弱网断连，生成立刻中断。而如果全塞 Redis Stream 不裁剪会把内存打爆，按 1000 条裁剪后离线超 50 秒又会找不到 Last-Event-ID。
    • 怎么设计：
      • 拆 POST + GET 与 Stream Multiplexer 多路复用：浏览器 EventSource 原生只支持 GET 且自带 Last-Event-ID，先 POST 建幂等 Turn 防连点、后台独立跑，再 GET 订阅。不给每个 runId 独占 1 条 XREAD BLOCK 线程（Lettuce 基于 Netty 单连接多路复用禁跑阻塞命令，200 个同学并发提问会瞬间借光 200 条独立 Redis 连接打爆连接池！），改为每台网关固定 4 条分片读线程，每条循环用单条原生 XREAD BLOCK 50 STREAMS k1..kN id1..idN 同时监听本分片几十～上百个活跃 runId，读到增量帧后内存扇出给各 SseEmitter（线程与 Redis 连接恒定 O(1)）。
      • 50ms 微批 + 1000 条窗口(≈50s) >> 5s 检查点：50ms 攒一块降一个量级写压力，1000 条近似裁剪保内存可控，且 50 秒窗口远大于 5 秒检查点间隔——只要重连发现游标被裁，拿最新的 5 秒检查点让前端整体覆盖，后面的增量一定还在 Stream 里，拼出来与终态逐字一致！

点击核对核心采分点（先自己脱稿讲一遍再点开）
  1. 常数堆内存接入与零穿境：512MB 堆下 128MB 字节数组远超 G1 半个 Region，直接作为巨型对象塞进连续老年代，8 路并发必爆 Full GC/OOM。改成前端 8MB 分片直传 MinIO + Java 同步回调仅 Range: 0-4095 读前 4 KB 验魔数（0 MB 大文件穿境、毫秒返回）+ 异步阶段 1 8KB 缓冲流式读 MinIO 边算 SHA-256 边 15 页微批 OCR，堆内存与文件总大小无关。
  2. 精确汇聚防假阳性：布隆过滤器存在假阳性，万一某个真实批次撞上假阳性被误当成重复丢掉，主表 done_batches 就会永远少 1 卡死建索引。改用批次明细表条件更新 待处理→已完成，仅当影响行数等于 1 才同事务主表 +1。
  3. 断网 2 分钟无缝对齐：先调 XINFO STREAM 拆 - 前 64 位整数比较游标与首条序号（严禁字典序比防 "9-0" > "10-0"，也不裸调 XREAD 防静默跳字）。确认被裁后查 MySQL Turn，已完结直返终态全文，运行中先下发 5 秒检查点前缀让前端整段覆盖，再续接 Stream 尾部（5s≈100 帧远小于千条 50s 窗口，首帧二次核验 = 游标+1）。

4.1 约 1 分钟速答与约 2 分钟 STAR

  • 面试官主问：「第四条写了 128 MB 文件拆四阶段 Kafka 接入和 Redis Stream 中转 SSE 续读，具体是怎么设计和实现的？」：
    • 约 1 分钟速答（先抛结论 + 拆三步 + 抛钩子）：

      「这条其实是两条工程链路：写侧保 128 MB 大文件不 OOM、不阻塞，读侧保 AI 流式回答断网切网关续读一字不差。

      ① 大文件用 8 MB 分片直传 MinIO，Java 同步回调只用 Range 读前 4 KB 验魔数毫秒返回、0 MB 穿境，异步阶段 1 用 8 KB 流式读取边算 SHA-256 边 15 页微批解析，-Xmx512m 小堆下 8 路并发零巨型对象 Full GC。

      ② 解析、切片、6 分区并行向量化和建索引（与撤回删索引同 docId 分区保序）拆成四阶段 Kafka，按处理版本幂等推进并用批次明细表精确汇聚。

      ③ 回答侧拆成 POST 幂等 Turn + GET SSE 订阅，中间用 Redis Stream 50ms 微批裁剪配网关 4 路分片 XREAD 多 Key 多路复用（O(1) Redis 连接防打爆连接池）加 MySQL 5 秒检查点兜底，重连按 64 位整数比对无缝续推。

      更想先听大文件怎么防 Full GC 和汇聚，还是 SSE 离线太久怎么对齐不丢字？」

    • 背景（S）：面向学校/学院场景，学生常需上传百兆级扫描教材 PDF 或课程录屏（单文件最大 128 MB），若同步解析会直接阻塞接口，后端整包 getBytes() 在 512MB 受限堆下多路并发会触发 G1 巨型对象 Full GC，向量化也易堵死单分区。回答侧若把生成绑死在单条 HTTP 连接上，弱网断连或切网关就会丢失生成进度。
    • 任务（T）：以常数堆内存异步接入百兆文件并拆出可独立扩缩的幂等流水线，同时解耦模型生成和前端 SSE 连接。
    • 做法（A）：
      • ① 常数堆内存卸载与零穿境：前端 8 MB 分片直传 MinIO 合并，Java 同步回调仅 Range: bytes=0-4095 读前 4 KB 验魔数（不回拉 128 MB），本地事务升版写待投递事件发 Kafka（仅传几百字节指针），异步阶段 1 以 8 KB 缓冲流式读取 MinIO 边算 SHA-256 边 15 页微批解析。
      • ② 四阶段版本幂等推进：拆成解析、切片、6 分区并行向量化（批次明细表条件更新影响 1 行才累加完成批数）与 ES 同步（阶段 4 建索引与撤回删索引共用按 docId 分区 Topic 保序，external_gte），各步核对处理版本跳过旧版。
      • ③ Stream 多路复用中转与检查点对齐：POST 建幂等 Turn、GET 订 SSE（停止走 Pub/Sub 中断），50ms 微批写从 1 递增的 Stream（MAXLEN ~ 1000），网关固定 4 路分片 XREAD BLOCK 50 STREAMS k1..kN 多 Key 多路复用扇出（O(1) Redis 连接），每 5 秒刷 MySQL 检查点。重连拆 64 位整数比首条序号，没裁直接续推，被裁先推检查点整体覆盖再续接 Stream 尾部。
    • 结果（R）：在 -Xmx512m 受限堆下 8 路并发接入 128 MB，GC 日志里没有巨型对象引发的 Full GC。断网、切网关、长时间离线三类故障注入后，前端拼出的全文与终态逐字一致。

核心机制4.2 核心技术点

  • 1. 分片上传、4 KB Range 验魔数与阶段 1 流式校验
    • 怎么用：前端按 8 MB 一片调 MinIO 的分片上传（支持 S3 原生分片校验 ChecksumSHA256），失败的分片单独重传，全部上传后由服务端合并。Spring Boot 同步上传完成回调不把 128 MB 全量拉回业务机，而是只发一次 Range: bytes=0-4095（前 4 KB） 流式检查文件头魔数防伪造后缀，毫秒级返回。全文件 SHA-256 复算下沉到异步消费阶段 1，通过 8 KB 缓冲流式读取 MinIO 对象流边校验去重、边按 15 页微批解析，全程堆里只有一个常数级缓冲区。
    • 为什么不用 getBytes() 也不在同步接口拉全文件：在 -Xms512m -Xmx512m 受限堆参数下，128 MB 的字节数组远超过 G1 半个 Region 的大小，会作为巨型对象直接分配到连续的老年代 Region，8 路并发就会触发 Full GC 乃至 OOM。而如果让 Java 同步回调流式回拉整个 128 MB 算哈希，依然会把百兆带宽倒灌进业务机且引发接口超时。
    • 对比：前端分片直传 + 同步 Range 4 KB 嗅探 + 阶段 1 异步流式读算哈希，才真正做到“业务机 0 MB 大文件穿境 + 全程常数堆内存”。
  • 2. 四阶段 Kafka 主题
    • 怎么用：解析、切片、向量化、ES 同步（阶段 4 建索引与撤回删索引共用同一按 docId 分区的 ES 同步 Topic，保证同文档建删严格 FIFO 因果有序）四个阶段，向量化 6 个分区，其他三个各 3 个分区。消息体只有资料 ID、处理版本号和 MinIO 路径，几百字节。解析、切片和 ES 同步以资料 ID 作分区键，向量化以「资料 ID 加批次号」作分区键，一个大文件的多个批次打散到不同分区并行。每阶段消费成功后，同事务更新阶段状态并写入下一阶段的极简同库待投递事件记录，提交后异步发 Kafka（异常由后台扫未投递记录幂等补发），再手动提交位点。
    • 生产端参数：acks=all，开启幂等生产者 enable.idempotence，重试次数不限、配合交付超时控制总时长。
    • 消费端参数：关闭自动提交。向量化快阶段（64 切片一批）设 max.poll.records = 10。重型产物队列消费线程只做毫秒级幂等落库/抢槽并立刻提交位点（不在消费线程同步跑 2～6 分钟长任务），从根源保证单批处理耗时远小于 max.poll.interval.ms。
    • 为什么拆四阶段：四个阶段的瓶颈不同，解析吃 CPU 和内存，向量化受模型接口并发限制，建索引是 ES 写入，拆开后各自扩缩容，某一步失败只重试这一步。
  • 3. 批次汇聚
    • 怎么用：向量化开始前在批次明细表里为每个批次插一行，状态待处理。每批完成后执行条件更新，把这一批从待处理改成已完成，影响行数为 1 才给资料主记录的完成批数加 1，两步在同一个事务里。完成批数等于总批数时投递建索引任务。
    • 为什么：消息可能重复投递，直接给主记录加 1 会重复计数，提前触发建索引。
  • 4. 建索引
    • 怎么用：用 ES 的 bulk 接口，每批 500 条或 5 MB，写入时带 version_type=external_gte 允许同版本批次幂等重放并拒绝旧版本写入。建索引期间把索引的 refresh_interval 保持默认 1 秒，不在请求里强制刷新。
  • 5. 幂等 Turn
    • 怎么用：前端每次发送生成一个客户端请求号，后端在 Turn 表上对「会话 ID 加客户端请求号」建唯一索引。插入冲突就查出已有的 Turn 和运行编号直接返回。
    • 为什么：用户连点、网络重试都会产生重复请求，唯一索引是最简单可靠的去重。
  • 6. Redis Stream 中转与 Pub/Sub 停止中断
    • 怎么用：每次运行一个 Stream 键（sse:stream:turnId，turnId 与下文 runId 均指本次生成执行流 ID，不加 {} Hash Tag）。生成端把模型输出按 50 毫秒攒成一个增量块，用 XADD 写入，带 MAXLEN ~ 1000 近似裁剪，消息 ID 显式采用从 1 开始单调递增的 <seq>-0（Redis 规定 0-0 非法）。每次写入刷新过期时间为 15 分钟，每 5 秒把累计前缀和对应序号写进 MySQL 检查点，结束时写终态全文。用户点击「停止生成」时后端更新状态并经 Redis Pub/Sub 广播中断信号，生成实例收到后立即切断上游模型流。
    • 参数怎么定：50 毫秒微批在用户感知上仍是流畅的逐字输出，又能把写入次数降一个数量级。1000 条按 50 毫秒算大约覆盖 50 秒，远大于 5 秒的检查点间隔，保证检查点之后的增量都还在 Stream 里。
  • 7. SSE 推送与 Stream Multiplexer 固定分片多路复用
    • 怎么用：前端先 POST 提交 Turn，再用 EventSource GET 订阅运行的事件流，后端用 SseEmitter 推送，每 15 秒发一条注释行做心跳，防止代理和负载均衡把空闲连接断掉。网关侧不给每个 runId 独占 1 条 XREAD BLOCK 线程，而是每台网关仅开固定 4 条分片读循环（Stream Multiplexer），活跃 runId 按哈希归入对应分片，每条循环用单条 Redis 原生 XREAD BLOCK 50 STREAMS k1 k2 ... kN id1 id2 ... idN 一次性监听几十～上百个活跃 Stream，读到增量帧后在内存按 runId 扇出分发给对应的多个 SseEmitter。
    • 为什么不能 1 个 runId 开 1 条阻塞读线程（核心八股）：Spring Boot 默认 Redis 客户端 Lettuce 基于 Netty 单连接多路复用，严禁在共享连接上跑 XREAD BLOCK / BLPOP 阻塞命令（会卡死整条连接上的其他所有短命令），必须从连接池借独立物理连接。如果 200 个同学同时生成回答、每个 runId 独占 1 条线程和 1 条独立连接，瞬间打爆 Redis 连接池与线程上限。改成 4 路多 Key 多路复用后，单机承载数百并发 SSE 流始终只占 4 条线程 + 4 条 Redis 连接（O(1)）！
    • Nginx 配置：关闭代理缓冲，或者响应头带 X-Accel-Buffering: no，读超时调大到心跳间隔之上。
    • 对比：不选双写 Pub/Sub + Stream 是为了避免订阅切换缝隙丢帧与双路状态机复杂度（校级几百并发纯 Stream 多路复用最简洁统一。若未来扩至单机万级活跃流，再进一步演进为 Pub/Sub 分片通知 + Stream 仅做 XRANGE 补读）。
  • 8. 断线续读与 64 位整数序号比对
    • 怎么用：重连时浏览器自动带 Last-Event-ID。网关先调 XINFO STREAM 取当前首条 ID，拆出两边 - 前面的 64 位整数做数值比对（严禁字典序比对，防止 "9-0" > "10-0" 误判，且直接调 XREAD 在位点已裁时会静默从现存首条跳读漏字），并在 XREAD 首帧返回时二次核验帧序号等于游标加 1。游标还在就直接续推，已被裁掉的话，运行已结束就返回 MySQL 终态全文，还在运行就先下发带 5 秒 检查点序号的前缀同步事件让前端整体覆盖已显示内容，再续接大于该序号的 Stream 尾部增量，不重不跳。
  • 9. 解析阶段怎么处理大文件
    • 怎么做：解析在无状态 Python Worker 里按 15 页微批流式加载，文字版直接抽取文本和版面结构，扫描版按微批渲染成图片后交进程池并发 OCR，每批写回 MinIO 即释放图像张量内存。音视频不走此处，转给 MCP 服务，完成后汇总章节结构写回 MinIO 交给切片阶段。
    • 为什么按微批：128 MB 扫描 PDF 可达几百页，整份加载光栅化会撑爆 Worker 内存，按 15 页微批流式处理时内存与文件总大小无关，只取决于单批页数。
    • 失败处理：单页异常记页码跳过，不中断整份文档解析，最后在资料详情提示异常页码。
点击展开：本章流式底座与性能指标原理速查（G1 Humongous 巨型对象 / Kafka 零拷贝 sendfile & ISR / Lettuce 阻塞红线 / Stream MAXLEN ~ / P95 分位延迟含义）
  1. JVM G1 Humongous（巨型对象）触发 Full GC 原理：
    • G1 把堆划成大小相等的 Region（512 MB 堆下默认每 Region 约 1 MB）。凡是单个数组体积 ≥ 半个 Region（即 ≥ 512 KB），就会被判为巨型对象，绕过年轻代直接分配在老年代的连续多个 Region 中。128 MB 整包 getBytes() 需要连续 128 个 Region，多路并发直接碎片化打穿老年代触发 STW Full GC。改为 8 KB 流式读取后对象留在 Eden 朝生夕死。
  2. Kafka 高吞吐（零拷贝 sendfile）与三端防丢（ISR）：
    • 磁盘文件不经过用户态 JVM 堆，靠操作系统 PageCache + Linux sendfile 系统调用经 DMA 从内核页缓存直推网卡缓冲区（4 次拷贝降为 2 次、4 次上下文切换降为 2 次）。可靠性靠生产端 acks=all + enable.idempotence、Broker 副本同步集 ISR 配 min.insync.replicas=2 且禁非同步副本选主、消费端业务落妥后再手动提交 offset。
  3. Lettuce 单连接阻塞红线与 Stream MAXLEN ~ 原理：
    • Lettuce 基于 Netty 单 TCP 连接多路复用短命令，若在共享连接上发 XREAD BLOCK 阻塞命令，会卡死同一连接上所有普通 GET/SET。用固定 4 路分片 XREAD BLOCK 50 STREAMS k1..kN 仅占 4 条独立连接（O(1)）。
    • Redis Stream 底层是 Radix Tree（前缀树）索引多个 listpack 宏节点。MAXLEN ~ 1000 中的波浪号 ~ 表示近似裁剪——仅当整块 listpack 宏节点全部早于阈值时才 O(1) 整块释放，避免每次 XADD 都在紧凑数组内搬移字节。
  4. P95 / P99 分位延迟（与均值区别）：
    • 定义：把压测窗口内全部请求的端到端耗时从小到大排序，排在第 95% 位置的数值即 P95（表示 95% 的请求响应时间 ≤ P95，仅最慢 5% 超过它）。
    • 为什么工程 SLA 看 P95 不只看均值：均值极易被 90% 的快速缓存命中拉低，掩盖 5%～10% 的严重长尾毛刺（如 GC、锁排队、热点大 Key）。本项目检索 P95 ≈ 180ms 直接刻画了 95% 真实请求的延迟上限。

高频追问4.3 高频追问

  • 追问 1（四阶段拆分与批次汇聚） ★★：「一个文件任务跑到底不行吗，为什么拆四阶段？批次去重为什么不用布隆过滤器？」

    「四阶段吃计算、受模型并发限、写 ES 的瓶颈各不相同，拆开后可独立扩缩容，某一步报错也只重试当前阶段不用重头解析。批次汇聚不用布隆过滤器是因为它有假阳性，一旦某个真实批次撞上假阳性被误当成重复丢掉，主表完成批数就会一直少 1 导致整篇文档卡住进不了索引。」

    • → 触发八股（G1 巨型对象、Kafka 为什么快与三端防丢 ISR） ★★★：超过半个 G1 Region 的大字节数组会直配连续老年代 Region 易触发 Full GC，故用 8 KB 流。Kafka 高吞吐靠分区顺序追加写、操作系统页缓存、sendfile 零拷贝直推网卡与批量压缩，配合对象存储传指针（Claim Check）。防丢靠生产 acks=all 加幂等、Broker 多副本配 min.insync.replicas=2 禁落后副本选主、消费端业务落妥再手动提位点。
  • 追问 2（生成连接解耦与断网检查点对齐） ★★★：「为什么把提问 POST 和订阅 GET 拆开？如果断网太久 Last-Event-ID 已经被 Stream 裁掉了怎么办？」

    「① 浏览器原生 EventSource 只支持发 GET 请求且自带断线重连带 Last-Event-ID 能力，拆成先 POST 创建幂等 Turn 拿运行编号再 GET 订阅（Nginx 关代理缓冲防攒块，点停止时经 Pub/Sub 广播中断），既解决了提问传参和防双击，又让后台生成脱离单条 HTTP 连接独立跑。

    ② 高频 50ms 增量按从 1 开始的序号只写 Redis Stream 近似裁剪千条，MySQL 每 5 秒 低频写滚动检查点前缀。

    ③ 重连时网关先拆出 - 前 64 位整数比对 Stream 首条序号与 Last-Event-ID（防字典序 "9-0" > "10-0" 误判），仍在保留窗口内就直接续推并核验首帧连续，若已被裁掉则按是否完结分流：已完结直接返回 MySQL 终态全文，仍在生成中则先取出最新 5 秒 检查点作为专用前缀同步事件发给前端整体覆盖对齐，再从该检查点序号无缝续接 Stream 尾部（5 秒 约一百个微批，远小于千条保留窗口，中间不会断档）。」

    • → 触发八股（SSE vs WebSocket、Lettuce 阻塞连接坑与 Stream vs Pub/Sub） ★★★：AI 回答是服务端单向推流，SSE 走普通 HTTP 免去 WebSocket 协议升级和连接状态管理（HTTP/2 多路复用破除同域 6 连接限制）。Lettuce 底层单 TCP 共享连接禁跑阻塞命令，每 runId 开 XREAD BLOCK 会借光连接池，故用 4 路固定分片单条 XREAD STREAMS k1..kN 多路复用将线程与连接压到 O(1)。Pub/Sub 即发即弃只发停止中断广播，Stream 保留最近窗口支持按位点补读，MAXLEN ~ 只在整块 listpack 宏节点可整体移除时裁剪（万级流再演进 Pub/Sub 通知 + Stream XRANGE 补读）。

车祸现场推演：每一步为什么被迫这么设计？

  1. 车祸 1（多类产物代码耦合 + 一次吐 20 页长讲义写到后面烂尾截断 + 错一页重算整份）→ SKILL.md + Schema + 五段模板方法
    • 不加它怎么炸：报告、测验、PPT、PDF 各写一套流程，改个校验或重修逻辑要改四处。让大模型一口气生成 20 页讲义，中后段注意力退化、字数超框甚至截断，第 14 页超宽还得整份重新花钱生成。

  2. 车祸 2（Kafka 扛 5 分钟长任务触发超时重平衡 / 位点死卡 6 分钟 + 单工作区连提交 24 单堵死所有人）→ Kafka 毫秒落库提交 + MySQL 权威状态表 + 产物独立 8 槽与原地接力
    • 不加它怎么炸：
      • 如果消费线程自己跑 5 分钟任务，超过 max.poll.interval.ms（默认 300 秒）没调 poll()，Broker 判定死亡踢出消费组触发 Rebalance，任务反复重跑。
      • 即使退一步把任务丢进异步池再在内存维护“连续最大位点 + pause/resume”，一旦单分区最早那条跑 6 分钟没完，连续位点就会卡死 6 分钟不能提交，实例重启会触发几十条重放风暴，还要手写极脆弱的分区位点空洞与 onPartitionsRevoked 清理逻辑。
      • 入口 QPS 限流管不住在途长任务数，单工作区一口气提交整学期 24 讲课程视频，若不按工作区隔离就会挤垮共享算力，若与深度研究混池还会连带拖死交互式调研。
    • 怎么设计（职责解耦，让每个中间件只干最擅长的事）：
      • Kafka 仅做 6 分区并行削峰与入队派发（毫秒安全提交 offset）：消费线程不跑 2～6 分钟任务，也不用位点兜底分钟级执行——拿到消息只做毫秒级幂等校验并尝试抢槽：抢到产物独立 8 槽且本机 32 线程 有界执行池有空位，就条件置 MySQL RUNNING（带 300s 运行租约与 exec_gen+1）异步投递执行池。满 8 槽或满池就条件置 DB DELAYED 放行后续其他工作区——两支都在毫秒内安全提交 Kafka offset，不再触发 Rebalance、零 6 分钟位点空洞！
      • 宕机兜底与工作区公平让道下沉到 MySQL + Redis 独立 8 槽：任务权威状态与执行租约留在 MySQL（心跳每 60 秒先续 DB 租约再经 Lua 续期 Redis ZSET，写页与终态核验 exec_gen 防慢实例双写。实例宕机后由后台 30 秒扫描回收超时 RUNNING 单与唤醒 DELAYED 单）。产物专用池 nw:slots:artifact:wsId 限 8 槽（相对单机 32 线程严控 ≤ 25%，与深度研究 8 槽池物理舱壁隔离）。
      • 为什么原地接力要先续期再认领：完单顺手接同工作区 1 条 DELAYED 单，减少绕回扫描延迟。但必须先用 Lua 验 ZSCORE > now 续期成功、再 DB 条件更新认领，防止拿完单才发现槽位已经过期被别人抢走。且最多连跑 1 次就释槽，防其他工作区饿死。
  3. 车祸 3（把 FFmpeg 和 Whisper 塞进主应用撑爆显存，或用普通 Function Calling 无法跨模块复用）→ 独立 Media MCP 服务
    • 不加它怎么炸：音视频解码和语音模型吃 GPU 显存且依赖重，塞进主服务连带拖垮常规问答。普通 Function Calling 工具注册写死在单个应用里，深度研究和产物模块各写一套。
    • 怎么设计：独立部署 Media MCP 服务走 Streamable HTTP，按标准 tools/list 和 tools/call 只暴露 2 个工具，服务间只传 15 分钟有效期的 MinIO 预签名链接，既隔离重依赖独立扩缩容，又让研究和产物直接共用。

点击核对核心采分点（先自己脱稿讲一遍再点开）
  1. 三组件职责边界（架构克制加分项）：Kafka 是高吞吐日志流，不是 6 分钟任务调度器——同步跑必超 max.poll.interval.ms(300s) 重平衡。硬写 pause + 内存连续位点会让 1 条慢单卡死分区位点 6 分钟，重启引发重放风暴。所以 Kafka 只做 6 分区并行削峰（毫秒判幂等、抢槽入池或置 DELAYED 后立即提交 offset），MySQL 做权威状态机与 300s 租约兜底，Redis ZSET 独立 8 槽管多工作区公平准入。
  2. 秒提交 offset 宕机不丢单：任务在投递进 32 线程池前已在 MySQL 落盘 RUNNING 并写 lease_expire_at = now + 300s（正常每 60s 先续 DB 再续 Redis）。实例宕机停跳后，后台 30s 扫描发现超期僵尸单，自动递增 exec_gen 重置重派（已校验落库的产物页保留，只重做未完页），写页与终态均核验 exec_gen 防慢实例双写。
  3. 先续期后认领 + 最多连跑 1 次：先调 Redis Lua 验 ZSCORE > now 并 ZADD XX 续期成功，再 DB 条件认领最早 1 单并递增执行代次（认领 0 行立刻 ZREM），防止先认领完单才发现槽已过期被别人占走。最多连跑 1 次即释槽让出，防止单个大户工作区长期霸占线程饿死其他工作区。

    • 结果（R）：新增产物只需加目录契约与渲染器。并发长任务压测窗口内没有观测到超时重平衡或单工作区满槽造成的队头阻塞。

核心机制5.2 核心技术点

  • 1. SKILL.md 与 JSON Schema 契约
    • 怎么用：每种产物一个目录，SKILL.md 用自然语言写清取材范围、大纲结构和写作规范，JSON Schema 约束每页或每节的字段和字数上限，比如讲义每页标题不超过 20 字、要点 3 到 5 条、每条不超过 40 字。启动时加载所有契约并校验 Schema 合法。
    • 为什么分两份：SKILL.md 给模型看，描述怎么写好。Schema 给解码器和校验器用，保证结构正确、能被渲染器直接消费。
  • 2. 五段流水线（模板方法）
    • 怎么用：抽象基类定义取材、规划、写作、校验、渲染五个步骤和失败重修逻辑，每种产物只覆盖差异部分。规划先生成大纲并给每页分配独占的论点和素材。写作逐页受限解码。校验用代码检查字数、超宽和引用是否绑定，有问题的页单独重修一次。渲染时 PPT 用 python-pptx，PDF 讲义用 XeLaTeX。
    • 为什么逐页生成：一次生成二十页，写到后面注意力退化，内容质量下降甚至截断，而且某一页出错就得整份重来。
  • 3. Kafka 6 分区并行削峰与 32 线程有界执行池（不让 Kafka 位点扛 6 分钟长任务）
    • 怎么用：重型产物提交主题设 6 个分区（按 taskId 散列并行消费），消费线程不亲自执行 2～6 分钟任务，也不把 Kafka offset 绑定在长任务完成上：拿到消息后毫秒级查 DB 幂等状态并检查工作区产物 8 槽与本机 32 线程 有界池余量——有槽且有空闲则 DB 条件置 RUNNING(300s 租约 + exec_gen+1) 并异步投递 32 线程池。满 8 槽或本机池满则条件置 DB DELAYED——两条路径都在毫秒内安全提交 Kafka offset。
    • 参数怎么定：每个产物任务两到六分钟，Java 侧线程主要时间在等待外部模型与 Python 服务 I/O，32 个线程对应单机面向高并发商业模型 API 池分配到的并发额度（且保证单工作区产物独立 8 槽严格 ≤ 25% 即 8/32 不打满机器，同时不挤占深度研究独立 8 槽池）。
    • 为什么放弃初版 max.poll.records=1 + pause/resume + 内存连续位点 方案（架构演进加分点）：同步执行必超 max.poll.interval.ms(300s) 触发重平衡。而即便拆池再在内存维护连续最大位点，只要单分区最早那条任务跑 6 分钟未完，位点就会死卡 6 分钟不提交，实例重启直接引发几十条重放风暴且 onPartitionsRevoked 清理极脆弱。改为“Kafka 只干削峰分发秒提交 + MySQL 权威租约兜底”，代码复杂度砍 70% 且没有观测到位点空洞。
  • 4. 工作区产物独立并发准入（与深度研究舱壁隔离）
    • 怎么用：采用独立的产物槽位 ZSET（nw:slots:artifact:wsId 限 8 槽，与深度研究池 nw:slots:research:wsId 8 槽做快慢舱壁隔离，且不加 {wsId} Hash Tag 防 Cluster 分片倾斜。300 秒过期、每 60 秒心跳先刷 MySQL 运行租约超时时间再经 Lua 续期 Redis 槽位），满槽时条件更新为 DELAYED 立即提交位点放行后续其他工作区消息。工作线程完单准备释槽前，若同工作区有 DELAYED 积压单，先调 Redis Lua（验 ZSCORE > now 并 ZADD XX）续期工作区租约成功，再通过数据库条件更新原子认领最早 1 单并递增执行代次令牌接力执行（若认领影响 0 行则立即 ZREM 释槽，最多连跑 1 次即让出防其他工作区饥饿），无积压或已连跑 1 次则立即 ZREM 释槽，后台每 30 秒扫描补偿超时僵尸单与 DELAYED 积压单。
    • 为什么：入口 QPS 限流管不住后台在途长任务数，按工作区准入防止单工作区连发占满模型并发。
  • 5. MySQL 权威运行租约与 exec_gen 执行代次令牌防双写
    • 怎么用：Kafka 毫秒提交 offset 后，任务可靠性完全由 MySQL 权威任务表托底——在途任务带 RUNNING 状态、300s 运行租约与单调递增执行代次 exec_gen。实例宕机停跳后，后台 30 秒扫描超时回收并递增 exec_gen 重新派发，写产物页与终态均核验 exec_gen 防慢实例双写（已校验落库的产物页保留，只重做未完页）。
    • 为什么：把 Kafka 从长任务执行态中解放出来，既无 6 分钟位点滞后，又能精确到单页断点续跑。
  • 6. MCP 服务
    • 怎么用：严守全项目仅 2 个 MCP 工具（faster-whisper 语音转写工具 + 关键帧抽取与板书多模态理解工具），封装成独立的 Media MCP 服务走 Streamable HTTP 传输。入库阶段的全片稀疏抽帧与产物取材阶段的局部时间窗高密度补抽，共用第 2 个关键帧理解工具的不同时间窗与分辨率档位参数（读取真实显示时间戳 PTS，算 64 位感知哈希，相邻帧汉明距离小于 10 视为同一画面滤掉压缩噪点）。服务之间传有效期 15 分钟的 MinIO 原视频只读 GET 与抽帧受限目录单次 PUT 预签名链接。
    • 为什么独立服务：FFmpeg 和语音模型依赖重、要占显存，和主服务分开部署可以单独扩缩容，深度研究和产物两个模块都能通过 tools/list 和 tools/call 调用。
    • 对比：直接在应用里写函数调用，工具注册和调用逻辑和单个应用绑定，别的模块用不了。
  • 7. 资料版本冻结
    • 怎么用：下单时把所选资料的当前处理版本号写进产物任务，取材时只检索这些版本的切片。
    • 为什么：产物生成要几分钟，期间用户可能重传资料，冻结后同一份产物的素材前后一致。
  • 8. 关键帧理解与视频转讲义
    • 怎么做：视频先走转写服务，得到带时间戳的逐句文本。同时抽关键帧，每个关键帧记录出现时间。关键帧理解调多模态模型，对板书和课件画面做文字识别和内容描述，输出这一帧的标题、要点和公式。然后按时间戳把转写文本切到相邻两个关键帧之间，形成「画面加这段讲解」的片段。规划阶段以这些片段为素材生成讲义大纲，写作阶段每页结合画面内容和对应的讲解文字。生成 PPT 与 PDF 讲义时关键帧作为配图，板书推导密集处按局部时间窗与高分辨率档位参数复用第 2 个关键帧理解工具做高密度补抽（异常自动降级回退入库基础稀疏帧）。
    • 为什么按时间戳对齐：老师讲的内容和当时屏幕上的画面是对应的，按时间切能保证每页讲义的文字和图是同一件事。
    • 对比：只用转写文本生成讲义，会丢掉板书上的公式和图示。逐帧都送多模态模型，成本太高，而且大部分帧是重复画面，所以先去重再理解。
点击展开：本章多模态与协议底层原理速查（pHash 64 位 DCT 感知哈希 + 汉明距离 / PTS 时间戳 / MCP JSON-RPC 2.0 & Streamable HTTP / Tool Poisoning）
  1. pHash（Perceptual Hash，64 位感知哈希）与汉明距离原理：
    • 为什么不用 MD5/SHA-256 去重视频帧：密码学哈希对 1 个像素的编码噪点都会雪崩全变，导致同一张静止 PPT 画面算出的哈希截然不同。
    • pHash 四步算法：① 将帧缩小为 32×32 灰度图去掉高频细节。② 做 2D-DCT（离散余弦变换） 转到频域，只取代表画面宏观结构的左上角 8×8 低频系数（64 个数）。③ 计算这 64 个数的均值（跳过直流分量），大于均值记 1、否则记 0，拼成 64-bit 整数指纹。④ 汉明距离（Hamming Distance） = popcount(hash1 XOR hash2)（两指纹不同比特位的个数）。相邻帧汉明距离 < 10 视为同一静止板书/课件画面，天然抗 H.264 压缩噪点与轻微光照波动。
  2. PTS（Presentation Time Stamp，真实显示时间戳）：
    • 视频编码存在 B 帧双向预测，解码顺序（DTS）与人眼看到画面的显示顺序（PTS）不同，抽帧必须读 FFmpeg 的真实 PTS 才能和 faster-whisper 语音转写时间戳精准对齐。
  3. MCP（Model Context Protocol）协议栈与防工具投毒：
    • 通信协议：基于 JSON-RPC 2.0，暴露 tools/list（发现工具与 Schema）、tools/call（执行调用）、resources、prompts。本地进程用 stdio，跨网络远程服务已从早期易被企业代理阻断的双通道 HTTP + SSE 演进为单端点按需升级流式并支持断线续传的 Streamable HTTP。
    • Tool Poisoning（工具描述投毒）防护：恶意或被篡改的第三方 MCP 服务可能在 tools/list 返回的 description 字段里夹带隐藏提示注入指令诱导模型外传隐私。启动阶段对受控 MCP 服务的工具描述计算校验哈希即可拦截非预期篡改。

高频追问5.3 高频追问

  • 追问 1（设计模式与 MCP vs Function Calling） ★★：「五段流水线用了什么设计模式？音视频走 MCP 和普通 Function Calling 有什么区别？」

    「五段固定骨架与单页重修逻辑是模板方法模式，不同产物的取材规则与渲染器是策略模式从注册表按类型获取，符合开闭原则。Function Calling 只是模型输出调用意图，工具怎么注册和调用写死在单个应用内，而 MCP 把语音转写和关键帧理解这两个重依赖工具做成独立服务按标准 tools/list 与 tools/call 协议暴露，既隔离了 FFmpeg 和模型显存方便单独扩缩容，又让深度研究和产物两个模块无需重复开发直接共用。」

  • 追问 2（长任务为何不让 Kafka 位点扛执行态、如何防丢与原地接力） ★★★：「2～6 分钟的重型产物走 Kafka 消费，怎么防止超时重平衡和单工作区堵死别人？如果提交了 offset 机器又宕机了怎么办？」

    「① 我早期试过用 max.poll.records=1 + pause/resume + 内存连续位点提交来扛长任务，但复盘发现 Kafka 是为高吞吐日志流设计的，不是为 6 分钟作业调度设计的——只要单分区最早那条跑 6 分钟未完，位点就卡死 6 分钟，重启触发重放风暴且代码很脆。所以我做了职责解耦：Kafka 6 分区只管削峰与并行派发，消费线程毫秒级判幂等、尝试抢工作区产物独立池 nw:slots:artifact:wsId 8 槽并检查本机 32 线程池——抢到就条件置 MySQL RUNNING(300s 租约 + exec_gen+1) 异步投池，满 8 槽或满池就置 DB DELAYED 放行其他工作区，两支都在毫秒内安全提交 offset，从根源消除 Rebalance、6 分钟位点空洞和跨工作区队头阻塞。

    ② 秒提交 offset 宕机不丢单，因为任务权威执行态与 300s 租约已持久化在 MySQL（每 60s 心跳先续 DB 再 Lua 续 Redis）。实例宕机停跳后，后台 30s 扫描自动回收超时单、递增 exec_gen 重新派发（已落库产物页保留只补未完页），写页与终态均核验 exec_gen 防慢实例双写。

    ③ 原地接力防饥饿：工作线程完单释槽前，若同工作区有 DELAYED 积压单，先调 Redis Lua 验未过期并续期租约成功，再 DB 条件认领最早 1 单接力（影响 0 行立即 ZREM，最多连跑 1 次即让出防其他工作区饥饿）。这一思路和我在制造业实习项目里“MQ 轻唤醒秒 ACK、权威状态与租约交 DB”是一脉相承的第一性原理。」

7.2 离线研究评测：67% 到 83% ★★★

  • 指标含义：一个格子是「一个调研对象的一个待验证字段」。有效格子要同时满足三条，状态是已采纳，至少一条结论能回溯到逐字原文、网页快照和网址，高风险列有两个以上独立来源。离线评测有效单元完成率是全部有效格子除以全部活跃规划格子（不含标为不适用的豁免格），按微平均算。83% 是 145 个格子里 120 个有效，改造前是 140 个里 94 个。分题型是对比 59/68、综述 33/37、事实 16/19、冲突 12/21。

  • 实验设计：改造前后两个版本跑同一套题，模型、搜索工具和预算上限保持一致。每次运行保存规划、格子、补查和反证的原始记录，指标由脚本从原始记录算出来，不手工改。
  • 质量评分：除了完成率，还用独立评分模型给整份报告打分，维度是事实准确、引用准确、完整性、来源质量和工具效率。评分模型和研究用的模型不是一个家族，每个运行评三次取多数，事实准确和引用准确都不低于 0.7 才算通过。证据不足时如实说明缺口不扣分，编造结论严重扣分。评分本身失败的运行单独列出，不计入报告评分的统计，格子完成率的分母始终是全部规划格子。
  • 怎么防刷分：分母用规划格子，风险是主控建表时少拆难查的格子。我加了两道约束，对比题统计实体覆盖率，看规划有没有漏掉题目点名的对象，评分模型按 3 条要点逐项判断有没有答到，少拆了完整性分会掉。
  • 没过的格子怎么归因：按四步看，关键证据有没有进召回，进了有没有被选中，选对了结论有没有写错，写对了有没有被 Verifier 误杀或放过。每一步都能从保存的原始记录里查到，所以改进时知道该动检索还是动校验。
  • 稳定性：同一版本在全量题上重复跑过几次，完成率都在八成上下，我报的是其中一轮，没有挑最高的那轮。
  • 还有一套健壮性评测：24 题，正常、证据缺失、来源冲突、故障注入各 6 题。它不看结论好坏，看流程对不对，比如证据不足时有没有编结论、补查是不是只动缺口格、旧执行者的回调有没有被拒、外部调用有没有重复。

    • 「为什么不用 LLM 当裁判判断事实对不对？」

      「检查点有明确的预期答案，规则匹配更稳定、可复现。规则判不了的交给人工复核，样本量不大，人工成本可以接受。」

7.5 工程类数据 ★★

  • 128 MB 单文件接入：在 -Xms512m -Xmx512m 受限堆参数下，用扫描版 PDF 和录屏视频跑 8 路 × 128 MB 并发上传并开启 GC 日志。对照组用整包 getBytes() 读入，能直接复现巨型对象分配和 Full GC。实验组前端分片直传 MinIO，Java 同步回调仅 Range: 0-4095 读前 4 KB 验魔数（0 MB 大文件穿境），异步阶段 1 用 8 KB 缓冲流式读取算 SHA-256 与 15 页微批解析，堆内存曲线平稳，没有巨型对象引发的 Full GC。
  • 断线续读与终态逐字一致：注入三类故障，浏览器断网几秒后恢复、生成过程中杀掉一个网关实例、离线超过 Stream 保留窗口后再回来。每次结束后把前端拼出的全文和 MySQL 终态全文逐字比对，同时检查事件序号连续、没有重复和跳号。
  • 长任务调度（职责 5）：单工作区连续提交超过 8 个产物任务，同时同工作区发起深度研究且其他工作区也在提交产物。观察四件事：消费者日志里有没有因处理超时触发的重平衡，单工作区在途产物任务有没有超过 8 个，同工作区深度研究独立 8 槽是否完全不受产物满槽阻塞，以及其他工作区的任务有没有被同分区前面的满槽任务阻塞。

08八、和项目挂钩的延伸八股

  • 「你的提示词是怎么调的？」（Prompt 三步评测驱动优化闭环） ★★

    「我按冻结评测集来调，不凭感觉改，分三步：

    ① 定结构契约，提示词固定分任务说明、数据围栏输入、硬规则、输出格式四块，结构化输出走受限解码，量纲错配与规则边界交代码一票否决。

    ② 放少量边界样例，重点选省略主语追问、隔轮回旧话题、只改格式等边界，每类一正一反不超过两个防照抄措辞。

    ③ 按错误样本回归迭代，每轮按失败根因归类，一次只改最大一类再跑全量回归，无退化才随版本号合入（见 04 篇 8.13）。」

  • 「怎么监控？告警怎么配？一个请求慢了怎么定位到哪一步？」（全链路可观测性与异步透传） ★★★

    「① 指标与症状告警，用 Micrometer 暴露 JVM、连接池、线程池、Kafka 滞后及补查率、Verifier 打回率、主库复核拦截数、第 2/6 段缓存命中率、检查点回补数，配 Prometheus 与 Grafana 按检索 P95 超阈值等可感知症状告警。

    ② 跨异步边界透传 traceId，HTTP 走请求头、Kafka 走消息头，InheritableThreadLocal 仅建线程复制一次在池复用下会串号，单层池配 TaskDecorator 提交时拷父快照、执行前先备份工作线程原 MDC 上下文并在 finally 按备份还原（原为空才清空，防 CallerRunsPolicy 误清空主线程 traceId），多层嵌套池用阿里 TransmittableThreadLocal 按 Capture-Replay-Restore 加 Java Agent 透传。

    ③ 排障案例，曾靠火焰图抓出融合后 30 条候选循环单查主库的 N+1 耗时，改为精排取前 6 后按去重资料 ID 走主库主键批量点查压回毫秒级（见 05 篇 12.6）。」

  • 「新增一种检索模式或产物类型要改哪些地方？Spring 的扩展点与循环依赖怎么工作？」（Spring 扩展点与三级缓存） ★★★

    「① 策略注入与启动自检，检索模式和渲染器实现统一接口，启动组装为不可变 Map 并校验无重无漏，新增类型只加一类。

    ② 核心扩展点与自动装配，BeanFactoryPostProcessor 实例化前改定义，BeanPostProcessor 初始化后生成 AOP 代理（同类自调用绕过代理致事务失效），Boot 3 读 AutoConfiguration.imports 配条件注解按需生效并让位自定义 Bean。

    ③ 三级缓存与双反证，一级存成品、二级存早期半成品或代理、三级 singletonFactories 存延迟工厂：去三级要么所有 Bean 违背生命周期提前造代理、要么裸对象与成品代理引用分裂，去二级则在 A→B→A 且 A→C→A 多路依赖下重复调工厂造出两个不同代理破坏单例，构造器循环连空壳都造不出需加 @Lazy（见 05 篇 12.7）。」

  • 「接 128 MB 文件时怎么确认内存没问题？堆内堆外泄漏与线上 CPU 100% 怎么排查？」（JVM 内存与 CPU 100% 排障） ★★★

    「① 堆内排查，512 MB 堆整包读 128 MB 超半个 G1 Region 直配老年代触发 Full GC，改 8 KB 流根治，若 GC 后老年代底线持续涨则导堆进 MAT 比对 Shallow 与 Retained Heap（如未清 ThreadLocal 强引用链拽住大对象）。

    ② 堆外排查，堆稳但进程 RSS 猛涨多源于直接内存、Netty 池化内存或压缩库 JNI C 堆，开原生内存追踪前后对比，JNI 层用 pmap 配 jemalloc 采火焰图，MinIO 流放进 try-with-resources。

    ③ 线上 CPU 100% 五步 SOP，先 top 定进程、top -Hp 找线程、转十六进制后 jstack 抓栈区分业务死循环或正则回溯还是 GC 飙高，留现场后止损（见 05 篇 12.8）。」

  • 「项目深度用了 Redis、Kafka 与 SSE，底层编码、零拷贝与万级长连接容量账怎么串？」（Redis / Kafka / OS 计网速记口诀） ★★★

    「① Redis 编码、Rehash 与迁槽，SDS <= 44B 走只读 embstr（取消对齐占 3B 的头加 16B 对象头与 1B 结束符凑 64B 缓存行，一改即转 raw），quicklist 串 listpack（取代 >= 254B 写 0xFE 五字节标志触发级联更新的 ziplist，靠尾部首字节 MSB=0 变长长度逆向定界），ZSet 超阈值转哈希加跳表，渐进式 Rehash 在快照期将负载因子提至 5，Cluster 迁完回 MOVED 刷路由、迁中回 ASK 配 ASKING 单次转向（见 01 篇 6.4）。

    ② Kafka 幂等、事务与截断防丢，单会话单分区靠生产者号加递增序号去重，跨分区写加提位点靠事务协调器与读已提交隔离，副本恢复靠 Leader Epoch 精准截断防 HW 异步滞后丢数据或分叉（见 05 篇 12.2）。

    ③ OS 与计网串联，epoll 红黑树加就绪链表支撑主从 Reactor，边缘触发 ET 不循环读则残留字节不会再次通知导致死等、循环读配阻塞句柄则抽空后最后一次读挂死整个单线程 EventLoop 故必配非阻塞读至重试信号，Kafka sendfile 配网卡分散收集达成 2 拷 2 切，HTTP/2 破同域 6 连接限制、单空闲 SSE 占 16～32 KB 万连接仅 160～320 MB（见 05 篇 12.9）。」
