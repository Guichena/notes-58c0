方案业界代表 / 典型实现怎么做优点缺点结论
纯 Python 单体FastAPI + LangChain / LlamaIndex 常见原型业务与 Agent 都在 Python 里生态最全、开发快事务、权限、版本、长任务恢复都要自己补，工程约束弱原型阶段合适
纯 JavaSpring AI、LangChain4j模型调用也放在 Java技术栈统一、事务能力强音视频、解析、评测等 AI 生态在 Python 更成熟不选
Python 任务队列Celery / RQWeb 层投递任务，Worker 执行简单好用任务状态与业务事务不在一起，长任务所有权难以严格保证不选
Java Host + Python Worker 采用多语言微服务的常见分工Java 做业务与状态，Python 做 AI 执行，经消息与回调交接各用所长；状态集中可审计跨语言契约要维护；多一跳网络采用

业务约束：一个人开发、要支撑长时间运行的研究和产物任务、资料与版本要可追溯；AI 侧依赖 Python 生态（解析、转写、模型 SDK）。

为什么选它：把需要事务和一致性的东西集中在 Java 一侧，Python 只做可重试的计算，任何一侧故障都能从数据库恢复。

放弃了什么：跨语言的接口契约和联调成本；部署上多一类服务。

什么时候换：AI 侧逻辑稳定、Java 生态的模型与工具支持足够时，可以把部分执行收回 Host；反过来，若业务变薄，也可以整体迁到 Python 并补齐事务层。

01可恢复的 Deep Research Agent

简历原文设计验证驱动、可恢复的 Deep Research Agent：针对开放研究易漂移、证据不足和长任务中断的问题，将研究过程抽象为 Table-as-State ，显式维护研究对象、待验证字段、Evidence 与结论，通过 Plan / Replan、Verifier 和受限反证持续纠偏；结合 Checkpoint 与引用审计支持任务断点恢复和结论逐项回溯。离线评测中，有效研究单元完成率由 67% 提升至 83%。
简历里的说法在设计里对应什么
Table-as-State研究状态是一张表：行是研究对象，列是待验证字段，每一格是一个研究单元
研究对象、待验证字段、Evidence 与结论每格独立保存候选、证据（支持 / 反驳）和判定
Plan / Replan先规划成表；只对缺口格局部重规划，有轮次和时间预算
Verifier逐格验证（规则短路在前、模型判定在后）+ 全局完成度检查
受限反证只做有预算的一次反证复查；预算内解决不了就转人工
Checkpoint每一波子任务结束写检查点，恢复时只重做未验证的格
引用审计报告里每条结论核对引文位置、归属、数字与否定极性
任务断点恢复数据库租约 + 心跳 + fencing，Worker 挂掉后被接管，旧结果写不进去

架构：研究生命周期

ReAct模型交替思考、调用工具、观察结果；简单通用，但长任务容易漂移、状态散落在上下文里只用于单格内部的临时推理
Plan-and-Execute 与 Replan先规划再执行，执行中发现计划不对再重规划；计划本身可能错规划成表，Replan 只针对缺口格，并受轮次与时间预算约束
Reflexion / 自我批判让模型检查自己的输出再修正；同一个模型自评有盲区Verifier 先用确定性规则短路，再交模型判定；模型不可用时绝不判“已验证”
检查点与持久化执行把长任务拆成可重放的步骤，每步结果持久化，崩溃后从最近一步继续每波子任务结束写检查点
租约与 fencing token锁会过期，持有者可能在过期后醒来继续写；用单调递增的令牌让存储拒绝旧写入（Kleppmann 对 Redlock 的经典讨论）领取时代际加一，回执带代际，数据库条件更新校验
CAS 与并发合并多个子任务并发写同一结构时，按版本条件更新防止后到覆盖先到格子级 CAS
引用核验 / NLI先做确定性检查（位置、归属、数字），再用模型判断“证据是否蕴含结论”引用审计不过的结论被修订或降级为“证据不足”

业界做法与优缺点

方案业界代表 / 典型实现怎么做优点缺点结论
ReAct 长循环 + Scratchpad通用 Agent 框架的默认形态模型自己决定搜什么，过程写进同一段笔记实现最简单、灵活状态无法结构化查询；中断只能重来；错误在笔记里自我强化不选
多视角大纲成文Stanford STORM多视角提问 → 大纲 → 分章节写适合维基式长文难以只重做某个对象的某个字段，完成率难定义借鉴“规划前拓宽问题面”
Planner + 并行研究员GPT Researcher、LangGraph 的开源 deep research 模板主 Agent 拆子问题，子 Agent 并行检索后汇总并行快子结果合并缺少格子级并发控制，后到覆盖先到借鉴并行
产品级 Deep Research各大模型厂商的深度研究产品长时间迭代搜索与浏览，生成带引用报告浏览深度强不开放状态与恢复机制，无法逐项回溯不可比
Table-as-State 采用本项目每格独立的候选、证据、判定；Host 唯一写者；检查点可量化完成率、可续跑、可回溯计划拆错表就错；叙事型综述不适合硬塞成表采用

长任务所有权：业界做法与优缺点

方案业界代表 / 典型实现怎么做优点缺点结论
Redis 分布式锁Redisson、Redlock带过期的锁 + 续期快、通用锁与业务库不是同一真源，锁易主后旧持有者仍可能写库不选
数据库行级租约 + fencing 采用本项目任务行上记录持有者、到期、代际，回执条件更新校验所有权和账本同库，提交即校验比 Redis 慢；心跳太接近租约时长会误判采用
协调服务租约ZooKeeper / etcd 的 lease 与会话由协调服务管理所有权强一致、成熟多一套集群，仍需 fencing 才能保护存储不选
持久化工作流引擎Temporal（活动心跳与超时）、LangGraph 检查点引擎管理重试、心跳和状态开箱即用的恢复能力引擎状态与格子账本是两套真源，需要对账跨天等待多时再换

业务约束：开放研究动辄几分钟，Worker 可能崩溃或长 GC；结果要能逐条回溯；只有 MySQL、Kafka、Redis 可用，没有工作流引擎。

为什么选它：研究要能量化完成率、能断点续跑、能拒绝晚到写回，这三件事都要求状态是可查询的格子，并且所有权和账本在同一个库里。

放弃了什么：开放网页上的浏览深度不与产品级 Deep Research 比；计划阶段要多做一步“建表”。

什么时候换：叙事题为主时加重文章化路径；等待人工成为耗时大头时引入工作流引擎管理等待，格子账本仍留在库里。

02任务感知的 QA / Note / Wiki 知识链路

简历原文构建任务感知的 QA / Note / Wiki 知识链路：针对问答、资料精读和长期知识沉淀对相关性与上下文组织方式的不同需求拆分三条链路：QA 采用 BM25 + Vector + RRF + Rerank ，Note 采用资料级召回与连续原文窗口，Wiki 通过页面关系与来源回链组织长期知识，避免统一链路在任务语义差异下的效果损耗。
简历里的说法在设计里对应什么
问答、资料精读和长期知识沉淀的不同需求查事实要准确片段；精读要连续原文；知识沉淀要跨资料组织
QA：BM25 + Vector + RRF + Rerank两路召回、按名次融合、精排，再判断证据是否足够回答
Note：资料级召回与连续原文窗口先决定读哪几份资料，再在资料里锚定命中处、按原文顺序扩成连续窗口
Wiki：页面关系与来源回链知识页之间的链接参与排序；每页都能回到来源资料，资料删了页面跟着收缩
避免统一链路的效果损耗三条链路共用权限与证据预算，但召回、融合和证据形态各自不同

架构：三条链路

PageRank / 个性化 PageRank按链接结构传播重要性；个性化版本从种子节点出发并以一定概率重启Wiki 在种子页面周围的小子图上做个性化 PageRank
检索评测Recall@k / Hit@k / MRR；离线回归集防止改动退化三条链路各自的回归集

业界做法与优缺点

方案业界代表 / 典型实现怎么做优点缺点结论
统一向量 TopK最常见的 RAG 入门做法所有任务都取最相似的若干切片实现最简单编码类查询召回漂移；精读时片段有空洞，模型会脑补不选
Hybrid 检索 + RRFElasticsearch / OpenSearch 混合检索、Weaviate 等关键词与向量两路召回后融合兼顾精确与语义只解决“找得到”，不解决证据形态用于 QA
父文档 / 句窗口检索LlamaIndex 的父文档、句窗口、自动合并检索用小块命中，返回更大的父块或周边句子改善上下文连续性仍以单个片段为中心，跨资料时版本归属易混借鉴，用于 Note
GraphRAG微软 GraphRAG抽实体关系建图、社区摘要，回答全局问题适合跨文档的全局问题建图成本高、抽取噪声大，个人资料规模小不划算不选
知识页 + 链接 + 来源回链维基式个人知识库（双链笔记的思路）页面是检索单位，链接参与排序，每页回链到来源长期可维护、可追溯冷启动时链接稀疏用于 Wiki
按任务拆三条链路 采用本项目按任务选择召回、融合与证据形态每种任务都用合适的证据形态维护三套链路和三套回归集采用

业务约束：资料里既有专名、公式、编号，也有口语化提问；用户既要快速问答，也要通读长文，还要长期沉淀；规模是个人资料量级，标注数据少。

为什么选它：三种任务的“好证据”本来就长得不一样，统一链路只能在中间妥协；RRF 不需要标注数据来校准分数，适合小规模。

放弃了什么：三条链路的维护和评测成本；只有一路能命中的专名题在 RRF 下会吃亏。

什么时候换：积累到足够的相关性标注后，用学习式排序替代 RRF；跨十几份资料做综述成为主场景时，在资料级召回之上加一层综述编排。

03Kafka 异步资料处理流水线

简历原文搭建异步资料处理流水线：针对大文件同步解析阻塞请求、资料处理链路耗时较长的问题，将解析、切片、向量化和索引构建拆分为 Kafka 异步任务，并通过任务幂等与失败恢复保障长链路可靠执行，支持 128 MB 单文件异步接入，避免大文件处理占用业务请求链路。
简历里的说法在设计里对应什么
大文件同步解析阻塞请求上传接口只落资料版本和投递意图就返回
解析、切片、向量化和索引构建拆分为 Kafka 异步任务四个阶段四个 topic，阶段之间只传资料快照 ID，各自独立扩消费者
任务幂等每个阶段按“资料快照 + 阶段”去重；向量化按批次落库，重复只补缺口
失败恢复Outbox 派发退避重试与死信；消费失败进死信 topic；租约过期的批次可被重领；索引失败自动重试
128 MB 单文件异步接入单文件上传的配置上限

架构：四阶段流水线

重试 topic 与死信阻塞重试会卡住整个分区；把失败消息转到重试 / 死信 topic，不阻塞后续消息短重试后进死信 topic，业务重试交给任务层

幂等消费去重表 / 唯一键 / 状态机条件更新按资料快照 + 阶段去重；向量批次唯一

业务约束：单文件最大 128 MB，解析和向量化可能耗时很久；个人项目资源有限，组件只有 MySQL、Kafka、ES、MinIO；资料一旦接收就不能丢。

为什么选它：Outbox 保证“已接收就一定会被处理”，分阶段让慢的阶段（向量化）可以单独扩容和重试，幂等把至少一次变成业务上的恰好一次。

放弃了什么：接受重复投递，所有阶段必须幂等；多一张表和轮询扫描；端到端延迟比同步处理高。

什么时候换：派发延迟从秒级漂到分钟级、或扫描压力持续高于业务写入时，把轮询换成 CDC；表结构和消费端幂等键都不用改。

05Context 与长期 Memory

简历原文设计 Context 与长期 Memory 机制：针对长会话全量回放导致 Token 膨胀、自动记忆容易污染后续事实的问题，采用 Topic-aware Window + 增量摘要 压缩长会话上下文，通过候选提取与门控晋升沉淀长期 Memory，并将用户偏好与资料 Evidence 分层隔离。相比全量历史回放，平均输入 Token 降低 34%，关键事实检查通过率 92%。
简历里的说法在设计里对应什么
Topic-aware Window会话按话题切分（词项覆盖度与向量余弦融合，显式“回到 / 改聊”优先），当前话题保留最近原文
增量摘要窗口之外的内容由该话题的增量摘要覆盖，摘要与窗口共用一条边界
候选提取从对话和反馈中抽出的只是候选，归入语义槽位
门控晋升证据可信度（Beta 后验）、证据量、效用、风险四道门都过才自动生效，否则让用户确认
用户偏好与资料 Evidence 分层隔离记忆只影响语气、结构和要避免的写法；事实和引用只来自资料证据

架构：上下文编译

知识点核心要点落在本设计哪里
上下文窗口与成本输入 Token 随轮次线性增长，成本和时延一起涨；长上下文里中间部分更容易被忽略（lost in the middle）只保留当前话题的原文，其余压成摘要
滑动窗口 / 摘要缓冲最近 N 轮原文 + 更早内容的摘要，是最常见的会话记忆方案在此基础上按话题而不是按时间切窗口
话题切分按相邻内容的相似度落差找边界（TextTiling 思路），再结合显式话语标记词项覆盖度 + 向量余弦融合，显式“回到 / 改聊”优先
记忆分类短期（会话）与长期；情景记忆（发生过什么）与语义记忆（偏好、事实）长期记忆只存偏好类，不存资料事实
贝叶斯更新：Beta-Bernoulli支持 / 反对证据分别累加到 α / β；均值表示可信度，方差表示证据是否足够均值管可信、方差管证据量
记忆投毒错误或被注入的内容一旦写入长期记忆，会持续影响后续回答门控 + 用户确认 + 偏好与证据分层

方案业界代表 / 典型实现怎么做优点缺点结论

自动记忆抽取Mem0 等记忆层从对话中抽取记忆并增删改自动化程度高抽错就长期污染借鉴抽取，加门控

话题窗口 + 增量摘要 + 门控记忆 采用本项目按话题压缩上下文，记忆门控晋升，偏好与证据分层省 Token 且保留关键事实；记忆错了不改事实话题切错会丢历史；阈值是初始值、未大样本校准采用

业务约束：研究和精读的会话很长、经常在几篇资料之间切换话题；回答里的事实必须可引用；记忆一旦写错，个人用户很难察觉。

为什么选它：按话题压缩比按时间压缩更符合实际对话结构；把记忆限定为“表达偏好”，事实只来自资料证据，记忆错了最多影响表达方式。

放弃了什么：话题切分本身可能出错；一部分本可自动生效的记忆需要用户确认；摘要可能压掉数字和限定语，所以 −34% 必须和 92% 一起看。

什么时候换：跨会话引用很久以前的内容成为常态时，加一层长期记忆检索；回放集上切分错误率升高时，把切分全面交给模型并接受更高成本。

指标口径

简历数字定义（公式）不代表什么
−34%降幅 = 1 − Context 编译后平均每轮输入 Token ÷ 全量回放平均每轮输入 Token；同一批长会话离线回放，同一 Token 估算器，只算对话历史不含输出和摘要成本，不是线上省下的钱
92%关键事实检查通过率 = 压缩上下文下答对的关键事实检查数 ÷ 检查总数（数字、截止日期、限定条件等后续会用到的事实）；先关键词规则、再人工判定不是整体回答正确率
