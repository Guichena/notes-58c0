01整体架构

模型不参与告警判定、基础触达和正式工单写入。

02模块 ① 通知可靠触达

解决：落库与发布不一致、重复投递、渠道超时结果未知。

故障窗口手段
提交后未发出Outbox + 定时兜底扫描
MQ 未真正入队Publisher Confirm / Return
重复投递消费账本 + 处理轮次
渠道超时结果未知稳定请求号 + 对账
持续失败退避重试 → 死信 → XXL-Job 补偿

03模块 ② 分级治理与流量保护

解决：设备抖动和重复催办形成通知风暴。

级别去重合并限流降级时
P0— 不合并预留配额始终送达
P1— 不合并令牌桶保留
P2 / P3● 窗口内合并● 令牌桶先合并后延迟

04模块 ③ 隔离式告警分析 Agent

解决：基础告警缺少现场处置依据；AI 故障不能拖累告警。

校验层检查什么失败时
结构输出符合诊断卡结构重试一次后降级
引用回链每条结论指向真实证据片段删去无依据条目
事实回填设备、时间等字段与快照一致以快照为准回填
危险建议 Guardrail不输出高风险操作建议拦截并标记

05模块 ④ HITL 维修工单 Agent

模型只起草，人决定；幂等收在我方。

并发 / 重复风险防线
两人同时审批版本号 CAS，只有一个成功
审批成功但执行丢失审批结果与执行意图同事务
建单超时重试稳定请求号 + 回查
回查仍不确定转人工，不自动重建

06关键设计取舍

问题备选选择理由代价
写库与发消息一致XA / CDC / 提交后直接发本地事务 + Outbox只需最终一致，简单可观测，不加组件多一张表和 Relay 扫描
消息中间件Kafka / RocketMQRabbitMQ任务型消息，需要逐条确认、死信、延迟重试吞吐上限低于日志型 MQ
外部重复调用唯一键 / 落库后 ACK稳定请求号 + 未知对账唯一键管不住外部系统的重复要实现对账查询
向量检索专用向量库 / ESPostgreSQL + pgvector规模不大，一库做全文、向量、结构化过滤超大规模需迁移
补偿调度Temporal 等工作流引擎XXL-Job分钟级扫描对账，现成调度够用复杂编排表达力弱
AI 与主链路同步调用模型持久化任务旁路模型不可用或积压不影响基础告警诊断有延迟
工单写入Agent 直接建单人工审批后执行写操作有外部副作用，必须可追溯、可拒绝多一步人工
