00整体架构：主链路与旁路

架构总览

依赖挂了会怎样

MySQL 是事实源；其他组件挂了只降级、不丢事实。每个依赖都写清“影响 → 降级 → 恢复与发现”。

依赖挂了的影响降级恢复与发现
MySQL 主库受理返回 503，上游带同一幂等键重试；消费退避独立应急通道发送 P0切换后按上游受理清单对账（异步复制 RPO 不为零）
RabbitMQ 集群受理照常，消息表积压P0 应急直发，复用同一发送记录协议恢复后 Relay 补发；监控最老待发布年龄
Redis去重和限流失去加速去重回库；令牌桶切本地保守额度，优先 P0/P1档位按收紧档初始化
调度中心（XXL-Job）普通重试、未知对账、全局对账暂停P0/P1 的应用内扫描不受影响恢复后按到期时间继续扫；“未知”最老年龄告警
模型 / 检索库诊断卡不可用只输出事实摘要，不影响基础告警分析任务持久化，可重放
外部渠道 / CMMS发送或建单结果不确定备用渠道；结果“未知”进入对账按请求号查询收口

01通知可靠性闭环

简历原文设计通知可靠性闭环：针对任务落库与 MQ 发布不一致、重复投递、渠道超时结果未知等问题，采用 Transactional Outbox + Publisher Confirm/Return 保证已受理任务可恢复发布；消费侧以数据库账本和处理轮次防重复执行，调用渠道前持久化稳定请求号，超时归为“未知”先对账再决策，结合退避重试、死信隔离与 XXL-Job 补偿收敛异常任务。压测叠加进程强杀，89,982 条已受理任务 100% 最终发布，最老待发布延迟峰值控制在 8.6s；故障演练下 5.4% MQ 重投均被幂等拦截，重复通知 0 次。

端到端流程

数据模型

四张表各回答一个问题、各有自己的写入者：Relay 只碰 Outbox，消费者主要碰账本和发送记录。主键用自增 BIGINT 保证顺序追加写，对外的任务号、事件号、请求号用 ULID（26 位、时间有序、不暴露自增量）；时间一律用数据库 NOW(3)，不信应用服务器时钟；扫描类索引都以 status 开头；不用外键，引用完整性由应用和对账任务保证。

表回答什么问题写入者典型状态变化
message_task这次通知最终走到哪一步受理接口、消费者、重试 JobACCEPTED → SENDING → SUCCESS / RETRY_WAIT / UNKNOWN / DEAD_LETTER
outbox_event这条事件发布到 Broker 了吗受理事务插入，Relay 推进PENDING → PUBLISHING → PUBLISHED
processed_event这个消费组接管 / 完成该事件了吗消费者PROCESSING → DONE
channel_send_record对外部做过什么动作、用的什么请求号、结果确定吗消费者、对账 JobINTENT → IN_FLIGHT → 四态结果

状态机

受理与发布：逐步处理与参数

  1. 受理：鉴权、模板和值班快照在事务外准备；事务内只做本地写入：任务行、Outbox 行、治理决策。同键同载荷返回原任务，同键异载荷返回 409。提交成功才返回 202“已受理”。
  2. 快路径：事务提交后回调把消息行 id 交给本进程发布线程，毫秒级发出；兜底：每秒扫描一次 status=PENDING 且到期的行（小批次，例如 100 行），进程挂了由任一存活实例捞回。
  3. 领取：先拿未决发布许可（每个实例同时等待 Confirm 的数量有上限，P0 单独一份），再条件更新 PENDING→PUBLISHING，影响 1 行才发布；同时写发布尝试号和 Confirm 截止（例如 5 秒）。
  4. 发布：mandatory 发布，同一次发布既拿到 Confirm ACK 又没有 Return（不可路由）才置 PUBLISHED；回写带 publish_attempt_id 条件，恢复后第二次发布的迟到回调影响 0 行。
  5. 背压：Confirm 回写、超时看门狗、发布异常三条路径都会释放许可，保证“每次发布只释放一次”，否则上限失效、快路径和扫描一起停住。
  6. 恢复：超过 Confirm 截止仍停在 PUBLISHING 的行由截止扫描放回 PENDING；Broker 已收但本地未回写会重复发布，由消费侧账本吸收。

六个故障窗口

宕机位置库里留下什么谁恢复必须避免
受理提交后，Relay 未领取PENDING任一存活实例的兜底扫描把“已受理”说成“已进 Broker”
领取提交后，publish 前PUBLISHINGConfirm 截止 / 租约扫描放回只扫 PENDING，行永久卡住
Broker 已接收，本地未回写仍是 PUBLISHING恢复后重复发布下游没有幂等
渠道已受理，结果事务前宕机发送记录 IN_FLIGHT，请求号已存按请求号查询 / 对账 / 人工因“没有成功记录”而重发
结果已提交，ACK 前宕机任务有结果，账本 DONE重投后读账本直接 ACK再调一次渠道
旧执行者停顿超租约后复活账本已是新的处理代次只允许当前代次收口旧结果覆盖新状态

消费三段事务：账本、处理轮次与稳定请求号

重复来源典型原因手段
同一事件被重投Broker 重投、Relay 重复发布（事件号相同）消费账本唯一键 (tenant_id, event_id, consumer_group)，插入成功才拿到处理权
旧事件覆盖新状态任务重试生成新事件号，旧事件仍在路上任务上的重试代次；事件代次比任务旧就按过期收口
外部副作用重复渠道已执行、本地结果未提交就宕机调用前写发送记录（IN_FLIGHT + 稳定请求号），恢复者看到 IN_FLIGHT 去对账而不是重发
  1. T1 抢处理权：INSERT 账本（PROCESSING, epoch=1, 租约）。唯一键冲突就读已有状态：DONE 直接 ACK；PROCESSING 且租约未过期就放弃；租约过期则条件更新接管，epoch 加一。
  2. T2 准备动作：校验账本仍是我的 epoch 且租约有效，校验任务的 retry_generation、状态、接收人和告警仍有效；INSERT 或读取发送记录（稳定请求号 + 渲染后内容哈希），原子标记 IN_FLIGHT，任务推进到 SENDING。
  3. 事务外调渠道：带稳定请求号和冻结的载荷；HTTP 客户端自动重试关闭，重试只由业务决定。
  4. T3 收口：结果、任务状态、账本 DONE 同一事务提交，所有写都带 epoch 条件，旧执行者的写影响 0 行；提交后才 ACK。
  5. 参数：消费租约 30 秒、续租 5 秒、恢复扫描 5 秒；prefetch 普通队列 20、P0 10、分析入口 50（控制未 ACK 数，不等于业务并发）。

超时归为“未知”：先对账再决策

渠道结果分四态：成功、可重试、不可重试、未知。连接超时和熔断拒绝属于“明确未执行”，可以切备用渠道；读超时、连接中途断开、无法判断的 5xx 一律归“未知”。错误码到四态的映射放在适配器配置里，契约没说清的错误码默认按未知处理。未知由 XXL-Job 每分钟扫到期的 UNKNOWN 发送记录，按渠道能力处理，查询有次数上限，超限转人工。

渠道已验证能力未知后如何处理
支持同请求号原子幂等，且有效期覆盖恢复窗口查询优先；契约允许时同号重试，不换载荷
能查询，但未证明原子幂等查到成功补登记；查不到不直接证明没执行
既不能可靠查询，也不支持幂等停自动重发，转人工；不能承诺任意故障下无重复且必达

退避重试与死信隔离

  1. 业务重试不用 MQ 重投：MQ 重投是“同一事件再交付一次”，适合消费者崩溃；“限流了 30 秒后再试”是业务决定，有自己的次数、间隔和截止时间。
  2. 消费者只写 RETRY_WAIT 和下一次时间，然后 ACK，不在消费者里创建新消息；唯一的重试 Job 负责创建重试。
  3. 重试事务：锁住任务，确认仍是 RETRY_WAIT 且到期，检查截止时间和次数；代次加一、状态回 ACCEPTED，同时插入新事件号的 Outbox，业务键 notify/{taskId}/{generation} 唯一，两个 Job 实例并发创建只有一个成功。
  4. 为什么换事件号：旧事件号在账本里已经 DONE，同号再发会被当成重复投递直接 ACK。渠道请求号不换：它代表“给这个人发这条通知”这个逻辑动作，渠道去重才生效。
  5. 退避：限流类 30 秒起步、指数增长、上限 5 分钟，加随机抖动；到期时间用数据库时间计算；受通知截止约束，P0 剩余时间不够就直接升级备用渠道或人工。
  6. 扫描精度：P0/P1 由应用内每 5 秒扫一次（时限只有 2 / 5 分钟），普通通知由 XXL-Job 每分钟扫一次；都走 (status, next_retry_time, id) 索引。

XXL-Job 补偿与全局对账

XXL-Job 只跑分钟级、不紧急的补偿；秒级的 Relay 扫描、P0/P1 重试、续租放在应用内调度线程，核心链路不依赖调度中心可用性。多实例用分片广播只为分摊扫描量，正确性靠每一行的条件更新：分片重分配的瞬间两个实例扫到同一行，也只有一个 CAS 成功。阻塞策略统一“丢弃后续调度”，错过的调度不补跑——扫描的是“当前到期的业务行”，下一次扫描自然能捞到。

补偿任务执行器做什么正确性靠什么
UNKNOWN 发送记录对账触达按渠道能力查询；超次数转人工发送记录条件更新 + 请求号
普通通知 RETRY_WAIT 重试触达代次加一 + 新事件号 Outbox业务键 notify/taskId/generation 唯一
摘要窗口 flush触达到期窗口生成一条摘要通知窗口 + 代次唯一
升级任务触发触达到期升级前查确认、恢复、新轮次升级任务条件更新
全局对账触达五项跨表检查，只读，发现即告警不改业务状态
CMMS 建单未知对账、关单补偿分析按外部参考号查询执行意图条件更新

全局对账是最后一道防线：只发现、计数、告警，必要时生成待处理工单，不改业务状态。轻量检查每小时一次，全量 T+1 每天凌晨一次，都走状态加时间索引并限制时间窗。

检查项发现了说明什么动作
已受理但没有 Outbox受理事务有 bug（理论上必须为 0）告警
Outbox 已 PUBLISHED 超过 10 分钟，但没有任何消费账本Broker 侧丢消息或路由错误：队列误删、绑定写错，Publisher Confirm 覆盖不到按原 event_id 重新发布（消费者幂等，安全）
发送记录 IN_FLIGHT / UNKNOWN 超过 30 分钟对账任务卡住或渠道查询能力失效告警
任务 SENDING 超过 10 分钟消费者租约恢复失效告警
任务 SUCCESS 但发送记录不是 SUCCESS结果事务有 bug告警

只用数据库唯一键账本按事件号唯一插入，插成功才处理挡不住“渠道已执行、本地未提交就宕机”，恢复时会再发一次最简单留有外部重复窗口
唯一键 + 调用前写发送记录 采用唯一键之外，调用前持久化 IN_FLIGHT 和稳定请求号；未知结果走对账部分未知要人工确认；不能同时承诺不重复和必达多两段短事务，每段毫秒级；要实现对账查询采用
Redis SETNX先占 key 再处理主从切换或过期丢 key 就放过重复；占 key 后写库失败要补删 key最快不能作为最终判断
一个大事务包住 HTTPT1、渠道调用、T3 放同一事务回滚撤不回已发出的 HTTP；渠道慢几秒就占住连接，风暴时连接池被打满实现直观不可行

重复投递在 RabbitMQ 里一定会发生，外部渠道又不在事务里，所以只有“调用前留证据 + 未知不盲发”能把外部重复也收住。量级上 MySQL 唯一键点写完全够用，不需要 Redis 做最终幂等。

代价是三段事务和一套对账；账本保留期必须大于 MQ 最长重投窗口加对账周期。量涨后先按时间归档已完成账本，再按事件号哈希分表，判断仍留在数据库。

端到端流程

告警轮次与版本：去重的身份是什么

“设备 + 告警码”只能识别同一类问题，识别不了它处于什么阶段：9 点异常、9 点半恢复、10 点再异常，10 点那次是新的一轮，值班人必须知道。所以去重身份是告警轮次：一轮从首次触发开始，经过持续、升级、人员确认，到恢复结束；恢复后再触发就是新一轮。轮次号和单调版本号由上游给，平台只校验和保存，乱序时按版本比较，不依赖 MQ 顺序，也不用服务器收到时间排序。

输入序列应当得到的结果
普通异常 → 严重升级升级通知不被普通异常的窗口压制
恢复 → 旧触发晚到保持恢复，不重新打开同一轮
已恢复 A → 同码新异常 BB 按首次处理
重复恢复同恢复操作幂等，不连续发多张恢复卡
人员已确认 → 定时升级到期检查当前确认状态，取消未执行的升级动作

去重决策事务

  1. 决策表的唯一键就是去重维度：租户、告警轮次、语义状态（严重度、通知目的）、接收对象。不把每个上报序号塞进去，否则每次都是新 key、压不住同状态噪声。
  2. 受理事务里先 INSERT 决策窗口行，唯一键冲突则按唯一键 SELECT … FOR UPDATE 锁已存在的行（或 INSERT … ON DUPLICATE KEY UPDATE 一条语句完成创建和加锁）。不对不存在的键先 FOR UPDATE：RR 下拿的是间隙锁，并发 INSERT 会死锁。
  3. 命中有效窗口、且不是必须直发的状态变化 → INSERT suppress_record（引用已发出的 taskId），返回“已压制”；否则 INSERT 任务 + Outbox，更新决策指向新 taskId，返回“已受理”。
  4. 提交后才把决策写进 Redis 缓存；缓存写失败不撤销库结果，只是下一次多查一次库。Redis 里的每一个命中都必须能指向库里一条真实决策。
  5. 策略矩阵存 MySQL 配置表，按租户、告警类型、优先级配置，每次修改生成新的 policy_version；应用每 30 秒检查版本号、变化才重载。新规则先影子运行，确认首次 / 升级 / 恢复零误压后再启用，出问题一键切“全部直发”。

摘要合并：1000 次催办发多少条

答案取决于落进几个摘要窗口，而不是“超过 N 次就发摘要”——那样第 4 到第 1000 次每次越阈都发一张摘要，摘要本身成了新的风暴。两层设计：滑动日志计数回答“最近一段时间有效催办几次”，持久化窗口负责“一个窗口只发一次”。

出口 Redis Lua 令牌桶

企业微信和短信网关对每个账号都有调用频率配额，超了返回限流，进入重试又加剧拥堵。令牌桶有两个参数：容量是允许的突发量，补充速率是长期平均额度——告警天然是突发的，令牌桶允许在配额内一次发出，而漏桶会强行排成匀速、P0 也得排队。

key 作用域示例形式为什么
去重缓存notify:dedup:{tenant}:{episode}:{state}:{purpose}:{recipient}区分租户、告警轮次和通知对象
催办窗口notify:urge:{tenant}:{episode}:{purpose}计业务命令，不计传输尝试
渠道总桶notify:bucket:{channelAccountId}:total额度属于真实账号，不是“企业微信”这个渠道名
单元子桶notify:bucket:{channelAccountId}:tenant:{tenant}:unit:{unit}在账号总额度内防止一个单元的风暴耗光配额
治理档位notify:policy:{tenant}:{channelAccountId}一个园区故障不误降级其他独立账号

多个桶要在一个 Lua 里原子扣减，必须落在同一个槽：令牌桶用 {渠道账号} 做 hash tag，让总桶和子桶同槽；去重 key 不需要进同一个 Lua，上 Cluster 时去掉大括号按全名散开，避免一个园区的 key 全落一个热点分片。

P0 全链路预留：领取、执行与渠道配额

按积压滞回降级

  1. 档位存储：Redis HASH 里存 state、version、observed_at；切档用 Lua 做真正的 CAS：只有预期版本匹配、且采样时间不比当前旧才写入。早期写的“GET → 判断 → SET”不是 CAS，两个实例并发判断会互相覆盖。
  2. key 丢失：不默认恢复 NORMAL，按保守的 TIGHTEN 初始化。
  3. 滞回不是 P0 的保护：它等积压持续一段时间才触发，那时 P0 的两分钟可能已过去一半；P0 每条单独检查 deadline_at − NOW()，不等全局档位。

数据模型与状态机

草稿、执行、案例拆成三个独立对象，各有状态机，通过事件串联——混在一条状态机里，“已批准但建单失败”“已建单但通知失败”“已关单但案例审核驳回”这些组合状态会爆炸。

字段责任与低置信度规则

字段责任方约束
标题、故障现象、观测整理、疑似原因模型辅助必须来自当前诊断卡或已授权材料；原因写成“可能”并挂证据
检查项、SOP 引用模型选择 ＋ 代码校验限定在本轮证据和受控检查项中，校验适用于当前设备和工况
设备身份、告警轮次结构化事件自由文本不能改主体
优先级、SLA、班组、审批角色确定性规则优先级 = 告警等级 × 设备关键度 × 是否影响产线 查表；SLA 由优先级决定；班组来自资产台账；规则表有版本
正式建单许可授权审批人绑定看到的具体 revision 和载荷
CMMS 请求、重试与对账确定性执行器模型不持有建单工具和令牌
确认根因维修事实与人工确认草稿阶段没有这个字段，只有“疑似原因”

不用模型自报的 0–1 置信度——它和实际正确率几乎不相关，错的内容也常说 0.9；token logprob 也不是业务正确性。改为六条可解释规则逐字段打标：

规则触发条件标记
证据缺失字段（如疑似原因）没有关联任何证据编号无依据
依据只来自案例只有历史案例支持，没有 SOP 支持仅经验参考
检索质量低关联证据的 rerank 分数低于阈值，或是迭代扫描 / 放宽排序后才找到依据相关性弱
型号不完全匹配依据适用于同系列其他型号型号近似
数据质量问题关键测点缺测比例超过 20% 或质量码异常数据不完整
与规则冲突疑似原因不在该告警码的原因类别映射里（如温度告警给出接线松动）原因类别异常

审批页上带标字段旁边是黄色提示和原因；带标字段必须逐个点“已确认”或修改后，“批准”按钮才可用。阈值按“标记字段修改率”调，目标是大部分草稿只有零到两个标记，避免标记泛滥没人看。

审批事务：版本 CAS 与执行意图同事务

审批是一个事务三步：带版本号、参数摘要、状态和截止时间的条件更新草稿 → 插入唯一执行意图 → 写审计；影响行数不为 1 就整体回滚。审批人从登录态取并重新校验权限，审批命令 ID 唯一，重放只返回原结果。截止判断写在审批 SQL 里，不依赖定时任务；过期绝不自动批准。会签按同一 revision 收集全部必需角色，先锁草稿行串行收敛到一条执行意图。
