# JVM运行机制垃圾回收与故障诊断面试手册

# JVM运行机制、垃圾回收与故障诊断面试手册

回答 JVM 问题，核心是把“代码怎么运行、资源放在哪里、垃圾怎样回收、问题如何定位”讲成一条因果链，再用具体条件和证据解释取舍。

先说清讨论口径。Java 规范里的运行时数据区、某个 HotSpot 版本的实际布局、某种收集器的实现策略，是三个层次。下面默认讨论 Java 21 的 HotSpot；遇到 CMS、旧版默认收集器或版本变化，会单独说明。这个学习口径不能代替项目实际使用的 JDK 版本和启动配置。

回答时可以分三层展开：第一层用一句话给结论；第二层说明触发条件、执行过程和失败边界；第三层放进业务场景，讲清为什么这样选、付出什么代价、怎样验证。比如“GC 停顿变长”只是现象，要继续区分是否同一种事件、是否同一统计口径、哪些阶段耗时增长，以及业务线程、CPU 配额和内存压力在同一时间窗口里发生了什么。

涉及项目，先讲自己确实做过的链路，再讲有条件的设计推演。文件接入能力不等于 JVM 堆预算，累计 GC 时间不等于请求尾延迟，一次小实验也不能直接推出生产收益。能把业务对象的生命周期、并发数量、缓冲和队列上限、观测证据与回滚办法说清楚，比背一组参数更有说服力。

## 这册可以怎样复习

把 JVM 学成“代码进入运行时、对象占用资源、回收器回收、证据指向根因”的连续过程。排错时先确认哪一类资源出了问题，再讨论参数或收集器。

### 第一轮：建立运行和内存地图

- 5 运行时数据区与进程内存预算 → 8 直接内存和缓冲区生命周期

### 第二轮：从对象存活走到回收选择

- 对象存活、GC Roots 与常量引用 → 强软弱虚引用与资源清理 → 三色标记、并发屏障与安全点 → 回收算法与完整 GC 口述

### 第三轮：用证据复述一次诊断

- 运行时证据与监控指标 → GC 突然变慢与频繁 Full GC 的排查 → 内存泄漏、OOM 与资源边界 → 从分配热点与保留根定位代码 → 带证据和取舍讲调优案例

从暂停、分配速率、存活集和进程内存变化建立假设，区分正常高占用、泄漏与资源上限。沿 GC 日志、线程/堆证据找到保留根或分配热点，再比较改动前后相同负载的结果；放大堆或换收集器不是默认根治。

### 怎样算学会了

重点练习“现象是什么、哪份证据改变了判断、为什么这样改、还有什么代价”。类身份、加载隔离、对象细节、版本迁移与所有诊断实现仍有各自的完整阅读位置。

## 第一部分：JVM 运行时与内存

理解 JVM，最有效的主线是跟着一次方法调用走：类怎样被找到并初始化，字节码怎样执行，对象怎样获得空间，引用怎样延长对象和类的寿命，以及这些工作怎样消耗整个进程的资源。本篇先建立运行链，再分别展开类、执行、对象、字符串和直接缓冲区。语言和虚拟机规范负责解释可观察行为；涉及物理布局、编译器和分配路径时，以 HotSpot 21 为基线，历史版本和后续版本单独说明。

### 1 JVM 负责什么以及怎样串起运行链

JVM 接过编译后的类文件，负责把类加载进来、检查并连接好，再执行代码、分配对象和管理运行时资源。Java 等语言共用这套执行契约；不同操作系统和处理器的差异，由各平台的具体 JVM 实现适配。

常见问法有“介绍一下 JVM”“JVM 的结构是什么”“为什么 Java 要先编译成字节码”“为什么需要 JVM 这一层”。可以先从三个方面回答，而不是直接罗列垃圾收集器名称。

#### 从源码到进程分别由谁负责

第一层是语言和编译器。Java 语言规定类型检查、异常、表达式求值和并发等语义；javac 通常把源码编译成 class 文件。class 保存的不只是指令，还包括类型、字段、方法、常量池和属性等信息。它是平台无关的二进制格式，不是直接交给任意 CPU 执行的机器码。其他语言只要能生成合规类文件，也可以利用 JVM。

第二层是 JVM 与类库。加载器找到或生成类的二进制表示，JVM 建立运行时类型，进行验证、准备和解析，在需要时执行类初始化。随后，解释器或编译后的代码执行方法，运行时协助对象分配、异常处理、同步和垃圾回收。标准类库提供文件、网络、集合等接口；“类库负责业务可用接口”和“虚拟机负责执行语义”有分工，二者共同构成应用运行环境。

第三层是操作系统与硬件。通常启动 java 命令后，操作系统运行一个包含 JVM、本地库和应用代码的进程，为它提供虚拟地址空间、线程调度、文件和网络能力。JVM 不是另一个替应用运行的操作系统，也不意味着每条 Java 指令都会陷入内核。普通计算通常在用户态完成，需要系统能力时才通过运行时和本地接口进入相应路径；实际内核切换取决于操作及平台实现。

#### 用一次对象调用串起来

假设应用第一次执行 `new Parser().parse(data)`。JVM 可能先查找 Parser 的定义、建立类元数据并完成必要的链接；若它尚未初始化，则按规则处理父类、相关接口和静态初始化。实例创建获得空间并建立初始状态，构造过程填充字段。调用 parse 时，逻辑栈帧承载参数、局部值、操作数和返回状态，接收者 this 指向实例。方法可能先解释执行，成为热点后进入编译代码。

parse 返回以后，先问“谁还持有它创建的对象”。临时对象若不再可达，就可能被回收；返回值、静态字段、任务队列或其他对象仍持有引用时，对象可能继续存活。收集器依据可达性等存活规则判断，再按自己的策略回收空间，并不是方法一返回就销毁对象。

沿这条引用链回看，就能分开四件事：类加载使类型可用，对象初始化建立实例状态，对象分配获得空间，GC 回收可回收对象的空间。它们有关联，却不是同一个事件；一次 new 不等于一次 GC。

#### 这一层带来的收益和成本

统一类文件与行为契约让应用能在不同平台的兼容 JVM 上复用；动态加载和运行时编译让程序能按实际负载选择实现并优化热点；自动内存管理减少手工释放对象的负担。代价包括启动与预热、运行时及元数据占用、编译和回收开销，以及一套更复杂的排错体系。

跨平台也有边界。依赖特定本地库、文件名大小写、路径分隔、默认字符编码或时区的应用，仍可能在迁移后出问题。正确说法是 JVM 提供可移植的基础，不是保证任意 Java 应用无需验证就能跨平台运行。

如果被问“以前了解过 JVM 吗”，先说明自己实际学习和使用过的范围，再选择熟悉的一条主线展开。没有实际调优经历时，可以讲清掌握的原理和排查思路，不把方案推演说成亲身实践。

### 2 字节码怎样执行以及 JVM 怎样跨平台

Java 通常先由编译器生成字节码，再由 HotSpot 的解释器和 JIT 协作执行：解释器让代码先跑起来，JIT 把值得优化的热点编译成机器码。可跨平台复用的是规范化的类文件和行为契约；各平台仍需要自己的运行时，机器码也仍针对具体平台。

常见问法有“Java 是编译执行还是解释执行”“JIT 的作用是什么”“为什么刚启动比较慢”“除了 class 文件，编译器怎样最大程度复用代码”“怎样屏蔽 Linux 和 Windows 的同步细节”。回答时要分清应用可移植性与 JVM 自身的移植工程。

#### 解释器与分层编译怎样接力

解释器按字节码的语义推进执行，不是逐行重读 Java 源码，也不是必须先把每条字节码单独编译成一段机器码。JIT 在运行中利用调用频率、循环回边和类型剖面等信息，挑选值得编译的方法或循环。具体决策受编译模式、计数策略、编译队列与运行时负载影响，不能把一个固定调用次数当作所有版本的承诺。

HotSpot 21 常见的分层编译结合解释执行、C1 的较快编译与剖面收集，以及 C2 的更深优化。并非每个方法都必须按同一顺序走完全部层级；有的方法不够热，有的可以跳过中间状态。编译工作通常与应用执行并行推进，安装编译结果后，后续调用可以进入适合的编译入口，未被编译的部分仍可解释执行。

OSR 即栈上替换，解决的是“方法只调用一次，但内部循环运行很久”的问题。运行时可以在循环的特定位置，把正在解释执行或处于较低编译层级的状态转换到编译版本继续执行，不必等下一次方法调用。它与对象的“栈上分配”不是一回事。

#### 优化为什么能更快又保持正确

内联把被调用方法的逻辑纳入调用点，既减少调用开销，也让编译器看见更完整的数据流。随后可能进行常量传播、常量折叠、死代码消除、循环优化、边界检查优化和分配消除。内联并非只看方法是否短，还受热点、代码规模、调用形态与编译预算限制；无限内联会膨胀代码并加重指令缓存压力。

有些优化依赖推测。例如某个接口调用点在已观察的负载中总是遇到一种实现，编译器可能将其去虚拟化，加入类型检查后走直接调用或内联路径。如果后来遇到不同类型，程序可以走保守路径，必要时发生反优化。类层次依赖失效等情况也可能使旧编译代码不再适用。

推测不再成立时，JVM 要先保证程序还能按原语义继续运行。反优化利用保留的调试与状态信息重建执行状态；此前若消除了对象，还可能需要把它重新物化出来，再转回解释器等安全路径。

所以一次反优化本身不代表 JVM 出错。诊断时要继续看它是否反复发生、是否伴随编译抖动，以及业务延迟是否在同一时间变差，不能一看到反优化就关掉优化。

逃逸分析也是编译优化分析的一部分，判断对象如何被使用，为标量替换和锁消除提供条件。它不承诺把每个局部 new 变成完整的栈对象。对象分配的具体边界在后面的分配章节展开。

#### 如果要移植一个 JVM 应当怎样分层

只回答“class 文件通用”解决的是应用层问题。实现 JVM 时，还要把公共语义和目标平台差异拆开。

公共层可以共享类文件解析与验证、运行时类型管理、很多中间表示和优化逻辑，以及 GC 和监视器的通用协议。CPU 后端处理目标指令选择、寄存器分配约束、调用约定、原子操作和汇编生成；操作系统适配层处理线程、虚拟内存映射、文件、等待和唤醒等系统能力；OS 与 CPU 的组合层处理信号上下文、异常恢复等交叉差异。HotSpot 21 的 share、cpu、os、os\_cpu 目录体现了这种分工，但真正重要的是接口和语义边界，不是背目录名。

例如 Java int 的加法要保留规定的 32 位整数溢出行为，x86 与 AArch64 可以用不同指令编码实现同一结果。对于同步，Java 层要求互斥、重入和规定的内存可见性，公共运行时维护监视器语义，目标平台提供适合的原子操作、内存序和等待唤醒机制。无竞争路径、优化消除和竞争后阻塞可能走不同实现，不能说每次 synchronized 都直接调用同一个操作系统互斥锁函数。

移植还包含引导 JDK、C/C\+\+ 工具链、链接器、ABI/JNI 边界和平台测试。共享优化也必须尊重目标的指令能力及内存序；某条指令不可用时，可以选择等价指令序列或运行时辅助函数。验证不只检查“编译成功”，还要覆盖异常、并发、内存分配和本地调用等行为。JNI 调用使 Java 与本地代码协作，但其二进制本身仍需匹配平台。

#### 怎样评价启动性能和 AOT

第一次请求慢可能同时包含类加载、静态初始化、连接建立、缓存建立和编译预热，不能全部归因于解释执行。JIT 可以利用真实剖面改善稳态性能，却需要编译 CPU、Code Cache 空间和预热时间；冷启动特别短的任务可能无法充分摊薄这些成本。

AOT 是“提前做工作”的一组路线。提前生成目标机器码的方案，需要明确动态加载、反射和部署环境等支持边界；提前缓存类加载与链接结果的方案，则没有因此把整个应用变成独立本地可执行文件。例如 JDK 24 的提前类加载与链接属于后者。比较时应先说具体 JDK 和具体产品，再评价启动、峰值吞吐、内存、训练/构建成本与动态能力，不能把所有 AOT 混为一项功能。

性能实验应区分冷启动和预热后的稳态，使用代表性输入，观察计算结果，避免常量折叠或死代码消除把被测工作删掉。编译器也可能合并或消除源代码中的分配，单次循环的耗时不能证明“某类对象都在栈上”。微基准适合使用 JMH 等专门工具；服务评估还需要真实并发、尾延迟、CPU 和内存一起看，不能由一个加法基准推出整个业务的收益。

### 3 类的加载链接初始化使用与卸载

类的生命周期包括加载、链接、初始化、使用，以及满足条件后可能发生的卸载。先记清前三步各自解决什么：加载建立运行时类型，链接让它满足执行条件，初始化才处理静态初始化逻辑。找到 class 文件、完成链接和执行静态初始化，不能互相替代。

常见问法有“class 文件怎样进入 JVM”“类加载全过程是什么”“加载与初始化有什么区别”“new 之前发生什么”“元空间参与回收吗”“类怎样才能卸载”。可以先说生命周期，再沿初始化触发和类的存活边界深入。

#### 加载与链接分别做什么

加载器根据二进制名称找到或生成字节序列，交给 JVM 建立运行时表示，包括类型关系、字段和方法描述、运行时常量池等，并使程序能够取得相应的 Class 镜像。来源不局限于磁盘上的独立 class 文件，还可以是 JAR、网络、加密内容或动态生成的字节码。数组类没有对应的 class 文件，由 JVM 根据组件类型创建；加载引用类型的数组组件类，不意味着初始化组件类。

链接包含三个工作。验证检查类文件格式、字节码类型安全及相关约束；准备为静态字段提供存储并赋默认值，还可以建立实现需要的辅助结构；解析将符号引用按类型、名称、描述符和访问权限等规则，确定为对应的运行时实体。解析不必全部在初始化前完成，可以延迟到首次使用相关引用时发生，也不必把每个符号都机械变成裸内存地址。

比较两个字段，先区分默认值和常量赋值。`static int value = 42` 的默认值是 0，源码里的 42 通常在类初始化方法中赋入，不能说加载时就已经执行了这次赋值。

`static final int LIMIT = 11` 这样的常量字段则可以有 ConstantValue 属性。按 JVMS 的初始化规则，相应常量赋值发生在初始化过程中、执行类初始化方法之前。因此也不能把所有 static final 都背成“准备阶段赋源码值”。实现内部可能更早安排存储；回答规范阶段时，仍要保留这个区分。

#### 哪些使用要求初始化

关键不是代码中有没有出现类名，而是发生了哪种操作。常见主动使用包括创建该类实例、调用它声明的静态方法、读取它声明的非常量静态字段，以及写它声明的静态字段。某些反射调用、特定方法句柄的首次调用以及虚拟机启动等也有相应初始化规则。

几个容易混淆的边界需要逐一判断：

- 通过 Child\.value 访问实际由 Parent 声明的非常量静态字段，要求初始化的是 Parent，不因使用了 Child 这个名字就要求初始化 Child。

- `new Child[2]` 创建的是数组，只把两个元素初始化为 null，不创建两个 Child，也不因为这一操作初始化 Child。

- `Child.class` 取得类镜像，本身不触发 Child 的初始化。

- 读取编译期常量通常在使用方直接使用编译期嵌入的值，不触发声明类初始化。修改常量后只更新被引用类而不重新编译使用方，还可能继续读到旧的嵌入值。

- `Class.forName(name)` 的常见单参数形式要求初始化；`Class.forName(name, false, loader)` 可用于加载而不主动要求初始化。ClassLoader\.loadClass 的通常用途也不是执行静态初始化。

常量变量要求 final、基本类型或 String 类型，并用常量表达式初始化。`static final Integer N = 11` 涉及包装对象，`static final String S = new String("x")` 涉及对象创建，`static final int N = compute()` 涉及方法调用，都不能仅凭 final 就当作编译期常量。

#### 父类接口与初始化同步

初始化一个类时，需要先初始化它的父类，以及规范要求的、声明了默认方法的相关父接口，按规定的递归顺序处理；这包括编译器生成默认方法的情形。不能简化成“初始化实现类一定初始化所有接口”。初始化一个接口本身，也不因此初始化它的所有父接口。若接口只定义一个通过方法调用求出的静态字段，没有默认方法，它不会仅因实现类初始化就必然初始化；主动读取该接口声明的非常量字段时，才按相应规则触发。

对同一个类身份，初始化流程由 JVM 协调：一个线程开始执行，其他需要初始化该类的线程等待结果；初始化成功后，后续使用不会再次执行静态初始化。这里的“线程安全”保证的是初始化协议及其可见性，不会让静态字段之后的任意修改都自动安全。类不一定存在实际的 `<clinit>` 方法，但仍有初始化状态。初始化线程自己递归请求初始化同一类时不会重新完整执行一遍，这也是静态循环依赖可能观察到部分默认状态的原因之一。

静态初始化应保持短小、可预测。若初始化代码启动另一个线程并等待它，而该线程又需要使用正在初始化的类，就可能互相等待；两个类跨线程互相等待初始化也可能形成死锁。把远程请求、无界阻塞或复杂资源依赖放入静态块，会把首次访问变成难定位的延迟与失败入口。

如果初始化代码异常结束，类会被标记为错误状态。第一次使用可能收到 ExceptionInInitializerError；如果原异常属于 Error，传播方式另有规则。后续再次要求初始化同一类，通常会收到 NoClassDefFoundError。此时 class 文件可能一直存在，问题是该类此前初始化失败了，应该寻找最早的异常原因，而不是只检查路径。ClassNotFoundException 常出现在显式动态查找未找到定义时；加载、验证、链接和初始化还可能分别产生 ClassFormatError、VerifyError、LinkageError 等错误。

#### 把初始化顺序落到完整程序

下面的程序把数组、常量读取、不初始化的查找、继承静态字段和实例创建放在一起。先推导事件，再看断言：最初不会出现 Child 的静态事件；读取继承字段只出现 Parent\.static；第一次创建 Child 后，才依次追加 Child\.static、Child\.field 和 Child\.constructor。

```Java
import java.util.*;
public final class InitializationOrder {
    static final List<String> events=new ArrayList<>();
    static int mark(String message) { events.add(message);return 7; }
    static class Parent { static int value=mark("Parent.static"); }
    static class Child extends Parent {
        static final int CONSTANT=11;
        static int childValue=mark("Child.static");
        int field=mark("Child.field");
        Child() { events.add("Child.constructor"); }
    }
    public static void main(String[] args) throws Exception {
        Child[] array=new Child[2];
        Class.forName(Child.class.getName(),false,Child.class.getClassLoader());
        if(Child.CONSTANT!=11 || !events.isEmpty() || array.length!=2) throw new AssertionError(events);
        if(Child.value!=7 || !events.equals(List.of("Parent.static"))) throw new AssertionError(events);
        Child child=new Child();
        if(child.field!=7 || !events.equals(List.of("Parent.static","Child.static","Child.field","Child.constructor"))) throw new AssertionError(events);
        System.out.println("PASS: "+events+"; arrays/constants/noninitializing lookup did not initialize Child");
    }
}
```

Parent 没有显式实例初始化日志，所以这里的输出不是在宣称父构造器被跳过。对普通类，先给整个对象的实例字段默认值，再沿构造链完成父类的实例初始化和构造过程，之后执行本类字段初始化、实例初始化块和构造器体。静态初始化按类身份进行，实例初始化按每个新对象进行；两者的“只执行一次”与“每次执行”要分别回答。

#### 卸载要看整个引用图

对普通的、由类加载器定义的类，关键条件是定义它的加载器可以被垃圾回收。活跃实例、Class 镜像、反射对象、线程上下文类加载器或其他结构，都可能通过引用关系使类型与加载器继续存活。不能只检查“业务列表里已经没有该对象”，也不能只看“没有创建过实例”。数组类型的存活还要结合其组件类型理解。

热部署后若旧类没有释放，可以沿一条保留链查：长期存活线程的 contextClassLoader 是否还指向旧应用？父加载器可达的缓存是否还保留旧 Class/Method？只要这种链还在，旧加载器、旧类集合和相关元数据就可能一起留下。

因此，停止应用功能后，还要清理线程、注册的回调、共享缓存和 ThreadLocal 等引用，才可能让旧加载器整体不可达。旧对象彼此形成环并不自动构成泄漏；真正要找的是从存活根通向它们的那条路径。

满足条件也不保证立即卸载，仍取决于收集器、选项及相应回收周期。启动加载器定义的普通类不能按上述方式卸载；系统加载器通常随应用长期存活，不能期望清空一个对象列表就卸载普通应用类。隐藏类有独立的存活规则，不应把普通类的加载器粒度结论无限推广。

HotSpot 的类卸载可以释放相应类元数据及加载器管理的空间，因此元空间并非“永不回收”。不过卸载、释放分配块和归还物理页给操作系统并不是同一时刻，看到元空间统计或 RSS 没立即下降，不能单凭这一点确认卸载失败。具体根路径定位和回收日志分析应结合内存诊断。

### 4 双亲委派类身份与应用隔离

双亲委派优先把加载请求交给父加载器尝试处理，以复用它提供的类型，是 ClassLoader 常见的默认加载策略。解释共享和隔离时，还要加上更关键的一句：一个类的身份由二进制名称和定义加载器共同决定。名字相同，不一定是同一个类型。

常见问法有“类加载器有哪些”“双亲委派怎样走”“为什么需要委派”“能否打破”“反双亲委派是什么”“Tomcat 如何让同名不同版本的库共存”。

#### 默认委派怎样工作

一次典型 loadClass 请求先检查这个加载器是否已经记录了相应的加载结果，避免重复定义；没有结果时，先交给父加载器；没有显式父加载器时，按默认实现尝试启动加载器。父路径找不到时，当前加载器再通过 findClass 查找并定义。需要链接时再做相应处理。沿途如果某层已经找到定义，不需要把同一请求继续无条件传到最顶层。

“父”是委派关系，不是加载器实现类的 Java 继承关系；“双亲”也不是两个父加载器。改变类数据来源时，通常只重写 findClass 并保留 loadClass 的默认协议。确实需要应用私有类优先时，才改变加载顺序，同时处理已加载检查、加载锁、类型约束和失败回退，避免重复定义或并发死锁。

默认委派能够复用平台类型和共享库，减少不必要的重复加载，也降低随意替换核心类型的风险。它不是 JVM 对所有加载器强制规定的唯一算法，更不是可以执行任意不可信代码的安全沙箱。类文件验证、访问控制、模块可读性和包约束等也各有作用。

#### 加载器名称要带版本

JDK 8 常说启动、扩展和应用类加载器，扩展加载器与当时的 ext 机制有关。JDK 9 模块化之后，扩展机制被移除，通常讨论启动、平台和应用/系统类加载器；应用类可能来自类路径，也可能与模块路径相关。内置模块加载还可能有跨加载器委派，不能把一幅 JDK 8 目录图直接套到现代 JDK。

启动加载器在 Class\.getClassLoader 等 API 中通常用 null 表示，这不等于该类型没有被加载。启动加载逻辑如何在 Java 和本地代码间拆分属于实现细节，不能把“所有 JVM 都由 C\+\+ 写一个不可访问对象”当作规范。自定义加载器可以选择合适的父加载器，不必一律以应用加载器为父；若希望访问现代平台类，选择平台加载器与选择 null 的效果也不一样。

#### 同名类型为什么不能相互转换

设 A 和 B 各自定义了 `com.example.Message`。虽然名称相同，但定义加载器不同，得到的是两个 Class 身份；A 创建的对象不能强转成 B 定义的类型。

现在只改一个条件：A 和 B 不自己定义，而是都委派给同一个定义加载器。此时就可能拿到同一个 Class。判断类型是否相同，要追到“谁最终定义”，不能只看“谁发起加载”。

运行时包也与定义加载器有关；相同包名不自动赋予不同加载器定义的类彼此的包级访问权限。公共接口若跨越应用边界，应由双方共同可见的加载器定义。一个实用结构是把稳定接口放在共享父层，将各插件的实现及私有依赖放在子层；边界上传递的 DTO、异常和回调类型也要检查，不能只共享接口名字。

如果需要让两个不兼容版本交换信息，可以用共同约定的数据格式或共享的稳定抽象做适配。把对象先转为 Object 只能绕开编译期静态类型检查，不能把运行时类型变成另一个加载器的同名类。

#### Tomcat 怎样兼顾隔离与共享

以 Tomcat 10\.1 的 Web 应用加载规则为例，每个应用有自己的 Webapp 加载器，可从本应用的 WEB\-INF/classes 与 WEB\-INF/lib 读取类。默认情况下，对一般应用私有类采取本地优先的策略，之后再查 System、Common 等父层；平台基础类优先交给 JVM，容器实现的 Jakarta API 等还存在必须委派的例外。配置 delegate=true 后可改为父层优先。这里是按类型与配置分层处理，不是所有类都反转默认顺序。

因此，两个应用各自携带不同版本的同名库时，可以由各自的 Webapp 加载器定义，互不替代。若希望共享一份共同库，可以放入合适的公共层；Tomcat 也支持配置 Server 和 Shared 层，但这两个额外层默认并未单独定义，不能把 SharedClassLoader 当成所有安装都必有的固定节点。

共享可减少重复元数据、代码和某些资源，但同时共享 static 状态、升级节奏和类型身份，库还必须适合被多个应用使用。私有加载提升版本隔离能力，却增加多份类与缓存的开销。热部署后必须释放旧应用的线程和跨层引用，隔离不等于自动无泄漏。并且类加载器隔离不提供进程级的 CPU、堆或故障隔离：一个应用耗尽共享进程资源，仍可能影响其他应用。

线程上下文类加载器常用于让通用框架按调用环境找到实现，例如服务发现机制选择应用可见的提供者。它改变的是查找所使用的加载器入口，不是把 JVM 的类型身份规则取消。解释这种场景时，应说清“谁发起查找、谁最终定义、哪些 API 需要共享”，而不只是背“打破双亲委派”。

### 5 运行时数据区与进程内存预算

回答 JVM 内存问题，要同时给出两张图：规范描述执行需要哪些逻辑结构，HotSpot 实现决定这些结构怎样占用堆、元空间、线程栈和 Code Cache 等资源。前者帮助解释代码，后者帮助做进程预算。Xmx 只限制 Java 堆，不能当成整个进程的上限。

常见问法有“JVM 内存分哪几块”“哪些线程共享”“堆和栈为什么分开”“static 放在哪”“对象的属性和方法各在哪里”“堆没满为什么还 OOM”。若面试官只说“内存模型”，先确认是在问运行时分区，还是 JMM 的可见性、原子性与有序性。后者是多线程可观察行为的规则，不是下面这张内存地图。

#### 线程执行状态与共享数据

程序计数器表达一个线程当前执行的位置。执行普通 JVM 方法时，它与当前指令位置有关；执行 native 方法时，其值在规范中未定义。它不要求物理上永远对应某一个 CPU 寄存器，也不应该被解释成操作系统给每个 Java 方法建立的计数器。

每个线程有自己的 JVM 栈。一次方法调用建立逻辑栈帧，包含局部变量表、操作数栈、动态链接以及方法返回等信息。参数是局部变量的一部分，实例方法还需要接收者 this。局部变量可以保存基本值，也可以保存对象引用；操作数栈用于字节码运算的中间值。动态链接使当前方法能够使用所在类的运行时常量池来找到被调用方法或访问字段。正常返回或异常传播时，相关栈帧按调用关系退出。

“每次调用一帧”首先是逻辑模型。解释帧与编译帧的布局不同，内联后几个 Java 方法可能没有一一对应的物理帧，某些局部值还可能留在寄存器或被优化掉。字节码局部变量槽位也不能直接当作物理内存字节数。定位问题时应结合实际执行模式和工具能重建的逻辑栈。

本地方法栈支持本地代码的执行环境。native 方法没有 Java 方法体，可能由 C、C\+\+ 等符合调用接口的本地实现提供；它不意味着只能用某两种语言，也不意味着任意 native 调用都必然进入内核。JVM 实现可以让 Java 栈与本地栈共享某些物理设施，不必在进程中划出两块完全独立的连续区域。

堆为对象实例和数组提供存储，在规范层面由线程共享。共享表示多个线程能够通过引用访问同一对象，不表示所有对象都实际被多线程使用。方法区也是共享的逻辑区域，描述每类结构、字段与方法数据、运行时常量池和代码等。JVMS 在逻辑上把方法区视为堆的一部分，但不要求它与普通对象使用相同的回收或分配方式；面试中说“Java 堆”时通常特指对象堆，要交代语境。

#### 方法区元空间与静态字段如何对应

以 HotSpot 21 的一个引用型 static 字段为例，可以沿“字段说明 → 字段当前值 → 被引用对象”分三处看。名称、描述符、修饰符等是类元数据，主要在本地内存中的 Metaspace；启用相应配置时还会涉及压缩类空间等实现结构。程序能访问的 java\.lang\.Class 镜像则是堆对象。

static 字段的实际值位于类镜像相关布局中。引用型 static 保存的是一个引用，它指向的普通对象仍在 Java 堆。把字段的元数据、引用值和目标对象分清，就不会把“static”简单等同于“整个对象放在元空间”。

方法也要分开看。方法描述、字节码等属于类相关结构；JIT 产生的本地机器码放在 Code Cache；执行某次调用所需的局部值和操作数属于该次执行状态。每个实例不会各自复制一份方法体，但同一方法在运行过程中可以有不同编译版本，不能反过来说“一个方法在整个进程里永远只占一份固定机器码”。

运行时常量池是每类或每接口的结构，包含常量及待解析/已解析的引用。不能因名字里都有“常量池”，就把它与字符串驻留表画成一个盒子；其中引用到的 String 对象又是堆对象。HotSpot 对元数据、符号、已解析对象引用等还会采用不同的存储结构，因此“常量池全部就是一块字符串元空间”也不成立。

JDK 8 移除了 HotSpot 的永久代，类元数据主要转向本地 Metaspace。这不是把所有曾被笼统称作“方法区”的东西统一搬到堆外，更不是从此不再发生类空间 OOM。元空间会随类加载增长，并受本地资源和限制参数约束。MetaspaceSize 主要是初始的元数据回收高水位，不等于一启动就预分配的固定容量；MaxMetaspaceSize 则用于限制相应元空间使用。把前者调大不能修复旧加载器被保留的问题。

#### 为什么区分堆和栈

栈帧的寿命通常跟随调用进入和退出，适合管理参数、局部值和返回状态；对象却可能跨越方法返回继续存活，也可能被多个线程共享，因此需要另一种生命周期管理。分开后可以分别优化调用状态与对象存储，而不是用“基本类型放栈、引用类型放堆”这条错误口诀划线：实例中的 int 字段也属于对象，栈中的引用也可能指向共享对象。

假设一个方法创建局部 ArrayList，随后把它放进全局缓存。局部变量的槽位属于该线程，但被引用的列表已经可以通过全局缓存访问，线程封闭不再成立。返回时栈帧退出，只释放该帧对应的执行状态，不会把全局缓存里的列表自动销毁；反之，局部引用不再活跃时，对象也不必等到源代码块结束才具备回收条件。

GC 会识别执行状态中的活跃引用，因此不能说“GC 完全不管栈”。同时，堆和本地栈仍竞争进程资源，不能保证堆 OOM 与栈问题互不影响。递归过深导致 StackOverflowError，通常应该检查终止条件、调用深度和栈设置，增大 Xmx 并不直接解决；无法创建本地线程，则还要考虑线程数、本地内存及系统限制，二者不是同一种错误。

Java 21 虚拟线程还提醒我们不要把逻辑模型硬画成固定物理布局：虚拟线程的栈状态可以保存在 Java 堆中的 stack chunk 对象里，运行时再与载体线程协作。它们仍拥有独立的逻辑执行状态，却不是每个虚拟线程都拥有一块与平台线程等价的独占本地栈。它们的堆中栈块也不能机械视为与平台线程本地栈完全相同的 GC 根结构。

#### 给整个进程留预算

Xmx 约束 Java 堆的最大容量，堆外仍有类元数据、平台线程栈、Code Cache、直接缓冲、GC 辅助结构、JIT 和本地库分配等。操作系统看到的虚拟地址保留量、实际提交量和 RSS 也不是同一指标。容器或系统可以因为总资源压力终止进程，此时未必来得及抛一个 Java 层 OutOfMemoryError。

做预算时，先确定容器或进程可用总额，再给堆、直接缓冲池、类空间、线程以及其他本地开销分别预留，并给短时峰值留余量。上限之和也不是实际常驻占用之和，但把每项都配到理论最大、指望它们从不同“区域”各取一份独立资源，显然不可行。排错要先判断是堆对象膨胀、类增长、缓冲未释放、线程过多还是别的本地分配，再进入相应工具链。

以 NoteWeave 的资料处理链路练习预算，先核清入口：资料接入按 128MB 单文件能力设计；具体配置同时把单文件和整个 multipart 请求上限设为 128MiB。实际文件还必须给请求封装留出空间，并受入口限制。这些接收限制并不等于 Java 堆只需 128MB。

再沿 Java Host 与 Python Worker 的分工追一份文件：原始字节、解析树、字符串、分片结果和序列化副本，哪些同时存活，哪些在 Java，哪些在 Python？再加上排队任务和并发文件，才有峰值预算的依据。流式解析、有界缓冲、限制同时处理数和及时释放阶段结果，是可以进一步评估的设计选择。

这仍是设计延伸，不代表项目已经实施这些 JVM 调优或取得特定内存收益。异步化可以释放请求等待路径，也可能因积压留住更多数据，不能自动推出总内存下降。

#### 怎样实际观察栈溢出时的方法调用深度

想把“递归过深”变成可以观察的实验，可以继续阅读[当前 Java 方法的栈溢出深度和栈预算](https://my.feishu.cn/wiki/RSRkw1EaUiOJX8kB9DkcUJoDnFh#doxcnhSjAvwyCLA6kDWhK0Gceqc)。示例在独立子进程中设置栈预算，捕获并展开异常后再输出观察到的调用深度。方法进入次数不等于栈字节数，编译与运行条件变化也会影响结果，不能从一次深度直接推定固定帧大小。

### 6 对象创建 TLAB 与分配消除

对象和数组在 JVM 抽象语义中由堆提供存储，但源代码中的每个 new 不一定对应一次真实分配。HotSpot 可能先消除不必要的分配；仍需分配时，适合的对象通常走堆内 TLAB 快路径，快路径失败后再走与收集器有关的慢路径。

常见问法有“new 一个对象的全过程”“创建对象后 JVM 内存发生什么变化”“对象一定在堆上吗”“什么时候栈上分配”“TLAB 在哪里”“TLAB 满了是否立刻 GC”“数组分配在哪里”。先讲可观察语义，再讲优化路径，才能避免把语言保证与实现策略混成一张固定流程图。

#### 先解释创建语义

对普通 new，目标类首先要满足必要的加载、链接和初始化条件。实例所需空间取决于实际类型和布局；取得空间后，实例字段先有默认值，运行时建立对象头等可供自身识别的状态，再通过构造过程完成业务初始化。HotSpot 可以预先清零一批分配区，也可以在对象初始化时清零，优化还可能省略随后必被覆盖且不可观察的写入，所以不要把某个物理写指令顺序当成所有实现的统一要求。

普通对象构造涉及父类与子类。整个新对象先具备默认字段值，构造链先完成父类一侧的初始化和构造，再执行本类实例字段初始化、实例初始化块和构造器体；本类字段初始化与实例初始化块按源码顺序执行。构造器之间的 this 调用会影响进入哪条构造链，但不会使同一个对象的本类字段初始化无端重复执行。

构造器还可能抛异常，或者在构造过程中错误地把 this 发布出去。获得了一块不重叠的内存，不等于另一个线程就能安全观察已经完成的业务状态；跨线程使用仍要遵守安全发布规则。对象分配的并发正确性与对象内容的并发正确性是两个问题。

类第一次初始化可以执行任意静态代码，构造器也可以做任意复杂工作，分配慢路径还可能等待回收。因此整个 new 表达式没有统一的 O\(1\) 时间保证。已初始化类型的小对象 TLAB 分配通常很短，不代表每次对象创建都有固定时限。

#### 对象头字段引用与数组

普通实例可以从对象头、实例字段和对齐填充三部分理解。对象头保存运行时识别、状态或类型相关信息；确切结构受架构、压缩指针、锁实现和 JDK 版本影响。实例字段包含从父类继承的状态和本类状态，物理顺序可能由实现布局决定，不保证严格等于源码声明顺序。

例如一个对象有 int count 和 Object child 两个字段，count 的值属于该实例，child 保存的是对另一个对象的引用，不是把子对象完整嵌进去。估算空间需要区分浅大小和沿引用可达的总体大小，不能把共享的 child 在每个父对象下都重复计入独占内存。static 字段属于类身份，不是每个实例一份；方法代码也不随每个实例复制，this 才决定访问哪一个对象的字段。

数组本身也是对象，包含长度和元素存储。基本类型数组保存元素值，引用数组保存引用；`new Parser[100]` 建立一个含 100 个 null 引用的数组，不建立 100 个 Parser。多维数组是数组的数组，不应一律当成一块连续的二维数值矩阵。估算时还要考虑各层数组对象、引用宽度与对齐。

常见 64 位 HotSpot 的某组参数可以得到常见对象头和引用大小，但这些不是 Java 语言常量。涉及容量规划时，应写明版本、架构、压缩选项、对象形状和统计口径，再用布局/采样工具核实；不能只按字段的基本类型字节数相加。

#### TLAB 优化了哪段路径

TLAB 是线程本地分配缓冲，本质上是 Java 堆里一段暂由该分配线程使用的区域。对适合的对象，线程只需检查剩余空间并推进本地分配位置，就能减少每次都争用共享分配点的成本。在 HotSpot 里应理解为当前执行所依附的 VM 线程分配路径，不要进一步推导成“每个虚拟线程一出生就永久得到一个固定 TLAB”。

TLAB 放不下当前对象，下一步不一定是申请新 TLAB，更不一定是 GC。运行时可能保留余量还较多的旧缓冲，让这次对象在缓冲之外分配；也可能退休旧缓冲，再申请一个新 TLAB。对象太大或策略不适合时，本来就可能直接走缓冲之外的分配。

这些补充缓冲和共享空间分配，要由收集器及运行时协调，可以使用 CAS 等手段。不能把它们全画成“争用同一把堆分配互斥锁”。

TLAB 剩余不足只说明这一小段缓冲不适合当前请求，不说明整个堆满了。慢路径可能仍能直接成功，必要时才进入回收、等待或最终失败的路径。TLAB 大小还可自适应，过大增加闲置尾部浪费，过小增加补充开销，要结合分配行为衡量，而不是为所有线程设置一个终身固定值。

线程私有的是分配权限，不是对象以后永远私有。一个对象从 TLAB 分配后放入共享队列，其他线程仍然可以使用它；队列或发布协议应提供需要的可见性，之后的可变状态还需要符合业务同步规则。

#### 逃逸分析与标量替换怎样理解

逃逸分析追踪对象能否被分析范围外的代码观察。返回对象、写入共享字段、交给未知调用或传到其他线程，可能使分析更保守；但把对象作为方法参数并不必然阻止优化，内联和跨方法分析可以让编译器看见调用实际做了什么。反过来，源码里只有一个局部变量，也不证明对象未逃逸，因为其引用可能被方法间接保留。

如果一个临时 Pair 只用于计算两个数字之和，编译器可能把这两个字段直接当作标量值处理，根本不建立一个完整 Pair。值可以位于寄存器、栈槽或被进一步常量折叠，这叫标量替换及分配消除，不能据此画出一个与堆对象一模一样的完整栈对象。HotSpot 21 的常见 C2 优化应按这条路径解释。

不逃逸只是条件之一。没有成功内联、复杂控制流、无法分析的调用、对象使用方式、数组处理限制或编译预算，都可能让分配仍然保留。分析结论和标量可替换性不是一个词。优化必须保持可观察的身份和行为，不能为了减少分配改变 `==` 的结果。

若编译器证明锁对象只在当前线程中可见，没有其他线程会参与相同监视器的竞争，还可能消除相关锁操作。锁消除不意味着程序员可以删除本来保护共享状态的锁；只有在优化器证明等价的条件下才成立。反优化时需要恢复的对象和锁状态，也要由运行时保持语义。

大对象、长期存活对象和跨代引用会进一步影响收集器的分配与回收策略，但“数组一律在老年代”“超过固定字节数就直接晋升”“TLAB 满就 Full GC”都不成立。比如 G1 有 Humongous 对象路径，其他收集器又有自己的结构与阈值；分代和晋升问题应接着按具体收集器展开。

### 7 字符串常量池对象身份与拼接

字符串题先区分内容和对象身份，再区分常量表达式、运行期计算与 intern；底层数组是否共享、池中是否已有值和实际分配次数，不能替代这几个语义判断。

常见问法有“String 常量池在哪里”“String 底层随版本怎样变”“s1、s2、s3 的 == 结果是什么”“第三个一定 true 吗”“给定代码打印 b 是什么”“一共创建多少对象”。输出和对象数必须建立在完整声明、表达式和比较对象上。

#### 三种常被叫作常量池的东西

class 文件的常量池是文件结构，保存数值、字符串常量描述、类/字段/方法的符号信息等；运行时常量池是加载后每类或每接口的运行时结构；字符串驻留结构则负责为内容相同的字符串找到规范表示。它们有关联，但不是同一块存储。

在现代 HotSpot 中，普通 String 实例及其内容数组是堆对象，驻留查找所用的表结构与这些对象分开管理。读取字面量或对常量表达式求值得到驻留表示，不等于所有 new String 和运行期拼接都自动成为同一个池对象。也不能说“字符串内容全部在元空间里”。

驻留不等于永久强引用。HotSpot 21 的驻留表有可清理的弱句柄机制；若没有其他保留路径，动态驻留的字符串并不因此永久存活。但已加载类的常量关联、静态字段或业务缓存可能继续保留它，因此“设一个变量为 null 后池中对象必然立刻被收集”同样错误。这里先记住驻留与存活是两个维度，可达性和引用强度再沿回收基础章节深入。

#### 从最明确的比较开始

`==` 比较是否同一个对象，String\.equals 比较内容。两个相同字面量可以指向同一个驻留对象；`new String("abc")` 则创建新的 String 身份，与字面量引用不同。即使实现复用了不可变的内容数组，也不能推出两个 String 对象相同。内容相等的字符串 hashCode 本来就相等；identityHashCode 也存在碰撞可能，不能代替引用比较。

把声明补全再判断：`String s1 = "abc"`，`String s2 = new String("abc")`，`String s3 = s1 + ""`。s2 由 new 建立新的 String 身份，所以 s1 与 s2 引用不同。s3 要看表达式：这里 s1 是普通变量，s1 \+ "" 不是字符串常量表达式，连接结果在可观察语义上是新的 String，因此 s1 == s3 为 false。

三个字符串的内容相等，身份却不必相同。编译器和 JIT 可以改变连接的实现方式，但不能把这个可观察的 false 优化成 true。下一步再把 s1 改为 final 常量变量，才能看清究竟是哪一个条件改变了答案。

如果改成 `final String s1 = "abc"`，它是用常量表达式初始化的常量变量，s1 \+ "" 也可成为常量表达式，与同内容字面量共享驻留表示，此时相应比较为 true。普通变量即使从未再次赋值、满足 effectively final，也不会自动成为 JLS 的常量变量。若写成 `final String s1 = new String("abc")` 或由方法返回值初始化，虽禁止重新绑定，却不满足常量表达式条件。

intern 返回内容相等的规范表示：池中已经有相同内容时返回已有对象，没有时按 API 语义将当前字符串作为规范表示并返回。因此上例中 s2\.intern\(\) == s1 为 true，但只调用 `s2.intern()` 而不接收返回值，不会让 s2 变量自动改变指向。不要把 intern 讲成原地改变对象身份。

#### 完整变体与字符存储

下面是声明条件完整的教学程序，分别覆盖普通拼接、常量折叠、final 非常量初始化、intern、输入数组的防御性复制和 UTF\-16 长度。先判断每个表达式属于哪一类，再阅读断言，不必靠背输出顺序。

```Java
public final class StringCases {
    public static void main(String[] args) {
        String s1="abc";
        String s2=new String("abc");
        String s3=s1+"";
        if(s1==s2 || s1==s3 || !s1.equals(s2) || !s1.equals(s3)) throw new AssertionError();
        final String constant="abc";
        String folded=constant+"";
        if(folded!=s1 || ("a"+"bc")!=s1 || s2.intern()!=s1) throw new AssertionError();
        final String notConstant=new String("abc");
        String runtime=notConstant+"";
        if(runtime==notConstant || runtime==s1 || !runtime.equals(s1)) throw new AssertionError();
        char[] input={'a','b','c'};
        String copy=new String(input);input[0]='z';
        if(!copy.equals("abc")) throw new AssertionError();
        String unicode="A\uD83D\uDE00";
        if(unicode.length()!=3 || unicode.codePointCount(0,unicode.length())!=2) throw new AssertionError();
        System.out.println("PASS: ordinary runtime concat=false, constant concat=true, final nonconstant=false, intern=true, defensive copy, UTF16 units");
    }
}
```

OpenJDK 8 的 String 主要使用 char\[\]；JDK 9 引入 Compact Strings 后，常见实现使用 byte\[\] 加 coder，在适合时采用 Latin\-1，否则采用 UTF\-16 表示。它不是把全部 Java 字符串改成 UTF\-8，也没有改变 length 返回 UTF\-16 代码单元数的 API。示例中的 A 加一个补充平面表情共有 3 个代码单元、2 个码点；用户感知的一个字符还可能包含多个码点，所以按“可见字符”截断时需要更高层的字素簇规则。

String 不可变依赖 final 类、私有存储、没有公开修改内部内容的接口，以及需要时的防御性复制。仅把数组字段声明为 final，只能限制数组引用重新绑定，不能禁止数组元素被修改。示例从 char\[\] 构造 String 后再改输入数组，不会改变已构造字符串，说明调用方不应持有可改变其内部内容的别名。

长度限制也分层。class 的 CONSTANT\_Utf8 项使用 u2 长度，限制的是最多 65535 个修改版 UTF\-8 字节，不是 65535 个字符；编译器如何将较长表达式生成常量还需具体看代码。运行期 String\.length 使用 int，不等于一定能成功分配接近 Integer\.MAX\_VALUE 的字符串，底层数组、编码方式和可用内存可能更早限制它。

#### 对象数为什么不能固定背两个

讨论“创建几个对象”至少先确定四件事：完整表达式是什么，字面量是否已被驻留，数 String 身份还是也数底层数组与辅助对象，以及数语言语义还是这次 JVM 的物理分配事件。

例如在字面量已经存在、仅统计这次表达式引入的 String 身份时，`new String("abc")` 引入一个新的 String；不能额外把已经存在的字面量再算作“本次新建”。如果还没有驻留对应字面量，类的解析/使用过程又可能建立规范表示。JDK 8 与 JDK 9 以后的存储、编译器采用的连接策略，以及 JIT 是否消除不可观察分配，都会影响更底层的数量。现代 javac 常通过 invokedynamic 描述字符串连接，不能固定把每个加号展开成一套 StringBuilder 对象计数。

因此，只给 `s1 == "abc" / s2 = new String / s3 = s1 + ""` 这类不完整片段，不能唯一推出输出：s1 的声明缺失、构造参数缺失、比较哪两个对象也没有明确。问“第三个一定 true 吗”，应指出普通变量与 final 常量变量的区别，并让比较对象明确。若只说“打印变量 b”或“上述代码创建几个对象”却没有代码，输出与数量就仍然未知，不能拿另一段教学代码代替。

把 intern 用于业务也需要取舍。对大量重复、可控取值的文本，规范化可能降低重复对象占用；对高基数、任意外部输入，驻留增加查找成本和表项负担，不是无条件省内存。应先看重复比例、引用寿命和实际分配证据。锁字符串字面量或驻留结果，还可能与其他组件意外共用同一监视器，通常更适合使用私有专用锁对象。

### 8 直接内存和缓冲区生命周期

直接缓冲把内容放在适合本地 I/O 访问的存储中，可能省掉一段中间复制。选它之前要同时回答两件事：这次 I/O 是否真的少复制了，以及谁负责让缓冲在正确时机释放或归还。它仍占进程资源，收益和释放时机都取决于具体实现与用法。

常见问法有“什么是 JVM 堆外内存”“哪些类会用直接内存”“direct 一定更快吗”“ByteBuffer 怎样切换读写”“小 slice 为什么可能留住大块内存”“堆还有空间为什么直接缓冲申请失败”。

#### heap 与 direct 的差别在哪里

ByteBuffer\.allocate 创建由 byte\[\] 支撑的堆缓冲；allocateDirect 创建直接缓冲，HotSpot 21 通常使用 DirectByteBuffer 及本地存储。包装对象依然是 Java 堆对象，内容区域与包装对象的浅大小是两个不同的资源量。FileChannel 映射文件得到的 MappedByteBuffer 也是直接缓冲，但它的映射与文件语义还需要单独考虑；JNI 和网络/存储库也可能使用本地缓冲及自己的内存池。

通道把堆缓冲内容交给本地 I/O 时，某些路径需要临时本地缓冲和复制；直接缓冲可让运行时尽力直接使用适合本地访问的区域，减少这段中间复制。它不保证跨过所有用户态、内核页缓存和设备路径，也不等于 TCP、TLS、文件系统等整条链路都零拷贝。应明确省掉哪次复制，而不是只说“在堆外所以快”。

直接内存的分配和释放通常更贵，频繁创建小缓冲可能得不偿失；长期复用、大块且确实参与本地 I/O 的缓冲更值得评估。选择前应比较真实负载的吞吐、尾延迟、CPU、分配频率与总内存。仅比较几次 put/get 不足以证明通道 I/O 的收益。

访问数组之前要检查 hasArray。allocate 返回的缓冲有可访问的数组；allocateDirect 的 API 不保证有可访问数组。HotSpot 21 常见直接缓冲的 hasArray 为 false，调用 array 会抛 UnsupportedOperationException，不能把 direct 当成另一种随时能取出 byte\[\] 的包装。

#### 游标变化与半包处理

ByteBuffer 的 capacity 是容量，position 是下一次相对读写位置，limit 是当前允许访问的边界。写入数据后，flip 将 limit 设为原 position，再把 position 置为 0，让读者只看到已写入部分。clear 则把 position 置为 0、limit 恢复为 capacity，并丢弃 mark；它没有擦除内容，也不代表释放内存。

如果读了一部分，还有未处理字节，compact 把剩余区间搬到开头，把 position 放到剩余字节数，limit 恢复为 capacity，以便继续追加输入。网络协议出现半包时，通常要保留这部分数据，不能简单 clear 后覆盖。compact 会移动剩余字节，代价随保留的数据量增长，不能因为它看上去只调用一个方法就算 O\(1\)。

下面在 16 字节直接缓冲中写入 1、2、3、4，flip 后读走 1，compact 保留 2、3、4，再追加 5，下一次读取应得到 2、3、4、5。它还演示了 duplicate 共享内容而不共享 position。这段程序中的无数组断言以 HotSpot 21 的直接缓冲实现为前提。

```Java
import java.nio.*;
public final class DirectBufferSemantics {
    public static void main(String[] args) {
        ByteBuffer heap=ByteBuffer.allocate(16);
        ByteBuffer direct=ByteBuffer.allocateDirect(16);
        if(heap.isDirect() || !heap.hasArray() || !direct.isDirect() || direct.hasArray()) throw new AssertionError();
        try { direct.array(); throw new AssertionError(); } catch(UnsupportedOperationException expected) { }
        direct.put(new byte[]{1,2,3,4}).flip();
        if(direct.get()!=1) throw new AssertionError();
        direct.compact(); // keep bytes2,3,4; position3, limit16
        if(direct.position()!=3 || direct.limit()!=16) throw new AssertionError();
        direct.put((byte)5).flip();
        byte[] actual=new byte[4];direct.get(actual);
        if(!java.util.Arrays.equals(actual,new byte[]{2,3,4,5})) throw new AssertionError();
        direct.clear();
        ByteBuffer duplicate=direct.duplicate();
        duplicate.put(0,(byte)9);
        duplicate.position(3);
        if(direct.get(0)!=9 || direct.position()!=0 || duplicate.position()!=3) throw new AssertionError();
        System.out.println("PASS: direct vs heap, absent backing array, flip/compact, shared bytes and independent positions");
    }
}
```

#### 视图为什么容易留下隐藏引用

slice 只为指定范围或当前剩余内容建立新视图，duplicate 为同一内容建立另一套游标状态。它们不是复制数据；position、limit、mark 独立，重叠字节仍然共享。对字节缓冲的 slice/duplicate，新的字节序按 API 规则初始化为 BIG\_ENDIAN，不应假定自动继承原缓冲后续或原有的字节序；使用多字节数据时应显式设置并核对。

HotSpot 的直接缓冲视图会保留到所属存储的关联，因此把一个大缓冲的一小片长时间放入缓存，也可能让整块直接存储不能释放。若确实只需要少量内容长期存活，可以权衡复制这几字节，与继续持有整个大块资源的成本。只读视图也只是限制通过该视图写入，其他可写别名仍可改变底层内容，它不是不可变快照。

假设缓冲已经提交给异步 I/O，但操作尚未完成。若此时 compact 搬动字节，或把缓冲 clear 后重新写入，或提前归还池供别人复用，就可能破坏尚在使用的数据。因此，租约要持续到真正的 I/O 完成，不能在“提交成功”时就结束。

独立游标只保证视图之间不互改 position，不提供重叠数据的同步。多个线程通过不同视图修改同一字节，仍可能竞争；另一个视图或线程尚在使用时，同样不能提前复用底层存储。

#### 释放协议和预算要一起设计

普通 ByteBuffer 没有通用的 public close 方法让应用保证 allocateDirect 的区域马上释放。在 HotSpot 中，Java 包装对象的可达性与内部清理机制参与本地存储释放，但清理时机不是业务请求结束的同步承诺。不要把调用 System\.gc 当成资源归还协议，也不要默认推荐通过反射或内部 Unsafe/cleaner 强制清理：版本封装、别名和仍在进行的 I/O 都可能使这种做法不安全。

如果采用库提供的缓冲池或引用计数对象，要明确每次借出由谁归还、异常与取消怎样处理、视图是否共享所有权、异步完成前能否复用、空闲池保留多少。池必须有总容量与并发上限，否则只是把频繁分配变成了长期无限占用。引用计数归零与普通 Java 引用不再使用之间也要有一致契约，不能一边释放本地资源，一边还把可访问视图交给调用方。

当确实需要显式、作用域化的本地内存生命周期，可按所用 JDK 和库评估正式支持的资源 API。例如 JDK 22 的外部函数与内存 API 可通过可关闭的 Arena 管理分配；这不改变既有 allocateDirect 对象的契约，且需遵守 Arena 的线程和存活期限制。JDK 21 中对应 API 仍属于预览边界，不能直接当成无版本前提的替代代码。

内存映射也要单独回答。关闭 FileChannel 并不等同于立即解除已经建立的映射；MappedByteBuffer 的引用和映射仍有自己的生命周期。清理映射、把修改强制写回以及关闭文件通道是不同操作。对被截断或外部修改的映射区域，还要考虑操作系统相关行为，不能把它当成永久稳定的普通数组。

HotSpot 的 MaxDirectMemorySize 约束 JDK 直接缓冲相关的预留容量，不是所有堆外分配的统一限额；JNI、本地库、映射和自管分配器要分别核对。Java 堆还没满，也可能因为直接缓冲上限、系统本地内存不足或容器限制而失败。以独立子进程、32MiB 堆、1MiB 直接缓冲上限申请一个 2MiB 直接缓冲，是区分两个预算的教学条件；实际诊断要确认异常确实来自直接缓冲预留，而不能只捕获任意 OOM 就下结论。

观测时可先看 BufferPoolMXBean 的 count、totalCapacity 和 memoryUsed：它们分别表达缓冲数量、总容量估计和底层内存使用估计，不保证数值完全相等。再结合进程 RSS、容器指标、库的池指标与 NMT。NMT 面向 JVM 自己跟踪的本地内存，不能承诺覆盖所有第三方 malloc；堆转储中 DirectByteBuffer 的浅大小很小，也不表示它关联的本地存储很小。

最终需要区分正常池预留、未归还租约、小视图保留大块、异步操作尚未完成和不可达后的清理延迟。先找到具体拥有者及生命周期，再决定减少副本、限制池、缩短保留或修复归还协议；只提高上限可能把可识别的缓冲申请失败，拖成整个进程的资源事故。

## 第二部分：可达性、引用与回收基础

### 对象存活、GC Roots 与常量引用

判断对象能否回收，核心是看运行时还能否通过有效引用路径访问它，而不是看它多久没用、有没有名字，或者引用数量是否为零。以常见 HotSpot 为例，回收器从根引用出发追踪对象图；强可达对象必须保留，其余对象还要按软、弱、虚引用及相应生命周期规则处理。找到垃圾和立即释放垃圾占用的内存，是两件事。

这一组问题常被问成“GC 怎么找到垃圾”“GC Roots 有哪些”“循环引用会不会泄漏”，也可能追到“静态常量算不算根”“intern 后的字符串是不是永远存在”。回答时先讲可达关系，再讲根从哪里来，最后讲特殊引用和实现边界，比背一份固定名单更稳妥。下文以 Java SE 21 的契约和 HotSpot 21 的实现为基线；规范不要求所有 JVM 使用同一种 GC 算法。

#### 业务不用了，为什么 GC 还不回收

GC 能判断的是程序可达性，不能推断业务意图。长寿命缓存、线程池线程中的 ThreadLocal、没有注销的监听器，都可能保留业务已经不用的对象。假设一个长寿命任务表仍把已经完成的解析任务保存在集合中，任务又引用整份文档和中间结果，那么“任务已经完成”不会自动切断这些引用。只要从根还能一路访问到它们，回收器保留它们就是正确行为。

可以把这种假设关系画成一条简单的链：

活动线程或仍存活的类状态 → 任务表 → 已完成任务 → 文档缓冲区

如果只把当前方法中的局部变量赋为 null，而任务表仍持有任务，根路径并没有消失。反过来，一组对象即使彼此引用，只要没有任何外部可达路径进入这组对象，也不会因为内部的环而必然泄漏。例如 A 引用 B、B 又引用 A，在外部最后一条强路径断开后，整组对象可以进入后续回收处理。

这也解释了引用计数和根追踪的区别。朴素引用计数给对象维护被引用的次数，增删引用时更新计数；一个没有外部入口的环，内部计数仍可能为正。根追踪关注是否存在外部入口，因此可以识别这种不可达的环。引用计数体系也能增加循环检测等机制，不能由这个例子断言所有引用计数方案都无解，更不能把算法比较编成“Java 曾经统一用引用计数，后来统一换成可达性分析”的历史。

业务无用但长期被强路径保留，可能构成内存泄漏；短时间内有很多真正需要使用的对象，则可能只是合理的活集变大。判断泄漏应结合对象用途、预期生命周期、实际保留链和对象的保留大小（retained size），而不是看到内存增长或某个对象活得久就下结论。

#### GC Roots 应按持有引用的位置理解

GC Root 更准确地说是追踪的起点或根引用位置，口语中也常把它指向的对象叫根对象。根必须足以覆盖程序仍可能使用的对象，但收集器可以保守地多保留一些对象。它不是 Java 源码关键字的集合。

常见来源可以归成三类。

- **线程和本地调用状态。** 活动线程执行时，栈帧局部变量、操作数栈，以及实现中的寄存器等位置，可能保存仍有效的对象引用。HotSpot 会结合解释器状态、编译代码的引用位置映射等识别它们，不是把栈上所有看起来像地址的数都当成对象。词法作用域尚未结束，也不意味着某个已经不再使用的局部引用一定保活到右花括号。

- **JNI 等运行时登记的引用。** JNI 局部引用和普通全局引用能维持对象存活。局部引用通常随本次本地方法调用结束而释放，也可以提前删除；普通全局引用需按 JNI 规则显式释放。JNI 弱全局引用另有弱语义，不能跟普通全局引用混为一谈；本地代码里的任意裸地址或数值也不会自动成为受 JVM 识别的强根。

- **类、代码及 JVM 内部状态。** 存活类相关的静态字段、已解析对象常量、活动代码需要的对象，以及运行时内部持有的引用，都可能形成保留链。不同收集器和工具展示根路径的方式不同，应说明是哪一个持有关系，而不是泛称“所有系统类的实例都是根”。同步执行所需的对象也受运行时保护，但“写过 synchronized 的对象永久是根”显然不成立。

静态字段是常见保留者，却不必在所有实现中都是直接、独立、永久的根。例如“存活加载器关联的类状态 → 静态缓存 → 缓存值”是一种概念上的保留链；真正分析堆时，还会看到类镜像、加载器和运行时句柄等具体节点。

这里还要区分**整堆的根**与**某次局部回收的边界入口**。只回收年轻代或若干 Region 时，其他堆区域指入回收范围的引用，也必须纳入这次追踪。它们不因此变成 Java 层面的永久 GC Roots，而是本次收集不能遗漏的外部入口。卡表与记忆集就是减少这类边界扫描成本的重要办法。

#### “常量是 GC Root”需要拆成四种情况

“常量”这个词同时出现在语言、class 文件和运行时实现中，不拆开就容易答错。

第一，**基本类型常量值不是对象引用**。例如 static final int N = 42 存的是数值，并不天然指向某个 Integer 对象。发生装箱以后，才有包装对象及其引用关系可讨论。

第二，**final 不等于常量变量，也不等于永久存活**。static final Object O = new Object\(\) 中的 O 不能重新赋值，但 Object 类型变量不属于 Java 语言所说的常量变量。语言中的常量变量必须是 final 的基本类型或 String 变量，并以常量表达式初始化。这个对象是否保留，要看类相关状态及其他路径是否仍可达；不是 final 关键字替它取得了永久根身份。final 数组变量也只是不能改指向，不代表数组元素不可变。

第三，**运行时常量池不是一篮子已经创建好的 Java 对象**。它有数值、类名和成员名等符号信息，也有与解析相关的结构。未解析的类名、字段名或字符串描述，不能一律当成已经存在的对象实例。需要区分符号信息、解析结果与保存对象引用的运行时位置。

第四，**已解析的对象引用可能形成实际的强保留链**。HotSpot 21 会用 resolved references 对象数组缓存部分已解析对象，例如字符串，并通过类加载器数据相关的句柄管理它。类或相关运行时状态仍存活时，这条链可以保留字符串。这个实现事实支持“活运行时结构持有的对象常量引用需要被追踪”，却不支持“常量池每一项都是永久强根”。

编译期常量还可能被内联到使用它的类中。例如一个类声明的字符串常量，被另一个类使用后，不能只盯住声明类是否初始化、是否仍被业务调用，就推断那个字符串的全部保留关系；使用类的已解析常量、静态字段和执行状态同样可能持有它。字符串身份和常量折叠的具体判断，与这里的存活路径问题应分开回答。

#### intern 字符串不会仅因驻留就得到永久保活

String\.intern\(\) 提供等内容字符串的规范表示，但“规范表示”不等于“永久存在”。在 HotSpot 21 的常规 StringTable 中，表项通过弱句柄关联字符串，并有清理失效表项的机制。因此，一个动态创建并驻留的普通字符串，若没有任何其他强保留链，不会仅仅因为在常规驻留表中出现过，就永远不能回收。

这里有两个重要限制。

一是**常规驻留表的弱关联，不会消除其他强路径**。某个字面量可能已经被存活类的已解析引用数组、静态字段、活动栈或代码相关结构保留。看见 StringTable 是弱的，不能反向推出所有字面量都会很快消失。

二是 **CDS 共享归档字符串存在独立路径**。HotSpot 21 使用归档堆时，共享字符串表通过由 VM 全局句柄持有的共享字符串数组访问归档字符串；不能把常规表的弱句柄结论不加区分地套到这个分支。排查一个具体字符串为什么没被回收，仍然要检查当前运行配置及实际根路径。

一个合适的反例是：动态构造独特字符串内容，取得 intern\(\) 返回值，然后清除业务中的所有强引用。对普通、非归档驻留项而言，驻留表自身不足以保证它永久存活。但这只是在说明**允许回收的条件**，不能据此承诺一次 System\.gc\(\) 或等待若干毫秒后，弱引用必然变空。

#### 类加载器的生命周期会把静态对象一起保留下来

普通类能否卸载，与它的定义加载器能否被回收密切相关。线程上下文类加载器、外部注册表、存活的类镜像或实例等，都可能继续保留应用类加载器，从而让类元数据以及有关静态对象继续存在。热部署之后不再主动调用某个类，不足以证明它已经可以卸载。

反过来，某个自定义加载器、它加载的类与静态对象即使彼此构成环，也不意味着这个环能无条件自保活。关键仍是有没有来自仍存活世界的保留路径。满足卸载条件只是允许实现释放相关状态，不保证立即发生；普通类规则以及特殊隐藏类的生命周期，应结合具体类加载机制理解。

面试时如果被追问“GC Roots 该怎么选”，可以收束成一句话：**从活动执行状态和运行时必须保留的引用位置出发，覆盖所有仍可能使用的对象，再按引用强弱和具体收集范围处理；对静态变量、常量、锁与类加载器，都落实到真实路径，而不把名词本身当成永久根。**

### 强软弱虚引用与资源清理

四种引用表达的是不同的对象保留关系：强引用用于仍必须可用的依赖，软引用允许内存敏感的缓存丢失，弱引用让辅助关联不阻止对象回收，虚引用用于安排清理通知。它们不是四种对象内存，也不是一张固定的回收先后时间表。

“为什么不能全用强引用”“软引用和弱引用什么时候回收”“四种引用有什么场景、优先级怎样”可以用同一条主线回答：先看全部根路径，再解释允许丢失什么，最后说明如何安全处理引用变空和资源释放。

#### 强弱取决于全部路径，而不是一个包装对象

普通字段、局部变量、集合元素都可以保存强引用。只要对象还有一条有效强路径，额外创建 WeakReference 或 PhantomReference 就不会使它变成弱可达或虚可达。比如静态集合强引用一个任务，同时又有 weak 指向任务，集合的强路径仍然起决定作用。

也要分清 Reference 对象与它指向的对象：程序通常强持有 WeakReference 这个包装对象，但包装内部受 GC 特殊处理的 referent 关系是弱的。包装对象中自行增加的普通字段，并不会自动变弱；如果一个自定义弱引用类又用普通字段保存同一个 referent，就重新引入了强路径。

从保留强弱看，可以按强、软、弱、虚逐层理解。对象不强可达，才进一步考虑是否软可达；既不强可达也不软可达，才可能是弱可达。虚可达还涉及终结状态及虚引用的存在。不同对象之间不存在“所有弱对象先释放，才能处理任何软对象”的全局保证；引用级别也不是线程调度优先级。

#### 软引用与弱引用：区别在保留政策，不在固定倒计时

**软引用是允许回收器根据内存需求清除的保留关系。** 当对象只剩软可达路径时，回收器可以选择清除相关软引用；Java 21 API 保证，在虚拟机抛出 OutOfMemoryError 之前，对软可达对象的软引用已经被清除。这个保证不等于“软缓存永不导致 OOM”：强可达的缓存对象不在这项清除保证中，软引用包装和索引本身也占内存，资源不足的原因还可能超出这些可回收对象所能缓解的范围。

除这项保证外，不应承诺固定的清除时间、存活时长或跨对象清除顺序。更不能把某个 HotSpot 参数或经验规则说成所有 JVM 的软引用契约。当回收器选择清除时，会按 API 定义成组、原子地清除相应软引用，而不是任由相关对象的软保留关系出现不一致状态；注册过队列的引用可在同一时刻或稍后入队。

软引用适合“丢了可以重建，丢失时机也能接受”的辅助缓存。假设资料解析结果用软引用保存，内存吃紧时大量条目一起失效，请求又同时重建，就可能把 CPU、分配速率和外部存储压力一起推高，形成加载风暴。需要可预测资源上限时，更适合显式容量或权重上限、过期策略与加载去重；缓存是否能丢、重建是否昂贵，应该由业务设计明确，不能全部交给 GC 决定。必须可靠保存的数据应有相应持久化方案；强引用只能维持进程内可达性，不能充当持久化保证。

**弱引用更适合不参与对象所有权的索引或附加关联。** 当回收器判定一个对象弱可达时，会按 API 规则原子清除指向它及相关弱可达对象的弱引用，然后将已注册队列的引用安排入队。口头说“弱引用下次 GC 就会回收”只是一种粗略概括：某次收集可能只覆盖部分区域，发现可达性变化、清除引用、入队和重用对象内存也并不同步，不能承诺某一次调用或某个时间点必然完成。

读取弱引用时，先调用一次 get\(\)，把结果保存为局部强引用，再判断是否为 null 并使用。不要写成“第一次 get 非空，第二次 get 就直接调用方法”，因为两个读取之间，弱关联可能已经被清除。一次成功读取能支持这次对象使用，但不等于为业务状态加锁，也不能阻止另一线程显式关闭对象管理的外部资源。

#### WeakHashMap 为什么仍然可能保留 key

WeakHashMap 对 key 使用弱关联，但对 value 通常是强引用。若 value 直接或间接引用 key，就出现了这样的强链：

存活的 Map → value → key

这条强路径足以使 key 继续存活。把普通 HashMap 换成 WeakHashMap，并不能修复这种反向保留关系。两个条目的 value 交叉指向对方的 key，也可能形成同样的问题；检查时要追完整路径。

WeakHashMap 表达的是“key 不再被外部需要后，这个关联可以消失”。它不提供固定缓存容量或过期时刻，也不是线程安全容器。对于 String 这类能够重新构造等值实例的 key，还要记住：equals 相等不代表是同一个被弱关联的对象，旧 key 被回收后，后来创建一个等值 key，不保证还能查到之前的条目。

引用队列通常用于移除已失效的包装条目。否则即使 referent 回收了，索引中的 WeakReference 包装、键值元数据或其他业务状态仍可能越来越多。弱引用减轻的是特定保留关系，不是整个数据结构的生命周期管理责任。Reference 包装、引用发现与处理、通知队列都有开销，大量软弱虚引用并非免费的优化；已经不需要的强引用，也仍应按生命周期主动解除。

#### clear、enqueue 与队列通知分别表示什么

ReferenceQueue 中存的是 Reference 包装对象，不是原 referent。应用可以用非阻塞的 poll\(\) 取通知，也可以用 remove\(\) 等待；队列不会自动执行你的资源释放代码，更不能替你知道哪个业务键需要删掉。

以 Java 21 API 为准，有三个操作需要分开。

- **get\(\)** 尝试取得 referent。软、弱引用取得非空结果时，返回的是普通强引用；虚引用的 get\(\) 始终返回 null。若只想检查是否已经清除，可用 refersTo\(null\)，不必为了检查而先取出 referent。

- **clear\(\)** 主动清除这个包装与 referent 的关联，调用本身不使包装入队。它不会把所有其他强引用一并清掉，也不等于立刻释放原对象。若 GC 已经在并发处理这个引用，不能仅凭调用过 clear\(\) 就断言队列绝不可能出现通知。

- **enqueue\(\)** 在 Java 21 中会清除关联，并尝试把包装加入注册队列。它可以由应用显式调用，即使 referent 仍被其他强路径保留。因此，队列中出现一个引用，不足以单独证明“GC 已回收了对象内存”。已成功入队过的同一引用，即使已被取出，也不能再次入队。

GC 处理引用时，清除与入队可以有时间间隔；从队列取出通知，与某块内存已经重用，也不是同一事件。不要用队列的先后顺序推导所有对象的回收顺序。isEnqueued\(\) 还存在状态观察的竞态，并已在 Java 16 起弃用；消费通知用队列，判断是否清除用对应引用 API。

还有一个容易遗漏的条件：**把引用注册到队列，并不意味着队列会在入队前替应用强持有这个引用对象。** 如果你创建完 PhantomReference 就把它本身也丢掉，不能期待以后一定收到通知。自行实现清理机制时，应保存引用包装及清理需要的独立元数据，收到通知后再移除；这些元数据不能反过来强持有待清理对象。

#### 虚引用、Cleaner 与 close 各管一层

PhantomReference 的 get\(\) 始终为 null，是为了不让应用通过它重新取得已经进入相应生命周期阶段的对象。get\(\) 为 null 也不证明虚引用已经被清除：它从创建时起就返回 null。在 Java 21 中，GC 判定对象虚可达后，会按规则清除相关虚引用，再在当时或稍后入队；不能把旧版本关于虚引用清除的描述直接套过来。

虚引用的用途是让程序知道何时可以安排对象关联的收尾工作，例如释放独立记录的本地资源。通知反映的是可达性和回收资格的变化，既不是业务结束信号，也不是外部资源已经释放的证明。需要及时释放文件、连接等资源时，应以 close\(\) 和 try\-with\-resources 建立明确生命周期。

Cleaner 从 Java 9 起提供对虚引用和清理动作的封装。注册时传入对象与独立清理状态，返回 Cleanable；显式调用 clean\(\) 会注销并执行清理动作，同一个 Cleanable 的动作至多执行一次。如果没有显式清理，则可以在对象达到虚可达后由 Cleaner 处理，但没有业务期限内必定执行的保证，进程退出时也不能依赖它完成全部清理。

判断 Cleaner 能否成为后备清理，先检查动作是否反过来留住了对象。若注册的 lambda 使用实例字段，就可能捕获 this；于是形成 Cleaner → 清理动作 → this 的强路径，对象无法达到虚可达，后备清理也就等不到触发条件。

常见写法是静态嵌套状态类，只保存关闭资源所需的信息，不引用外层实例。动作应短小、不阻塞，否则会拖延其他动作。“同一个动作至多一次”也只解决重复执行问题；不同动作之间、显式 close 与对象使用之间的并发关系，仍需资源类自行设计。

finalize\(\) 是另一套历史机制：在启用终结的情况下，对象可能在终结方法中重新把自身发布到可达位置，俗称“复活”；终结执行时机和顺序并无可依赖的业务保证。finalization 在 JDK 18 起被标记为将来移除，Java SE 21 也允许实现禁用它。新代码不应把 finalize\(\) 作为资源管理方案，更不能把 final、finally 和 finalize 混为一谈。

#### reachabilityFence 防的是过早失去可达性

源码还在执行某个实例方法，不保证运行时始终需要保存 this。假设方法从对象中读出了一个本地资源编号，后续只使用编号；优化器可能认为对象本身已经不再需要，但清理机制却会在对象失去可达性后释放那个资源。这就可能出现“方法逻辑尚未用完资源，对象关联的清理已经具备触发条件”的风险。

Reference\.reachabilityFence\(owner\) 用来确保 owner 至少强可达到该调用之后。通常放在资源操作后的 finally 路径中，让异常路径也经过保护。它不发起 GC，不让对象永生，也不是 volatile、锁或线程间发布机制；另一线程主动 close 的竞争仍需锁、状态机或其他资源使用协议解决。

普通业务代码通常不必到处加 fence。它适合由对象生命周期驱动外部清理、而对象最后一次语义使用与外部资源最后一次使用可能错开的少数情况。判断是否需要它，应先画清对象、资源与清理状态的关系。

#### 用确定的 API 行为理解引用

下面的完整程序同时保留同一个对象的强、软、弱、虚关系，检查显式清除和队列操作。value 通过 finally 中的 reachabilityFence 保持可达，因此队列变化来自程序的显式操作，而不是对 GC 时机的猜测。循环只是反复检查这些契约，不用于测量吞吐或证明某次 GC 发生。

保存为 ReferenceSemantics\.java，使用 Java 21 编译并运行：javac ReferenceSemantics\.java，然后执行 java ReferenceSemantics。

```Java
import java.lang.ref.PhantomReference;
import java.lang.ref.Reference;
import java.lang.ref.ReferenceQueue;
import java.lang.ref.SoftReference;
import java.lang.ref.WeakReference;

public final class ReferenceSemantics {
    private static void check(boolean condition, String message) {
        if (!condition) {
            throw new AssertionError(message);
        }
    }

    private static void verifyOnce() {
        Object value = new Object();
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        SoftReference<Object> soft = new SoftReference<>(value);
        WeakReference<Object> weak = new WeakReference<>(value, queue);
        PhantomReference<Object> phantom = new PhantomReference<>(value, queue);
        try {
            check(soft.get() == value, "strong path preserves soft referent");
            Object snapshot = weak.get(); // Read once, then use this strong reference.
            check(snapshot == value, "strong path preserves weak referent");
            check(phantom.get() == null, "phantom get is always null");
            check(phantom.refersTo(value), "null get does not mean cleared");

            weak.clear();
            check(weak.get() == null, "clear removes referent");
            check(snapshot == value, "clear does not erase another strong reference");
            check(queue.poll() == null, "clear alone does not enqueue");
            check(weak.enqueue(), "explicit enqueue succeeds once");
            check(queue.poll() == weak, "queue contains the Reference object");
            check(queue.poll() == null, "queue drained");
            check(!weak.enqueue(), "removed reference cannot be enqueued again");

            WeakReference<Object> direct = new WeakReference<>(value, queue);
            check(direct.enqueue(), "enqueue without prior clear succeeds");
            check(direct.refersTo(null), "JDK 21 enqueue also clears");
            check(queue.poll() == direct, "explicit notification while value is live");

            check(phantom.enqueue(), "explicit phantom enqueue succeeds");
            check(queue.poll() == phantom, "phantom reference in queue");
            check(phantom.get() == null && phantom.refersTo(null), "phantom cleared");
            soft.clear();
            check(soft.get() == null, "soft clear removes referent");
            check(queue.poll() == null, "no remaining notifications");
        } finally {
            Reference.reachabilityFence(value);
        }
    }

    public static void main(String[] args) {
        for (int i = 0; i < 10_000; i++) {
            verifyOnce();
        }
        System.out.println("PASS: 10000 explicit reference API checks; no GC timing assertion");
    }
}
```

这个例子最重要的区别是：weak\.clear\(\) 只清掉 weak 的关联，snapshot 仍保存原对象；phantom\.get\(\) 一开始就是 null，但当时 phantom\.refersTo\(value\) 仍为 true；手动 enqueue\(\) 能在对象仍强可达时产生通知。它没有使用 System\.gc\(\) 加固定等待时间来断言回收，因为那不是 Java 的保证。

### 三色标记、并发屏障与安全点

三色标记是描述对象图追踪的模型；要让标记与应用同时运行，还必须有处理引用变化的协议。白、灰、黑三个名字本身不会消除停顿，也不会自动解决漏标。面试问“标记垃圾时用户线程能不能工作”，答案取决于收集器及阶段：有的阶段暂停应用，有的阶段并发进行，不能仅凭“三色标记”判断。

#### 三种颜色描述扫描进度，不是三种对象

先看一个停止修改的对象图。

- 白色：本轮尚未发现。

- 灰色：已经发现，但它的出边尚未全部扫描完成。

- 黑色：已经发现，出边已经扫描完成。

从根引用找到初始对象，放进待处理集合。每次取出一个灰对象，检查其引用，把尚未发现的目标加入灰集合，然后把当前对象变黑。直到根已处理、灰集合为空，剩下未发现的对象才可以结合特殊引用处理等规则进一步判断。

“黑对象的引用已经扫描完”，并不等于它引用的所有对象都已经变黑；它可以指向仍在工作队列里的灰对象。颜色也不要求真的存进对象头。实现可以用位图记录已标记对象，用工作队列或栈表示待扫描工作；颜色是帮助推理的抽象。

在这个静止图模型里，扫描黑对象时已经发现了它指向的白对象，所以扫描完成后不会留下未经处理的黑到白强边。沿根可达的对象最终都能被发现，循环也不会导致无限扫描，因为已发现状态可以避免重复遍历。

#### 并发修改为什么会让活对象“消失”

假设应用与标记器同时工作，根能到达 A、C，当前 A 是灰色、C 已经是黑色，B 仍是白色，A 原来引用 B。

如果没有屏障、重扫描或其他补偿协议，下面的交错就有风险：

1. 应用取得 B，并让已经扫描完的 C 新增一条 C → B 的引用。

2. 在标记器扫描到 A 的相关字段之前，应用删除 A → B，并切断其他尚待扫描路径到 B 的入口。

3. 标记器之后扫描 A，看不到 B；C 已经扫描过，也不再查看新字段。

此时 B 仍可经 C 被程序访问，却没有被标记。这类漏标可能让回收器错误回收仍在使用的对象，破坏程序正确性。

教材常把反例总结为两个条件：出现黑到白新边，并且灰到白的所有待发现路径消失。应保留它的前提：这是简化的并发追踪反例，讨论的是尚未被其他根扫描、日志或重扫描保护的路径；不能把它当成所有 GC、所有根变化的完整判定公式。应用的临时局部引用、根变化和新对象分配，也需要收集器的整体协议覆盖。

修复思路有两个方向：一是记录新增关系或被修改区域，保证稍后补扫；二是保留被删除的旧关系，保证开始时可达的图不会因删除而丢失。这两条思路分别帮助理解增量更新和 SATB。

#### 增量更新与 SATB 保护的是什么

**增量更新侧重追踪变化后的引用图。** 概念上，当已经扫描过的部分出现新的引用关系时，必须让新增目标或来源重新进入可处理范围，不能让一条黑到白边成为唯一且未受保护的存活路径。它不要求每次字段赋值时都精确读取对象的三色状态。

历史 HotSpot CMS 属于增量更新式追踪。实际实现会利用写屏障维护的脏卡信息，以及汇总修改信息的 mod\-union 结构，对相关已标记对象重新扫描；并发预清理可提前消化一部分工作，最终重新标记继续处理剩余工作及相关根。因而，“CMS 每次发现黑对象指向白对象，就把这条精确边记下来”只适合作为教学类比，不能当成其真实屏障的逐条执行逻辑。

**SATB 侧重保住标记开始时的可达快照。** G1 的写前屏障在必要时记录将被覆盖的旧引用值，再让程序完成字段更新。哪怕程序删除了 A → B，B 仍可通过日志进入后续追踪，不会因为开始时存在的路径被删除而漏掉。

这个“快照”不是复制整个堆，也不是停止应用直到扫描完；它是用初始状态和变更记录共同维护的一种逻辑视图。G1 21 的具体屏障会根据标记是否处于活动期、旧值是否为 null、目标是否尚未初始化等条件过滤或省略不需要的记录，并非只在“灰对象删掉白对象”这一种颜色组合下才工作。新分配对象、根变化和特殊引用访问还由收集器对应的规则配合处理，单记“写前保存旧值”不等于完成了全部并发正确性证明。

两者可以用同一个反例记忆：增量更新要让 C 的新增引用有机会被补扫；SATB 要保住 A 被删掉的旧引用所代表的工作。都允许保守地多保留一些对象，但不能遗漏程序仍可能使用的对象。CMS 是历史实现，在 JDK 21 中已经不可选；这里用它解释思路，不把旧实现当作当前部署建议。

#### 浮动垃圾为什么可以留下，不能随便改回白色

标记器已经发现一个对象，应用随后删掉了它的最后一条业务路径，这个对象可能仍被本轮视为存活。对 SATB 来说，只要它在开始时属于需要保留的快照，期间变成垃圾也可能继续保留；CMS 的并发追踪同样可能产生浮动垃圾。

这通常影响回收及时性和空间余量，而不会像漏标那样错误回收活对象。不能因为看见某条边被删除，就把目标对象立即改白：它可能还有其他路径，其他线程也可能正在处理相关引用，已经传播出去的标记关系并不能通过一次局部删除简单撤销。

后续周期能够重新判断届时的可达性，但没有“下一次某个时刻必定释放”的时间承诺。并发期间应用仍在分配，浮动垃圾又暂时占空间，所以回收器需要足够余量和及时启动策略。并发不代表回收可以无视容量约束；工作来不及完成或搬迁空间不足，仍可能进入代价更高的处理路径。

#### 第一次 STW 到底在做什么

第一次 STW 通常先解决“能否安全辨认线程当前持有哪些引用”，为后续追踪建立起点，并不等于一次扫完整个活对象图。HotSpot 先协调线程，使相关状态位于可识别的位置；编译代码再借助 OopMap 等元数据，找到栈槽和寄存器里的对象引用。

如果在任意机器指令处直接冻结线程，就可能无法可靠区分某个数值是不是指针、某个临时状态是否已经完成。这正是安全点和状态描述要解决的问题；具体初始暂停还做多少工作，要继续按收集器区分。

“到达安全点的等待”与“到达以后做 GC 的工作”要分开理解。根的规模、线程数量、执行状态和同步过程，会影响前者及根处理成本；对象图大小、引用密度等则影响后续遍历。安全点也服务于 GC 之外的 VM 操作，不是专门为三色标记发明的一种颜色切换。

不同收集器的初始阶段并不相同。

- 历史 CMS 的初始标记主要处理从根以及相关其他代直接到达的老年代对象，之后并发追踪，重新标记补足变化。

- G1 的 Concurrent Start 通常搭载一次年轻代疏散暂停，除了年轻代收集，还建立并发标记的起点。之后有相关并发根区域处理、并发标记及 Remark 等工作；不能把 CMS 的阶段名称逐个照搬给它。

因此，若面试官只问“三色标记第一阶段的 STW”，可以先回答“建立安全起点和必要初始状态”，再确认是在说哪个收集器。如果初始阶段就把整个活对象图递归遍历完，暂停可能随活图增长，并发标记降低停顿的主要意义也会被削弱。反过来，也不能说首次暂停永远只碰几个根、耗时恒定，G1 搭载的年轻代疏散就已经是明显反例。

并发阶段的标记器虽然和应用一起运行，整个并发周期内仍可能穿插别的暂停。低停顿设计是在不同阶段重新分配工作，不是从此没有 STW。

#### SATB 日志、卡表、记忆集与内存屏障别混在一起

它们都可能出现在一次引用写操作附近，但解决的问题不同。

**SATB 日志解决时间上的变化。** 它保留因删除旧引用而可能丢失的待追踪对象，维护并发标记所需的逻辑快照；记录旧目标不等于保存整条引用边或复制完整对象图。

**卡表与记忆集解决空间上的边界扫描。** 假设本次只回收年轻代，老年代某个对象指向年轻代对象，回收器不能因为没遍历老年代就把这个年轻对象误当垃圾。卡表用较粗粒度的区域记录哪些位置可能发生了有关引用写入；记忆集进一步组织哪些外部位置可能指入某个代或 Region。回收时扫描这些候选位置，找到实际引用，既能保留活对象，也能在对象搬迁后修正外部指针。它们通常是保守记录，不等于始终精确维护每一条真实边。

在 G1 中，写前的 SATB 记录和写后的卡表、脏卡处理可以同时存在。前者关注旧值和开始快照；后者帮助维护跨区域入口。同样叫“写屏障”，不能因此把 SATB 缓冲当成 remembered set，或把 remembered set 当成一个不再需要根扫描的完整对象图。CMS 又会利用卡信息支持并发标记补扫，说明一种数据结构可以承担不同职责，判断时应回到具体协议。

**GC 屏障与 JMM 内存屏障也不等同。** GC 屏障是在引用访问附近插入的回收器协作逻辑，用来记日志、记脏卡或维护其他 GC 不变量；JMM 讨论线程间的可见性、顺序与 happens\-before。GC 屏障的实现内部可能需要 CPU 内存序指令，但应用不能借它获得 volatile 或 synchronized 的同步语义。

这些机制的代价也应说出来：引用访问多了判断和元数据写入，日志缓冲占内存，脏卡需要处理，并发线程会争用 CPU 和内存带宽。追求低暂停是在正确性约束下移动、拆分和并行化工作，并不是让回收工作凭空消失。

### 回收算法与完整 GC 口述

回答垃圾回收算法，先分清三件事：**怎样判断对象仍存活，哪些区域这次要回收，以及怎样把可用空间交还给分配器。** 根追踪解决存活判定；分代、Region 选择等决定回收范围；标记清除、复制和标记整理解决空间回收方式。CMS、G1、Parallel、ZGC 则是组合多种机制的具体收集器，不能用收集器名单替代算法原理。

这条主线同时适用于“常见 GC 算法有哪些”“讲一种回收方式”“介绍 Java 的 GC 机制”“整个 GC 过程是什么”。问法很宽时，先把结构讲全，再展开一个机制；问得很具体时，直接进入对应算法，不必先背所有收集器的名字。

#### 标记清除：不搬活对象，把死对象占用变为空闲块

可以先用标记清除讲清一轮回收。回收器从根及本次收集范围所需的外部入口出发，标记应保留的对象，处理相应特殊引用，然后识别没有保留下来的空间，把它们归还空闲结构，后续分配从这些空闲块中取得内存。

它的一个明显特点是正常清除过程不需要搬迁存活对象，因此省去相应搬运和引用修正。但仍有根与对象图追踪、空间遍历或位图处理、空闲块合并与管理等工作。“不移动”不能直接推出“总是最快”。

主要代价是碎片。假设可用空闲块分别是 3 MiB、4 MiB、3 MiB，总量有 10 MiB，某次分配却需要一块连续的 6 MiB 空间，就可能无法直接满足。这个算例只展示外部碎片的影响；真实结果还取决于收集器布局、是否扩容、是否有其他区域以及后备整理等策略，不是看到碎片就立即 OOM。

空闲链表或其他分配结构可以提高空闲块管理效率、合并相邻空闲块，却不能隔着一个仍存活的对象，把两块不相邻空间凭空拼成连续块。要消除这种阻隔，通常需要搬迁活对象或改变分配策略。碎片还可能影响后续分配成本和访问局部性，因此只比较本次清除耗时会漏掉代价。

#### 复制：只搬幸存者，但必须有足够目的空间

复制型回收把收集范围中的存活对象搬到目标区域，修正相关引用，之后让原区域整体重新可用。一个对象可能从多个位置被引用，实现必须避免复制出多份彼此独立的逻辑对象，常见做法是利用转发信息或等价机制，让所有引用最终指向正确的新位置。

复制为什么常适合低存活率？因为回收范围里已经死去的大多数对象不用搬，工作主要跟着幸存者走；幸存对象集中后，目标区域也更容易连续分配。

但“只搬幸存者”不等于“只付复制字节的成本”。根和跨区域入口仍要扫描，对象字段仍要遍历，相关引用要修正，还需要并行协调和引用处理。判断一次暂停为什么慢，要继续分清这些工作。

假设一个 100 MiB 的收集范围只有 1 MiB 存活，与其中 99 MiB 存活相比，需要搬迁的字节量显然不同。这个例子说明存活量重要，不是在预测两个运行的实际暂停比值；对象数量、指针密度、根规模、带宽和实现都会改变结果。一个巨大的基本类型数组与相同字节量的密集引用小对象，扫描工作也未必相同。

**“复制必须占双倍内存”只对典型等大双半区模型成立。** 如果总容量是 100 个单位，两个半区各 50，正常分配使用其中一个半区，另一个作为目的地，为最坏情况下全部幸存预留空间。于是当前分配区只占总量一半。

但传统 Eden 加两个 Survivor 的年轻代并不是整个堆的二等分。仅作算术示意，若 Eden 是 80、两个 Survivor 各 10，一般一块 Survivor 作为复制目的地，另一块保存之前幸存对象，幸存者还可能晋升到老年代。这个 80:10:10 不表示所有实现的固定默认比例，更不保证目标 10 个单位必然装得下全部幸存者；需要晋升空间及对应失败处理。

G1 的疏散同样是把选中 Region 的活对象搬到目标 Region，而不是永远把全堆一半空着。它仍须留下足够目的空间和安全余量。复制空间不足可能导致提前晋升或疏散失败等收集器特定结果，所以“不是固定双倍”也不意味着复制没有空间成本。

#### 标记整理：通过搬迁把空闲空间集中起来

标记整理先确定存活对象，再按整理方案计算或确定它们的新位置，更新引用并移动对象，使目标范围的空闲空间更集中。经典滑动整理可以把活对象压向一端，另一端留出连续空闲区；具体实现可能采用不同扫描次数、并行分工和引用修正顺序，不能把某一版阶段顺序当成算法定义。

整理减少外部碎片，使后续分配更容易使用连续空间，某些布局还可能改善局部性。代价是活对象搬迁、引用定位与修正，以及所需的协调和元数据工作。不能把“没有碎片”说成绝对没有任何空间浪费：对象对齐、区域边界、预留空间或暂时不能移动的对象，仍可能造成不能立即利用的空间。

复制与整理也并非完全互斥的标签。把某批对象复制到更紧凑的目标区域，本身就达到了局部整理效果；分区式收集器可以靠多次疏散逐步回收空间。需要问清是在讨论基本算法、某个阶段，还是整个收集器，才能准确比较。

#### 算法没有脱离负载的固定快慢顺序

用同一批存活对象比较三种方式，可以从四个方面展开。

1. **要处理多少活数据。** 追踪至少涉及相关可达对象及其引用；复制、整理还受需要搬迁的存活字节数影响。活集大、引用密集、根很多，都可能增加成本。

2. **怎样管理可用空间。** 清除要管理不连续空闲块；复制和整理更容易产生连续目标空间，却需要搬迁余量或整理阶段，不能只看堆的名义容量。

3. **工作何时做、由谁做。** 多个 GC 工作者一起干活叫并行；GC 与应用线程在时间上重叠叫并发；STW 表示暂停应用的相关执行。并行的 GC 完全可能是 STW，并发 GC 也仍可能有暂停阶段。

4. **业务付出什么代价。** 既看暂停分位数、最长暂停和频率，也看总 GC CPU、业务吞吐、尾延迟和内存余量。一次停顿变短，可能换来更频繁的回收或更多并发 CPU 竞争，不能只选一个漂亮数字。

因此，标记清除不一定比复制快，标记整理也不必在所有负载上最慢。清除省下搬迁，但碎片管理及后续分配未必便宜；复制在低存活率时可能有优势，高存活率又会增加搬运与空间压力。选择要落到实际负载和实现，抽象算法不能直接给出 HotSpot 的毫秒级结论。

“年轻代越大，单次停顿一定同比增加”同样不成立。范围变大可能改变回收间隔、积累的幸存对象、晋升量及根扫描比例；若绝大多数对象已经死亡，暂停不必按 Eden 容量线性增长。但这也不是“年轻代越大越好”的理由，仍须同时比较延迟、吞吐和占用。

#### 分代为什么有用，老年代为什么不能固定配一种算法

分代利用的是许多应用中短命对象较多这一经验规律：频繁处理较小、低存活率的年轻区域，可能以较少的幸存对象搬迁换回大量空间；让较长寿的对象进入另一部分，则减少对它们的重复处理。跨代引用仍要被追踪，不能把两代当成互不相干的两个堆。

“新生代为什么常用复制”可以从低存活率、批量回收与紧凑分配解释。但如果对象普遍活得很久、任务积压让短期对象跨过多次收集，这种成本优势会变化。分代是经验驱动的策略，不是 Java 语言保证所有对象都朝生夕死。

“老年代为什么普遍采用标记清除”则需要先修正前提。高存活率使反复整代复制的空间与搬迁成本值得关注，但并不能推出老年代统一使用标记清除。历史 CMS 的正常老年代周期采用标记清除；Parallel Old 等采用整理；G1 对选中的老年代 Region 进行疏散。不同设计在暂停、CPU、碎片和空间余量之间取舍，老年代不天然绑定某一个算法。

同样，老年代对象活得久，不意味着老年代很久才需要回收。晋升突然增多、大对象分配、无界保留、并发回收跟不上，都会使老年代压力快速上升。Old GC、Mixed GC 与 Full GC 的含义要结合具体收集器和日志；不能把一次老年代并发周期等同于一次整堆 STW 整理。具体触发规则、代布局和收集器选型应在明确版本后继续展开。

#### 把整个 GC 过程讲成一条因果链

可以这样组织一段完整口述：

“Java 的自动内存管理首先要保证仍可使用的对象不被误回收。常见 HotSpot 收集器从 GC Roots 和本次收集范围所需的外部入口追踪对象，结合软弱虚引用等规则判断保留关系。接着根据收集器策略确定处理范围，把垃圾空间通过清除、复制或整理交还分配器。分代和 Region 是组织回收工作的方式；并发阶段要靠屏障维护引用图变化的正确性，必要阶段仍会暂停应用。最后评价效果要一起看暂停、吞吐、CPU 和内存余量，而不是只看算法名字。”

这是一条解释顺序，不是说每个收集器都必须先完整标记全堆，再选择区域，最后按同一个阶段表执行。复制式年轻代收集可在搬迁时完成相应存活追踪；G1 的全局并发标记与后续多次疏散，也不是每次暂停都重新走一遍全堆流程。

若面试官只让“讲一种方式”，可以展开前面的标记清除，从根追踪讲到空闲块和碎片，再比较复制、整理为何要移动活对象。若接着问“标记时用户线程能不能工作”，进入并发屏障与初始暂停；若问“用过什么 GC、为什么选它”，则需要实际运行环境与负载证据，不应把学习用的 Java 21 基线当成项目部署版本。

以资料异步处理作为假设场景，可以分析队列积压如何延长任务与文档缓冲区的存活时间，以及有界缓冲、尽早解除不必要引用如何减少保留压力。回答个人实践时，要把确认过的经历与方案推演分开。NoteWeave 的 Kafka 异步资料流水线、Java Host 与 Python Worker 分工可以作为讨论背景；是否真实发生过 OOM、是否切换过收集器、取得过怎样的 GC 优化效果，不能由这些架构事实推出来。实际运行时 JDK、收集器、堆配置与故障记录仍需分别确认，再按真实经历作答。

最后记住 System\.gc\(\) 的边界：它提出回收建议，不保证收回某个对象、释放固定大小、完成特定阶段，或按你设想的时间清除并入队引用。程序正确性和资源释放期限都不应建立在这个请求必然生效之上。

## 第三部分：分代、垃圾收集器与 JDK 版本

讨论 GC，先说清楚运行时和版本，再解释它怎样让程序在有限内存里持续前进。以下以 HotSpot JDK 21 为主要教学基线；CMS 单独放在 JDK 8 的历史背景中，其他版本的变化会明确标出。收集器、收集算法和 JVM 规范是三个层次：规范不要求所有 JVM 都分代，更没有统一规定对象十五岁晋升、年轻代固定占三分之一或堆必须按 8∶1∶1 划分。

### 1\. 分代、Survivor、晋升与大对象

分代的价值，是利用对象寿命的差异，把经常发生的回收集中在较小、垃圾比例通常较高的年轻集合；代价是管理年龄、晋升和跨代引用。新生代就是年轻代，不能再把这两个名字算成两代。

面试可能从“为什么要分代”问起，再追问“Eden 和 Survivor 怎样流转”“对象除了年龄到了，还能怎样进入老年代”“能不能改晋升阈值”“Survivor 应该调大还是调小”。这几种问法可以沿着对象的一生回答。

#### 为什么年轻对象值得单独收集

很多对象只服务于一次表达式、一次请求或一个处理阶段，业务完成后便不可达。若每次回收这些短命对象都重新扫描整个长期缓存，GC 会反复处理大量仍存活的数据。把新分配对象集中起来，可以用较少工作回收较多空间；已经经历多轮收集的对象则较少接受这种高频检查。这是经验性的分代假设，不是对每个对象未来寿命的保证。

年轻代适合复制型回收，是因为它主要需要追踪和搬走幸存者，不必把大量已经死亡的对象逐一复制。假设一次分配了 100 MiB，而回收时仅剩 5 MiB 活数据，搬迁对象的主要负担接近这 5 MiB，另加根扫描和引用处理等工作。不能由此说这次 GC 的总成本就等于“复制 5 MiB”：根数量、跨代引用、对象图形状和可用 CPU 都会影响停顿。

老年代也不能统一回答成“使用标记清除”。HotSpot 的 Parallel Old 采用整理路线，历史 CMS 常规周期主要清除而不移动，G1 通过区域疏散逐步整理。活对象较多时，复制全部活数据可能很贵；到底选择什么策略，还要看暂停目标、空间余量和是否支持并发移动。

局部收集有一个正确性前提：老对象可能持有年轻对象。假设一个长期缓存新增了指向请求对象的字段，即使线程栈已不再引用它，这个请求对象也仍然存活。写屏障配合卡表、记忆集等结构记录需要检查的位置，年轻代收集据此找到从收集范围外指入的引用，避免每次遍历整个老年代。记录会有近似性，扫描时还要验证；维护这些结构需要额外 CPU 和内存。如果工作负载普遍长寿、引用修改又密集，分代收益就可能缩小。

#### 从 Eden 到 Survivor，再到老年代

传统 Serial、Parallel 及历史 ParNew 的年轻代可以用 Eden 和两个 Survivor 空间说明。一次正常年轻代复制收集前，一个 Survivor 承担 From 角色，另一个 To 准备接收对象：

1. 新对象通常先尝试在年轻代分配，小对象常使用线程的 TLAB。TLAB 属于堆内分配空间，并不把对象变成栈对象。

2. 收集时，从相关根以及跨代引用出发，确定 Eden 和 From 中必须保留的对象。

3. 适合继续留在年轻代且目标空间足够的对象复制到 To；达到相应晋升条件或 Survivor 无法容纳的对象尝试进入老年代。

4. 存活对象及引用处理完成后，Eden 和旧 From 的空间可以复用。From、To 交换角色，下一轮再重复这个过程。

两个 Survivor 是交替的角色，不能理解为对象必须从 Eden 依次经过“S0 一次、S1 一次”才能晋升。常说的 8∶1∶1 是特定配置下 Eden 与两个 Survivor 的容量比例示例；自动调节、收集器实现和启动参数都会改变实际布局。G1 采用 Region 集合表达这些逻辑角色，不能把固定的三个连续地址段硬套进去。

对象年龄表示在相应年轻代存活处理中的年龄累计，不能按运行秒数计算，也不能把所有 GC 事件都当作“年龄加一”。最大晋升年龄只是策略输入。实际进入老年代，至少要区分三类路径：

- 年龄策略：年龄达到当前收集器采用的阈值；这个阈值可能比配置上限小。

- 容量和分配路径：Survivor 或疏散目标容纳不下，存活对象可能提前晋升；老年代也放不下时，会进入失败恢复，而不是悄悄丢弃对象。

- 实现特定的大对象路径：对象创建时就按大小走特殊分配，未必经历 Survivor 年龄累计。这与前两类晋升不是同一件事。

“除了刚才说的两种，还有吗”必须承接已经回答的内容。没有那两项具体内容时，可以按上面的分类查漏补缺，但不存在一个脱离上下文的固定“第三种”。

#### 年龄阈值和 Survivor 怎样调整

在使用相应机制的 HotSpot 收集器中，`-XX:MaxTenuringThreshold` 可以影响最大晋升年龄，但设成 8 不等于每个对象都必须、也必然恰好在第八次 GC 进入老年代。

年龄阈值为什么可能低于配置上限？以 HotSpot 21 的年龄表为例，GC 先统计各年龄幸存对象的占用，再从低年龄开始累加，与目标 Survivor 容量比较。累计量越过目标时，就可能选出一个更低阈值，并继续受最大阈值约束。

这里的依据是累计占用与目标容量，不是“某一个年龄超过整个 Survivor 一半，就把所有对象立即晋升”。算出的阈值怎样用于后续疏散，还要看收集器当轮策略和可用空间。

调 Survivor 要同时看两边的代价。太小，中等寿命对象可能来不及在年轻代死亡就提前晋升，老年代增长加快；太大，在固定堆预算中会减少其他用途的空间，也可能让更多对象在年轻代反复复制。提高最大年龄可能减少过早晋升，却可能增加年轻代搬迁；降低年龄则可能把工作转移给老年代。减少一次暂停、减少回收次数、减少总 GC CPU，是不同目标。

判断顺序应当是：先看 GC 后活集是否稳定，再看年龄分布和晋升量，最后调整参数。HotSpot 21 可用 `-Xlog:gc*,gc+age=trace,gc+heap=debug` 在有界实验中观察整体事件、年龄表和各类区域变化。重点看日志中的目标 Survivor 大小、实际阈值、各年龄字节数、回收后老年代增长。JDK 8 的 `PrintTenuringDistribution` 属于旧日志体系，不能原样当作 21 的命令。

传统收集器里的 `SurvivorRatio`、`NewRatio` 与 G1 的 Region 数量策略也不是一套通用旋钮。G1 应优先保留年轻代自适应能力；用 `-Xmn` 或固定年轻代比例限制它，可能让暂停目标驱动的调节失效。能够通过诊断接口读取某个选项，也不代表该选项支持在线修改。

例如，假设解析任务的中间对象被一个有界队列保留两轮年轻代回收，随后正常出队死亡，适当保留 Survivor 空间可能避免不必要晋升。但如果任务一直不出队，或者全局集合永久保留结果，调年龄只能推迟压力，不能修复保留关系。

下面的完整程序只检查启动时的年龄上限和是否可以通过管理接口修改，不通过对象地址猜测真实晋升年龄。保存为 `TenuringEvidence.java`，使用 HotSpot 21 的 G1 运行。

```Java
import com.sun.management.HotSpotDiagnosticMXBean;
import java.lang.management.ManagementFactory;

/** HotSpot 21: inspect a startup setting, not an object's promotion age. */
public final class TenuringEvidence {
    public static void main(String[] args) {
        if (args.length != 1) {
            throw new IllegalArgumentException("Expected: maximum tenuring threshold");
        }
        int expected = Integer.parseInt(args[0]);
        var bean = ManagementFactory.getPlatformMXBean(HotSpotDiagnosticMXBean.class);
        if (!Boolean.parseBoolean(bean.getVMOption("UseG1GC").getValue())) {
            throw new IllegalStateException("Run this example with -XX:+UseG1GC");
        }
        var threshold = bean.getVMOption("MaxTenuringThreshold");
        if (Integer.parseInt(threshold.getValue()) != expected || threshold.isWriteable()) {
            throw new AssertionError("Unexpected threshold or management capability");
        }
        System.out.println("VM=" + System.getProperty("java.vm.name") + " "
                + System.getProperty("java.runtime.version"));
        System.out.println("ARGS=" + ManagementFactory.getRuntimeMXBean().getInputArguments());
        System.out.println("PASS: startup MaxTenuringThreshold=" + expected
                + ", manageable=" + threshold.isWriteable());
        System.out.println("This checks configuration, not any object's actual promotion age.");
    }
}
```

```Bash
javac TenuringEvidence.java
java -Xms16m -Xmx64m -XX:+UseG1GC -XX:MaxTenuringThreshold=1 TenuringEvidence 1
java -Xms16m -Xmx64m -XX:+UseG1GC -XX:MaxTenuringThreshold=8 TenuringEvidence 8
```

这两个命令启动两个独立进程。断言成功表示当前选项与预期相符，并且管理接口不允许写这个选项；它不证明某个对象具体在第几轮晋升。这个程序没有制造足够分配来保证发生年轻代收集，不能把一次配置检查当作年龄分布实验。

#### 数组和“大对象直接进入老年代”的边界

数组同样是对象。`int[]` 的元素存储属于该数组，`Object[]` 的元素是引用，所引用对象并不会自动内联进数组。局部变量保存数组引用，不等于数组数据就在栈里；具体分配还可能受到逃逸分析和分配消除影响。

传统 HotSpot 的某些 Serial、ParNew 分配路径支持 `PretenureSizeThreshold` 这样的预晋升参数，但不是所有收集器都采用它。不能把设置了该选项等同于 Parallel、G1、ZGC 都会遵守同一条大对象规则，也不能忽略 TLAB 与慢分配路径的区别。

G1 的大对象路径另有清晰边界：以 OpenJDK 21 GA 的实现为准，完整、已经对齐的对象大小严格大于半个 Region 时，按 Humongous 对象处理。这里包含对象头、数组长度信息、元素区及对齐，不只计算数组元素的字节数。假设 Region 为 1 MiB，完整对齐大小恰好为 512 KiB 与比它多一个对齐单位，分配分类可能不同；而长度为 512 KiB 的 `byte[]` 加上对象头后通常已经超过这个界限。没有确认对象布局前，不应直接把数组长度当作精确阈值。

Humongous 对象使用老年代中的连续 Region，相关布局和回收见 G1 一节。调整最大年龄不控制这个边界；改 Region 大小才会改变半区阈值，同时又会改变回收粒度与空间浪费。大文件大小、单个数组大小、全部处理中间结果和进程内存峰值也必须分开，不能因为支持 128 MB 文件接入，就推导出只需要 128 MB Java 堆。

### 2\. Young、并发周期、Mixed 与 Full 什么时候发生

GC 会因分配需要、对未来空间的预测、元数据压力、显式请求或失败恢复而启动，并不只在整个堆完全用尽时才发生。回答“什么时候 Full GC”，先交代收集器，再把正常工作与兜底路径分开。

常见问法包括“Minor GC 和 Full GC 的触发条件”“内存没满为什么已经 GC”“调用 `System.gc()` 是否马上 Full GC”“这行代码会不会触发 GC”。其中 Young、Minor 常用于年轻代回收；Major、Old 的口径并不统一，不能离开日志和监控定义判断它们是否等于 Full。

#### 从一次分配请求看正常路径

TLAB 用完只表示一个线程的本地分配缓冲不足。它可能重新取得 TLAB，或者让较大对象走缓冲外分配；只要年轻代仍有空间，这些操作不必引发 GC。传统分代实现通常在年轻代分配无法继续时尝试年轻代收集。G1 也会根据年轻代目标和可用 Region 调度疏散暂停，而不是要求先把 `Xmx` 对应的全部空间填满。

年轻代收集必须为幸存对象找到去处。Survivor 放不下，可以尝试晋升；老年代或其他疏散目标也不足，才可能进入更重的处理。一次 Young GC 后老年代增长，并不自动意味着内存泄漏，它可能只是正常晋升。相反，Young GC 后年轻代下降很多，也不能证明长期保留没有问题，还要看老年代或全堆活集的长期基线。

并发 GC 开始时堆还有空闲，往往正是为了避免稍后无处可分配：GC 工作期间，应用还会继续消耗空间。启动得太晚，即使本轮最终能回收很多，也可能来不及支撑这段新增占用。

历史 CMS 会结合老年代占用和预计完成时间；G1 的自适应 IHOP 则根据近期老年代分配、标记耗时和预留空间预测启动时机。分配率或晋升率突然上升、CPU 被限流，都可能使原本足够的提前量失效。因此“当前还有空闲”不能用来否定这次 GC。

#### G1 的几类事件怎样衔接

普通 Young 暂停负责年轻代疏散。需要启动并发标记时，一次年轻代暂停可以同时承担 Concurrent Start；它仍是一次暂停，但后面的并发标记不是整段 STW。不是每次 Young GC 都开启完整的标记周期。

并发标记和收尾为老年代提供存活信息及回收候选。若老区回收值得做，随后进入 Mixed 阶段：每次处理年轻代，再加一部分选中的老年代 Region。Mixed 的“混合”描述收集集合，不表示把整个堆一次性收完；没有值得回收的老区时，也不必强行安排 Mixed。

Full 是另外的整堆重处理路径。G1 在普通分配、疏散或并发进度无法满足需要，以及某些显式请求等条件下，可能执行停顿式整堆整理。疏散失败与 Full 也不是同义词：一次 evacuation failure 可以先完成必要的引用修复、保留未移动对象并恢复应用，若空间仍不足，后续再转 Full。JDK 21 的 G1 Full GC 已采用并行处理，不能把所有 Full GC 都说成单线程 Serial Old。

Humongous 分配可能推动并发周期，也可能因为缺少连续 Region 而失败；并不是每分配一个大对象都要先 Full GC。实际事件应查同一个 GC 编号下的类型、原因、前后容量和阶段耗时，例如 Concurrent Start、Mixed、G1 Compaction Pause，以及该更新版输出的疏散失败标记。不要把日志中表示一个并发周期的记录数当作 STW 次数。

#### 元数据压力和显式请求

Java 堆还有空间时，类元数据分配也可能达到触发回收的高水位。JVM 会尝试回收并在条件允许时卸载类；加载器及其类仍被有效引用时，这些元数据不能凭空释放。触发水位不等于元空间容量硬上限，失败也不能只按堆对象占用解释。某些直接缓冲区的分配重试和清理路径同样可能请求 GC，这不意味着 Java 堆已经满了。

`System.gc()` 与 `Runtime.gc()` 表达回收请求，不承诺立即回收指定对象，也不保证所有配置下都走同一种路径。HotSpot 的 `-XX:+DisableExplicitGC` 可以忽略相应显式请求；对支持的收集器，`-XX:+ExplicitGCInvokesConcurrent` 可使相关请求采用并发路线。具体适用范围要看收集器，外部诊断命令也不能一律视为已被前一个参数屏蔽。

因此，不要把定时 `System.gc()` 当作常规“清理内存”方案。它可能制造额外停顿，也可能掩盖无界保留。文件、连接、锁和事务等资源应按协议显式释放，常用 `try-with-resources` 或 `finally` 完成；等待 GC 不是业务资源生命周期管理。

#### 怎样回答“这段代码会不会触发 GC”

看到 `new` 只能说明源程序有对象创建语义，实际分配还受编译优化影响；即使确实分配，也要看当前剩余空间、收集器策略、并发线程及请求原因，才能解释某次 GC。单独一行源码不能保证“执行到这里就发生一次 Full”。

完整分析至少需要源代码、输入规模、实际 JDK/收集器、启动参数和对应日志。缺少代码或前后状态时，应先说明可分析的一般路径，不能编出对象个数、执行行号或 GC 次数。复习时可用两个反例自检：TLAB 耗尽可以不 GC，而预测性并发标记可以在堆尚未满时启动。

### 4\. G1：Region、回收集合与暂停目标

G1 用固定字节大小的 Region 作为管理单元，保留年轻代和老年代的逻辑分工，通过并发标记获得存活信息，再用 Young 或 Mixed 暂停逐步疏散选中的区域。它追求吞吐与暂停的平衡，`MaxGCPauseMillis` 是软目标，不是硬实时承诺。

面试常连续追问：“分区怎样提高效率”“Region 大小会不会动态改变”“标记完为什么不马上清空那个 Region”“目标 200 ms，为什么实际用了 300 ms”。回答要区分布局、选择策略和实际执行成本。

#### 固定的是 Region 大小，变化的是角色和数量

在同一个 G1 进程中，各 Region 使用相同的字节大小，启动时选定后不会随着每轮 GC 随意改成不同尺寸。一个区域可以用于 Eden、Survivor、Old 或 Humongous，也可以是空闲区域；年轻代和老年代由相应区域集合组成，在地址上不必各自连续。回收后重新使用区域，或增减年轻代占用的 Region 数，并不是把一个 Region 本身放大或缩小。

还要区分保留的虚拟地址范围、已提交给堆使用的内存、实际已用空间。堆扩容可以提交更多相同尺寸的 Region；归还适当空闲区域会降低已提交量。`Xmx` 不等于进程的实时 RSS，更不代表每一页都已经驻留物理内存。

以 OpenJDK 21 GA 为边界，自动 Region 大小按最大堆规模计算，目标大约是 2048 个 Region，并在 1～32 MiB 内按二的幂选择；手工指定 `G1HeapRegionSize` 的实现范围可到 1～512 MiB，也受对齐和合法性检查约束。“自动选择上限 32 MiB”与“手工支持上限 512 MiB”是两回事，不能拿某本旧书里的范围概括所有 JDK。

Region 较小，回收粒度更细，通常更容易把工作分成小批次；但区域更多、跨区关系和元数据成本可能增加。Region 较大，可能减少一些跨区记录并提高 Humongous 大小门槛，也可能使最小回收工作粒度变粗，降低找到整块空区的机会。不要仅为了让大数组不再被统计为 Humongous 就认定调大一定更好，普通年轻代复制和实际内存峰值也可能随之变化。

下面的程序同时读取 Region 大小与已提交堆容量，在有界分配前后比较。它保留 96 个 128 KiB 数组，并用 `reachabilityFence` 保证观察结束前这批对象仍具有所需可达性。保存为 `G1RegionEvidence.java`。

```Java
import com.sun.management.HotSpotDiagnosticMXBean;
import java.lang.management.ManagementFactory;
import java.lang.ref.Reference;
import java.util.ArrayList;
import java.util.List;

/** HotSpot 21: region size and committed heap are different measurements. */
public final class G1RegionEvidence {
    public static void main(String[] args) {
        if (args.length != 1) {
            throw new IllegalArgumentException("Expected: region size in bytes");
        }
        long expected = Long.parseLong(args[0]);
        var bean = ManagementFactory.getPlatformMXBean(HotSpotDiagnosticMXBean.class);
        if (!Boolean.parseBoolean(bean.getVMOption("UseG1GC").getValue())) {
            throw new IllegalStateException("Run this example with -XX:+UseG1GC");
        }
        var before = bean.getVMOption("G1HeapRegionSize");
        long committedBefore = ManagementFactory.getMemoryMXBean()
                .getHeapMemoryUsage().getCommitted();
        List<byte[]> live = new ArrayList<>();
        for (int i = 0; i < 96; i++) {
            byte[] block = new byte[128 * 1024];
            block[0] = (byte) i;
            live.add(block);
        }
        var after = bean.getVMOption("G1HeapRegionSize");
        long committedAfter = ManagementFactory.getMemoryMXBean()
                .getHeapMemoryUsage().getCommitted();
        if (before.isWriteable() || after.isWriteable()
                || !before.getValue().equals(after.getValue())
                || Long.parseLong(after.getValue()) != expected) {
            throw new AssertionError("Unexpected region size or management capability");
        }
        if (live.size() != 96 || live.get(95)[0] != 95) {
            throw new AssertionError("Allocation workload incomplete");
        }
        System.out.println("VM=" + System.getProperty("java.vm.name") + " "
                + System.getProperty("java.runtime.version"));
        System.out.println("ARGS=" + ManagementFactory.getRuntimeMXBean().getInputArguments());
        System.out.println("PASS: region=" + after.getValue() + " not writeable; committed before="
                + committedBefore + " after=" + committedAfter);
        Reference.reachabilityFence(live);
    }
}
```

```Bash
javac G1RegionEvidence.java
java -Xms16m -Xmx64m -XX:+UseG1GC -XX:G1HeapRegionSize=1m -Xlog:gc* G1RegionEvidence 1048576
java -Xms16m -Xmx64m -XX:+UseG1GC -XX:G1HeapRegionSize=2m -Xlog:gc* G1RegionEvidence 2097152
```

两个进程分别验证 1 MiB 与 2 MiB 配置。断言检查 Region 值一致、符合预期且不可通过管理接口写入；已提交堆容量只是记录，没有断言它一定增长或增长多少。JVM 的具体扩容时机不是这个程序的契约，这也不是比较两种 Region 大小性能的基准。

#### 从年轻代回收到一次并发标记周期

可以把 G1 的正常运行看成“年轻代阶段”和“空间回收阶段”交替。

开始时多次 Young\-only 回收处理年轻对象。需要获得新的老年代存活信息时，一次 Young 暂停承担 Concurrent Start，完成启动并发标记所需的工作。根区域扫描随后处理这次暂停形成的相关根区域，例如 Survivor 中指向老年代的引用；相关扫描必须与下一次可能移动这些区域的年轻代回收正确协调。

并发标记沿对象图追踪。应用继续修改引用时，SATB 屏障保留需要保留的旧引用信息，使收集器能够按开始时的快照安全判断对象存活。周期中才变成垃圾的对象可能保守保留到以后；新分配对象也有保证安全的处理约定。屏障记录、根区域扫描、对象遍历共同维持正确性，不能把“并发”理解为随时读一遍字段就足够了。

Remark 暂停完成标记收尾、引用处理及相关清理。之后还有并发准备工作，Cleanup 完成回收候选和是否进入下一阶段等决策。完全无须保留活对象的区域，可以在安全阶段直接归还；含活对象的普通老年代区域，则需要等待适当的疏散回收。阶段名相似不表示可以照搬 CMS 的四步流程，G1 的并发标记主要为后续区域化回收提供依据。

需要回收老年代时，经过相应过渡进入多次 Mixed：每次收集年轻代，再加入部分老年代候选。达到本轮回收目标、剩余收益不足或候选耗尽后，回到 Young\-only 阶段。Humongous 对象还有专门的存活判断和可提前回收路径，不能把它们当作每轮必定搬走的普通老区。

#### 标记完一个 Region，怎样决定要不要回收

标记回答“哪些对象必须保留”，选集回答“这一轮做哪些工作最划算”。有存活对象的 Region 不能因为垃圾比例很高，就把整区直接清零；必须先找到所有需要保留的对象及相关引用，搬到可用目标区域并更新引用，随后才能重用源空间。

G1 选 collection set 时，问的是“这次暂停能以多少工作换回多少空间”。它会一起估计存活字节数、复制时间、根与跨区引用扫描成本、可回收空间和暂停预算。

Young\-only 要完成年轻代任务，不能随意跳过年轻代，只挑垃圾最多的老区。Mixed 才在年轻代之外加入老年代候选：既有必须推进的部分，也有预算允许的部分，还可能在剩余时间中追加可选部分。这就是为什么“垃圾最多”不足以单独决定先收谁。

假设 A、B 两个候选 Region 都为 4 MiB，A 只有 0\.2 MiB 活数据，B 有 3\.5 MiB。只看复制量，A 往往更划算；但如果大量其他区域指向 A，扫描成本会影响选择。判断依据更接近“回收收益相对于预测成本”，而不是一个静态垃圾百分比排行榜。

`G1MixedGCLiveThresholdPercent` 影响哪些老区值得进入候选，`G1MixedGCCountTarget` 影响把候选工作分摊到多次 Mixed 的目标，`G1HeapWastePercent` 则参与判断剩余可回收空间是否值得继续处理。参数不是每次必须执行的硬承诺，具体选集还受暂停、回收进度和实际空间制约。只减少每次选入老区，可能让暂停更短，却使回收长期追不上晋升。

局部收集还需要处理收集集外部的引用。G1 用写后屏障、卡表和记忆集维护近似的指入位置，再在暂停中合并、扫描相应信息；对象移动后必须修正相关引用。SATB 主要保证并发标记的快照正确性，记忆集主要帮助局部收集发现外部引用，这两个问题不能混为一谈。跨区引用很多，或脏卡处理来不及，暂停中的扫描成本就可能上升。

#### Humongous、疏散余量和超过暂停目标

满足大对象条件时，G1 在一串连续的 Region 中分配一个 Humongous 对象，从首区起始位置放置。最后一个区域剩下的尾部空间，通常不能马上拿来分配另一个普通对象，可能形成明显浪费。总空闲 Region 足够，也不意味着存在满足要求的连续序列。

Humongous 不走普通对象的年龄晋升过程，通常也不参与常规年轻代或 Mixed 的普通搬迁。G1 可以在标记后的相应阶段回收不可达大对象，对符合条件的对象还存在年轻代暂停中的提前回收机会；极端兜底整理下的移动行为也不能概括成“永远不移动”。讨论精确阈值时要用完整对齐对象大小；讨论回收时机时要看存活、引用信息及具体路径。

普通疏散也需要目标空间。假设这一轮要搬走一批存活对象，但可用 Region 不足，GC 不能为了完成目标而删除它们。疏散失败时，一部分已搬迁对象留在新位置，未搬迁对象需要在原位置得到安全处理，随后修复必要的状态和引用；额外工作可能增加暂停。进一步没有空间时才进入 Full 等兜底路径。

`-XX:MaxGCPauseMillis=200` 表达的是期望目标，实际出现 300 ms 不代表违反保证。预测依赖过去的存活率、扫描成本和 CPU 供给；突发活集增长、跨区引用激增、CPU 配额不足、系统调度或缺页都可能改变实际耗时。目标也不能取消必须完成的根处理和正确性工作。

如果 Object Copy 主导，应看复制量、对象寿命和年轻代大小；如果根或记忆集扫描主导，应看引用结构和相关处理积压；如果 Real 时间显著高于实际 CPU 工作时间，应检查 CPU 是否拿不到或系统是否存在其他等待。降低目标可能让年轻代或可选老区集合变小，却提高回收频率、降低吞吐。先用阶段证据决定改什么，再看业务尾延迟、总 GC 成本和是否出现失败，不要把参数数字调小当作完成优化。

### 5\. G1、ZGC 与其他低暂停方案

G1 和 ZGC 的核心区别，是把对象移动等工作放在哪里完成：G1 的常规疏散主要发生在 STW 暂停中，ZGC 则把标记和重定位等大量工作并发执行，并用屏障协议保证应用访问正确。低暂停需要资源和协议支持，不等于业务请求必然更快。

回答“G1 和 ZGC 的优缺点、适用场景”“怎样把停顿压低”“ZGC 为什么还会卡”，应从机制、资源预算、版本模式三个方面展开。

#### ZGC 怎样在应用运行时移动对象

应用可能持有一个对象的旧地址，而并发 GC 正准备把它搬走。收集器必须保证：应用最终访问有效对象，搬迁前后的引用具有一致含义，多个线程不会各自把同一个对象当成互不相关的两份数据。

ZGC 使用有色指针携带与 GC 协议有关的元信息，并在加载、存储引用等路径插入屏障。快速路径尽量只做轻量检查；需要慢路径时，屏障协助完成相应标记、寻找重定位后的对象或修复引用。颜色具体编码和屏障分工随版本、代模式变化，不能把某一版的位图直接背成所有 ZGC 的永久结构。

在 JDK 21 的分代 ZGC 中，加载屏障与存储屏障分别承担适合的职责，存储屏障还配合代际引用记录及标记协议。年轻代与老年代可以按不同节奏处理，减少对长期存活对象的反复工作。它仍有短暂停顿和必要的协调，不是整个生命周期完全无 STW；也不是把 G1 的 Eden、两个固定 Survivor 和年龄上限原封不动搬进来。

G1 的优势在于成熟的整体平衡和区域化回收策略，常规停顿中可以高效并行疏散，但活数据搬迁和扫描量仍可能压到暂停上。ZGC 将更多工作并发化，可作为更严格暂停目标下的候选；与此同时，应用执行屏障、并发 GC 线程和业务线程共享 CPU，且需要在回收完成之前维持分配空间。没有一个名字能同时免除全部 CPU、内存和延迟成本。

#### 暂停很短，业务为什么仍然高延迟

ZGC 的暂停很短，分配仍可能卡住。若应用消耗空间的速度超过回收速度，线程会因为暂时拿不到分配空间而等待，这就是 allocation stall；它不是一次长 STW，却一样会增加请求时延。

遇到这种现象，先对照四个条件：活数据是不是很多，流量是否突然增加，并发 GC 是否拿不到 CPU，堆余量是否太小。检查的是“空间能否及时周转”，只看暂停图会漏掉这段等待。

可以用一个假设反例检查选型思路：GC 暂停从 20 ms 降到 1 ms，但并发 GC 与业务争抢 CPU，使计算排队增加了 40 ms，端到端响应反而恶化。这些数字只是解释口径的例子；真正比较时，需要把 GC 暂停、分配等待、CPU、吞吐与接口 p99/p999 对齐，而不是只看一张暂停图。

堆预算至少要容纳活数据和回收期间的新分配，并留出实现需要的余量。`Xmx` 是最大 Java 堆容量，`SoftMaxHeapSize` 是 ZGC 努力遵守的软目标；为了让应用继续分配，后者可以被突破，但仍受 `Xmx` 限制。它既不是容器总内存上限，也不能让活集超过物理预算后继续无代价运行。

释放不用的已提交内存可以降低占用，重新提交和访问这些页又可能增加延迟。`Xms=Xmx` 配合预触页，可以把更多提交和缺页成本提前到启动阶段，代价是启动时间与较大的内存承诺；不是每个服务都应照抄。盲目增加并发 GC 线程，也可能挤占业务 CPU。资源变化必须一起看，而非只追求更小的单次暂停。

#### ZGC 的模式必须带版本回答

以下说明的是 OpenJDK 主线对应版本，实际发行版和平台仍需确认是否提供该实现：

- JDK 11：ZGC 以实验特性引入。当时的非分代实现不能代表后来所有版本。

- JDK 15：ZGC 转为生产特性；“ZGC 一直是实验功能”不再成立。

- JDK 21、22：同时存在非分代与可选分代 ZGC。选择 ZGC 后，分代模式需要 `-XX:+UseZGC -XX:+ZGenerational`；单独 `UseZGC` 不表示已经使用分代模式。

- JDK 23：选择 ZGC 时，分代模式成为默认，非分代模式被弃用。这不表示 ZGC 成了整个 JDK 的默认收集器。

- JDK 24：移除非分代 ZGC。`ZGenerational` 成为过时选项；在 JDK 24、25 中相关旧开关会被忽略并产生警告，不能再用它切回非分代。

- JDK 26：这个旧选项到期并移除，迁移时应删除，不依赖它继续被宽容接受。

因此，“ZGC 不分代”和“ZGC 默认分代”都只有放在版本及“已经选择 ZGC”的前提下才完整。启动成功、没有明显异常也不等于模式符合预期，必须读实际参数和 GC 初始化日志。

#### Shenandoah 如何作为对照候选

Shenandoah 同样以低暂停为目标，把包括疏散在内的大量工作与应用并发执行，并通过自己的屏障和转发协议维护访问正确性。它不是 ZGC 的另一种名称，两者的元信息、屏障、分代演进与资源代价不同。

在 OpenJDK 主线中，Shenandoah 于 JDK 12 以实验特性进入，JDK 15 转为生产特性；分代模式在 JDK 24 作为实验特性引入，JDK 25 成为产品特性。JDK 25 若发行版提供支持，可用 `-XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational` 选择分代模式。这里的产品状态不表示所有厂商构建都包含它，也不能外推后续版本的默认模式。

把 Shenandoah 列入候选后，同样要检查可用 CPU、活集、分配突发和空间余量，观察是否出现分配等待、退化收集或 Full 等现象。版本说明或官方基准可以帮助提出假设，不能直接变成“我的服务一定降低多少延迟”的结论。真正的适用性仍由同负载、同资源边界下的验证决定。

### 6\. 按业务目标选择收集器

选择 GC 的顺序应是：确认版本和可用实现，明确业务目标与资源预算，建立基线，再用代表性负载比较。Serial、Parallel、G1、ZGC、Shenandoah 都有合适的使用条件，没有“超过 4 GB 必须换某个 GC”这样的统一分界。

“项目用了哪种 GC，为什么”“两个项目是不是一样”“小堆不能用 G1 吗”“批处理和低延迟接口怎样选”，既考机制，也考是否能把部署事实与设计判断分开。

#### 先认识候选，再判断是否值得换

Serial 使用串行的回收工作方式，结构和运行开销相对简单，可作为小堆、少量可用 CPU 或小型工具的候选。它并不是只能在物理单核机器启动，也不能仅凭“运行在多核”就排除；要看可用资源、活集和可接受停顿。

Parallel 用多个 GC 线程在暂停中完成工作，年轻代复制与老年代整理配合，适合把完成吞吐放在较高优先级的负载。批处理、离线计算可以将其列入候选，但若任务有严格的完成时间分位数，也仍需检查暂停。并行度过高会争抢 CPU，多线程并不能保证每次都比 Serial 更划算。

G1 通过区域化、并发标记和分批疏散平衡吞吐与暂停，适合作为很多常驻服务的基线。小堆可以使用 G1；是否比其他方案合适，取决于其固定开销、分配模式和目标，没有 4 GB 的准入门槛。8 GB、16 GB 也只能是某次部署的容量条件，不能当作通用选型线。

ZGC 和可用发行版中的 Shenandoah 适合纳入更严格暂停目标的比较，尤其当现有停顿确实来自 GC 处理活数据，而不是数据库、锁或网络。它们的并发机制需要 CPU 和内存余量，选择之前必须确认资源限制。CMS 则只保留为旧系统机制和迁移背景，不是 HotSpot 21 的候选。

历史名称可以帮助理解组合：Serial、ParNew、Parallel Scavenge 常用于年轻代；Serial Old、Parallel Old、CMS 常用于老年代。ParNew 的“并行”不表示它自身已经能并发回收老年代，也不代表 Parallel GC 的整套组合。现代回答应先报完整收集器，再解释各代采用的机制，避免只背一张旧组合连线图。

#### 用哪些数据建立比较基线

第一组是业务目标：完成吞吐、p99/p999、错误率、超时率与队列等待。交互服务可能更在乎高分位响应，批处理更在乎限定资源下的完成时间；两者都不能只看平均值。极高分位还需要足够样本量，几个请求的最大值不能冒充稳定的 p999。

第二组是对象行为：单位时间分配量、GC 后活集、晋升率、大对象分布、指针密集程度及引用修改频率。相同堆大小下，一个服务主要分配短命缓冲，另一个长期保留大对象图，适合的回收节奏可能完全不同。队列积压也会延长对象寿命，把原本短命对象推成跨多轮回收的幸存者。

第三组是资源边界：应用实际拿得到的 CPU、容器内存额度、堆外缓冲、元空间、代码缓存、线程和 GC 元数据。单看 `Xmx` 无法描述完整内存预算；在 Java 与其他进程共享资源时，还必须分别核算。ZGC 不同版本的虚拟内存映射也可能影响内存工具的统计解读，比较时要固定并说明测量口径。

要比较两个 GC，先把它们放在同一组条件下：JDK 构建、业务输入、数据集、并发模型、CPU 和总内存预算保持一致，再分别观察启动预热、稳定负载、突发和恢复。

只把 Xmx 设成相同，还不能叫“同资源”。某个方案若额外拿了更多 CPU 或进程内存，性能差异就混入了资源差异；日志级别、监控开销和测量时钟也应尽量一致。这样测到的结果，才更能回答是否值得更换收集器。

先判断基线是否已满足目标。若已经满足，换收集器带来的版本、观测和回滚成本也要算进去；若不满足，则用最长阶段和对象行为提出可验证假设。一次只调整少数相关变量，保留原配置，再观察收益是否以更多 CPU、更高 RSS、更多回收频率或更差错误率为代价。

#### “项目用什么 GC”怎样给出可核验答案

对每个项目分别确认实际运行的 JDK 版本、厂商构建和启动配置，再检查进程中生效的 GC 标志及初始化日志。构建文件中的 `source`、`target` 或开发机版本，只能说明某些构建条件，不能替代线上 Java 进程信息。镜像入口脚本和 `JAVA_TOOL_OPTIONS`、`JDK_JAVA_OPTIONS` 等环境注入也可能改变最终启动参数。

JDK 8 的常见 HotSpot Server\-class 环境默认选择 Parallel；JDK 9 把 G1 设为相应服务器配置的默认收集器。但显式选项、资源环境、发行版或其他 JVM 实现可能改变结果。没有手写 GC 参数时，正确做法仍是查实际进程，而不是用“默认应该是”结束回答。

确认使用 G1 后，还要能接着解释：为什么该服务需要吞吐与暂停平衡，存活集和分配模式是什么，实际观察到的暂停是否影响目标。如果只是使用了框架默认启动方式，也可以如实说明选择来自当前部署基线；知道如何核验和解释，不等于必须声称自己做过收集器迁移或生产调优。

以 NoteWeave 为例，已知链路把资料解析、切片、向量化和索引构建拆成 Kafka 异步任务，并由 Java Host 与 Python Worker 分层承载工作。这个架构可以帮助提出资源问题，却不能单凭架构推断实际 JDK、GC 或堆参数。如果评估其内存表现，应先确认大文件和中间结果到底保留在哪个进程，再检查并发任务数、有界缓冲、队列积压与对象存活时间。异步化减少业务请求链路被长任务占用，不自动证明总内存减少或吞吐提升。

#### 怎样回答“为什么不直接用暂停最低的那个”

业务目标通常是约束下的整体结果。严格暂停可能值得付出额外 CPU 和内存，但如果服务主要在等待慢 SQL，换 GC 的收益可能很小；如果 CPU 已接近配额，并发回收可能进一步延长排队。反过来，大活集导致长疏散暂停而资源还有余量时，评估并发移动方案就有明确理由。

最终答案应能说出候选、机制依据、测量指标和回滚条件。不要许诺“这个 GC 必定低于 10 ms”，也不要因为某个实现最初是实验功能，就忽略它在后续版本中的成熟度变化。

### 3\. 历史 CMS：低暂停从哪里来，失败时怎样恢复

CMS 是历史 HotSpot 中面向较短老年代停顿的收集器：把主要标记和清理工作放到并发阶段，常规回收不全面移动存活对象，换来碎片、浮动垃圾以及并发 CPU 和空间余量的要求。以下机制以 JDK 8 系列为背景；CMS 在 JDK 9 被弃用，JDK 14 被移除，JDK 21 不再提供这一选择。

“CMS 的流程和缺点”“为什么用 Serial Old 做后备”“CMS 和 G1 有什么区别”“Java 会不会碎片化”，都可以从正常周期、两类空间问题和兜底恢复展开。

#### 正常周期为什么仍然有停顿

CMS 负责老年代，年轻代常与历史 ParNew 配合。年轻代收集可能穿插在老年代并发周期之间；这不意味着两次暂停完全重叠，靠近的暂停仍可能让业务感受到一次较长中断。

初始标记需要暂停应用，建立本轮老年代追踪的起点，包括从根及年轻代等位置进入老年代的引用。它不是在这一步递归扫描整个对象图。随后并发标记沿引用关系追踪存活对象，应用线程继续执行。并发预清理等阶段尽量提前处理引用修改留下的工作，减少最后收尾负担。

重新标记同样需要暂停，补齐并发修改期间尚未处理的可达关系，达到本轮安全清理的条件。CMS 的增量更新协议会记录需要重新扫描的位置，不是先任由活对象“消失”，再在 remark 把它救回来。最后并发清理将可回收空间加入空闲结构，并准备下一轮；它通常不把全部存活对象紧挨着搬到一端。

减少暂停的关键，是把耗时工作与应用并发执行，以及常规路径避免全面搬迁；不能只归结为“标记清除天生最快”。并发 GC 消耗的 CPU 仍来自机器预算。计算密集服务可能在没有长 STW 的时段吞吐下降，引用修改多也可能增加重新标记的工作。

#### 碎片和浮动垃圾是两个问题

碎片是可用空间的布局问题。清理后可能留下很多分散的空闲块，空闲总量看起来够，却找不到本次分配所需的连续块。举例说，两个 4 MiB 空闲块之间隔着存活对象，不能直接满足一个要求连续 6 MiB 的对象。这个例子强调连续性，不代表真实服务的分配大小。

浮动垃圾是本轮判断与应用继续变化之间的时间差。一个对象在标记时可达、已经被保留，随后才失去最后一条引用，本轮可能仍不回收，要等后续周期。它并不只产生于清理阶段，更不等于内存泄漏；后续回收能否恢复空间才是关键。

两者都会挤压空间，但治理方向不同。碎片要关注空闲块分布和大对象分配；并发追不上要关注分配、晋升速率和回收完成时间。提前启动或增加余量可能让周期及时完成，却不保证消除碎片。减少不必要的大对象、缩短中间数据保留以及改用有移动整理能力的收集器，也是不同层次的选择。

#### 为什么需要停顿式后备，而不是继续并发等下去

CMS 没来得及回收，或者现有空闲块不能满足老年代分配时，可能出现 `concurrent mode failure`。此时继续放任应用分配无法解决空间短缺，需要停下来完成回收。另一个名字 `concurrent mode interruption` 通常表示显式或诊断回收请求打断并发周期，不能把两者一律解释成并发进度不够。

历史面试常把后备概括为 Serial Old。更完整的回答是：JDK 8 的 CMS 有前台回收和压缩等分支，特定路径会使用停顿式标记整理；是否压缩与该更新版、`UseCMSCompactAtFullCollection`、`CMSFullGCsBeforeCompaction` 等历史配置及失败状态有关。这个名称有助于说明兜底设计，但不能推广为“任何 CMS Full GC 都是同一个算法”，更不能推广到 Parallel 或现代 G1。

为什么空间已经紧缺时，还要停下应用？因为继续让应用分配，会继续消耗回收所需的余量。停顿先稳定这个过程，再按需要移动活对象、修正引用和合并碎片，让正确的对象状态与分配进展优先得到保证，代价是较长暂停。

但整理只能重新组织已有空间。活数据已经接近或超过容量时，它不能创造额外内存，最后仍可能 OOM；即使这次 Full 成功，后续分配与回收速率也未必已经平衡。

#### 与 G1 对比时抓住哪些差别

CMS 的常规老年代回收以非移动清理为主；G1 管理整个堆，用等大 Region 保留逻辑分代，通过年轻代和 Mixed 的停顿疏散逐步整理空间。两者都有并发阶段和暂停阶段，区别不是“一个并发、一个不并发”。

CMS 需要防范空闲块碎片与并发模式失败；G1 需要防范疏散目标不足、Humongous 连续区域压力和 Full 兜底。CMS 的增量更新与 G1 的 SATB 服务于不同并发标记协议；这与记忆集支持局部收集又是不同职责。G1 有整理能力，也仍会有尾部浪费、连续空间压力，不能说它绝不会有任何碎片问题。

旧系统迁移时，应移除已经失效的 CMS 配置，重新建立目标收集器的基线。先把问题描述成分配模式、存活集、暂停和资源预算，再选择新实现；不要把一整串旧 CMS 参数换个收集器名称继续使用。

### 7\. Java 与 Go GC 的比较边界

Java 和 Go 都可以通过从根出发的追踪来保留仍可达对象，但具体收集器、分配方式、移动协议和调参模型不同。比较应明确为 HotSpot 的某个 GC 与 Go 标准工具链的某个版本，而不是断言某种语言天生更快、暂停更短或更省内存。

“Java/Go GC 的核心原理与优缺点”可以按共同原则、实现差异和评价方式回答；如果提问只说“讲一下垃圾回收”，先确认语言或用通用追踪框架开头，不要自动把所有运行时都描述成 Eden、Survivor、老年代。

#### 共同原则：仍然可达，就可能继续保留

运行时沿根引用追踪对象图，发现必须保留的对象，再回收其余可回收空间。循环引用本身不是追踪式 GC 的障碍；一组对象相互引用但整体已经无法从根到达，仍可以回收。反过来，一个全局集合永久保存所有请求上下文，即使业务再也不需要这些内容，GC 也无法凭业务意图把它们删除。

并行表示多个 GC 工作者协作，并发表示部分 GC 工作与应用同时执行；两者可以同时存在。并发过程需要屏障和阶段协调以防漏掉仍可能使用的引用，仍可能有短暂停顿。GC 写屏障服务于对象追踪或移动协议，与语言内存模型中为了线程可见性、顺序约束而讨论的屏障不是同一概念。

自动管理内存减少手工释放错误，却不能消除无界缓存、队列积压和外部资源泄漏。把 Java 集合换成弱引用，或把 Go 对象放入 `sync.Pool`，都不能自动表达业务保留期限；缓存和复用机制也必须满足容量、生命周期与正确性要求。

#### HotSpot 多收集器与 Go 标准运行时

HotSpot 21 可以选择不同策略。G1 是区域化分代、并发标记与 STW 疏散的组合；ZGC 可以选择非分代或分代模式，把更多移动工作并发完成。不能用 CMS 的非移动清理概括全部 Java GC，也不能说 Java 对象一定采用某种统一的年龄和空间布局。

以 Go 1\.26\.0 标准运行时为具体边界，其堆 GC 是并发标记清除、非分代、非压缩的追踪实现，支持多个工作者并行处理，并使用写屏障。开始标记前要完成必要的阶段切换；随后后台标记工作者和分配者协助共同推进，标记终止也包含短暂停顿，清扫在后台和分配路径中继续进行。

分配者协助意味着分配对象的 goroutine 可能需要承担一部分 GC 工作，不能把低 STW 时间理解成每次分配都没有额外成本。对象图里的指针数量、扫描局部性和分配速率同样重要。按大小级组织对象、配合与 P 相关的分配缓存，可以减少常见路径的共享锁和部分碎片成本，但非压缩堆并不意味着没有碎片。

Go runtime 不只负责 GC，还支持 goroutine 调度、栈管理等运行时工作。goroutine 栈可随需要增长和复制，这与堆 GC 是否压缩是两个问题。因此，“Go 堆对象在这个实现中不由压缩 GC 移动”不能简化为“Go 的所有内存永远不移动”。逃逸分析也会影响一个值放在栈还是堆上，判断要依据实际编译版本和上下文，不能只看源码出现 `new` 或返回指针。

#### GOGC、GOMEMLIMIT 与版本演进

`GOGC` 控制 GC 在空间和回收工作之间的取舍。提高目标增长比例，通常给两轮 GC 之间留下更多分配空间，有机会减少回收频率，但会提高内存需求；降低它则可能增加 GC 工作。现代 Go 的目标计算会考虑存活堆和相关根扫描成本，不能简单把某一刻 RSS 乘以固定倍数当作下一次触发点。

GOMEMLIMIT 从 Go 1\.19 引入，限制的是运行时管理内存的软目标，不能直接当成进程 RSS 上限。cgo 等外部申请的内存可能不在这个口径内，容器中的非 Go 内存和外部组件仍要单独留预算。

如果把目标压得过低，GC 可能一直忙，却难以让程序前进。运行时为避免无限消耗 CPU，可以在压力下突破软目标。因此，把容器限额原样填进 GOMEMLIMIT，并不能保证进程绝不 OOM。

Go 1\.25 提供实验性的 Green Tea GC，Go 1\.26 将它设为默认，主要改进小对象标记、扫描的局部性和 CPU 扩展性。这是具体版本中的实现变化，不意味着 Go 从此变成类似 G1 的年轻代/老年代布局，也不能据此给任何业务承诺固定百分比收益。

Java 侧也不能把参数机械对应过去。`Xmx` 的 Java 堆上限、ZGC 的 `SoftMaxHeapSize` 与 Go 的 `GOMEMLIMIT`，约束对象和软硬程度不同；`MaxTenuringThreshold` 更没有在上述非分代 Go GC 中直接对应的意义。

#### 怎样比较优缺点而不变成语言排名

先保持业务语义和资源预算一致，再观察分配量、活集、CPU、实际内存、吞吐和端到端延迟。Java 与 Go 的库实现、对象表示、JIT 预热、数据结构及外部调用都可能不同，结果不能全部归因于 GC 名称。

Java 的多个收集器提供了更丰富的取舍空间，也带来版本与配置的复杂度；Go 标准工具链的统一策略减少了选择项，但仍需要管理 assist、指针扫描和内存目标。排查 Java 可以结合 GC 日志、JFR 和对象保留路径；Go 可以结合运行时指标、堆与分配 profile、`gctrace` 和编译器逃逸信息。累计分配量说明生产了多少对象，当前存活量说明保留了多少，两个指标不能互相替代。

一个完整答案应该落在这样的判断上：两边都要控制无意义分配与无界保留，再针对具体运行时优化；没有经过同负载实验，不能声称某一语言的 GC 在自己的项目里赢了多少。

### 8\. JDK 版本迁移：运行时变化怎样落到项目

从 JDK 8 迁到 21 或 22，不只是换编译器：默认与可用 GC、线程模型、日志和封装边界都会变化。先确认真实部署版本，再做兼容性与性能回归；“使用了新版本”不等于“所有相关 API 都已稳定”。

“平时用哪个 JDK”“8 与 21、22 有什么区别”适合先说当前项目的真实版本，再围绕 GC、并发和运维变化展开。构建版本、目标字节码版本与运行版本必须分开，不能仅凭项目能编译就推断它采用的 GC 或运行时行为。

#### 把几个重要边界记成时间线

JDK 8 已经移除 HotSpot 永久代，类元数据使用 Metaspace；不是到 21 才发生这件事。方法区仍是 JVM 规范里的逻辑概念，Metaspace、堆中的类镜像和静态值、代码缓存等物理位置不能合并成一句“方法区全部搬到堆外”。元空间可以增长，也仍有容量和加载器保留问题。

JDK 8 常见服务器配置默认 Parallel；JDK 9 将 G1 设为相应服务器配置默认，并引入统一 JVM/GC 日志。CMS 在 9 弃用、14 移除。G1 的 Full GC 在 JDK 10 并行化，所以不能用 JDK 8 时代对 G1 Full 的描述解释 JDK 21。

JDK 21 正式提供虚拟线程，21、22 都可选择分代 ZGC，但还不能套用 23 的 ZGC 默认代模式或 24 的非分代移除行为。JDK 22 对 G1 引入 Region pinning，让 JNI 临界访问中的对象所在区域可以被固定，其余区域仍能参与相应回收；这与“虚拟线程固定载体”是不同问题，不能因都叫 pinning 就混为一谈。

版本讨论应到具体实现和功能状态。JDK 22 的 `StructuredTaskScope` 仍是预览 API，需要对应的预览编译、运行设置；它的生命周期模型值得理解，但不能因为虚拟线程在 21 已正式化，就把所有与之相关的并发 API 一并称为稳定。

#### 虚拟线程带来的机会与新边界

JDK 8 的平台线程常通过线程池复用和限制数量。JDK 21 的虚拟线程由 JVM 调度到载体线程执行，适合大量等待型任务，让阻塞式编程模型在高并发等待下更便宜。它不会增加 CPU 核心，也不会扩大数据库连接池、远端配额或内存。

虚拟线程通常可以一任务一个，不必为了复用廉价线程再建固定虚拟线程池。真正需要限制的是任务和下游资源：入口允许多少任务进入，下游同时允许多少调用，应分别控制。

若先把全部任务都创建出来，再让它们在内部等许可，等待中的请求上下文和结果句柄仍可能大量存活。平台线程少了，只说明这一项资源减少，不能据此断定全部在途状态也减少。

在 JDK 21、22 中，虚拟线程在持有 `synchronized` 监视器时执行某些阻塞操作，以及某些 native 或外部函数路径，可能无法卸载载体。需要关心的是频繁、长时间阻塞造成的资源占用，短小内存临界区不应因为看到关键字就被全部改写。JDK 24 消除了 `synchronized` 导致的这类固定载体问题；native 等边界仍需检查，版本升级也不会解除业务锁本身的等待。

虚拟线程支持 `ThreadLocal`，但过去“每个固定池线程缓存一份昂贵对象”的策略，迁移后可能变成每个任务一份。任务数量增加时，这些对象会影响内存与 GC。迁移应检查上下文传播、阻塞库适配、超时和取消，而不是只替换执行器名称。

#### 日志、依赖与运行参数也要迁移

JDK 9 之后的 `-Xlog` 使用标签、级别和输出选项表达日志。旧的 `PrintGCDetails`、`PrintTenuringDistribution` 等参数及解析脚本，要按目标版本核对和迁移。监控可能错误地把所有 Old 事件相加当作 STW、漏掉并发周期或继续查找已经不存在的 CMS 名称，应用没有报错也可能已经失去可靠观测。

模块化和后续强封装会影响依赖 JDK 内部类、深反射和某些字节码工具的代码。迁移前应检查框架、序列化组件、代理、agent、JNI 库与打包方式；需要临时开放某些包时，应明确对象和原因，不把无限制开放当作永久兼容方案。动态加载 agent 等行为也可能在不同版本产生新的警告或限制，运维和诊断路径同样需要回归。

启动参数应从清洁基线开始，保留有明确目的且目标版本支持的设置。删除无效 CMS 和永久代参数，核对 ZGC 模式开关的生命周期，检查容器中的实际 CPU 和内存识别。某个选项启动时被忽略的警告，不能视为它仍然按旧含义工作。

#### 一个可执行的迁移验证思路

先记录旧进程的实际版本、完整启动配置、关键业务指标和资源口径，保留原镜像、配置及可行的回滚方式。新版本先跑功能测试和依赖兼容性检查，再建立默认或少量明确参数的性能基线；不要同时升级框架、换 GC、改线程模型和翻倍并发后，把所有变化混在一组结果里。

性能验证应分启动、预热、稳定负载、突发和恢复五种状态。启动时可能有类加载、编译和页提交成本；稳定阶段需要看吞吐、业务高分位延迟、GC CPU、暂停和活集；突发后要确认队列能消退、内存基线能恢复。长期任务还要检查超时、取消、失败重试和资源释放路径。

如果进一步把平台线程任务迁到虚拟线程，单独验证入口准入、下游容量、`ThreadLocal` 和固定载体相关行为。如果进一步换 GC，保持业务和资源条件不变，确认变化来自收集器，而不是无意扩大了内存或 CPU。达到预先定义的目标且没有破坏其他约束，再扩大使用范围；出现兼容性或资源回归时，能明确退回哪一套组合。

面试口述可以收束为：“我先确认实际运行版本和配置，再按 GC、线程模型与观测兼容性比较。机制变化能解释为什么值得评估，项目结论要由真实回归结果支持。”这样既能展开原理，也不会把尚未验证的收益说成个人经历。

## 第四部分：JVM 诊断与调优

### 运行时证据与监控指标

运行中的 JVM 要把内存、GC、线程、类加载与编译、进程资源放在同一时间线上，再用业务吞吐、错误率和尾延迟判断问题是否真的影响服务。

可能的问法：程序运行时关注哪些 JVM 核心指标？两个项目分别用了什么 GC？累计 GC 时间能算出 p99 吗？堆占用不高，为什么进程仍然危险？

#### 先证明自己观察的是哪个运行环境

诊断的第一张“底图”是实例身份，而不是参数推荐。记录服务版本、制品或构建哈希、实例与进程启动时间、JDK 发行版和补丁版本、收集器、堆参数、CPU 与内存配额。相同服务名下可能同时存在不同发布版本；同一 PID 也可能在进程退出后被复用。因此，指标差分至少要识别同一实例的同一次启动。

构建时使用 JDK 21，并不能证明生产进程也运行在 JDK 21；启动脚本没有写收集器选项，也不能独立证明最终用了哪一个收集器。环境变量、容器入口脚本和运行时自适应选择都可能影响实际结果。被问到“两个项目用了什么 GC”时，要分别核对各项目部署的版本、启动日志和运行时证据。真实配置暂时不清楚，就说明查证方法，不凭开发机默认值代答。

在有权限的目标进程上，可先使用以下只读检查思路。PID 要替换成已确认的目标，命令是否支持及影响等级以该进程的帮助为准：

```Plaintext
jcmd <pid> help
jcmd <pid> VM.version
jcmd <pid> VM.command_line
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
```

`java -version` 读取的是本次启动的 Java 可执行文件；`jcmd <pid> VM.version` 针对已经运行的目标进程。两者不能随意互换。`getInputArguments()` 提供传给 JVM 的输入参数，GC MXBean 提供实际管理器名称，但输入参数不等于全部生效默认值。分享命令行、系统属性和日志前要检查是否包含凭据或业务敏感值。

#### 把存量、增量与分布分开

**内存是存量，增长速度和回收后基线才解释趋势。** 堆的 `used` 是当前已使用量，`committed` 是 JVM 已承诺可用的容量，`max` 是允许达到的上限；`max` 或初始值可以为 `-1`，表示未定义。它们不是三份相互独立的内存，更不能把 `committed` 直接当 RSS。即使 `used < max`，进一步提交内存仍可能因系统资源不足而失败。

年轻代的锯齿式上升再下降通常是分配与回收在工作。值得关注的是：相近负载下，经过能够回收相应区域的收集后，活集是否持续扩大；老年代晋升速度是否超过回收速度；是否出现很多大对象、疏散失败或分配等待。一次 Young GC 后老年代没有下降，不等于老年代泄漏，因为那次收集可能根本不以回收该老年代集合为目标。

非堆需要分别看 Metaspace、Compressed Class Space、Code Cache 等池；直接和映射缓冲区看 BufferPool 的数量、总容量与实际内存使用估计。容量与实际占用不必相等，部分估计值可以未知；库自己的缓冲池还应读其池内空闲、已借出、待释放等指标。堆中的一个小包装对象可能持有很大的本地缓冲。

**GC 次数和时间通常是累计计数，不是窗口事件明细。** 对标准 GC MXBean，`CollectionCount` 和 `CollectionTime` 分别给累计次数和近似累计毫秒数，未知时可返回 `-1`。先确认进程未重启、管理器未改变，再做前后差分。遇到未知值、计数回退或采样缺口，要保留缺失状态，不能当作零。

假设同一进程的同一管理器在 60 秒内，累计次数从 100 变成 130，累计时间从 2000ms 变成 2300ms。可以确认的是：这个口径新增 30 次，累计时间约增加 300ms。再算 300 ÷ 30，得到的 10ms 只是粗略平均，里面没有足够信息推出 p99。

也不能直接把 300ms ÷ 60 秒说成“所有请求停顿占比 0\.5%”。先核对统计的是并发收集耗时还是 STW、多个管理器是否有重叠；重叠时段不能直接相加。要回答尾延迟，必须继续看事件级数据和业务请求。

要知道尾部，必须保留事件级暂停数据，按 Young、Mixed、Full 或具体并发阶段分组，看窗口内次数、分位数和最大值。并发周期持续五秒不意味着应用暂停五秒；五次短暂停也不等于一次等长长暂停。窗口很小时，p99 可能只是在反复观察最大样本，解释时要带样本量和负载阶段。

**线程与类加载也要区分当前值、峰值和累计值。** 平台线程关注数量、创建速度、运行与阻塞状态、CPU 热点和死锁；线程池另看活跃任务、排队长度、排队时间、拒绝数及任务完成速度。Java 21 的 `ThreadMXBean` 主要管理平台线程，不能据其数量推导所有虚拟线程。虚拟线程任务需要结合该版本支持的录制事件、线程转储和业务执行器指标，不能把载体线程少理解为并发任务少。

类加载要同时看当前加载数、累计加载数和累计卸载数。累计加载数本来就不会因卸载下降；当前类数、加载器数、Metaspace 一起上升，才值得进一步调查动态生成类或热部署生命周期。编译侧看预热阶段、编译活动、Code Cache 余量及反优化线索。新实例刚启动时的编译 CPU 与稳定态业务热点不是同一种现象。

#### 把 JVM 放回进程、容器和业务链路

同一窗口至少再关联三组证据：

- CPU：进程消耗、分配到的 CPU 配额、节流时间与次数、宿主争用。容器被节流时，GC 和业务线程都可能排队；平均 CPU 百分比还可能因分母不同而误导。

- 内存：RSS、容器当前用量与上限、系统内存压力、缺页和交换。`Xmx` 之外还有线程栈、元空间、代码缓存、直接内存、GC 元数据和本地库。容器统计也不一定等于某个 Java 进程 RSS，可能包含同容器其他进程和文件缓存等。

- 业务：进入请求数、完成请求数、错误与超时、p95/p99、队列深度、最老任务年龄、输入文件尺寸、重试量、缓存条目和下游耗时。吞吐已经掉下去时 GC 次数减少，不能认作优化成功。

假设某服务回收后堆长期稳定在 1GiB，但 RSS 持续上升，应沿本地缓冲、平台线程、类元数据、本地库以及内存归还行为继续排查；不能因为 Java 堆稳定就说“没有内存问题”，也不能立即说“Java 对象泄漏”。NMT 适合比较 HotSpot 所跟踪类别的增长，需要在启动时开启，可建立 baseline 再看差分；它不覆盖所有非 JVM 本地分配，也有额外开销。NMT 的 reserved、committed 不是操作系统 RSS 的直接替代。

工具的职责应清楚：监控适合发现趋势；GC 日志解释收集类型、原因、阶段与占用变化；JFR 把 GC、分配、CPU、锁和 I/O 等事件放到时间线上；线程转储提供线程状态和调用栈；heap dump 提供堆对象及引用图。它们互补，不是换一个工具就能回答全部问题。日常告警围绕 SLO、资源余量及稳定态基线设置，避免把“GC 次数不为零”当故障。

#### 完整示例：读取实际收集器并做有界分配

下面的 `GcEvidence` 面向 Java 21。它保留最多 32 个 16KiB 数组，不断替换旧槽位，总共做 10,000 次分配，并校验最后保留的内容。程序记录运行时身份、输入参数、收集器名称和累计计数前后差分，不把数组长度断言当作“发生过 GC”的证明。

```Java
import java.lang.management.GarbageCollectorMXBean;
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryUsage;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public final class GcEvidence {
    private static volatile int sink;
    private record Counter(long count, long millis) { }

    private static Map<String, Counter> snapshot(List<GarbageCollectorMXBean> beans) {
        Map<String, Counter> result = new LinkedHashMap<>();
        for (GarbageCollectorMXBean bean : beans) {
            result.put(bean.getName(), new Counter(bean.getCollectionCount(),
                    bean.getCollectionTime()));
        }
        return result;
    }

    private static String delta(long before, long after) {
        return before < 0 || after < 0 || after < before
                ? "UNKNOWN" : Long.toString(after - before);
    }

    private static void memory(String stage) {
        MemoryUsage u = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
        System.out.println(stage + " HEAP used=" + u.getUsed()
                + " committed=" + u.getCommitted() + " max=" + u.getMax());
    }

    public static void main(String[] args) {
        if (Runtime.getRuntime().maxMemory() > 64L * 1024 * 1024) {
            throw new IllegalArgumentException("Use -Xmx32m or -Xmx64m");
        }
        System.out.println("VM=" + System.getProperty("java.vm.name")
                + " " + System.getProperty("java.runtime.version"));
        System.out.println("PID=" + ProcessHandle.current().pid()
                + " START_MS=" + ManagementFactory.getRuntimeMXBean().getStartTime());
        System.out.println("ARGS=" + ManagementFactory.getRuntimeMXBean().getInputArguments());
        List<GarbageCollectorMXBean> beans = ManagementFactory.getGarbageCollectorMXBeans();
        System.out.println("GC=" + beans.stream().map(GarbageCollectorMXBean::getName).toList());
        memory("BEFORE");
        Map<String, Counter> before = snapshot(beans);
        long start = System.nanoTime();
        byte[][] retained = new byte[32][];
        for (int i = 0; i < 10_000; i++) {
            byte[] chunk = new byte[16 * 1024];
            chunk[0] = (byte) i;
            retained[i % retained.length] = chunk;
            sink += chunk[0];
        }
        long elapsed = System.nanoTime() - start;
        Map<String, Counter> after = snapshot(beans);
        for (int slot = 0; slot < retained.length; slot++) {
            int last = 9_999 - ((9_999 - slot) % retained.length);
            if (retained[slot] == null || retained[slot].length != 16 * 1024
                    || retained[slot][0] != (byte) last) {
                throw new AssertionError("Bounded retention invariant failed");
            }
        }
        for (String name : before.keySet()) {
            Counter a = before.get(name);
            Counter b = after.get(name);
            System.out.println(name + " COUNT=" + b.count() + " TIME_MS=" + b.millis()
                    + " DELTA_COUNT=" + delta(a.count(), b.count())
                    + " DELTA_TIME_MS=" + delta(a.millis(), b.millis()));
        }
        memory("AFTER");
        System.out.println("WORKLOAD_NS=" + elapsed + " sink=" + sink);
        System.out.println("PASS bounded allocation; counters are not pause percentiles or a benchmark");
    }
}
```

可以在独立实验目录编译后，以小堆、明确的 G1 选择和轮转日志运行：

```Bash
mkdir -p classes logs
java -Xmx128m -m jdk.compiler/com.sun.tools.javac.Main \
  -source 21 -target 21 -Xlint:all -Werror -encoding UTF-8 \
  -d classes GcEvidence.java
java -Xms32m -Xmx32m -XX:+UseG1GC \
  '-Xlog:gc*,safepoint:file=logs/gc.log:time,uptime,level,tags:filecount=2,filesize=1m' \
  -cp classes GcEvidence
```

每轮分配 16KiB、保留 32 份只描述程序控制的数组负载，不代表整个进程恰好使用 512KiB。类加载、管理接口、数组对象头、日志与 JVM 自身也需要资源。最后检查日志是否真的出现 Young 暂停，再看相应管理器的增量。不要要求每台机器收集次数和毫秒数相同；计数读取也不是对整个运行时的一次原子快照。

这个例子适合验证“我读到了哪个 JVM、哪个收集器、什么累计值”，不适合比较 G1 与 ZGC 快几倍，也不能代表生产 p99。性能对比还需要预热、代表性负载、重复窗口、CPU 与总内存预算以及端到端业务指标。

追问时可继续回答：如果累计次数变小，先查进程身份或计数重置；如果 GC 时间低但请求慢，转向排队、锁、I/O、分配等待与调度；如果 `max=-1`，展示绝对占用和可用的外部限额，而不是计算没有意义的使用率。

### GC 突然变慢与频繁 Full GC 的排查

GC 从一秒变成五秒时，先确认比较的是同一种事件和同一时间口径，再把耗时拆到阶段、存活数据和系统资源上；频繁 Full GC 则要进一步找到为何反复需要全堆恢复或显式收集。

可能的问法：原来 GC 一秒完成，现在五秒，怎么排查？线上 Full GC 很频繁怎么办？jstack 有什么用？响应时间周期性从 50ms 变成几秒，是不是 GC？

#### 先固定口径，再建立事件时间线

“一秒”和“五秒”可能分别是请求延迟、一次 STW、整个并发标记周期，甚至某监控窗口累计耗时。先问清定义，再对齐 JDK、GC、堆与容器配额、实例规格和部署版本。Young 变成 Full，是回收路径发生变化；并发标记周期变长，也不能直接说停顿增长五倍。

将业务尖刺、日志时间戳、JVM uptime 和 GC ID 对齐。GC ID 用于关联一次收集的阶段，但不应把安全点日志或相邻所有行强行归入同一 GC。JDK 9 以后的 HotSpot 可用统一日志保留 `gc`、阶段与 `safepoint` 信息，并给磁盘配额与轮转。只开摘要看不见关键阶段时，再在受控窗口提高所需标签的级别，避免长期全量 debug 日志把磁盘和 I/O 打满。

安全点总耗时至少要区分：发起请求后，线程到达安全点花了多久；已经进入安全点后，执行 VM 操作又花了多久。若主要慢在到达安全点，单调堆大小未必能解决；若主要慢在疏散复制，就应回到活对象和目标空间。业务线程被暂停后的积压还可能在恢复后继续影响延迟，因此请求尖刺可能长于 GC 暂停本身。

#### 按最慢阶段提出可反驳的假设

**复制、疏散或整理变慢：先看工作量。** 对采用 STW 疏散的年轻代收集，回收集合容量相同，不代表存活对象数量、字节数及引用扫描量相同。队列积压会让原本很快结束的请求对象跨过多次 GC；新增缓存会增加存活集；重试并发可能让同一份资料出现多份表示。看对象年龄、晋升量、收集集中的存活字节、老年代余量，判断是多做了复制工作，还是目标空间不足。

对 G1，继续看 Humongous Region 数量、可用 Region、疏散失败及 Full 前的收集序列。大对象可能需要连续的 Region，显示“总空闲还不少”不代表该次分配能成功。Region 大小、对象阈值和疏散机制本身需要结合具体版本；诊断时优先用实际日志中的 Region 大小与完整对象大小，而不是只看数组有效载荷。

**根或堆引用扫描变慢：看保留图的形状。** 线程大量增长可能增加栈根扫描工作；密集跨代、跨 Region 引用以及待处理的卡信息可能增加扫描量。观察 G1 的 Merge Heap Roots、Scan Heap Roots 等阶段以及对应版本的细项，不把 SATB 标记日志和记忆集扫描混成同一件事。只有这些阶段确实占主要时间，才值得围绕跨区引用、对象组织或 Region 粒度做实验。

**引用处理或类卸载变慢：看对象类别与生命周期。** 大量软、弱、虚引用以及需要处理的清理关联可能增加引用处理工作；动态生成类和加载器增长可能增加元数据压力。不是看见一个引用处理阶段就要关掉引用机制，而是找为什么这些对象集中产生、为什么加载器长久不退役，以及可否减少不必要的注册和临时结构。

**GC 得不到 CPU 或被系统拖慢：先把“干了多久活”和“等了多久”分开。** 日志的 User、Sys 是 CPU 时间，Real 是经过的墙钟时间。并行 GC 会把多个线程的 CPU 时间累计起来，所以 User 总和大于 Real 并不奇怪。

若 Real 明显增长，CPU 工作量却没有相应增长，先查容器节流、宿主争用、调度延迟和虚拟化环境。若 Sys 升高，再查内存提交、缺页、系统内存压力、交换和日志写入。高 Sys 能给调查方向，但不能单独证明某个原因。

`Xms=Xmx` 或预触页可把部分提交成本移到启动阶段，但会提高启动成本和内存预算要求，不能当成诊断前的固定模板。先证明相关成本在故障窗口出现，才有理由试验。增加 GC 线程数也受可用 CPU 约束，线程更多可能只是让业务与 GC 争抢同一份配额。

#### Full GC 要沿“触发原因—回收收益—再次触发”看一整段

先确认日志确实是 Full，而不是监控把所有老年代活动都标成 Full。历史 CMS 的并发老年代周期与全堆停顿不是同义词，G1 的 Mixed 也不是 Full。再看 cause 和前后事件：

1. **显式请求或工具操作。** 若原因是 `System.gc()` 或诊断请求，追查业务库、定时任务及运维操作。不要看到 Full 就先认定堆泄漏。禁止显式请求或使其走并发路径，需要核对版本、收集器、直接内存回收等依赖和实际收益；外部工具仍可能请求收集。

2. **分配、晋升或疏散进展不足。** 检查 Full 前年轻代是否频繁晋升、G1 并发标记是否来不及完成、Humongous 是否突增，以及回收所需余量是否被压缩。历史 CMS 还要看碎片与并发失败线索。应用分配速度突然变快、活集变大和 CPU 变少，都可能让原先够用的配置失效。

3. **元数据压力。** 结合 Metaspace 和类加载器数量，确认是正常的新类加载峰值、上限过小，还是旧加载器无法卸载。堆空间充足不意味着元空间也有余量；也不能说元空间只能靠 Full GC 才回收。

4. **回收后仍很满。** 若 Full 能回收很多空间但很快再次触发，重点查分配速率、并发峰值、晋升与配置；若在稳定负载下回收收益很小、回收后基线持续抬高，查真正活数据增长和泄漏。两类问题可以并存，不能只选一个解释。

Full GC 后基线抬升是线索，不是泄漏判决。缓存暖机、会话增长和业务数据增长也能产生类似曲线。最后要用对象保留路径和业务释放条件区分它们。

#### 周期性尖刺：先做竞争假设，再缩小到 GC

假设高并发压测时，正常请求约 50ms，随着流量上涨，响应时间稳定周期性冲到数秒。周期性不能证明 GC；可以同时建立以下检验：

- 若尖刺与 STW 完整重合，且恢复后短暂排队消散，再看对应 GC 类型和阶段。

- 若线程池活跃数到顶、队列年龄先上升、拒绝随后出现，而 GC 稍后才加重，可能是任务堆积先延长对象寿命。看线程栈是否集中等待下游或连接池。

- 若数据库调用段先变慢，检查慢查询、锁等待和连接获取时间；若 Redis 调用段先变慢，检查其阻塞与服务端延迟。JVM 参数不能替代下游诊断。

- 若定时批处理、缓存刷新、重试退避或流量周期与尖刺同相位，检查它们是否制造集中分配或资源争抢。

用链路追踪拆开排队、执行与下游等待，核对服务器和压测机时钟；必要时观察多次相同周期。线程转储适合查看阻塞链、线程爆炸或热点位置，`jstack` 不能直接证明“哪个堆对象泄漏”。一份采样栈里看到业务方法，也不能证明整个几秒都花在那里。

#### 止损、验证和回滚

影响已经扩散时，先用已有机制限制输入尺寸、并发、重试或批量，必要时隔离异常实例、恢复被误降的资源或回滚刚发布的改动。止损后保留足够现场，再深入分析；不要为了拿一个 dump 让所有实例同时停顿，也不要因急于重启而丢掉唯一可用日志。

每次实验明确一个主要假设。例如“消费减慢导致队列长期保留大数组”，就先限制待处理字节数或修复消费者，再比较相同输入与并发下的队列年龄、回收后活集、GC 阶段时间和请求 p99。若降低暂停目标后次数上升、CPU 更高、业务 p99 更差，说明只优化了局部指标，应回滚，而不是继续盲目压低目标。

完整结论应说得出：哪类事件变慢、哪个阶段多耗时、什么数据或资源变化解释它、哪个改动改变了该证据，以及付出了什么代价。没有现场日志时，可以给出这个流程和候选原因，不能把“一秒变五秒”直接诊断成某个真实事故。

### 内存泄漏、OOM 与资源边界

Java 有 GC 仍会泄漏，因为 GC 只能判断可达关系，不能判断业务还需不需要对象；OOM 则是某类分配失败，既可能来自泄漏，也可能来自正常活集、突发峰值、上限或本地资源不足。

可能的问法：有 GC 为什么还会泄漏？线上 OOM 怎么一步步排查？怎样分别让堆、元空间、直接内存和栈达到边界？ThreadLocal 为什么会泄漏？大文件解析为什么容易 OOM？

#### 先定位失败资源，不要先改 Xmx

OOM 排查的第一步是确认“哪一种资源分配失败”。先保留完整异常类型、消息、堆栈和时间，再核对 JDK、启动参数、容器限制以及进程是否还活着。

抛错栈通常指向最后那次失败的分配，不一定指向此前耗尽资源的保留者。因此不能看见某个方法抛 OOM，就认定它是泄漏入口。同样一句“内存满了”，下面这些错误会把调查带向不同资源：

- `Java heap space`：Java 堆中的一次分配无法满足。检查对象活集、数组规模、并发峰值和堆上限。缓存泄漏只是其中一种原因。

- `GC overhead limit exceeded`：在适用的 HotSpot 收集策略下，运行时间大量消耗在 GC、回收进展很小。关闭该保护不会自动创造可用空间，必须核对活集与容量；不要把某个策略的阈值泛化到所有收集器。

- `Requested array size exceeds VM limit`：申请的单个数组超过实现能支持的尺寸；不是只要物理内存多就能分配任意长度数组。检查长度计算、整数溢出和是否本就该分块。

- `Metaspace` 或 `Compressed class space`：定位类元数据相应区域。检查上限、动态类生成、加载器数量和卸载情况；调整 Java 堆无法直接取消这些上限。

- 含 `direct buffer memory` 的错误：检查 NIO 直接缓冲的额度、池和持有关系。`MaxDirectMemorySize` 管的是相关直接缓冲预算，不是进程所有 native 分配的总上限。

- `unable to create native thread`：检查平台线程数量、线程栈与本地内存、操作系统和容器任务数限制。线程数、栈大小和堆大小共同挤占进程资源，扩大堆有时反而让问题更严重。

- `StackOverflowError`：通常是当前线程调用栈深度超过可用空间，例如无终止递归或过深调用链。应检查递归终止和算法结构，再评估栈预算，不能用 `Xmx` 修复。

- 进程直接被系统或容器终止：检查退出原因、内核与容器事件、内存峰值。被 kill 不一定有 Java OOME，也不保证有 heap dump；退出码 137 本身也不能独立证明 OOM kill。

如果是 JNI 或本地库分配失败，还可能出现本地 OOM、崩溃或错误日志，需要操作系统内存映射和对应库的工具。PC 寄存器不是“给它多分点对象就能复现溢出”的区域；不要为了凑齐内存分区而编造实验。

#### 从趋势找到不合理保留者

先用低影响证据重建现场：相近业务负载下的回收后占用、对象或缓存条目数量、队列长度、会话数、输入规模、线程与加载器数量；把发布和异常重试标在时间线上。一个有限缓存从空到满后稳定，通常与无限增长不同；消费速度不足形成的积压也可能有明确业务原因。诊断既要问“对象还可达吗”，也要问“为什么现在仍需要它”。

对象直方图能说明类的数量与浅大小分布，不能直接给所有权。heap dump 是更完整的对象图，但采集可能带来长停顿、触发 GC、占用大磁盘，且包含文档内容、用户数据甚至秘密。先确认影响、可用空间、访问与保留策略，再选择必要的实例和时机。以 HotSpot 21 的 `GC.heap_dump` 为例，默认会请求 Full GC；`-all` 可包含不可达对象，但不意味着无停顿或无开销。分析不同 dump 时也要知道是否包含不可达对象，否则比较可能失真。

三个概念决定如何读图：

1. **Shallow size** 是对象本身占用，不包含它引用的所有后代。一个很小的集合或缓冲包装器可能保留巨大内容。

2. **Retained size** 表示若该对象不可达，连带可变为不可达的一组对象的大小，依赖分析器采用的引用边界。它不是“该对象分配过的总字节数”，也不是任意删除一个字段后立刻能归还给操作系统的字节数。

3. **Dominator** 描述支配关系：若从分析所用根出发到对象 B 的所有路径都经过 A，则 A 支配 B。支配树帮助找具有控制作用的上游节点；多个对象的 retained size 可能重叠，不能随意求和。最短根路径只是便于阅读的一条路径，修掉它后还可能存在其他强保留路径。

例如 `静态注册表 → 任务上下文 → 分块集合 → byte[]`，应追问任务完成后谁负责注销上下文。最多的 `byte[]` 是被保留的数据，长期存活的注册表才可能是修复入口。再结合两次可比快照中同类对象和所有者的增长，避免凭一张“最大对象”截图下结论。

#### 常见泄漏不是“没有回收”，而是生命周期错配

**缓存与队列。** 无界 Map、只有写入没有真正生效的过期策略、队列生产持续快于消费，都可能保留数据。TTL 不是容量上限，短时间内写入量极大仍会造成峰值；限制条目数也未必限制字节数，因为任务大小差异很大。缓存应同时考虑容量、失效和重建代价，队列应结合待处理字节数、并发与背压。清空缓存可能带来集中回源，要有分批和回滚方案。

**ThreadLocal。** 先沿 OpenJDK 21 的持有关系看：线程内部 Map 的 key 对 ThreadLocal 是弱引用，Entry 却仍强持有 value。key 被清除，只断了 key 的关联，不代表 value 当场消失；清理通常依赖后续相关操作，线程池的长寿命线程不能只等偶然清理。即使 ThreadLocal 一直被 static 强持有，漏掉任务结束时的 remove\(\)，也会延长 value 的寿命。

修复应落在任务边界：把设置与清理配对，成功、异常、取消都经过它；有嵌套上下文时，要保存并恢复外层值，不能清掉别人拥有的状态。把 value 一律换成弱引用，会让业务数据可能意外消失，并不是通用修复。

**监听器、回调与定时任务。** 一个页面、会话或任务结束了，但全局注册表仍持有监听器；监听器又捕获外部对象，于是整条图继续存活。检查注册是否有注销，取消是否真正从容器移除，完成回调是否又把大上下文捕获到另一个长期 Future 中。修复要落到生命周期的拥有者，而不是让每个下游都猜何时释放。

**类加载器。** 热部署或动态生成类后，旧加载器可能仍被线程上下文加载器、定时任务、缓存或 JNI 引用留住，进而保留其类元数据。加载器和类可以卸载需要满足相应可达性条件，也不保证立刻执行。要看同一应用版本是否留下越来越多加载器，而不是把每个新代理类都判为框架泄漏。

**直接缓冲与视图。** 小的 slice 或 duplicate 可能共享一整块本地存储，保留小视图会延长大块内存寿命。显式资源关闭、缓冲池归还和 Java 包装对象可达性是不同层面的协议。释放后 RSS 未立即下降也不独立证明泄漏，分配器和系统可能保留已可复用页面。应同时验证池可复用容量、存活引用和本地资源趋势。

#### 大文件和跨进程链路的峰值预算

处理大文档时，文件字节数不是堆预算。原始上传 `byte[]`、解码文本、解析树、全部分块、向量化批次、重试副本可能同时存在；解压内容也可能远大于压缩文件。峰值由各阶段同时活着的表示决定，不是把文件大小乘一个永远固定的系数。

一种有用的预算分解是：基础活集 \+ 各并发阶段的在途任务数 × 每任务峰值驻留 \+ 排队数据 \+ 缓冲池及安全余量。这个关系用于列清需要测量的量，不是精确容量公式。队列只传任务标识也不代表工作进程不会一次读完整个文件；异步化会缩短请求链路，但若增加了在途任务数，总内存仍可能上升。

对于几十 GB 的文件，且题目不允许使用 Redis、Kafka 等中间件，应让读取、解析、去重和输出都具有明确内存上限：固定大小读取缓冲，正确处理跨块的行和多字节字符；解析器真正按流消费；输出逐批写出；并发与待输出数据有上界。`readAllBytes()`、先收集成完整 List、再写出的流式 API 外壳都不算有界处理。

读入有界，不代表去重也有界。边读边把全部 ID 塞进 HashSet，内存仍随不同 ID 数量增长；每块单独去重，又会漏掉跨块重复。先明确是否要求精确的全局去重，再选择能满足它的路径。

需要精确全局去重时，可以评估磁盘外排序，或分区后逐批去重；题目允许时，也可借助数据库唯一约束。随之要核算临时磁盘、数据倾斜、分区过大、重复处理和输出原子性。内存必须容纳最坏的一批，装不下就继续拆分或归并。

单个超长记录、压缩炸弹和不能流式解析的格式，仍需拒绝、限额或隔离。完成、失败和取消都要清理临时文件；否则只是把堆耗尽变成了磁盘耗尽。

当 Java Host 与 Python Worker 分工时，先确认增长发生在哪个进程、哪个容器与哪个阶段。Java heap dump 无法解释 Python 对象或模型 native 内存；Python Worker 的峰值也不能直接算进 Java `Xmx`。若共享总资源上限，两边预算必须相加并留余量；若独立部署，则分别看各自限制及跨进程队列。通信协议、模型执行方式和部署拓扑都需要依据实际实现，不能从“跨语言”三个字推断。

#### 完整示例：四种低限额资源边界

`MemoryBoundaries` 仅用于独立实验子进程，面向 HotSpot 21，利用相同 `Seed.class` 被不同定义加载器加载并强保留的方式增加元数据占用。程序先校验小堆及相应限额，再制造指定失败；每种模式严格检查类型与消息，避免把“任何 OOME”都当成功。

```Java
import com.sun.management.HotSpotDiagnosticMXBean;
import java.lang.management.ManagementFactory;
import java.nio.ByteBuffer;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

public final class MemoryBoundaries {
    private static final int MIB = 1024 * 1024;
    private static final List<Object> ROOT = new ArrayList<>(10_000);
    private static int depth;

    private static final class Loader extends ClassLoader {
        Loader() { super(null); }
        Class<?> define(byte[] data) {
            return defineClass("Seed", data, 0, data.length);
        }
    }

    private static void recurse() {
        depth++;
        recurse();
    }

    private static long option(String name) {
        return Long.parseLong(ManagementFactory
                .getPlatformMXBean(HotSpotDiagnosticMXBean.class)
                .getVMOption(name).getValue());
    }

    public static void main(String[] args) throws Exception {
        if (args.length < 1 || Runtime.getRuntime().maxMemory() > 64L * MIB) {
            throw new IllegalArgumentException("Use an isolated child with -Xmx64m or less");
        }
        String mode = args[0];
        byte[] seed = null;
        switch (mode) {
            case "heap" -> {
                if (Runtime.getRuntime().maxMemory() >= 32L * MIB) {
                    throw new IllegalArgumentException("heap mode needs -Xmx16m");
                }
            }
            case "direct" -> {
                long cap = option("MaxDirectMemorySize");
                if (cap <= 0 || cap > MIB) {
                    throw new IllegalArgumentException("direct mode needs direct cap <= 1MiB");
                }
            }
            case "stack" -> {
                long kib = option("ThreadStackSize");
                if (kib <= 0 || kib > 512) {
                    throw new IllegalArgumentException("stack mode needs -Xss256k");
                }
            }
            case "metaspace" -> {
                long cap = option("MaxMetaspaceSize");
                if (cap <= 0 || cap > 16L * MIB || args.length != 2) {
                    throw new IllegalArgumentException("metaspace mode needs cap <= 16MiB and Seed.class");
                }
                Path path = Path.of(args[1]);
                if (Files.size(path) > 64 * 1024) {
                    throw new IllegalArgumentException("Unexpectedly large class file");
                }
                seed = Files.readAllBytes(path);
                ROOT.add(new Loader().define(seed));
            }
            default -> throw new IllegalArgumentException("Unknown mode");
        }
        System.out.println("START bounded boundary test");
        try {
            switch (mode) {
                case "heap" -> ROOT.add(new byte[32 * MIB]);
                case "direct" -> ROOT.add(ByteBuffer.allocateDirect(2 * MIB));
                case "stack" -> recurse();
                case "metaspace" -> {
                    for (int i = 1; i < 10_000; i++) {
                        ROOT.add(new Loader().define(seed));
                    }
                }
                default -> throw new AssertionError("Validated mode changed");
            }
        } catch (StackOverflowError error) {
            if (!mode.equals("stack") || depth == 0) throw error;
            System.out.println("PASS StackOverflowError");
            return;
        } catch (OutOfMemoryError error) {
            String message = error.getMessage();
            boolean expected = switch (mode) {
                case "heap" -> "Java heap space".equals(message);
                case "direct" -> message != null && message.contains("direct buffer memory");
                case "metaspace" -> "Metaspace".equals(message);
                default -> false;
            };
            if (!expected) throw error;
            // Constant output avoids new concatenation call sites after metaspace exhaustion.
            System.out.println(message);
            System.out.println("PASS expected OutOfMemoryError domain");
            return;
        }
        throw new AssertionError("Expected resource boundary was not reached");
    }
}

class Seed { int value; }
```

四种模式分别采用以下实验条件：

- heap：`-Xmx16m` 下申请 32MiB 数组，预期 `Java heap space`。

- direct：`-Xmx32m -XX:MaxDirectMemorySize=1m` 下申请 2MiB 直接缓冲，预期消息包含 `direct buffer memory`。

- stack：`-Xmx32m -Xss256k` 下有意递归，预期 `StackOverflowError`；深度取决于实现和执行状态，不以固定层数为结论。

- metaspace：`-Xmx64m -XX:MaxMetaspaceSize=16m`，用至多 10,000 个不同加载器定义同一类并保留 Class，预期 `Metaspace`。同名类由不同加载器定义时属于不同的类身份，重复定义并不是在同一个加载器里覆盖原类。

不要把这些条件直接注入已有服务，也不要通过海量创建线程或耗尽宿主内存补做演示。在独立实验目录中创建 `code` 子目录，将前面的两个完整 Java 程序分别保存为 `code/GcEvidence.java` 和 `code/MemoryBoundaries.java`；Seed 已包含在后一个文件中，无需另建源码。先确认 `/usr/bin/java` 是带有编译模块的 HotSpot 21 JDK。下面的完整脚本面向 Linux/POSIX，保存为 `code/run_examples.py`。

脚本清除可能注入额外 JVM 选项的环境变量，分别启动子进程，设置 20 秒墙钟、15 秒 CPU、64KiB 捕获输出和 8MiB 单文件大小上限，并关闭 core dump。编译进程的 Java 堆上限是 128MiB；演示子 JVM 使用 16、32 或 64MiB 堆，并限制元空间、直接缓冲、栈和代码缓存。它还检查未按要求设小堆的启动会被拒绝。编译产物和日志写入实验目录中的 `example-output`，这些限额用于演示安全边界，不是生产参数建议。

```Python
"""Run only the bounded Java examples in this package on a POSIX host."""
import json
import os
from pathlib import Path
import resource
import selectors
import signal
import subprocess

ROOT = Path(__file__).resolve().parents[1]

def child_limits():
    resource.setrlimit(resource.RLIMIT_CPU, (15, 15))
    resource.setrlimit(resource.RLIMIT_FSIZE, (8 * 1024 * 1024, 8 * 1024 * 1024))
    resource.setrlimit(resource.RLIMIT_CORE, (0, 0))


def run(name, arguments, deadline=20, output_cap=64 * 1024):
    start = time.monotonic()
    child = subprocess.Popen(
        arguments, cwd=ROOT, env=ENV, stdout=subprocess.PIPE,
        stderr=subprocess.STDOUT, start_new_session=True, preexec_fn=child_limits,
    )
    selector = selectors.DefaultSelector()
    selector.register(child.stdout, selectors.EVENT_READ)
    output = bytearray()
    reason = "completed"
    while selector.get_map():
        if time.monotonic() - start > deadline:
            reason = "wall_timeout"
            os.killpg(child.pid, signal.SIGKILL)
            break
        for key, _ in selector.select(0.2):
            data = os.read(key.fd, 4096)
            if not data:
                selector.unregister(key.fileobj)
                continue
            output.extend(data)
            if len(output) > output_cap:
                reason = "output_cap"
                os.killpg(child.pid, signal.SIGKILL)
                break
        if reason != "completed":
            break
    child.wait()
    selector.close()
    child.stdout.close()
    (OUTPUT / (name + ".log")).write_bytes(output[:output_cap])
    result = {
        "name": name, "argv": arguments, "exit_code": child.returncode,
        "elapsed_seconds": round(time.monotonic() - start, 3),
        "termination": reason, "wall_timeout_seconds": deadline,
        "output_cap_bytes": output_cap, "cpu_limit_seconds": 15,
        "file_size_limit_bytes": 8 * 1024 * 1024, "output_bytes": len(output),
    }
    print(name, child.returncode, reason, len(output))
    return result
```

错误处理也有资源边界。元空间耗尽后，首次执行字符串拼接、日志框架初始化或动态支持类加载，可能再触发失败；堆耗尽后，大 JSON 告警或异步队列入队也可能分配失败。例子先初始化常用路径并使用固定报告，不在捕获错误后继续执行业务。这样的演示并不证明任意 OOME 都可恢复；生产上应有进程外健康检查、受控退出与重启恢复策略，并保证已受理任务的状态能够核对。

#### 修复是否有效，要回到完整业务生命周期

复现后保留根路径，修复后重复相同规模的业务：正常完成、超时、失败、重试、取消、热部署都要覆盖。观察缓存和队列是否回到合理区间、旧加载器是否不再持续累积、相关对象在适当回收后是否不再增长，同时比较 p99、吞吐、错误率、RSS 和磁盘。

加堆可能为容量不足或紧急止损争取时间，但对无界增长只会延后失败，并可能扩大最坏暂停或挤占 native 预算。单次调用 `System.gc()` 后某个弱引用变空，也不能证明所有生命周期路径都已修复。真正的闭环是：找到不符合业务生命周期的保留关系，改变其拥有者，再证明可比负载下该增长不再出现。

### 从分配热点与保留根定位代码

定位代码要同时回答“谁创建了对象”和“谁把它留住”：分配采样寻找创建路径，堆引用图寻找保留者，再用实际部署版本的源码验证生命周期。

可能的问法：已经看到大对象，怎样定位具体哪一行？Full GC 排查之后怎么找到业务代码？分配量最大的函数就是泄漏点吗？如何证明修复的是根因？

#### 先区分创建过多与留下太久

某方法每秒创建大量短命对象，会增加分配与回收负担，但业务结束后对象可正常回收，活集可能稳定。另一个方法每天只注册一次回调，却把整份历史结果永久挂到全局列表，也可能形成慢泄漏。热点与泄漏可以来自不同位置，也可能同一链路同时存在。

先用回收后占用、分配速率与业务在途量决定主要方向。若占用低且稳定，但 GC CPU 高，优先看分配来源、临时表示与重复计算。若正常完成后仍保留越来越多对象，优先看根路径和释放条件。若故障只在大文件或高并发短窗口发生，再检查峰值是否超预算；不能因某个峰值消退了就忽略吞吐和延迟损失。

JFR 或其他分配采样可以按类、分配栈与业务入口聚合热点。必须确认录制配置开启了需要的事件和栈信息，采集窗口覆盖故障，采样频率与开销可接受。有些分配事件基于 TLAB 或采样策略，样本数不能直接当全部对象数；不同输入大小和热点形态可能导致不同偏差。没有采样到某路径不证明它从未分配，分配最多也不证明它长期保留。

还要避免把开启诊断后的行为变化误认为原有行为：高频采样、额外日志或大规模栈采集都可能改变延迟与调度。记录采集窗口、设置和影响，在较小范围验证工具成本后再扩大。

#### 从根链回到生命周期的代码入口

heap dump 通常没有给每一个对象保存完整创建栈，但类名、字段名、集合结构和定义加载器能够缩小范围。沿保留者搜索源码，通常比搜索 `new byte[]` 更有效。

假设堆图给出 `ExportRegistry.active → TaskContext → chunks → byte[]`。数组是大头，但排查入口先放在 active：谁把任务加进去，正常完成、失败、超时和取消后，谁把它移走？

若完成任务仍在 active，继续核对状态更新与清理动作是否必须一起发生。若 Map 条目已经删除，再查重试回调是否还引用上下文。只有弄清任务生命周期由谁负责，才能判断删哪条保留链；单纯把数组改小，或者只删一条 Map 引用，都可能留下原问题。

可以把调查拆为几对操作：

- 缓存：写入与失效，最大容量与淘汰，刷新与旧版本移除。

- 注册表：register 与 unregister，订阅与取消，定时任务提交与取消。

- 队列：入队与出队，消费失败与重试，拒绝与补偿，待处理数与实际待处理字节数。

- ThreadLocal：set 与任务边界清理，嵌套上下文保存与恢复。

- 类加载器：创建与退役，线程停止、上下文加载器重置、缓存和本地引用清理。

- 缓冲池：借出与归还，异步完成与取消，视图与底层内存的共同生命周期。

不是每个不平衡都代表泄漏。队列中的合法未完成任务就是应保留的数据；关键是其数量是否有上限、是否仍能推进，以及保留是否符合业务契约。若保留本来合理，可能应解决容量或下游吞吐，而不是删除仍需要的数据。

#### 必须匹配实际部署的代码

用制品哈希、构建版本和部署记录找到准确源码，再解释方法与行号。线上跑的是旧版本时，拿本地最新分支的同一行号会误判。混淆、生成类、代理、调试信息缺失及 JIT 内联也可能影响栈与源码的对应；需要核对符号和调用链，不能只看一个框架类名。

动态代理对象很多时，先看谁生成、是否复用、属于哪些加载器。生成类的名字往往不稳定，应沿调用方和加载器归属定位。看到解析库创建了大量对象，也不能直接责怪库：调用方可能一次并行打开很多文档，或把解析结果永久存入全局状态。

取一个明确的假设场景：导出流程先读整文件为 `byte[]`，再转成文本、解析树和所有分块；分配栈集中在解析器，而完成后 heap dump 显示全部分块留在静态 List。这里有两个独立修复点：减少中间表示和限制并发处理峰值；移除静态 List 对已完成任务的永久保留。只改其中一个，另一种压力仍可能存在。

#### 用最少追踪证明因果，再覆盖失败路径

在测试环境或受控流量给可疑生命周期添加必要的统计：当前条目数、累计注册与注销、在途任务数、任务终态后清理数、待重试队列数量以及保留字节估计。尽量使用任务标识和聚合计数，不复制完整文档、用户提示词或凭据到诊断日志。

先寻找可复现关系，例如每次取消任务后 active 条目多一个，而正常完成会清理；再针对取消路径修复，重复同样次数，验证条目能恢复、根链不再保留旧上下文、回收后活集趋稳。对照实验应保留相同输入与并发，同时观察吞吐和错误率，防止“因为任务没有执行，所以对象少了”的伪改善。

修复后至少覆盖成功、异常、超时、取消、重试和服务重载。若资源归还协议发生变化，特别检查重复 close、归还后仍被异步使用、误删活任务和重试状态丢失。回滚也要能安全处理新旧状态，不能只是把代码版本切回去。

面试中讲到具体行时，完整表达是：“分配栈指向创建入口，根链指向长期保留者，实际部署源码显示异常路径漏清理，回放后相关条目和活集不再持续增长。”只说“MAT 看到很多数组，然后改了代码”还没有解释机制。

### 带证据和取舍讲调优案例

JVM 调优应从业务目标和运行证据出发，用可验证假设驱动单变量改动，并同时交代收益、代价和回滚条件；没有实际操作经历时，就明确讲学习案例或条件方案。

可能的问法：有没有 JVM 调优经验？实习时了解过哪些 GC 参数？年轻代调大一定更好吗？为什么要调优？如何学习 JVM 并证明理解？Java Host 与 Python Worker 的故障怎样分辨？

#### 先确定优化目标，再选择能改变它的变量

默认配置是重要基线，不是“任何服务都最优”的证明。若服务稳定满足 SLO、吞吐和预算，继续观测通常比堆满一串历史参数更合理。出现问题后先说清目标，例如控制某个接口尾延迟、避免容量峰值失败、减少不必要分配 CPU，而不是只追求 GC 次数更少。

一份可复核的调优叙述至少包含：

1. **环境与现象。** JDK、GC、CPU/内存限制、负载与输入尺寸；问题持续多久，是否与发布或高峰有关。

2. **证据与假设。** 哪类 GC、哪个阶段、回收前后活集、分配或晋升变化，以及业务指标如何相互对应。把已观察到的事实与推断分开。

3. **改动与对照。** 每次改变一个主要因素，在同数据规模、并发、预热与资源条件下复验。必须同时比较吞吐、尾延迟、错误率、GC CPU 和总内存。

4. **代价与退出条件。** 堆变大可能减少频率但增大内存预算；并发回收可能减暂停但占业务 CPU；批次缩小可能减少峰值但降低吞吐。达到错误率、内存、队列年龄或 p99 恶化的预设边界时回滚。

比较调优前后时，先检查服务是否真的完成了同样的工作。请求发起数相同，但完成量下降、拒绝更多请求，也会让 GC 曲线显得轻松。

因此还要对齐请求分布、数据热度、缓存状态、慢任务比例和下游限额。冷启动与充分预热不能直接比较；否则看到的“改善”可能来自少做了业务，而不是运行时效率提高。

#### 哪些参数能影响什么，为什么不能照图套用

![diagnosis\-tuning\-boundaries\.png](Images_attachments/diagnosis-tuning-boundaries.png)

图中的固定 Eden、两个 Survivor 和老年代布局用于理解 JDK 8 的传统分代案例，面积不表示真实比例。`Xms` 与 `Xmx` 约束的是整个 Java 堆；`Xmn`、`NewSize`、`MaxNewSize` 影响特定收集器下的年轻代预算；`SurvivorRatio`、年龄阈值等还要结合自适应策略和真实晋升日志。年轻代与老年代 1:2、Eden 与两个 Survivor 的 8:1:1 都只是常见历史示意或配置，不能作为所有 JVM 的固定默认约束。

JDK 8 CMS 的占用触发百分比选项写成 `-XX:CMSInitiatingOccupancyFraction=<整数>`；`UseCMSInitiatingOccupancyOnly` 等是布尔开关，语法是 `-XX:+名称` 或 `-XX:-名称`，二者不能混淆。图保留历史参数作用域，目的在于读懂案例；CMS 参数不能复制到不再支持 CMS 的现代 JDK。迁移收集器时，应重新建立该收集器的基线，而不是把所有旧参数搬过去。

Metaspace 位于本地内存，不能把它画成 Java 堆的一部分或全部方法区概念的等价物。`MetaspaceSize` 是初始的元数据 GC 高水位，后续会依据使用情况调整；`MaxMetaspaceSize` 才是相应最大预算限制。前者不是启动时就分配好的一整块固定容量。

区域大小的变化要看两面。较小 Eden 在相同分配速率下通常更快用完，但暂停成本不只取决于 Eden 容量，还取决于存活对象和扫描工作。Survivor 容量不足可能促进提前晋升；预留过大又可能挤占其他用途。即使出现晋升，也不保证马上 Full GC，还要看老年代余量和回收进展。

一个简单时间线可以解释为什么尾延迟必须单独测量：假设接口不含 GC 的工作共 10ms，已经执行约 5ms 时遇到一次 50ms STW，暂停后再完成余下约 5ms，其他因素不变时总耗时约 60ms。真实业务还会叠加排队与下游等待。这个模型适用于相应 STW 暂停，不表示所有收集器的年轻代工作都全程暂停，也不能从 60ms 倒推 Eden 应该多大。

#### 历史学习案例一：CMS 碎片与低峰整理

**环境与目标。** JDK 8，ParNew \+ CMS，C 端核心接口希望在例如 100ms 内返回。高峰发生 Full GC，耗时甚至达到 1s，造成部分请求超时。案例将老年代碎片视为重要原因：剩余总空间仍可能很多，但缺少满足某次对象分配的连续空间。

**当时的策略与记录结果。** 在业务低峰，例如凌晨四点，显式调用 `System.gc()`，希望通过停顿整理减少 CMS 碎片，降低高峰触发 Full GC 的概率。案例记录高峰期基本没有再出现 Full GC，同时明确不能彻底避免。这是历史学习案例的观察，不是当前负载的保证，也不是自己的生产实绩。

**如何解释，而不是背做法。** 这个策略试图把部分不可避免的整理成本移到低峰，并没有消灭整理成本。`System.gc()` 是请求，可能被忽略，也可能受 `ExplicitGCInvokesConcurrent` 等选项影响走不同路径；不能承诺每次都以同一种单线程后备方式处理。还要查其他显式调用、定时任务与维护操作是否相互叠加。

**今天怎样验证与取舍。** 先核对当时收集器与具体更新版本，确认 Full 的原因和整理行为；若只有总空闲百分比，仍不足以证明碎片是唯一根因。比较低峰维护暂停、高峰最大暂停、吞吐和失败率，并检查低峰是否真无关键任务。现代方案还可以评估减少大块分配、增加并发回收余量或迁移收集器，但这些都要重新测量。如果低峰显式收集本身造成超时，或高峰改善不能复现，就不应保留这个定时动作。

#### 历史学习案例二：年轻代过小与晋升压力

**环境与原始现象。** JDK 8，ParNew \+ CMS。服务追求低延迟，最初把年轻代设得较小，希望缩短单次 Young GC。后来业务增长，出现 Young GC 每分钟约 50 次、每次约 25ms；Old GC 几分钟一次、每次记录约 200ms。

**假设链。** 年轻代过小使收集频率增加，部分对象在业务真正结束前经历多次收集，可能更早晋升；若 Survivor 容量也紧张，晋升压力进一步增大。老年代进入速率提高，可能带来更频繁的老年代回收。这个推断要用年龄、存活量、晋升速率及队列寿命验证，不能只凭频率高便确认所有环节。

**改动与记录结果。** 案例将年轻代扩大到原来的三倍；单次 Young GC 约增加 5%，频率约下降 60%，Old GC 降到数小时一次。这些数字只描述案例中的环境、负载和改动，不能作为“三倍最优”的经验公式。Old GC 的 200ms 还应核对究竟是某暂停阶段还是某种周期口径，不能未经确认就当成完整 CMS 周期的 STW 时间。

**数字能说明什么。** 若同一窗口、同一 Young 暂停口径成立，原先约 50 × 25ms，即每分钟 1\.25s；按案例比例估算，改动后约 20 × 26\.25ms，即每分钟 0\.525s。这个推算只能帮助理解“单次略长但总暂停负担下降”，不是重测结果，更不提供 p99。业务尾部仍可能由少数长暂停、排队或下游决定。

**为何不与“年轻代越大越慢”矛盾。** 复制工作更依赖需要搬迁的存活对象及扫描，而不是把整个 Eden 容量逐字节复制。让更多短命对象在下次 GC 前自然变成不可达，可能减少晋升和老年代压力。但固定总堆时扩大年轻代也会压缩老年代余量；活集很大时，还可能增加单次复制量。扩大堆的做法则另有 RSS 与容器成本。复验必须同时比较年龄分布、晋升、老年代回收收益和业务延迟；若余量变差或尾延迟恶化，就回滚。

#### 历史学习案例三：G1 暂停目标与年轻代选择

**环境与问题。** JDK 8，G1，Young GC 频繁。案例提出：`-XX:MaxGCPauseMillis` 目标过小，可能使 G1 选择较小的年轻代，从而增加收集频率。这是一条待日志验证的因果链，频繁 Young GC 本身不能证明暂停目标过紧。

**两种被讨论的做法。** 一是适度放宽暂停目标，让 G1 在其模型下有机会选择更大的年轻代；二是固定年轻代大小。第二种做法会削弱 G1 利用年轻代大小适应暂停目标的能力，因此通常不作为优先选择。G1 的暂停目标是软目标，放宽或收紧都不能当成每次暂停的硬保证。

**怎样做成可判断的实验。** 固定输入、并发和 CPU 配额，先看年轻代 Region 数、存活比例与暂停阶段，确认是否主要受年轻代预算影响。只调整目标后，比较次数、单次暂停分布、总 GC CPU、吞吐、尾延迟和老年代回收进展。如果只是次数少了，却因更长暂停让关键接口违约，就没有达到目标。这个案例没有给出可靠的前后改善数字，不应为了讲得完整自行补一个百分比。

现代 HotSpot G1 的基础策略仍强调暂停目标与自适应配合；复杂参数应在发现具体限制后才介入。无界缓存、过多在途任务或 CPU 配额不足，不会因为目标从一个毫秒值改为另一个就自然消失。

#### 把个人项目关联讲准确

NoteWeave 的可用事实是：资料解析、切片、向量化、索引构建拆成 Kafka 异步任务，通过幂等和失败恢复承载长链路，按 128MB 单文件异步接入能力设计；Java Host 与 Python Worker 分层承担相关职责。这些事实能够解释为什么要关注任务峰值、背压和跨进程资源归属，却不能推出已经发生过某次 OOM、采用了某个 GC、调整过某组参数或取得某个 JVM 收益。

128MB 描述的是单文件接入能力目标，不是 Java 堆只需要 128MB，也不是单条 Kafka 消息大小。当前配置的单文件与整个 multipart 请求上限均为 128MiB，请求封装也占用总额度，所以不能承诺恰好 128MiB 的文件一定能通过上传；还要核对网关等入口限制。制造业实习中的 RabbitMQ 通知链路与 NoteWeave 的 Kafka 链路也应分开叙述，不能把一边的经验数字或消息机制移到另一边。

一个合适的条件式回答是：“如果资料处理链路出现内存增长，我会先定位是 Java Host、Python Worker 还是外部服务；再按任务阶段确认是否同时保留原文件、解码文本和完整分块，观察在途量与队列年龄。如果确实是峰值和积压问题，我会评估流式处理、有界缓冲、并发限制和背压，并用同样文件与并发验证。”这里讲的是设计推演，不能改成“我曾把堆从多少调到多少，性能提升多少”。

背压也有代价：限并发会延长完成时间，限队列需要明确拒绝或延后处理的业务语义，文件落盘占用临时磁盘，分阶段恢复增加状态管理。要同时设任务时限、取消传播和失败清理，否则只是把内存压力转移到更长的队列或另一进程。

#### 没有生产调优经历，仍然可以回答得扎实

“是否亲自调过”“是否协助处理过”“是否只是学习过”是事实问题，应按实际经历回答。可以描述亲自执行过的实验和真实职责，也可以以明确的历史案例解释原理，但不要补造参与导师排障、阅读某本书或接入某监控平台的经历。

被问怎样学习 JVM，可讲一种能落实的学习路径：从程序行为提出问题，读规范理解语义边界，按具体 JDK 与收集器查实现，用有界实验观察日志，再主动找反例。例如先读懂 `used/committed/max`，再运行小堆分配，观察计数与日志为何不是同一种证据；然后比较“分配很多但活集稳定”和“分配不快却长期保留”的差别。真正有说服力的是能解释实验条件和不成立的推论，而不是报一个书名。

最后用一段闭环收束调优回答：先守住业务目标，再用证据定位瓶颈；优先修正不合理生命周期和无界资源；必要时在预算内调整 JVM；用可比负载验证收益与代价，异常时能安全回滚。这比列出一串参数更接近实际工程能力。
