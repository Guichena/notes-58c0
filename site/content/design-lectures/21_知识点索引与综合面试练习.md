## H.2 常见说法的前提、边界与反例

| 简化说法 | 需要补上的条件或修正 | 可以拿来讲的反例 |
| --- | --- | --- |
| 2000万行后必须分表 | 看访问路径、工作集、容量和恢复目标 | 一亿冷历史＋高效最近页可优于一百万行全扫描 |
| 范围条件后面的索引全部失效 | 分清定位范围、索引过滤、覆盖和排序 | 范围后的状态字段可能仍用于ICP或覆盖 |
| RC性能一定更好 | 锁范围和读语义改变，收益取决于工作负载 | 两事务以相反顺序更新同两行仍可死锁 |
| 换乐观锁即可消灭死锁 | 条件UPDATE仍会获取数据库锁 | 多行更新和二级索引维护仍有竞争 |
| Redis单节点固定十万QPS | 需要命令、数据尺寸、硬件、网络与延迟条件 | 大范围返回和小GET无法共用一个吞吐数字 |
| 分key后自然均匀 | 检查路由、槽位、热点访问模式和原子性范围 | 多个key都用同一hash tag仍落同槽 |
| ZSET score可任意拼高低32位 | score是double，整数精确表示有边界 | 大整数拼接后不同业务键可能变成同一score |
| 布隆过滤器可以精确去重 | 假阳性只能引导精确检查，不能直接丢业务 | 第一次发券被误判已处理会漏发 |
| 删除缓存就是强一致 | 还存在删除失败、CDC延迟和旧回填 | 老查询在失效后把旧版本写回 |
| 加分区就能消除顺序热点 | 单key总顺序仍有串行约束，旧日志不自动重排 | 一个会话占80%流量，加空分区仍热 |
| Kafka acks=all就是所有副本落盘 | 区分当前ISR、minISR、特性状态、持久化故障模型 | Broker ACK与整机掉电后的介质持久性不同 |
| Kafka事务会包住MySQL和HTTP | 事务边界需要各资源实际参与 | 消费后发短信，再回滚Kafka事务，短信仍已发出 |
| 用异步线程池即可清积压 | 先限制队列、下游并发与安全提交 | poll位置很新，但业务结果还在内存里 |
| 框架保证任务只执行一次 | 故障下仍需业务幂等、代次与核对 | 老worker租约到期后恢复并发出外部请求 |
| 微服务天然高可用 | 需要故障隔离、兼容契约和恢复能力 | 一个共享连接池被慢依赖拖满所有服务 |
| 重试三次总会好 | 区分可重放、未知副作用和剩余预算 | 超时后重试两家供应商各扣一次款 |
| 有备份等于可恢复 | 要验证恢复时间、完整性和跨系统水位 | 数据库恢复到昨天，但对象清理已经删除对应版本 |

回答时先说明方法成立的条件，再解释当前场景的竞态、需要补充的协议与验证指标。例如：“这个方法在某条件下成立；当前场景还有这个竞态，因此需要增加这一条协议，并用这个指标验证。”

## H.3 可选延伸：怎样把索引与排障能力迁移到 ES、MongoDB 和系统基础

### 小型案例 H1：文档搜索第一页快，第几千页开始拖慢整个集群

业务是假设的资料检索：用户按租户、资料类型和时间过滤，再按相关性或时间查看。先区分普通交互分页与全量导出。很深的 `from/size` 会让多个分片处理前面大量候选，不只是协调节点跳过几行。连续翻页可以使用稳定排序与 `search_after`；需要固定视图时结合 PIT，并维护一致的查询条件、排序和游标。[H13]

先查单次请求的分片数、返回尺寸、排序、聚合和队列，再对受控请求使用Profile定位内部算子。Profile会增加开销，而且不能覆盖网络等待、队列时间或协调节点合并的全部耗时，所以不能把Profile显示的几十毫秒当成用户总耗时。[H14]

长期改造包括限制交互深度、单独导出任务、合理路由与索引生命周期、控制返回字段和聚合规模。增加分片可能提高局部并行，也可能增加协调与小分片负担，仍需验证。PIT保留旧视图，不代表撤销权限也可以冻结：私有资料最终返回前仍要满足当前权限策略，已经删除或撤权的结果不能仅因快照里存在而继续放行。

**连续追问：新索引怎么切换？** 构建新索引时记录源数据版本和增量水位，验证删除与更新都已应用，再按发布协议切读。若依赖别名切换，也要处理仍使用旧索引的游标、PIT和在途请求；回滚要知道新索引是否承担过额外写入责任。不能用“换个别名”省略数据与权限的一致性。

### 小型案例 H2：MongoDB里有索引，租户任务列表为什么还扫很多文档

假设查询为 `tenant_id=某租户 AND status=READY`，按 `created_at,_id` 倒序取前50条。可从 `{tenant_id:1,status:1,created_at:-1,_id:-1}` 作为候选索引开始验证，但还要考虑查询是否总带status、字段类型、索引排序以及写入代价。复合索引的字段顺序、前缀和查询模式仍然重要，换成文档数据库不会让索引设计消失。[H15]

对受控查询查看 `explain("executionStats")` 中返回数、扫描键数、扫描文档数与扫描／取文档阶段，不只看出现 `IXSCAN` 就宣告成功。解释计划的结构随版本和执行引擎变化，且explain本身不直接复用或更新计划缓存；它是重要证据，但不能替代真实请求延迟与负载观测。[H16]

如果一个租户占绝大部分数据，只按tenant_id分片仍会形成热租户。需要结合访问局部性设计桶或读模型，并承担跨桶排序和迁移责任。若每个文档都嵌入无限增长的任务历史，问题来自数据模型，不能只靠新增索引解决。把历史事件拆成独立可分页集合或归档层，并清晰定义当前状态与历史记录的权威关系。

## H.4 性能问题诊断与方案验证

性能分析需要把受损的业务动作、等待链、根因和改造方案连接起来。比较结果时保持负载与统计口径可比，并同时检查正确性、资源成本和回滚条件。

| 分析维度 | 需要确认的内容 | 常见误区 |
| --- | --- | --- |
| 业务背景 | 哪个用户动作受损，成功与延迟如何定义 | “系统性能不好” |
| 初始结构 | 调用链、表与索引、队列和外部依赖 | 仅列技术栈 |
| 发现方式 | 哪个告警、哪类反馈、什么时候开始 | “我感觉有问题” |
| 定位证据 | Trace、执行计划、锁等待、分区lag等相互印证 | 只贴一张CPU图 |
| 根因 | 因果链和可复现条件 | 用症状代替原因，如“连接池满了” |
| 止血动作 | 限流／隔离／回退，影响哪些用户 | 直接删除积压或重启掩盖现场 |
| 长期方案 | 代码、数据模型、协议、参数怎样变化 | “加了Redis／Kafka” |
| 正确性 | 哪个不变量，哪些并发时间线 | “测试没发现问题” |
| 对照结果 | 同类负载下前后指标与成本、统计窗口 | 无负载说明的“快了100倍” |
| 灰度与回滚 | 停止条件、兼容窗口、写入与数据回退 | “发出问题回滚就好” |
| 余留限制 | 哪些规模或故障还没验证 | 把一次测试扩展成绝对承诺 |

代码推演、SQL执行计划、受控复现与负载测试回答不同的问题。每个结论都需要限定适用的负载、数据分布和故障模型；单次正常运行不能替代并发与故障下的正确性验证。

## H.6 连续追问详答

### Q1：面试官只问B+树，为什么要讲到具体SQL？

结构解释帮助理解范围扫描和索引顺序，但工程能力体现在能为真实查询选择字段、控制回表和排序、验证执行计划。可以先简洁说明结构，再落到评论列表的复合索引，最后由对方追问带到ICP、覆盖、MVCC或分片。不要离题讲一整套无关架构。

### Q2：如何说明Redis和Kafka的技术选型，而不是只列优点？

先说明需要可重建的低延迟读模型，还是持久事件流与独立消费进度。再比较消息保留、回放、消费语义、延迟、运维与规模。Redis可以承担某些任务流，Kafka也不能替代所有缓存或定时权威；选型取决于具体责任和故障模型。

### Q3：同一个排障方法可以迁移到不同数据库吗？

可以迁移“先看实际访问路径、扫描与返回量、排序与取数、资源和等待”的方法，不能照搬每个术语和实现细节。MySQL的回表与ICP、MongoDB的IXSCAN/FETCH、ES的分片查询与协调阶段各有语义。拿同一个查询目标做横向比较最容易说明差异。

### Q4：如何判断我只是在堆组件？

检查能否为每个引入的组件说出它解决的具体瓶颈、存什么权威状态、失败后由谁恢复、移除后会破坏什么。如果只能说“为了高可用”而说不出故障时间线，就还没有完成设计。很多小规模场景保留单库短事务反而更容易证明正确性。

### Q5：系统设计最有区分度的部分是什么？

通常是边界：成功返回后的责任、超时后的未知、重复与乱序的区别、旧执行者复活、迁移切换和回滚、权限变化后的陈旧数据。基础链路人人都能画，能用具体版本、表约束和时间线解释这些边界，才能把方案变成可评审设计。

### Q6：怎样通过完整场景检验系统设计能力？

先选一条完整业务路线，独立画架构、列三条不变量、算一个容量数、写一段关键SQL，再推演一次失败。对解释不清的节点补齐数据模型、状态条件和恢复责任。随后调整约束，例如从允许陈旧改为即时撤权，从均匀负载改成单key热点，检查哪些设计假设已失效。

## H.8 四条系统设计追问路线

**路线一：海量数据。** 40亿条号码是什么类型 → 值域是否已知 → 输出是集合还是只出现一次的值 → 内存预算包括什么 → 位图是否适用 → 分桶严重倾斜怎么办 → 外排的I/O和临时空间 → 中途退出如何恢复且不多输出。

**路线二：高并发与正确性。** 流量到达率和峰值持续多久 → 命中率下降时数据库承载 → 增加实例为什么可能扩大连接压力 → 令牌桶和并发限制如何配合 → 锁按谁分配 → TTL到期旧线程恢复 → 资源端如何拒绝旧授权 → 供应商不支持fencing时怎么办。

**路线三：慢接口。** 用户看到哪个完成点慢 → Trace如何分段 → SQL执行还是池等待 → 联合索引和排序怎样设计 → 批量还是并行 → 统一截止时间如何传播 → 取消后真实工作是否结束 → GC/网络如何拿证据 → 受理变快是否改善业务完成。

**路线四：高可用。** 什么业务算可用 → 哪个故障域 → 主库半失联如何处理 → 旧主为什么必须隔离 → 跨区多活写权如何分配 → 误删为何不能靠主从解决 → 数据库/MQ/对象存储恢复到什么共同边界 → 重放如何防重复和复活删除数据 → N-1与恢复洪峰能否承受。

每条路线都围绕具体业务动作展开：明确业务约束，选择数据模型，计算资源预算，再推演并发与故障。说明方案时给出成立条件、失效边界、观测指标和验证方法。
