# 附录二 连续追问路线与知识点索引

## B.1 每个主题可以怎样被追问一小时

每条路线从基本功能进入并发、故障与扩容边界。练习时先讲清基线，再随着约束变化逐步补齐状态、资源预算和恢复责任。

| 主题 | 连续追问路线 | 答案最终应落到什么 |
| --- | --- | --- |
| 登录 | 怎么保存登录态 → 多实例怎样共享 → 为什么不用纯JWT → 用户被封禁怎样生效 → 两个标签页同时刷新 → 刷新成功但响应丢失 → 密钥轮换与第三方故障 | 凭证、会话与权限状态分开；明确撤销检查点；刷新有原子状态转换与可解释重试 |
| 秒杀 | 谁锁谁 → 为什么条件扣减不超卖 → Redis预扣后宕机 → MQ发送结果未知 → 支付与关单竞争 → 两个支付尝试都成功 → 热SKU怎么拆桶 → Redis全部重建 | 库存守恒、订单与预留终态、稳定幂等键、每笔真实资金动作都有处理责任 |
| 聊天与弹幕 | WebSocket够不够 → ACK代表什么 → 消息去重 → 会话seq怎样分配 → 断线补洞 → 多端已读 → 百万人房间 → 慢客户端 → 跨地域切主 | 持久事实与实时通道分开；顺序范围、保留窗口和重连协议明确 |
| 定时任务 | 扫哪些任务 → 多实例怎么抢 → 领到后宕机 → 心跳停止 → 旧执行者恢复 → 外部操作已成功但取消 → 调度错过与DST → 百万任务补跑 | 计划与实例分开；领取、执行、核对、终态都有可恢复状态 |
| 排行榜 | ZSET怎么用 → 同分怎么算 → 分数重复增加 → 扣分旧消息 → 分片TopK为什么成立 → 精确名次 → 日切与迟到 → 结算发奖失败 | 全序、版本、快照和分片证明成立；结算与在线榜不是同一个瞬时读 |
| 文件与视频 | 为什么直传 → 分块怎么校验 → 断点续传 → complete超时 → 文件存在为何不可读 → 秒传权限 → Range版本 → CDN撤权 → 转码与直播延迟 | 上传、校验、发布三阶段；不可变版本；控制面与字节传输分开 |
| 朋友圈与运动 | 推还是拉 → 大V怎么办 → 策略切换 → 翻页插入新帖 → 拉黑后旧Feed → 多设备步数 → 累计值回退 → 时区与迟到 | 候选列表不代表授权；游标表达扫描进度；设备数据先统一语义再汇总 |
| 点赞 | Set还是表 → toggle为什么错 → desired state够不够 → 重复与乱序 → 计数如何不多不少 → 热点分桶 → 读你之写 → 无损重建 | 关系是事实、计数是投影；状态覆盖与增量求和采用不同协议 |
| 评论 | 树怎么存 → 楼中楼怎么查 → 根评论删除 → 审核回调晚到 → 热评翻页 → 置顶变化 → 恶意内容 → 可见总数重建 | 稳定树关系、审核绑定内容版本、可见性与计数一同定义 |
| Redis | 大key还是热key → 怎么定位 → 怎么拆 → hash tag影响 → 迁移旧写 → 固定TTL → 旧缓存回填 → 墓碑丢失 → Stream裁剪 | 访问粒度、资源预算、版本门槛与权威恢复，不把缓存优化当业务正确性证明 |
| 分库分表 | 何时拆 → 分片键 → 跨片查询 → 全局唯一 → 扩容快照 → CDC删除 → 切主权 → 回滚 → 备份恢复 | 单一写主权、连续复制水位、旧路由拒写和可验证回退 |
| MQ | 为什么用 → 怎么不丢 → 重复怎么办 → 顺序保证范围 → exactly once边界 → 积压分类 → 加组还是实例 → 扩分区旧积压 → DLQ重放 | 从业务责任到消费完成闭环，lag和业务成功分别观测 |
| MySQL | 慢在哪 → 看什么计划 → 索引怎么排 → 范围列后能否用 → 回表与ICP → 深分页 → 锁等待 → 长事务 → 刷盘 → 主从 → DDL | 用执行证据和等待链定位，优化结果同时考虑读写代价与可靠性 |

## B.3 一道题讲到什么程度算准备充分

可以从架构、正确性、故障、容量、取舍和验证六个维度检查设计是否完整。

| 维度 | 仅记住名词时的表现 | 能继续追问时的表现 |
| --- | --- | --- |
| 架构 | 只会画中间件方框 | 能沿一次读写逐步解释每个组件的必要性 |
| 正确性 | 说“加锁、防重、最终一致” | 能写出不变量、唯一键、条件更新与终态转换 |
| 故障 | 统一回答“重试” | 能区分未执行、已成功、结果未知，保留恢复责任 |
| 容量 | 说“加缓存、加机器” | 能计算流量、内存、扇出、连接与净消化能力 |
| 取舍 | 背一种固定架构 | 能说出另一方案适合什么约束及迁移成本 |
| 验证 | 只会跑正常链路 | 能列具体故障注入、观测指标和正确性判据 |

例如“秒杀不会超卖”不能只通过正常并发压测证明。还要测试重复请求、事务提交响应丢失、预扣与发布中间宕机、支付关单竞态、重复释放、Redis重建和旧版本恢复。如果某个故障模型不支持，明确停止准入或返回结果待确认，比含糊地宣称全程成功更有说服力。

## B.4 如何围绕一条业务链路展开设计

围绕同一条业务链路，先说明数据模型、代码路径与正确性条件，再分析故障现象、定位方法和根因，最后说明架构扩展的触发条件、实现成本和验证方法。

例如，资料解析可以使用Kafka形成异步流水线，回答事件用Redis Stream保留重连窗口。消费者积压时，先检查解析、模型调用和索引写入哪个阶段受限；大文件引起内存压力时，可以通过流式解析、批次和并发上限控制单任务内存。资料撤销以数据库状态和版本为依据，旧任务写回必须校验版本。

制造业告警可以沿“告警事实 → 通知任务 → 领取执行 → 外部结果核对 → 版本号条件写回”讲解。这样面试官问索引、锁、超时、幂等、消息重试或线程池时，都能回到同一条业务流程。

## B.5 阅读与复习顺序

第一轮按“秒杀 → MQ → Redis → MySQL → 定时任务”学习，共同建立库存、消息、缓存和异步任务的正确性基础。第二轮学“点赞 → 评论 → 排行榜 → 朋友圈与运动”，比较关系事实、派生计数、排序快照和分页。第三轮学“登录 → 实时通信 → 文件视频 → 分库分表”，补齐权限、连接、传输和扩容。

每轮选一题，独立画架构、写一条核心SQL、列三个宕机窗口，再用业务不变量检查方案。若能回答但写不出状态条件，就继续练实现；若能背代码但解释不了何时失效，就沿故障矩阵再推演。
