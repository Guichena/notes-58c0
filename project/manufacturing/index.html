00整体架构：主链路与旁路

简历原文面向制造园区设备异常、工单超时和质量异常等生产事件，建设统一的可靠触达与智能维修闭环平台。主链路负责事件受理、可靠发布、消费幂等与流量治理；设备告警在独立旁路生成可追溯诊断卡和待审批维修工单，模型不参与告警判定、基础触达及正式工单写入。

流量治理入口按告警轮次去重合并，出口令牌桶限速，P0 全链路预留，积压时滞回降级（02）
独立旁路 · 可追溯诊断卡分析服务独立进程，持久化任务驱动，结论回链到证据（03）

01通知可靠性闭环

简历原文设计通知可靠性闭环：针对任务落库与 MQ 发布不一致、重复投递、渠道超时结果未知等问题，采用 Transactional Outbox + Publisher Confirm/Return 保证已受理任务可恢复发布；消费侧以数据库账本和处理轮次防重复执行，调用渠道前持久化稳定请求号，超时归为“未知”先对账再决策，结合退避重试、死信隔离与 XXL-Job 补偿收敛异常任务。压测叠加进程强杀，89,982 条已受理任务 100% 最终发布，最老待发布延迟峰值控制在 8.6s；故障演练下 5.4% MQ 重投均被幂等拦截，重复通知 0 次。

Transactional Outbox任务和“要发布的消息”写在同一个本地事务里，提交后由 Relay 发布，扫描兜底
Publisher Confirm/ReturnBroker 确认接手且消息成功路由，才算发布成功；否则回到待发布

架构：一条通知从受理到送达

相关八股

“任务落库”和“消息发布”是两个系统里的两次写，中间任何一刻进程都可能被杀。下面这些知识点回答的是同一个问题：两次写之间出了事，系统靠什么回到一致？

1. 两阶段提交（2PC / XA）

协调者先向所有参与者发“准备”（Prepare），参与者写好重做 / 回滚日志、锁住资源后回答“可以提交”；所有人都同意后协调者再发“提交”（Commit）。它能做到原子提交，但代价是阻塞：参与者答完“可以”之后就只能等协调者的决定，如果这时协调者宕机，参与者既不能自己提交也不能自己回滚，资源一直被锁着。再加上每次提交多一轮网络往返、要求所有参与者都实现 XA 接口，它更适合同一机房内少量数据库之间的强一致。

在我们的设计里：MySQL 支持 XA，但 RabbitMQ 不能作为 XA 参与者，企业微信、短信、电话这些外部 HTTP 接口更不可能参与两阶段提交，所以 2PC 在这条链路上根本无从下手。

2. TCC 与 Saga

TCC 把一次业务拆成 Try（预留资源，如冻结额度）、Confirm（真正扣减）、Cancel（释放预留）三个由业务自己实现的接口，框架负责在全局成功时调 Confirm、失败时调 Cancel；三个接口都要幂等，还要处理“Try 没执行却收到 Cancel”（空回滚）和“Cancel 之后 Try 才到”（悬挂）。Saga 则把长事务拆成一串本地事务，每一步配一个补偿动作，失败时倒序补偿；它没有隔离性，中间状态对外可见。两者的共同前提是：每个动作都能被预留或被补偿。

在我们的设计里：一条短信、一通电话发出去就收不回，既没有“预留”也没有真正的“补偿”（最多再发一条更正，那是新的业务动作）。所以 TCC / Saga 解决不了“通知发没发”的一致性，我们只在数据库内部做本地事务，把外部动作的不确定性交给对账。

3. 本地消息表 / Transactional Outbox

核心思路是把“要发一条消息”这件事先变成数据库里的一行：业务数据和这行消息在同一个本地事务里提交，要么都有、要么都没有；事务提交后，再由一个独立的发布者（Relay）把消息行读出来发到 MQ，发成功再标记。这样“业务成功但消息丢了”的窗口就消失了。它的本质限制有两个：一是至少一次——发布者发出后、标记前崩溃，重启后会再发一次，所以下游必须幂等；二是发布有延迟，取决于发布者多快发现新行（提交后立即发、定时扫描或读 binlog）。

在我们的设计里：任务和消息行同事务提交；提交后走快路径立即发布，每秒扫描兜底，处理快路径失败或进程被杀的情况；发布结果以 Broker 确认为准回写。Outbox 只保证“已提交的发布意图不丢”，不保证渠道收到——后者交给消费侧和对账。

4. MQ 的投递语义

至多一次：消费者先确认再处理，处理中崩溃消息就丢了。至少一次：先处理再确认，处理完、确认前崩溃，Broker 会把这条消息重新投给别人。恰好一次：在“消息系统内部”可以靠事务做到（如 Kafka 的读-处理-写事务），但只要处理过程中有外部副作用（写另一个数据库、调 HTTP），端到端的恰好一次就只能通过至少一次 + 幂等来等效实现。RabbitMQ 在连接或信道断开时，会把未确认的消息重新入队投递；quorum 队列还会记录投递次数，超过上限可以转入死信交换机。

在我们的设计里：我们按至少一次设计，并且把重投当成常态而不是异常：故障演练里 5.4% 的投递是重投，全部被消费侧账本拦下。

5. Publisher Confirm 与 mandatory / Return

生产者调用发布方法返回，只代表消息写进了本地的网络缓冲区。开启 Publisher Confirm 后，Broker 在“接手了这条消息的责任”时回一个确认（对持久化消息和 quorum 队列，是在写入并复制到多数节点之后），出问题回否定确认。但 Confirm 不管路由：如果交换机找不到任何匹配的队列，消息会被直接丢弃，Broker 照样回确认。设置 mandatory 后，无法路由的消息会先以 Return 退回给生产者，再回确认。

在我们的设计里：“已发布”的判定是 收到 Confirm 且没有收到 Return；否定确认、Return 或确认超时，都把消息行退回待发布并退避重试。这样既不会把“只进了本地缓冲区”当成功，也不会把“发进黑洞”当成功。

6. 消费侧幂等

幂等的意思是同一个请求处理一次和处理多次，效果相同。常见做法：唯一键（插入去重记录，冲突即视为已处理）、状态机条件更新（只有处于某个状态才能推进）、去重表、乐观锁版本号。Redis 的 SETNX 也常被用来“占位”，但它可能因主从切换或过期丢掉 key，而且占位和写库不在一个事务里——它适合做加速，不适合做最终判断。另外，唯一键只能防住“本地重复执行”，防不住“外部动作已经做了、本地还没来得及记账就崩溃”这种情况。

在我们的设计里：消费时先在数据库插入一条唯一的处理记录，冲突说明是重投，直接确认；处理记录带“处理轮次”，过期的旧处理者写不进结果。外部动作的那半边重复，由下一节的请求号解决。

7. 外部调用的幂等键

调用外部服务时，超时不等于失败：请求可能已经执行，只是响应丢了。业界通用的做法是由调用方生成一个唯一请求号随请求发送，服务端按它去重——例如支付类 API 普遍支持的 Idempotency-Key 请求头，同一个键重复请求会返回第一次的结果。如果对方不支持按键去重，就只能退而求其次：把请求号带过去以便事后查询，超时后先查再决定是否重发。

在我们的设计里：调用渠道之前，先把“准备发送”和稳定请求号落库，所有重试复用同一个请求号；结果分成功、明确失败、未知三类，超时归为未知，先按请求号向渠道查询，查到就记成功，确认没收到才重发，查不清转人工。

8. 重试、退避与死信

重试要解决两个问题：别把下游打垮、别让坏消息堵住队列。指数退避让间隔随次数增长，再加随机抖动，避免一批失败的请求在同一时刻一起重试（“惊群”）；重试次数要有上限。超过上限或明显无法处理的“毒消息”转入死信队列隔离，等人处理，而不是无限重试拖住后面的正常消息。

在我们的设计里：重试状态和下一次重试时间存在数据库里，由定时扫描按到期时间领取，便于查询、暂停和人工干预；超过上限进入死信并告警；XXL-Job 负责重试到期扫描、未知结果对账和全局对账，把所有异常任务最终收敛到“成功”或“人工”。

业界做法

同样是“数据库写 + 发消息”，业界有六种常见做法。每种都画出它怎么工作，以及在哪里出问题或要付出什么。

A. 事务提交后直接发 MQ

怎么做：业务事务提交后，在代码里紧接着调用一次发送；也有人反过来先发消息再提交。

优点：最简单，没有额外的表和组件，延迟最低。

缺点：先提交后发送：两步之间崩溃就丢消息，而且不留痕迹，只能靠“时间差”猜测哪些任务没发。先发送后提交：事务回滚了消息却已经发出，下游收到一条“不存在的任务”。

放到我们的约束下：已受理的 P0 告警丢一条就是事故，这种写法不满足“已受理必有发布依据”的要求，直接排除。

B. Outbox + 轮询发布（我们的选择）

怎么做：消息行和业务数据同事务写入；发布者通过“提交后立即发”加“定时扫描”找到待发的行，发布成功后标记。这是微服务领域里被广泛描述的 Transactional Outbox 模式。

优点：只依赖已有的关系数据库，与 MQ 品牌无关；发布意图持久化在库里，可查询、可补发、可审计；实现简单，排障路径短。

缺点：至少一次，必须配合下游幂等；多一张表，需要归档清理；扫描会给数据库带来持续的读压力，发布延迟受扫描周期影响；多实例发布者要处理领取竞争。

放到我们的约束下：我们的量级下扫描压力很小，快路径让绝大多数消息在提交后立刻发出，扫描只兜底；下游幂等本来就因为 MQ 重投而必须做。代价都在可接受范围内。

C. RocketMQ 事务消息

怎么做：生产者先发一条“半消息”，Broker 存下但不投递；然后执行本地事务，根据结果向 Broker 提交或回滚。如果这一步的结果丢了，Broker 会定期回查生产者，由生产者查本地事务状态后给出答复。

优点：MQ 原生支持，不用自己维护消息表和扫描；消息在提交前对消费者不可见，语义清晰。

缺点：强绑定 RocketMQ；要实现可靠的回查接口，而回查本质上还是在查本地的业务状态（等于自己维护了一份“发布依据”）；消费侧依然是至少一次，幂等一样不能省。

放到我们的约束下：厂区现有基础设施只有 RabbitMQ，为了这个特性引入并运维一套新的 Broker 不划算；而且它省掉的消息表，换成了回查逻辑，复杂度并没有真正消失。

D. Outbox + CDC（如 Debezium）

怎么做：依然写消息表，但不再由应用轮询，而是由 CDC 连接器从数据库日志（如 MySQL binlog）里捕获消息表的插入，转成消息投递出去。Debezium 提供了专门的 Outbox 事件路由，通常跑在 Kafka Connect 上。

优点：没有轮询带来的数据库读压力，延迟低；应用代码只管写表，发布逻辑完全外置。

缺点：多一套连接器的部署、监控和位点管理；需要 binlog 读取权限；表结构变更、连接器重启和积压都会影响下游；排障多一跳；依然是至少一次。

放到我们的约束下：在我们的量级下轮询完全够用，团队也没有运维 CDC 的经验和需求。它是我们明确的“下一步”：当扫描压力或发布延迟成为问题时再换，而且消息表结构和下游幂等都不用改。

E. Kafka 事务（exactly-once）

怎么做：幂等生产者避免单分区内的重复写入；事务让“读消息 → 处理 → 写到其他 topic → 提交位移”作为一个整体原子生效，这就是常说的 Kafka 恰好一次语义。

优点：在纯 Kafka 的流处理链路里，可以真正做到端到端恰好一次，不需要业务自己去重。

缺点：边界只在 Kafka 内部：一旦处理过程中写了外部数据库或调用了 HTTP 接口，这些副作用不受 Kafka 事务保护；而且它要求链路本身就建在 Kafka 上。

放到我们的约束下：我们用的是 RabbitMQ，链路的终点是外部渠道，正好落在它覆盖不到的地方。所以它不是一个可选项，但它说明了一个结论：跨系统的恰好一次只能靠至少一次 + 幂等。

F. 分布式事务框架（如 Seata）

怎么做：引入一个事务协调器，把多个参与方登记为全局事务的分支。Seata 提供 AT（自动记录回滚日志、通过全局锁隔离）、TCC、Saga、XA 几种模式，由协调器在全局成功或失败时驱动各分支提交或回滚。

优点：对“多个数据库或多个服务的写入要么都成功、要么都失败”很友好，AT 模式对业务代码侵入小。

缺点：要部署和运维协调器；全局锁和额外的往返会降低吞吐；最关键的是，它只能回滚能回滚的资源——消息中间件和外部短信、电话接口都不在其中。

放到我们的约束下：我们的一致性问题恰恰出在“数据库”和“外部渠道”之间，框架帮不上忙，反而增加一个关键依赖。

结合业务的选择

业务约束。这是一个制造厂区的生产告警平台：P0 告警有分钟级的触达时限，已受理的任务丢一条就是事故；通知的终点是企业微信、短信和语音电话，它们都在我们的任何事务之外，发出去就收不回。基础设施方面，现有的是 MySQL 和 RabbitMQ，团队规模小，没有余力为一个特性多运维一套 Broker、CDC 连接器或事务协调器。

为什么选它。在这些约束下，问题的本质不是“怎么让数据库和 MQ 强一致”，而是“已受理的任务一定留下可查的发布依据，并且重复可以被收住”。Outbox 只依赖已有的 MySQL，就把前半句落实到了每一条任务；Publisher Confirm + mandatory 让“已发布”有确定的判据。后半句则由消费侧解决：数据库账本拦住 MQ 重投，调用前持久化的稳定请求号加上“未知先对账”，拦住外部渠道层面的重复。压测叠加强杀下 100% 最终发布、5.4% 的重投全部被拦下、重复通知 0 次，验证的正是这条思路。

放弃了什么。我们明确放弃了“发布恰好一次”：Relay 在发出后、标记前崩溃时会重复发布，这个代价被转移给了消费侧幂等。我们多维护了一张消息表、一个扫描任务和一套对账流程；“结果未知”中查不清的那一小部分需要人工确认；同时也接受了这样一个事实——系统不能既承诺绝不重复，又承诺一定送达，在两者冲突时我们选择先对账、宁可交给人。

什么时候换。如果发布量涨一个数量级，第一步是把 Relay 按消息分桶，每个实例只扫自己的桶；如果扫描压力或发布延迟仍然成为瓶颈，再把轮询换成 CDC——消息表结构和下游幂等逻辑都不用改，变的只是“谁来发现新行”。如果某个渠道开始支持按请求号去重，那个渠道的“未知”就可以改成同号直接重试，省掉查询这一步。

CAS 与 ABA比较并交换只看当前值；单调递增的版本号可以避免 ABA草稿每次修改版本号递增，批准绑定看到的那个版本
事务边界与“意图”把“要做的外部动作”作为一条记录和状态变更放进同一事务，再异步执行（Outbox 的同类思路）批准和执行意图同事务：要么都有，要么都没有
分布式锁的坑Redis 锁的过期和业务提交不原子，GC 停顿会出现双持有；需要 fencing token 兜底不用分布式锁，数据库条件更新本身就是 fencing
外部调用的不确定结果超时不等于失败：请求可能已执行；只能靠幂等键或查询确认超时归为未知，先查后建
幂等键由调用方生成、服务端按键去重（如支付 API 的 Idempotency-Key）CMMS 不支持去重，退而求其次：请求号写进外部参考号，可查询
读延迟与一致性主从复制下刚写入的数据短时间查不到（read-after-write 不一致）对账要等过查询延迟窗口，否则会误判“没建成”
Human-in-the-loop高风险、不可逆的动作前插入人工审批，模型只出建议建单前必须人批准；带标字段必须逐个确认

并发审批：业界做法与优缺点

方案业界代表 / 典型实现怎么做优点缺点结论
只用乐观锁版本号JPA 等 ORM 的版本字段更新时带版本条件简单通用防覆盖，但挡不住同一命令重放插两条执行意图不够
条件更新 + 唯一执行意图同事务 采用状态机 + 唯一约束一个事务完成状态推进与意图插入数据库原生保证，后到者自然失败会签要先锁草稿行串行收敛采用

HITL 的实现方式

方案业界代表 / 典型实现怎么做优点缺点结论
图编排框架的人工中断LangGraph 的 interrupt / 人工介入节点在图中暂停等待人输入，再从检查点恢复与 Agent 编排一体审批状态与业务库是两套真源不选
工作流引擎 / BPM 用户任务Temporal 信号、Camunda / Flowable 用户任务引擎管理等待、超时与指派审批流复杂时很强多一套引擎运维；我们的审批只有一两级不选
业务状态机 + 审批页 采用业务系统自建草稿状态存在业务库，审批页驱动状态推进状态与执行意图同库同事务会签、加签等复杂审批要自己实现采用

业务约束：CMMS 是已有系统、不支持幂等但能按外部参考号查询；审批人是班组长和主管，审批只有一两级；错建工单会派错人、占用维修资源。

为什么选它：冲突概率很低但后果严重，用数据库条件更新零额外依赖就能保证只产生一个执行意图；对方不幂等，就把幂等收在我方，用“先查后建”代替盲目重试。

放弃了什么：查不清的少数情况交给人；建单可能因为对账晚几分钟；复杂审批流（会签、转办）需要自己扩展。

什么时候换：CMMS 支持外部参考号唯一约束后，改为同号直接重试；审批流变复杂（多级、条件分支、超时转办）时引入 BPM 引擎，执行意图仍留在业务库。
