01受理与发布的一致性：已受理的通知不丢

写库和发 MQ 没有共同事务，任何先后顺序都有窗口：先提交后发，提交后进程退出则任务永远没人发；先发后写，库回滚后留下脏消息。

受理时在同一个本地事务里写入通知任务和一行 Outbox 消息（状态 PENDING）。同键请求以 (tenant_id, idempotency_key) 唯一约束收敛：相同键、相同载荷哈希返回原任务；相同键、不同载荷返回冲突，不覆盖。鉴权、模板和值班快照在事务外准备，事务内只做本地写入，提交成功后才返回“已受理”。

发布走两条路径：提交后回调立即发布（快路径，毫秒级），每秒一次的兜底扫描保证快路径丢失时仍有人推进。多实例都能扫描，但只有条件更新 PENDING→PUBLISHING 影响 1 行的实例才发布。一条消息只有拿到 Publisher Confirm 且没有被 Return（不可路由）时才置 PUBLISHED；超过 Confirm 截止时间仍停在 PUBLISHING 的行由恢复扫描放回 PENDING。

六个故障窗口

宕机位置库里留下什么谁恢复必须避免
受理提交后，Relay 未领取PENDING任一存活实例的兜底扫描把“已受理”说成“已进 Broker”
领取提交后，publish 前PUBLISHINGConfirm 截止 / 租约扫描放回只扫 PENDING，行永久卡住
Broker 已接收，本地未回写仍是 PUBLISHING恢复后重复发布下游没有幂等
渠道已受理，结果事务前宕机发送记录 IN_FLIGHT，请求号已存按请求号查询 / 对账 / 人工因“没有成功记录”而重发
结果已提交，ACK 前宕机任务有结果，账本 DONE重投后读账本直接 ACK再调一次渠道
旧执行者停顿超租约后复活账本已是新的处理代次只允许当前代次收口旧结果覆盖新状态

约束是：MySQL 和 RabbitMQ 已在用，外部渠道不在事务里，要的是“已受理就一定留下可查的发布依据”。Outbox 只保证已提交事务里的发布意图不丢，不保证渠道收到，也不保证数据库灾难下 RPO 为零。

放弃的是“发布恰好一次”：重复发布被明确接受，代价转移到消费侧幂等。量涨十倍时先把 Relay 按消息行分桶、每个实例只扫自己的桶；还不够再把轮询换成 CDC，消息表和下游幂等不变。

02消费幂等：重复投递不变成重复通知

至少一次投递 + 外部 HTTP 不在事务里，会产生三种不同的重复，各用一种手段拦。

重复来源典型原因手段
同一事件被重投Broker 重投、Relay 重复发布（事件号相同）消费账本唯一键 (tenant_id, event_id, consumer_group)，插入成功才拿到处理权
旧事件覆盖新状态任务重试生成新事件号，旧事件仍在路上任务上的重试代次；事件代次比任务旧就按过期收口
外部副作用重复渠道已执行、本地结果未提交就宕机调用前写发送记录（IN_FLIGHT + 稳定请求号），恢复者看到 IN_FLIGHT 去对账而不是重发

一次消费拆成三段短事务，渠道调用夹在中间、不在任何事务内：T1 插账本抢处理权；T2 复核“我仍是当前处理者、任务代次未变、告警仍有效”后写发送记录；调渠道；T3 把结果和账本 DONE 同事务提交后再 ACK。每段都是主键或唯一键上的点操作。租约过期只代表允许接管：每次接管处理代次加一，所有写都带代次条件，旧执行者的写影响 0 行。

渠道结果分四态：成功、可重试、不可重试、未知。连接超时和熔断拒绝属于“明确未执行”，可以切备用渠道；读超时一律归“未知”，按渠道能力用同一请求号查询或同号幂等重试，查不清时按优先级在“可能重复”和“可能漏发”之间取舍。HTTP 客户端的自动重试必须关闭，否则重试会绕过发送记录。

Redis SETNX先占 key 再处理主从切换或过期丢 key 就放过重复；占 key 后写库失败要补删 key最快不能作为最终判断

03通知风暴治理：少发噪声，但首次、升级、恢复永不被压

量不大但噪声大：阈值附近抖动、重复催办、产线断电的关联风暴会淹没关键通知。治理只影响“发不发通知”，不改告警事实。

去重的身份是告警轮次，不是“设备 + 告警码”：恢复后再次触发是新一轮，升级是状态变化，都不能被压。轮次和单调版本号由上游给，平台用版本比较防止旧事件覆盖新状态，不依赖 MQ 顺序。入口按“优先级 × 状态变化”的策略矩阵决定直发、去重或窗口内合并；每一次压制都和任务同事务写一条决策记录，Redis 只缓存已提交的决策，用来挡风暴时的重复读。

限流放在出口：真正稀缺的是渠道配额，配额按渠道账号算，所以在调用渠道前扣令牌，而不是在入口拒掉已经成立的告警。令牌桶由 Redis Lua 原子地完成“按时间补充 + 扣减”，时间取 Redis 服务端时间以防实例时钟回拨，key 按“渠道账号 × 业务单元”分层，并给 P0 预留份额。P0 要经过 Relay、MQ、消费线程、HTTP 连接、渠道配额五个环节，每个环节都单独隔离：P0/P1/普通各一个队列和独立消费者容器，连接和令牌也给 P0 留份额。

级别去重 / 合并出口限流降级时
P0不合并预留配额，不进普通桶始终送达
P1不合并令牌桶保留
P2 / P3窗口内合并令牌桶先合并、后延迟

Redis 只承担性能和协调，不承担事实：Redis 不可用时，去重回库读决策，计数回库，令牌桶切到本地保守额度并优先 P0/P1，档位按收紧档初始化；不静默丢 P0，也不无限放行。

04依赖故障、积压与扩容

每个依赖都说清“影响 → 降级 → 恢复 → 怎么发现”。MySQL 是事实源，其他组件挂了只降级、不丢事实。

依赖挂了的影响降级恢复与发现
MySQL 主库受理返回 503，上游带同一幂等键重试；消费退避独立应急通道发送 P0切换后按上游受理清单对账（异步复制 RPO 不为零）
RabbitMQ 集群受理照常，消息表积压P0 应急直发，复用同一发送记录协议恢复后 Relay 补发；监控最老待发布年龄
Redis去重和限流失去加速去重回库；令牌桶切本地保守额度，优先 P0/P1档位按收紧档初始化
调度中心普通重试与对账暂停P0/P1 的应用内扫描不受影响恢复后按到期时间继续扫
模型 / 检索库诊断卡不可用只输出事实摘要，不影响基础告警分析任务持久化，可重放
外部渠道 / CMMS发送或建单结果不确定备用渠道；结果“未知”进入对账按请求号查询收口

积压先定位在哪一层（Outbox、队列、消费、渠道），再判断谁慢。系统自动收紧：先保 P0，普通通知合并或延迟；发送前再查告警当前状态，已恢复或已过期的通知直接收口，这一步本身就在削峰；恢复时由令牌桶平滑放量。不清空队列、不提前 ACK。全局对账只发现、不改状态，其中最关键的一项是“已发布超过一定时间却没有任何消费账本”，它能发现 Publisher Confirm 覆盖不到的 Broker 侧丢失。

减事务 + 分库分表 采用先合并写、减少每条通知的事务数，再按受理键哈希分库（任务号带分片位）；Relay 竞争明显时按桶分片迁移期间跨库查询和对账变难迁移成本采用

05隔离式分析 Agent：证据链与幻觉控制

现场维修人会照着建议去做，错误不可回滚，还有时效要求。所以模型不参与告警判定和基础触达，分析是持久化任务旁路，任何失败只降级成事实摘要。

检索：告警码、设备编码和 SOP 编号走关键词一路，现场口语描述走向量一路；两路按名次用 RRF 融合（Σ 1/(k+rank)，k=60），不直接相加全文分数和向量距离，因为量纲不同。正式 SOP 和历史案例分组融合并各留保底名额，案例不能挤掉全部正式依据；rerank 放在权限复核之后。带过滤的近邻检索会出现“过滤后零候选”，用迭代扫描或小集合精确检索补，不放宽过滤条件。

生成：先定每个字段归谁。事实和数值由模型引用测点 ID、代码从快照回填，模型负责解释、不负责重写数字；趋势由代码计算；原因由模型生成并挂证据编号；检查项只能从受控库选 ID；优先级、班组等组织字段归规则。模型可以回答“证据不足”。

校验层检查什么失败时
结构输出符合诊断卡 Schema重试一次后降级
引用回链每条结论指向真实证据编号删去无依据条目
事实回填设备、时间、数值与快照一致以快照为准回填
危险建议硬规则过滤高风险操作拦截并标记

可预测、可审计比灵活更重要；需要的补查只有一两次，固定流程里留两次只读工具调用就覆盖了。

06HITL 维修工单：审批并发、执行意图与建单超时对账

模型只起草，人决定；正式工单写入有外部副作用，必须可追溯、可拒绝。CMMS 本身不幂等，所以幂等收在我方。

审批是一个事务三步：带版本号、参数摘要、状态和截止时间的条件更新草稿 → 插入唯一执行意图 → 写审计；影响行数不为 1 就整体回滚。审批人从登录态取并重新校验权限，审批命令 ID 唯一，重放只返回原结果。截止判断写在审批 SQL 里，不依赖定时任务；过期绝不自动批准。外部请求号在审批事务里生成一次，之后所有重试都复用。

建单超时不能直接再建：超时只说明本地没收到完整响应，第一次调用可能仍在执行，第一次查不到也可能只是 CMMS 查询延迟。执行意图记为 CREATION_UNKNOWN，请求号写进工单的外部参考号字段；等过查询延迟窗口后按参考号复查：查到原单就补登记；仍明确查不到才用同一请求号重建；查询失败或结果说不清就转人工确认，绝不盲目重试。建单成功后，“已建单”和通知班组长的消息行在同一本地事务写入，通知失败不回滚建单。

Redis 分布式锁锁住草稿再审批锁过期和事务提交不原子，GC 停顿时双持有，最后仍要条件更新兜底多一个依赖不选

审批冲突很少，但错了就会建两张单。条件更新与执行意图同事务，数据库自带 fencing。这条边界曾因事务注解自调用失效被打破过（对账发现已批准却无执行意图的草稿），之后改为编程式事务并加集成测试。
