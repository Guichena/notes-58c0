00整体架构：主链路与旁路

01通知可靠性闭环

简历原文设计通知可靠性闭环：针对任务落库与 MQ 发布不一致、重复投递、渠道超时结果未知等问题，采用 Transactional Outbox + Publisher Confirm/Return 保证已受理任务可恢复发布；消费侧以数据库账本和处理轮次防重复执行，调用渠道前持久化稳定请求号，超时归为“未知”先对账再决策，结合退避重试、死信隔离与 XXL-Job 补偿收敛异常任务。压测叠加进程强杀，89,982 条已受理任务 100% 最终发布，最老待发布延迟峰值控制在 8.6s；故障演练下 5.4% MQ 重投均被幂等拦截，重复通知 0 次。

这条简历讲的是一件事：已经受理的告警通知，任何一个进程在任何时刻被杀，都要能被找回来继续发；而找回来重发时，又不能让值班人收到两条。难点在于链路要跨过三个互相没有共同事务的系统：MySQL、RabbitMQ 和外部渠道（企业微信、短信、电话）。

下面按“总—分—总”展开：先定义清楚“可靠”到底承诺什么；再沿“生产者 → MQ → 消费者 → 外部渠道”三段，讲每段背后的八股机制、会在哪里断、业界有哪些做法；然后把它们落到六个具体的宕机位置上；最后讲结合业务为什么这样选，以及简历里每个数字的口径。

先定义“可靠”：五个不同的成功

“通知发送成功”其实是五件不同的事，原系统把它们混成一个状态，结果通知没到时根本查不出断在哪一层。我们把它拆开，每层有自己的记录，也只对自己那一层负责。

在这个拆分之上，我们给出的是有边界的承诺：已受理的一定留下可查的发布依据、并且有恢复者；重复投递不会变成重复的业务动作；结果不确定时先对账，查不清就交给人，而不是盲目重发。我们不承诺端到端恰好一次——外部渠道不在我们的任何事务里，这个承诺给不了，说大了反而经不起推敲。值班人迟迟不确认时的升级（班组长、电话）属于业务兜底，也不是 MQ 能保证的。

架构：三段链路，各用各的方案

第一段，生产者到 MQ：本地消息表（Outbox）保证“不丢”。受理时把“要发一条消息”也写成同库同事务的一行，提交后由 Relay 发布，Broker 确认接手且成功路由才算发布成功。这一段只管到 Broker 为止。

第二段，MQ 到消费者：数据库账本保证“不重复处理”。MQ 是至少一次投递，重投是常态；消费者先在库里抢到这条事件的处理权，重复投递撞上唯一键就直接收口。处理轮次让超时被接管的旧执行者写不进结果。

第三段，消费者到外部渠道：借鉴“最大努力通知”，用稳定请求号 + 对账处理“结果未知”。这是数据库技术本身解决不了的一段：调用之前先把“准备发送”和请求号落库，超时不当失败而当“未知”，按渠道能力去查，查不清交给人。

之所以分三段，是因为三段的失败语义完全不同：Broker 没确认、消费者半路宕机、渠道超时，各自需要的恢复手段不一样。指望用一个方案（比如一个“大分布式事务”）覆盖全链路，要么做不到，要么让某个组件去判断它根本判断不了的事情。

相关八股 · 一：两次写之间出了事，靠什么回到一致

“任务落库”和“消息发布”是两个系统里的两次写，中间任何一刻进程都可能被杀。分布式事务的各种方案，本质上是在回答同一个问题：由谁、在什么时候、依据什么，把两边拉回一致？它们的区别在于一致性的强弱、对业务的侵入，以及要求参与者具备什么能力。

两阶段提交（2PC / XA）

机制：协调者先向所有参与者发“准备”，参与者写好重做 / 回滚日志、锁住资源，回答“可以提交”；全部同意后协调者再发“提交”，任何一个不同意就全部回滚。MySQL 的 XA 就是这个协议在数据库层的实现。

断在哪：阻塞。参与者答完“可以”之后既不能自己提交、也不能自己回滚，只能等协调者；协调者宕机，资源就一直锁着。三阶段提交（3PC）多加一轮询问并引入超时，减轻了阻塞，但在网络分区下仍可能不一致，实践中很少使用。

代价：锁要跨越多轮网络往返持有，吞吐低；要求所有参与者都实现 XA 接口。它适合同一机房内少量数据库之间的强一致。

在我们这里：RabbitMQ 不能作为 XA 参与者，企业微信、短信、电话这些 HTTP 接口更不可能参与两阶段提交，2PC 在这条链路上根本无从下手。

TCC：Try / Confirm / Cancel

机制：把一次业务拆成三个由业务自己实现的接口：Try 预留资源（如冻结额度），Confirm 真正使用预留，Cancel 释放预留。框架在全局成功时调 Confirm，失败时调 Cancel。它把“锁”从数据库层上移到了业务层，不需要长时间持有数据库锁。

断在哪：三个接口都可能被重复调用，必须幂等；网络乱序带来“空回滚”（Try 没执行却收到 Cancel）和“悬挂”（Cancel 之后 Try 才到），都要业务自己记录事务状态来识别。

代价：侵入极大：每个参与的操作都要写三套逻辑。最根本的前提是资源可以被预留。

在我们这里：一条短信、一通电话发出去就收不回，没有“预留”可言，也没有真正的 Cancel。TCC 解决不了“通知发没发”的问题。

Saga：长事务拆成一串本地事务

机制：把长流程拆成多个本地事务，每一步配一个补偿动作；某一步失败，就倒序执行已完成步骤的补偿。可以由一个编排者集中驱动（编排式），也可以由各服务通过事件接力（协同式）。

断在哪：Saga 没有隔离性：中间状态对外可见，别人可能读到“扣了款但还没发货”的数据，需要语义锁、可交换的更新等手段缓解；补偿本身也会失败，所以补偿必须幂等、可重试。

在我们这里：Saga 的前提是“每一步都能被补偿”。通知的“补偿”最多是再发一条更正，那是一个新的业务动作，不是撤回。能回滚的只有数据库；外部动作至多补偿，而通知连像样的补偿都没有。

本地消息表与 Transactional Outbox

机制：把“要发一条消息”先变成数据库里的一行，和业务数据在同一个本地事务里提交，要么都有、要么都没有；提交后由一个独立的发布者（Relay）把消息行读出来投递，成功再标记。它用本地事务的原子性替代了跨系统的两阶段提交，是最终一致性方案里最朴素、依赖最少的一种。

经典本地消息表和 Outbox 的区别：国内常说的“经典本地消息表”，往往要等下游业务处理成功并回调才把消息标成完成，没回调就一直重发，相当于把端到端确认也塞进了这张表。Transactional Outbox 只负责到“消息交给 Broker”为止，下游有没有消费成功由下游自己负责。我们用的是后者：下游有 MQ、消费者、外部渠道好几层，每层失败语义不同，全塞进一张消息表的状态里，含义会变得混乱，Relay 也被迫去判断“企业微信超时到底算不算成功”这种它判断不了的事。

发布者怎么发现新行：三种方式：纯定时扫描（最简单，延迟等于扫描周期）；提交后回调立即发布（延迟低，但回调是内存里的，进程在回调前挂了就没了，只能当快路径）；读数据库日志（CDC，不轮询，但多一套组件）。

断在哪：两个本质限制。一是至少一次：发布后、标记前崩溃，重启会再发一次，下游必须幂等。二是消息表必须和业务数据同库同事务，跨库就退化回双写问题；分库之后每个库都要有自己的消息表。

代价：每次受理多一次写入；扫描带来持续的数据库读压力；表会膨胀，要归档。

事务消息（半消息）：以 RocketMQ 为例

机制：把“消息表”的职责交给 Broker。生产者先发一条半消息，Broker 把它存进一个内部主题，对消费者不可见；生产者接着执行本地事务，根据结果向 Broker 提交或回滚：提交后消息才被投递到真正的主题，回滚则丢弃。

断在哪：第 ④ 步可能丢失，或者生产者执行完本地事务就宕机了。Broker 会定期回查，生产者要实现一个回查接口，根据本地事务的真实结果回答提交还是回滚；回查有次数上限，超过上限的消息默认会被丢弃，需要业务自己兜底。也就是说，回查接口本身就要求本地有一份可靠的“这笔事务做没做”的记录。

代价：强绑定支持事务消息的 Broker；回查接口必须可靠且幂等；它只覆盖生产者这一侧，消费侧依然是至少一次，幂等一样省不掉。

最大努力通知

机制：发起方在本地事务完成后，按递增的时间间隔反复通知接收方，直到收到明确回执或达到次数上限；同时提供一个查询接口，接收方没收到通知时可以主动来查。支付平台回调商户就是典型：回调可能重复，商户必须幂等；回调可能丢，商户可以按订单号主动查询。

断在哪：它不保证一定送达，只保证“尽力并且可查”；接收方必须幂等，因为重试一定会带来重复。

在我们这里：我们对外部渠道的处理借鉴的正是这个思路，只是方向反过来：我们是调用方，渠道是接收方。重试有上限、复用同一个请求号，结果不确定时按请求号去渠道查询，而不是一直重发。

小结。从 2PC 到最大努力通知，一致性由强到弱，对参与者能力的要求也由高到低。2PC 和 TCC 要求参与者“能投票”或“能预留”，事务消息要求 Broker 支持，本地消息表只要求一个本地事务，最大努力通知只要求对方能查。我们这条链路上的参与者——RabbitMQ 和外部 HTTP 接口——恰好只具备后两种能力，这基本决定了方案的形状。

相关八股 · 二：MQ 的可靠性要按“三端”讲

“消息不丢”不是某一个配置能保证的，要分别看生产端、Broker 端、消费端，每一端都有自己丢消息的方式。

生产端：Publisher Confirm 与 mandatory / Return

机制：发布方法返回，只代表消息写进了客户端的网络缓冲区。开启 Publisher Confirm 后，Broker 在接手这条消息的责任时回一个确认（对持久化消息和 quorum 队列，是在写入并复制到多数节点之后），内部出错时回否定确认。但 Confirm 不管路由：交换机找不到匹配的队列时，消息被直接丢弃，Broker 照样回确认。设置 mandatory 后，不可路由的消息会先以 Return 退回，然后才回确认。

断在哪：确认超时不等于失败：Broker 可能已经收到，只是确认没回来。超时后重发是允许的，但会带来重复。另一个隐蔽的坑是迟到的确认：第一次发布的确认迟迟不来，恢复逻辑已经发起了第二次发布，这时第一次的确认才到——如果回写只按消息号更新，旧结果会覆盖新状态。

对比 Kafka：Kafka 的对应手段是生产者 acks=all（等所有同步副本写入）、配合 Broker 端的最小同步副本数和禁止非同步副本当选 Leader；再开启幂等生产者，避免重试造成的分区内重复写入。

在我们这里：“已发布”的判据是同一次发布收到 Confirm 且没有 Return；否定确认、Return 或确认超时，都把消息行退回待发布并退避重试。每次发布带一个发布尝试号，回写时要求尝试号仍然匹配，迟到的旧确认写不进去。

Broker 端：持久化、副本与“确认之后的丢失”

机制：交换机、队列声明为持久化，消息设为持久化投递，Broker 重启后才不会丢。quorum 队列基于 Raft 做多副本，写入多数节点才确认，只要多数副本存活就能继续读写；代价是比普通队列多一些写放大。

断在哪：Confirm 只能证明“那一刻 Broker 接手了”。之后队列被误删、绑定配置写错、运维误清空队列，消息都会在 Broker 那边静悄悄地消失，生产者和消费者都不会报错。

在我们这里：这正是全局对账存在的理由：它找出“已发布却始终没有任何消费记录”的消息，按原消息号重新发布；因为消费侧幂等，即使其实已经消费过，也不会造成重复。

消费端：ACK 的时机与 prefetch

机制：自动 ACK 在消息推给消费者时就确认了，消费者一崩溃消息就没了；手动 ACK 由业务决定何时确认。连接或信道断开时，所有未确认的消息会被重新入队投递。prefetch 限制的是每个消费者手里最多有多少条未确认消息，用来掩盖网络往返，它不是并发数；设得太大，少数消费者会囤积消息，重启时也会带来一大波重投。

断在哪：ACK 早了会丢：先确认再处理，处理中崩溃就没有任何恢复依据。ACK 晚了会重复：处理完、确认前崩溃，Broker 会重投。还有一种常见事故：处理失败就拒收并重新入队，一条处理不了的“毒消息”会在 Broker 和消费者之间热循环，把 CPU 打满。

在我们这里：原则只有一条：本次投递已经有了明确的持久化落点，才 ACK——结果已提交、发现已处理过、或者处理责任已持久化交给了别的处理者；查库失败、无法确认状态时不 ACK。ACK 本身失败时，不回退已提交的业务结果，重投到达时读账本发现已完成，直接确认收口。

投递语义：为什么“恰好一次”往往是幻觉

机制：至多一次：先确认再处理，可能丢。至少一次：先处理再确认，可能重。恰好一次：在消息系统内部可以做到，例如 Kafka 的幂等生产者（按生产者编号 + 序号在分区内去重）加事务（让“读 → 处理 → 写到其他主题 → 提交位移”原子生效）。但只要处理过程中有外部副作用——写另一个数据库、调 HTTP——端到端的恰好一次就只能用至少一次 + 幂等来等效实现。

在我们这里：我们按至少一次设计，并且把重投当成常态而不是异常：我们追求的不是让 MQ 不重投，而是让重投不产生第二次副作用。故障演练里主动制造的重复投递，相当于通知事件数的 5.4%，全部被消费侧账本拦下。

相关八股 · 三：消费侧的重复、并发与顺序

幂等要分层：三种不同的“重复”

机制：幂等的定义是同一个请求处理一次和处理多次，外部效果相同。常见手段有：唯一键（插入去重记录，冲突即视为已处理）、状态机条件更新（只有处于某个状态才能推进）、版本号 / 代次（旧版本的写不生效）、去重表（记录处理中 / 成功 / 失败和外部回执）。Redis 的 SETNX 常被用来“占位”，但它可能因主从切换或过期丢掉 key，而且占位和写库不在一个事务里，只适合做加速，不适合做最终判断。

断在哪：“处理前先查一下有没有处理过”并不等于幂等。唯一键只能说明“谁拿到了处理权”，说明不了“外部动作到底做了没有”。如果消费者调用渠道成功、写结果之前崩溃，消息重投后新的消费者看到“没有成功记录”，就会再发一次。

在我们这里：第一层用数据库账本（不用 Redis：Redis 丢了 key 就意味着可能重复通知，它不能做最终依据）；第二层用任务代次；第三层靠调用前持久化的发送记录和稳定请求号，见下一节。

一次消费为什么拆成三段短事务

机制：不能用一个大事务把“写账本 → 调渠道 → 写结果”包起来：数据库回滚撤不回已经发出的 HTTP 请求；事务里等外部接口，渠道一慢，数据库连接就被占住，风暴时连接池会被打满。所以拆成三段：第一段抢处理权；第二段在调用之前写下“准备发送”的证据和请求号；事务外调用渠道；第三段把结果、任务状态和账本“已完成”一起提交，提交后才 ACK。

断在哪：最危险的窗口在调用之后、第三段之前。有了第二段的“调用中”记录，恢复者就知道这个动作可能已经执行，不会把“没有成功记录”当成“没有执行”，而是转去对账。没有这条记录，恢复者只能再发一次——这就是重复通知的根源。

代价：多了两段事务，但每段都是主键或唯一键上的点操作，相比渠道调用的耗时可以忽略；真正的代价是必须显式处理“未知”这种结果，而这个代价本来就存在，只是以前被忽略了。

租约与 fencing token：旧执行者“复活”

机制：处理者拿到处理权时带一个租约，处理中定期续租；租约过期，恢复扫描就允许别人接管。但租约过期只说明“允许接管”，不说明旧处理者已经停了：一次长 GC 停顿、容器 CPU 被限流、网络分区，都可能让它几十秒没动静，醒来后继续往下写。经典解法是 fencing token：每次接管把一个单调递增的号码加一，所有写操作都带上自己拿到的号码，号码过期的写一律不生效。

断在哪：轮次只能挡住本地数据库的写。旧处理者如果醒来后先调了外部接口，这一下是挡不住的，必须靠调用前写的“调用中”记录和同一个请求号兜底：新处理者看到“调用中”不会再发，两者用的是同一个请求号，渠道支持去重时即使都发了也会被去重。

在我们这里：这就是简历里说的“处理轮次”。租约到期的判断统一用数据库时间，不用应用本地时钟；结果事务按固定顺序加锁，任何一步发现轮次不对就整笔回滚，不会出现“任务改成成功了、账本却没更新”的半成功状态。

消费者重平衡与重投

机制：在 Kafka 里，消费者组内成员变化（加入、退出、心跳超时、处理太久被踢出）或分区数变化，都会触发重平衡，把分区重新分配。传统的重平衡会让组内所有消费者暂停拉取；新版本的增量协作式协议和粘性分配减少了被迁移的分区和停顿时间。重平衡最大的副作用是重复消费：消费者已经处理到某个位置，但位移还没提交，分区就被分给了别人，新的消费者从上次提交的位移开始，重新处理那一段。

RabbitMQ 里的对应物：RabbitMQ 没有分区分配，也就没有重平衡；但它有一个等价的重复来源：消费者断开连接时，它手里所有未确认的消息（数量受 prefetch 限制）都会被重新入队，投给别的消费者。扩缩容、发布、重启都会带来一小波重投。

在我们这里：不管是哪种 MQ，结论一样：重投是常态。我们不靠“减少重平衡 / 重连”来保证正确性，只把它当作性能问题；正确性交给账本和处理轮次。也因此普通队列的 prefetch 不设得太大，避免一次重启带来过多无效重投。

消息顺序：只能保证局部有序

机制：Kafka 只保证分区内有序：相同 key 的消息哈希到同一个分区，就能按发送顺序消费；全局有序只能用单分区，吞吐和可用性都要牺牲。RabbitMQ 的有序更脆弱，只在“单队列、单消费者、没有重投”时成立：多个消费者并发、prefetch、断线重投、业务重试，任何一个都会打乱顺序。即使 MQ 有序，消费端多线程处理也会乱。

在我们这里：我们不依赖 MQ 的顺序。上游为每次告警状态变化给一个单调递增的版本号，受理时旧版本不覆盖新状态；消费者在发送前再查一次这一轮告警的当前状态。一条“首次触发”通知还没发出去告警就已恢复了怎么办，是一个和业务方一起定的规则：高等级照发并标注“已恢复”（值班人仍需要知道发生过），低等级收口为过期。渠道侧的到达顺序我们控制不了，所以通知内容里都带状态和时间。

相关八股 · 四：外部调用的超时、重试、死信与对账

先给失败分级：超时不是失败，是“不知道”

机制：失败至少分三类。瞬时失败：网络抖动、短暂超时、限流窗口，适合重试。确定性失败：参数非法、账号不存在、模板错误，不改输入重试多少次结果都一样，应该快速失败。结果未知：读超时、连接中途断开、无法判断的 5xx——请求可能已经执行，只是响应丢了。最后这一类最危险：当失败重试可能重复，当成功不管可能漏发。把“不确定”按“失败”处理，是重复通知最常见的来源。

断在哪：两个容易忽略的点。一是 HTTP 状态码不是业务契约：比如限流返回是否保证“没有执行”，要看渠道接口的约定，没写清的就按未知处理。二是 HTTP 客户端自带的自动重试必须关掉，否则它会绕过发送记录悄悄重发，业务层的所有防重都失效。

在我们这里：我们给每个渠道整理了能力：企业微信的重复消息检查是按消息内容去重的，所以把请求号的短码拼进正文，同一请求重试时内容逐字节一致就会被去重，不同通知又不会被误去重；短信网关可以带外部流水号、事后按流水号查询；电话既不能查也没有幂等，未知后不自动重拨。查不清时按优先级取舍：普通通知宁可转人工也不重复；P0 漏发的代价远大于重复，允许一次带“补发”标记的受控补发。

外部调用的幂等键：请求号一次生成，永不更换

机制：业界通用做法是由调用方生成一个唯一请求号随请求发送，服务端按它去重，同一个键重复请求返回第一次的结果——支付类 API 普遍支持的 Idempotency-Key 请求头就是这样。设计的关键是：同一个逻辑动作无论重试多少次都用同一个键，两个不同的动作永远不会拿到同一个键。对方不支持按键去重时，就退而求其次：把请求号带过去以便事后查询，超时后先查再决定。

在我们这里：请求号代表的是“给这个人发这条通知”这个逻辑动作，在调用之前就落库；业务重试只是同一个动作再试一次，所以复用同一个请求号，消息内容也在调用前冻结，重试只读这一份，不重新渲染——否则渠道的内容去重就失效了。

业务重试 ≠ MQ 重投；退避要有上限和截止时间

机制：MQ 重投是“同一个事件再交付一次”，适合消费者崩溃这类传输层问题；“渠道限流，过一会儿再试”是业务决定，有自己的次数上限、间隔和截止时间。用拒收重新入队做业务重试，消息会被立刻重新消费，没有退避。退避的通用做法是指数退避加随机抖动：避免立即重试压垮下游，也避免一批失败的请求在恢复瞬间同时重试（惊群）；同时要有最大次数和整体截止时间，否则失败的任务会一直占着资源、持续冲击下游，用户也迟迟拿不到结论。

断在哪：两个坑。一是用原来的事件号重发，消费者会把它当成重复投递直接收口；二是多个重试任务实例同时扫到同一行，各自创建一次重试，就会发两次。

在我们这里：消费者遇到可重试失败只写“等待重试”和下次时间，由唯一的重试任务在一个事务里把代次加一、插入带新事件号的消息行；“任务 + 代次”作为业务键唯一，防止并发双创建；渠道请求号不变。退避按失败类型设置，并且受通知截止时间约束：P0 剩余时间不够就直接升级备用渠道或人工，不会“等很久以后重试成功”。

延迟重试怎么实现：五种方式的取舍

机制：“到点叫醒”有五种常见实现。TTL + 死信交换机：消息过期后进入死信交换机再路由回业务队列，不加组件；但按消息设置的过期时间只在消息到达队首时才检查，一条长延迟的消息会挡住后面短延迟的消息，只能按延迟档位拆多个队列。延迟消息插件：用法最简单，但延迟中的消息存在所在节点本地、不随集群复制，节点挂了就丢。Redis 有序集合：按到期时间做分数轮询，快，但 Redis 不是事实存储。时间轮：内存里、精度高、开销小，进程重启就没了。数据库到期扫描：持久、可查、可干预，和任务状态在同一张表；精度等于扫描周期。

在我们这里：选数据库到期扫描。重试是业务行为，要能查、能停、能改，状态必须和任务在一起；高优先级通知由应用内更短周期的扫描负责，普通通知交给 XXL-Job。扫描走“状态 + 下次重试时间”的索引，只扫到期的行。量级上去以后，可以把“到点叫醒”交给时间轮或多档延迟队列，但状态仍以数据库为准。

死信与毒消息：两层死信要分开

机制：毒消息是“每次处理都会失败”的消息，例如载荷解析不了、版本不认识。如果失败就重新入队，它会无限循环，并堵住后面的正常消息。quorum 队列会记录投递次数，超过上限就转给死信交换机隔离。

断在哪：两点。一是应用确认处理不了、写库后正常 ACK 的消息，不会自动进入 Broker 的死信队列——两层死信是不同的东西。二是死信队列本身不是事实来源：较早版本的 quorum 队列死信是“最多一次”的，死信路由失败时消息会丢。

在我们这里：应用层死信：确认处理不了（模板参数缺失、接收人不存在）就把任务记为死信、写明原因再 ACK，通过管理后台修复。Broker 层死信：超过投递上限进入死信队列，专门的消费者只落摘要、原因并告警，不把可能含手机号的正文打进日志。重放都不是把死信塞回原队列，而是从业务记录生成新事件，再经过任务状态检查，避免把已经成功的任务又发一遍。

全局对账：所有局部恢复机制之外的最后一道防线

机制：每个环节都有自己的恢复者（发布截止扫描、消费租约接管、未知结果对账），但它们各自只看自己那一层。全局对账做跨表的只读检查：不改任何业务状态，只发现、计数、告警，必要时生成待处理工单交给人。

在我们这里：检查的是“理论上不该存在”的组合：已受理却没有消息行（受理事务有缺陷）；已发布很久却没有任何消费记录（Broker 侧丢失或路由错误——这是 Confirm 覆盖不到的盲区，按原消息号重新发布即可，消费侧幂等保证安全）；发送记录长时间停在“调用中 / 未知”（对账任务卡住或渠道查询失效）；任务长时间停在“发送中”（租约恢复失效）；任务成功但发送记录不是成功（结果事务有缺陷）。

把八股落到链路上：六个宕机位置

判断一个可靠性设计是否完整，最直接的办法是沿着一条通知的生命周期，指着任意一个位置问：“在这里宕机会怎样？”每个位置都要答清三件事：数据库里留下了什么、谁来恢复、要避免什么错误判断。

① 受理已提交、Relay 还没领取。库里是一行“待发布”；提交后回调丢了没关系，任何一个存活实例的兜底扫描都会捞到。要避免的是对上游说“已经发到 MQ 了”——此时只是受理了。

② Relay 已领取、还没发布就被杀。库里是“发布中”，Broker 里没有消息。如果恢复扫描只扫“待发布”，这一行就永远卡住了，所以还要扫“确认截止时间已过的发布中”，把它放回待发布。简历里 8.6s 的最老待发布延迟峰值，就出现在这条恢复路径上。

③ Broker 已接手、Relay 还没回写就挂了。库里仍是“发布中”，恢复后会再发一次，Broker 里出现两条同一事件号的消息。这是 Outbox 的设计代价，由下游账本吸收，不能把它说成“系统不可靠”。

④ 渠道已经执行、结果还没落库。最危险的一个。消息没 ACK 会被重投，新消费者看到发送记录是“调用中”，不再发，而是让任务进入“未知”，按请求号对账。如果没有调用前那条记录，这里就会重复发送。

⑤ 结果已提交、ACK 前宕机。任务已成功、账本已完成；重投到达后读到“已完成”，直接 ACK，不再调用渠道，也不把任务改回失败或未知。

⑥ 旧处理者超过租约后复活。账本轮次已经属于新处理者，旧处理者的所有写入影响 0 行；它如果在写库之前先调了外部，靠“调用中”和同一个请求号兜底。

这六个位置我们在故障演练里都做过注入，判断标准不看日志，只看两样：本地状态最终是否收敛到正确的终态，以及 Mock 渠道按请求号记录的实际调用次数是否为 1。

业界做法：同一个问题的八种解法

前六种解决的是“数据库写 + 发消息”这一段，后两种分别是“去掉 MQ”和外部调用这一段的常见写法。每种都画出它怎么工作，以及在哪里断、要付出什么。

A. 事务提交后直接发 MQ

怎么做：业务事务提交后，在代码里紧接着调用一次发送；也有人先发消息再提交，或者把发送放在事务里面。

在哪里断：先提交后发送：两步之间崩溃就丢消息。先发送后提交：事务回滚了消息却已发出，下游收到一条“不存在的任务”。在事务里发送：消息发成功、事务最后提交失败，消息撤不回；而且事务里做网络调用，MQ 一慢就占住数据库连接。

代价：没有额外的表和组件；但丢了的消息没有任何记录，只能靠“过了多久还没发”去猜，补发是分钟级的。

放到我们的约束下：已受理的告警丢一条就是事故，且接口已经告诉上游“受理成功”，上游不会再重试。不满足“已受理必有发布依据”，直接排除。

B. Outbox + 轮询发布（我们的选择）

怎么做：消息行和业务数据同事务写入；“提交后立即发”负责延迟，“每秒扫描”负责正确性，正确性不依赖快路径。多实例都能扫到同一行，区分“看到”和“拿到”：只有条件更新影响 1 行的实例才去发布。

在哪里断：至少一次：标记前崩溃会重复发布。多实例扫描时会有无效竞争。

代价：多一张表、一次写入、一个扫描任务；表要归档；发布延迟在异常路径上受扫描和确认截止时间影响。

放到我们的约束下：只依赖已有的 MySQL，与 MQ 品牌无关；发布意图逐行可查、可补发、可审计，运维能直接回答“这条发了没有、发了几次、最后为什么失败”。下游幂等本来就因 MQ 重投而必须做，代价可以接受。

C. RocketMQ 事务消息

怎么做：半消息存进 Broker 但不投递，本地事务完成后提交或回滚；二次确认丢失时由 Broker 回查生产者。

在哪里断：回查依赖生产者本地有可靠的事务状态；回查超过上限的消息默认被丢弃；消费侧依然至少一次。

代价：强绑定 RocketMQ；要实现可靠、幂等的回查接口。

放到我们的约束下：机制上和 Outbox 等价，但厂区现有基础设施只有 RabbitMQ，为一个特性多运维一套 Broker 不划算；而且回查查的仍是我们自己的任务表，复杂度并没有真正消失，反而少了一份可直接查询的发布记录。

D. Outbox + CDC（如 Debezium）

怎么做：依然写消息表，但由 CDC 连接器从数据库日志里捕获消息表的插入并投递；Debezium 提供专门的 Outbox 事件路由，通常跑在 Kafka Connect 上。它不是 Outbox 的替代品，而是 Relay 的另一种实现。

在哪里断：连接器重启、积压或表结构变更都会影响下游；排障多一跳；依然是至少一次。

代价：多一套连接器的部署、监控和位点管理；需要 binlog 读取权限。

放到我们的约束下：在我们的量级下每秒一次轮询的成本可以忽略，用不上它的优势。它是明确的“下一步”：扫描压力或发布延迟成为瓶颈时再换，消息表和下游幂等都不用改，变的只是“谁来发现新行”。

E. Kafka 事务（exactly-once）

怎么做：幂等生产者避免分区内的重复写入；事务让“读 → 处理 → 写到其他主题 → 提交位移”作为一个整体原子生效；下游以“只读已提交”方式消费。

在哪里断：一旦处理过程中写了外部数据库或调用了 HTTP 接口，这些副作用不受 Kafka 事务保护。

代价：要求链路本身建在 Kafka 上；事务带来额外延迟和协调开销。

放到我们的约束下：我们用的是 RabbitMQ，链路终点是外部渠道，正好落在它覆盖不到的地方。它不是一个可选项，但印证了一个结论：跨系统的恰好一次只能靠至少一次 + 幂等。

F. 分布式事务框架（如 Seata）

怎么做：引入事务协调器，把参与方登记为全局事务的分支。Seata 提供 AT（一阶段直接提交并记录回滚镜像，靠全局锁隔离，失败时按镜像反向补偿）、TCC、Saga、XA 几种模式。

在哪里断：它只能回滚能回滚的资源——消息中间件和外部短信、电话接口都不在其中。

代价：要部署和运维协调器；全局锁和额外往返降低吞吐；多一个关键依赖。

放到我们的约束下：我们的一致性问题恰恰出在“数据库”和“外部渠道”之间，框架帮不上忙。

G. 不要 MQ，直接把数据库表当队列

怎么做：消费者直接从任务表领取待发送的任务，用逐行条件更新（或支持时用跳过已锁行的加锁读）保证一行只被一个实例拿到。

在哪里断：风暴时所有压力都落在主库轮询和行锁上，没有缓冲。

代价：没有推送，延迟受轮询周期影响；没有按优先级拆队列和消费隔离，P0 只能靠轮询顺序和索引区分。

放到我们的约束下：量很小、只有一两个消费实例时是合理的平替；但我们要在告警风暴里保证 P0 不被普通通知拖住，需要 MQ 提供的队列级隔离和缓冲，所以不选。

H. 渠道超时就直接重试

怎么做：把读超时当成失败，交给 HTTP 客户端或业务代码自动重试几次。

在哪里断：渠道其实已经执行时，每次重试都是一条重复通知；HTTP 客户端的自动重试还会绕过所有业务防重记录。

代价：实现最简单；但重复率取决于超时率，而超时恰恰在渠道压力大、告警最密集的时候最多。

放到我们的约束下：只有渠道支持按请求号去重、且去重窗口覆盖恢复时间时才安全。我们的渠道能力各不相同，所以改为：超时归“未知”，按渠道能力对账，查不清再按优先级取舍。

结合业务的选择

业务约束。这是一个制造厂区的生产告警平台：高等级告警有分钟级的触达时限，已受理的任务丢一条就是事故，接口告诉上游“已受理”之后，上游不会再重试；通知的终点是企业微信、短信和语音电话，它们都在我们的任何事务之外，发出去就收不回。基础设施方面，现有的是 MySQL 和 RabbitMQ；团队规模小，没有余力为一个特性多运维一套 Broker、CDC 连接器或事务协调器。

为什么是这套组合。在这些约束下，问题的本质不是“怎么让数据库和 MQ 强一致”，而是两句话：已受理的任务一定留下可查的发布依据；任何一层的重复都能被收住。前半句由 Outbox 落实到每一条任务，只依赖已有的 MySQL；Confirm + Return 让“已发布”有确定的判据，发布尝试号让迟到的确认不会覆盖新状态。后半句按重复的来源分层解决：数据库账本拦住 MQ 重投，处理轮次挡住复活的旧执行者，调用前持久化的稳定请求号加“未知先对账”拦住外部渠道层面的重复。重试、死信、对账则保证所有异常任务最终收敛到“成功”或“交给人”，而不是停在半路。

为什么不是别的。2PC、TCC、Seata 被参与者能力直接排除：RabbitMQ 和外部 HTTP 接口既不能投票，也不能预留或回滚。事务消息在机制上等价，但要换 Broker，而且回查查的还是我们自己的表。CDC 是同一方案的升级版，现阶段用不上它的优势。数据库当队列丢掉了风暴时最需要的优先级隔离。超时直接重试则会把“不知道”变成重复通知。

放弃了什么。我们明确放弃了“发布恰好一次”，把重复发布的代价转移给了消费侧幂等；多维护了一张消息表、一个扫描任务、三段消费事务和一套对账流程；“结果未知”里查不清的那一小部分需要人工确认。更根本的是，我们接受了一个事实：当渠道既不能查询又不支持去重时，系统不可能同时承诺“绝不重复”和“一定送达”，只能按业务优先级在两者之间选——普通通知宁可交给人，P0 允许一次带标记的受控补发。

什么时候换。发布量涨一个数量级时，第一步把 Relay 按消息分桶，每个实例只扫自己的桶；扫描压力或发布延迟仍成为瓶颈，再把轮询换成 CDC——消息表和下游幂等不用改。账本变大先按时间归档，再按事件号分表，判断仍留在数据库，不换成 Redis。重试的“到点叫醒”可以交给时间轮或延迟队列，状态仍以数据库为准。某个渠道开始支持按请求号去重时，它的“未知”就可以改成同号直接重试，省掉查询这一步。

指标口径：每个数字证明了什么、不证明什么

89,982 条已受理任务 100% 最终发布。口径：最终发布率 = 状态为已发布的已受理任务数 ÷ 已受理任务数；同一幂等键、不同载荷而被拒绝的请求不进分母。它证明的是压测叠加进程强杀时，已受理的任务都能被恢复并最终发布——正常情况下 100% 是理所当然的，这个数字的价值在于“强杀之下仍然是 100%”。它不是渠道送达率，也不说明值班人看到了。

最老待发布延迟峰值 8.6s。口径：每次采样时，所有尚未完成发布的消息中最老一条的年龄，取观测期内的最大值。它衡量的是最坏情况下一条消息要等多久才被发布，峰值出现在“领取后被强杀、等确认截止再放回”的恢复路径上。它不是平均发布延迟；正常路径由提交后快路径发布，远低于这个值。

故障演练下 5.4% MQ 重投均被幂等拦截。口径：重投占比 = 同一事件第二次及以后到达消费者的投递次数 ÷ 演练中的通知事件数；重复是通过故障注入主动制造的（结果提交后、ACK 前强杀消费者，切断消费者与 Broker 的连接，Relay 在确认前被杀）。它证明的是重投在演练中是常态，并且全部在账本层被收口；它不是重复通知率。

重复通知 0 次。口径：以 Mock 渠道按稳定请求号记录的实际调用次数为准，统计调用次数大于 1 的请求号数量。不看消费日志，只看渠道侧真实发生的副作用。它证明的是在演练覆盖的故障窗口里没有重复副作用；它不等于“端到端恰好一次”，真实渠道的表现仍取决于各自的查询和去重能力。

向量检索的过滤先过滤再检索可能召回不足；后过滤可能把结果滤空零候选时走精确检索兜底，绝不放宽权限或型号过滤
Structured OutputJSON Schema 约束输出（函数调用 / 约束解码），保证结构可解析，但不保证内容正确结构由 Schema 保证，内容由引用和事实校验保证
幻觉与 Guardrail靠证据回链、事实回填、规则过滤降低幻觉；Prompt 约束本身拦不住四层校验，不过就降级
任务队列语义至少一次 + 租约 + 代次（fencing），防止旧 worker 覆盖新结果先落库再 ACK；最终事务校验代次和截止时间

04HITL 维修工单 Agent

简历原文实现 HITL 维修工单 Agent：基于诊断卡和检索证据抽取故障现象、疑似原因和检查项生成结构化工单草稿，优先级、班组和 SLA 由规则填充；通过字段完整性校验、证据回链和规则化低置信度标记辅助审核，审批以版本 CAS 与执行意图同事务防并发重复，CMMS 建单以稳定请求号对账防重复建单；审核后的维修记录回流案例库。草稿一次审批通过率 83.7%，报修到派单耗时中位数下降 39%。
简历里的说法在设计里对应什么
基于诊断卡和检索证据抽取草稿只能来自当前诊断卡和已授权证据
优先级、班组和 SLA 由规则填充组织约定交给确定性规则（告警等级 × 设备关键度 × 是否影响产线），不交给模型

审批以版本 CAS 与执行意图同事务防并发重复批准 = 一个事务里“按版本条件更新草稿 + 插入唯一的执行意图”
CMMS 建单以稳定请求号对账防重复建单请求号写进工单外部参考号；超时先按参考号查，查不清交给人
审核后的维修记录回流案例库关单后抽取候选案例，主管审核通过才进入检索库
