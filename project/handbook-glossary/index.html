01一、编程语言、并发底座与网络 IO 考点（Java 17 · Spring Boot 3 · Python · Linux IO · SSE）

1.1 Java 17 核心特性与集合底层（HashMap vs ConcurrentHashMap）

1. 痛点与本质定义

简历实习经历明确标注 Java 17。面试常从两个切入点发问：一是相比 Java 8 你实际用了 Java 17 哪些特性（以及为什么没直接上 Java 21 虚拟线程）。二是高频集合 HashMap 与 ConcurrentHashMap 在 JDK 1.8+ 的底层演进，并常与 Redis dict 渐进式 Rehash 对比。

2. 底层机制与源码细节

  • Java 17 核心特性落地：
    • record 不可变数据载体：编译器自动生成 private final 字段、全参构造、equals/hashCode/toString，无 setter，天然线程安全。制造业草稿三阶段拆解中，阶段一短事务读出的诊断卡、故障快照与设备上下文即封装为 record 传入阶段二事务外模型推理，避免多线程共享可变状态被篡改。
    • 封闭类 sealed classes 与模式匹配 instanceof / switch：编译期穷举状态分支（如任务终态结果分类），消除漏写 else 分支隐患。
    • synchronized 锁升级简化（JDK 15+ 默认废弃偏向锁）：早期偏向锁针对无竞争单线程重入优化，但在现代多线程池化应用（如 HikariCP、Tomcat、业务线程池）中频繁触发昂贵的偏向锁撤销（需等到全局安全点 SafePoint 暂停线程）。因此 Java 17 直接走「无锁 → 轻量级锁（在当前线程栈帧创建 Lock Record，通过 CAS 将对象头 Mark Word 替换为指向锁记录的指针，竞争轻微时走自适应自旋）→ 重量级锁（膨胀为 C++ ObjectMonitor，阻塞挂起线程切换内核态）」（参考 OpenJDK JEP 374 ↗）。
  • HashMap（JDK 1.8+）四大底层机制：
    1. 高低 16 位异或扰动：(h = key.hashCode()) ^ (h >>> 16)，因初始桶数组很小，取模 (n - 1) & hash 仅看低位，异或将高 16 位特征混入低 16 位减少哈希冲突。
    2. 尾插法 + 红黑树双阈值：改 1.7 头插法为尾插法消除并发扩容环形死链（但并发写仍会因覆盖槽位丢失数据，并发场景不能直接使用）。链表长度 >= 8 且桶数组容量 >= 64 才树化（若数组 < 64 优先触发 resize() 扩容而非树化），红黑树节点删减至 <= 6 时退化回链表（中间留 7 的差值作迟滞缓冲，防止在阈值边缘频繁插入删除导致树与链表反复转换抖动）。
    3. 2 倍扩容免重算哈希：容量恒为 2^k，扩容翻倍后仅掩码最高位多出一个 1，直接检测 (e.hash & oldCap) == 0，为 0 留原下标 j，非 0 移至 j + oldCap，O(1) 位运算完成拆分。
  • ConcurrentHashMap（JDK 1.8+）并发控制与协迁：
    1. 锁粒度细化：废弃 1.7 的 Segment（继承 ReentrantLock，默认并发度固定 16），改用 Node[] + CAS + synchronized。定位到空桶时用 CAS 无锁写入新节点。非空桶发生冲突时，用 synchronized 仅锁住当前桶的头节点，锁粒度精细到单桶，并发度随扩容自动增长。
    2. 多线程协助扩容（ForwardingNode）：扩容新建 nextTable，每个线程按 stride 步长（最小 16 个桶）领迁移任务。某旧桶迁移完毕后放入 hash = -1 (MOVED) 的 ForwardingNode，读请求遇到它直接转发查新表不阻塞，写请求遇到它主动加入协助搬迁。
    3. 分片计数防伪共享：效仿 LongAdder，用 volatile long baseCount 加 @jdk.internal.vm.annotation.Contended CounterCell[]（自动填充字节凑够独占 64 Bytes CPU 缓存行，防止多核高频修改相邻数组元素引发 MESI 缓存行反复失效即 False Sharing），size() 汇总 baseCount 与所有 CounterCell。

3. 项目落地与系统设计权衡

  • 在 NoteWeave 职责 2 与制造业职责 3 中，Spring 启动时组装策略模式注册表（QA/Note/Wiki 检索策略、工业 LOTO/BOM 校验策略）使用 Map.copyOf() 不可变映射无锁读取。动态运行态缓存（如制造业子 BOM 一级缓存、NoteWeave 墓碑超 1,024 故障/压测熔断水位 1s 本地短缓存）不手搓裸 ConcurrentHashMap（无容量上限会 OOM），而是使用基于 ConcurrentHashMap + W-TinyLFU 算法的 Caffeine 本地缓存。
  • 与 Redis dict 渐进式 Rehash 的系统设计对比：Java HashMap 单次 resize 同步搬完所有元素。ConcurrentHashMap 靠多线程并发写时按步长协迁。而 Redis 核心命令主线程是单线程，若千万级大字典一次性迁移会卡死所有客户端几百毫秒，故维护 ht[0] 与 ht[1] 双表加 rehashidx 游标，分摊到后续每次增删改查和后台时间事件每次只搬 1 个或少量桶（参考 Redis 7.2 dict.c ↗）。

4. 学生视角脱稿背诵与追问

【脱稿背诵】：「项目中我基于 Java 17 开发，主要用 record 封装三阶段短事务之间传递的不可变上下文快照，避免多线程误改状态。底层并发集合这块，HashMap 1.8 用高低 16 位异或降冲突，尾插法消死链，链长满 8 且数组容量满 64 才转红黑树、降到 6 退化防抖动，二倍扩容靠 hash & oldCap 位运算直接拆高低链。多线程下我用 ConcurrentHashMap 或它之上的 Caffeine，1.8 弃用分段锁改为『空桶 CAS + 非空 synchronized 锁桶头』，扩容放 MOVED 转发节点让写线程协助迁移，计数用 @Contended 填充 64 字节缓存行的 CounterCell 数组消除伪共享。」

  • 追问：为什么不用 Java 21 虚拟线程直接替代你们制造业的 3/3/6 线程池？

    答：「两点原因。第一是版本基线，实习公司统一用 Java 17 LTS，虚拟线程到 Java 21 才正式转正，且 JDK 21 到 23 里虚拟线程在 synchronized 代码块内发生阻塞会触发 Pinning（钉住载体平台线程），直到 JDK 24 的 JEP 491 才解决这一问题（参考 Oracle Java Virtual Threads ↗）。第二是系统设计的容量边界：虚拟线程只降低本机『等待 IO 的线程内存成本』，并不会增加下游模型服务的处理能力。内网模型网关分给草稿的并发硬配额只有 6 路，如果放几十个虚拟线程同时打过去，只会超出配额，所有请求一起变慢。所以在下游有明确硬配额的场景，用对齐配额的有界线程池加信号量反而是最稳的背压手段。」

1.2 JUC 锁、有界线程池（ThreadPoolExecutor）与 CompletableFuture 异步编排

1. 痛点与本质定义

简历在制造业职责 4 明确写了「采用有界线程池并发执行」，在 NoteWeave 中多处涉及双路召回并行、SSE 阻塞读池与 Kafka 产物消费池。面试必考线程池七参数、拒绝策略坑、异步死锁与 traceId 透传。

2. 底层机制与源码细节

  • AQS、ReentrantLock 与 volatile：
    • volatile 两大语义：① 可见性：写操作编译期插入 lock addl $0x0, (%rsp)（充当最重的 StoreLoad 内存屏障），把 CPU Store Buffer 刷回缓存并通过 MESI 协议使其他核缓存行失效。② 禁止指令重排：阻断 DCL 双重检查锁单例中 instance = new Singleton() 从「1.分配内存 → 2.初始化对象 → 3.引用指向内存」重排为「1 → 3 → 2」导致其他线程拿到未初始化完毕的半成品对象。volatile 不保 count++ 复合读改写原子性。
    • AQS（AbstractQueuedSynchronizer）：核心是 volatile int state（ReentrantLock 用它记重入次数，Semaphore 记剩余许可数，CountDownLatch 记倒计数）+ CLH 变体双向等待队列 + LockSupport.park()/unpark()。ReentrantLock 默认非公平锁，进门直接 CAS(0, 1) 抢锁，减少线程挂起唤醒的内核态切换故吞吐更高。公平锁先调 hasQueuedPredecessors() 看队列有无前驱。
  • ThreadPoolExecutor 七大参数与任务提交流程（参考 Java 21 ThreadPoolExecutor ↗）：
    • 七参数：corePoolSize（核心线程数）、maximumPoolSize（最大线程数）、keepAliveTime（非核心空闲存活时长）、unit（时间单位）、workQueue（阻塞队列）、threadFactory（命名线程工厂，出问题 jstack 一眼定位模块）、handler（拒绝策略）。
    • 铁律顺序：提交任务 → < corePoolSize 则新建核心线程 → 否则尝试先入 workQueue 队列 → 只有队列满了才新建非核心线程扩至 maximumPoolSize → 队列与最大线程全满才触发拒绝策略（因此使用默认 Integer.MAX_VALUE 的无界 LinkedBlockingQueue 时，maximumPoolSize 形同虚设，流量洪峰直接堆爆老年代 OOM）。
    • 四种内置拒绝策略与致命陷阱：
      1. AbortPolicy（默认）：直接抛 RejectedExecutionException，调用方可捕获感知过载并做持久化兜底。
      2. CallerRunsPolicy：池未关闭时由提交任务的线程亲自同步执行。大坑：若提交者是 Tomcat 主请求线程、Netty EventLoop 或 Kafka poll 拉取线程，而任务是耗时 7.5s 的大模型调用，提交线程会被直接卡死 7.5s，轻则拖垮上游接口吞吐，重则导致 Kafka 超过 max.poll.interval.ms 触发全组重平衡风暴。
      3. DiscardPolicy / DiscardOldestPolicy：静默丢弃当前或队首任务，在可靠任务或手动提交位点场景会造成静默丢单。
  • CompletableFuture 父子同池饥饿死锁：
    • 死锁时序：有界池 core = max = N，瞬间涌入 N 个外层请求（如 NoteWeave 检索请求）占满全部 N 条线程。每个父任务又向同一个线程池提交子任务（如双路召回）并同步调 .join() 阻塞等待。此时 N 条线程全卡在 WAITING 等子任务完成，而队列里的子任务永远等不到空闲线程执行，CPU 跌至 0%，且因为没有传统互斥锁环，jstack 的常规死锁检测无法自动报出。
    • 三道铁律：① 严禁不传 Executor 裸调 supplyAsync（默认共用全局 ForkJoinPool.commonPool()，会被慢 IO 一锅端）。② 父子任务物理拆分独立线程池，尽量用 thenCombine 非阻塞回调串联。③ 必配 .orTimeout(timeout, unit).exceptionally(...) 与底层 HTTP socketTimeout。
  • 异步线程池 MDC / traceId 上下文透传：
    • ThreadLocal 仅当前线程可见（且线程池核心线程长期存活不退出，若 Entry 的弱引用 Key 被回收，强引用 Value 仍挂在 Thread -> ThreadLocalMap 链上引发内存泄漏，必须在 finally 中 remove()）。
    • InheritableThreadLocal 只在 new Thread() 创建子线程那一刻复制一次，线程池复用已有工作线程时会导致后续请求读到旧请求的串号 traceId。
    • 工程解法：单层线程池配置 Spring TaskDecorator，提交任务时在主线程捕获 MDC.getCopyOfContextMap()，工作线程执行前先备份工作线程原本的 MDC、再写入捕获快照，finally 中按备份还原（只有备份为空才 MDC.clear()，防止触发 CallerRunsPolicy 时把调用方主线程自己的 traceId 误清空）。跨多层嵌套异步池则引入阿里 TransmittableThreadLocal (TTL) 按 Capture-Replay-Restore 标准三步透传。

3. 项目落地：三套差异化线程池定参逻辑（高频深挖）

  1. 制造业 HITL 草稿生成池（core=3, max=3, ArrayBlockingQueue(6), AbortPolicy）：内网模型网关分给草稿硬配额共 6 路，双实例对等部署每机恰好 3 路，设 core=max=3 省去线程扩缩抖动。草稿任务已先落 MySQL，投进线程池的只是不带业务 ID 的无状态唤醒信号，工作线程跑完一单会 while 循环用 SKIP LOCKED 把库里待办拉空才退出，因此队列满触发 AbortPolicy 丢掉多余唤醒信号不会因此丢任务（还有 1s 守护线程兜底）。
  2. NoteWeave 分钟级产物执行池（core=32, max=32，前置检查池余量与产物独立 8 槽）：单任务耗时 2～6 分钟，Kafka 消费线程不同步执行也不靠脆弱的 pause/resume 内存位点表——毫秒级发现本机 32 池满或单工作区产物 8 槽满时，直接条件置 MySQL 为 DELAYED 并立刻提交 Kafka offset，把长任务宕机恢复与公平重排交由 MySQL 300s 权威租约与 30s 扫描处理。
  3. NoteWeave SSE Stream Multiplexer 固定 4 路分片读线程：不给每个 runId 独占 1 条 XREAD BLOCK 线程（Lettuce 单共享连接禁跑阻塞命令，200 并发会借光独立连接打爆 Redis 连接池），而是固定 4 条分片读线程各跑单条原生 XREAD BLOCK 50 STREAMS k1..kN id1..idN 多 Key 多路复用，O(1) 线程与连接承接全机几百路活跃 SSE。

4. 学生视角脱稿背诵与追问

【脱稿背诵】：「我在两个项目里根据下游瓶颈定了不同的有界线程池。比如实习项目的维修草稿链路，内网模型网关分给草稿总共 6 路并发配额，双实例部署每台配 core=3, max=3 加容量为 6 的 ArrayBlockingQueue 和 AbortPolicy。为什么 AbortPolicy 抛异常不丢单？因为任务已经先持久化进 MySQL 了，往池子里投的只是无状态唤醒信号，工作线程跑完一单会 while 循环 SKIP LOCKED 自排空待办，再加 1 秒守护线程兜底。之所以坚决不用默认的 LinkedBlockingQueue 是防无界堆积 OOM，不用 CallerRunsPolicy 是防止约 7.5 秒的慢模型推理反向把上游提交线程或调度线程卡死。另外做双路并行检索用 CompletableFuture 时，我专门把父编排池和子检索池物理拆开，防止高并发下父任务占满全部线程同步 join 等队列里的子任务，造成CPU 空闲的线程池饥饿死锁。」

1.3 JVM 内存管理、G1 巨型对象（128 MB 流式读取）与线上排障 SOP

1. 痛点与本质定义

NoteWeave 职责 4 明确写到：「通过流式读取支持 128 MB 单文件异步接入」。面试官一定会问：128 MB 不算几十个 G，为什么直接 MultipartFile.getBytes() 整包读进内存会出事故？这直接考到 G1 垃圾收集器的 Humongous Object 机制与堆内/堆外内存排障。

2. 底层机制与源码细节

  • G1（Garbage-First）分区机制与巨型对象致命机理：
    • G1 将整块 Java 堆切分为最多 2048 个大小相等的独立 Region（大小取 1MB～32MB 的 2 的幂），逻辑保留 Eden、Survivor、Old 角色，通过 Remembered Set (RSet) + 写后屏障卡表（Card Table）记录跨 Region 引用避免全堆扫描。
    • 巨型对象判定红线：只要单个对象的大小超过半个 Region（> 0.5 × RegionSize），G1 就将其判定为 Humongous Object，绕过年轻代 Eden 区，直接在老年代寻找物理连续的多个 Humongous Region 分配。
    • 事故推演：容器受限堆 -Xms512m -Xmx512m 下，默认 Region 仅 1MB（即便手动调到最大 32MB，半个 Region 阈值也仅 16MB）。128 MB 的 byte[] 远超阈值，8 路并发上传瞬间申请 1 GB 连续老年代空间，不仅切碎老年代造成严重外部碎片，还会频繁击穿 IHOP 阈值乃至分配失败，退化触发单线程/串行整理的 Full GC 甚至直接抛出 OutOfMemoryError: Java heap space。
  • 三色标记并发漏标与分代 ZGC：
    • 并发标记期间应用线程修改引用，漏标误回收存活白对象当且仅当同时满足两个条件：① 黑对象新增了指向该白对象的引用。② 所有灰对象删除了通往该白对象的直接或间接引用。
    • CMS 解法（增量更新 Incremental Update）：写后屏障拦截条件①，黑对象一旦引用白对象就把黑对象退回灰集合重新扫描（缺点是重新标记阶段需重扫整个栈与关联结构，停顿随堆变大）。
    • G1 解法（原始快照 SATB，Snapshot-At-The-Beginning）：写前屏障拦截条件②，灰对象断开白引用前把旧引用记录到 SATB 队列，本轮一律视作存活（会产生少量浮动垃圾留待下轮收，但重新标记极快）。
    • Java 21 分代 ZGC：采用染色指针（Colored Pointers）+ 读屏障（Load Barrier）支持并发转移整理（无需等 STW 才搬迁存活对象），分代后高频单独回收朝生夕死的年轻代，在数十 GB 大堆下将 STW 停顿压至亚毫秒级。
  • 类加载五步与三次打破双亲委派：加载 → 验证 → 准备（普通 static 赋零值，static final 编译期字面量直接赋常量值）→ 解析 → 初始化。双亲委派自底向上检查、自顶向下加载以防核心 java.lang.String 被篡改。经典打破场景为 JDBC DriverManager（Bootstrap 加载器无法加载厂商驱动 Jar，借 Thread.currentThread().getContextClassLoader() 逆向委派 AppClassLoader）与 Tomcat WebAppClassLoader（优先自行加载当前 Web 应用依赖，隔离同容器不同版本 Spring）。

3. 项目落地与五步线上排障 SOP

  • NoteWeave 双端流式卸载方案：
    1. 上传校验侧（Java 零穿境 + 异步流式读取）：前端按 8 MB 分片直传对象存储 MinIO 并调原生 Compose 合并（支持 S3 原生分片校验），大文件字节流根本不经过应用网关内存。Java 同步回调仅对 MinIO 发 Range: bytes=0-4095 读前 4 KB 验文件头 Magic Number（魔数）毫秒级返回（0 MB 大文件穿境）。全文件 SHA-256 复算下沉到异步消费阶段 1，以固定 8 KB 缓冲流式读取 MinIO 对象流边校验边解析，-Xmx512m 下 8 路并发上传堆曲线平稳无巨型对象 Full GC。
    2. 解析侧（Python 微批释放）：几百页扫描版 PDF 在无状态 Python Worker 中按 15 页一个微批流式渲染图片交 ProcessPoolExecutor 跑 OCR，每批结果写回 MinIO 后立即释放图像张量，内存占用仅与单批 15 页正相关，与总文件大小解耦。
  • 堆内泄漏、堆外 RSS 暴涨与 CPU 100% 排查标准 SOP：
    • CPU 100% / 接口卡死五步法：① top -c 定位异常 Java 进程 PID 并看 us/sy 占比。② top -Hp <pid> 找到高占 CPU 线程 TID。③ printf "%x\n" <tid> 转十六进制。④ jstack <pid> | grep -A 30 0x<hex> 看栈——若是 VM Thread / GC 线程飙高转查内存与 Full GC，若是业务 RUNNABLE 查死循环或灾难性正则回溯，若是CPU 很低但接口 P99 暴涨，统计 WAITING / BLOCKED 线程卡在哪个连接池（如 HikariPool.getConnection）或线程池阻塞调用上。⑤ 偶发毛刺挂 Arthas trace 或 profiler 采火焰图。
    • 堆内 vs 堆外泄漏：jstat -gcutil 见 Full GC 后老年代基线单调抬升为堆内泄漏，摘流导 Dump 进 Eclipse MAT 对比 Shallow Heap（自身大小）与 Retained Heap（支配子树总大小）查 Dominator Tree 到 GC Roots 的强引用链。若堆平稳但容器因 RSS 超限触发 Linux OOM Killer（退出码 137），则是 Direct Memory、Netty 池化内存或压缩/解析库 JNI C 堆未释放，开启 -XX:NativeMemoryTracking=detail 对比 jcmd <pid> VM.native_memory detail.diff 并检查流是否全进 try-with-resources。

4. 学生视角脱稿背诵与追问

【脱稿背诵】：「在 -Xmx512m 的容器堆里，如果直接调 getBytes() 整包读取 128 MB 文件，在 G1 收集器下只要单对象超过半个 Region 就会被判定为 Humongous 巨型对象，绕过年轻代直接在老年代申请连续 Region，8 路并发上传瞬间就会切碎并撑满老年代触发 Full GC 甚至 OOM。所以我做了两层流式改造：接入侧前端按 8 MB 分片直传 MinIO 合并，Java 同步回调只发 Range: bytes=0-4095 读前 4 KB 验文件头魔数，毫秒返回、0 MB 大文件穿境。异步阶段 1 再用固定 8 KB 缓冲流式读取对象流边算全文件 SHA-256 边按 Python 15 页微批解析释放张量，堆占用始终是常数级，压测 8 路并发全程没有观测到巨型对象引发的 Full GC。」

1.4 Spring Boot / Spring Boot 3 自动装配、三级缓存与事务失效陷阱

1. 痛点与本质定义

两段核心项目分别采用 Spring Boot 与 Spring Boot 3.2。面试必问：Boot 3 自动装配改了什么？检索策略与五段流水线怎么利用 Spring 扩展点解耦？三级缓存为什么少一级都不行？为什么制造业草稿拆三阶段要用编程式 TransactionTemplate 而不用 @Transactional？

2. 底层机制与源码细节

  • Spring Boot 3 自动装配演进：
    • @SpringBootApplication 组合了 @SpringBootConfiguration、@ComponentScan 与核心 @EnableAutoConfiguration。
    • AutoConfigurationImportSelector 在 Spring Boot 2.7 之前扫描 META-INF/spring.factories。Spring Boot 3.x 移除了旧键支持，统一改为读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 按行加载候选配置类，再经 @ConditionalOnClass（类路径有对应客户端 Jar 才加载）、@ConditionalOnProperty、@ConditionalOnMissingBean（用户自定义了同名/同类型 Bean 则默认配置自动让位）按需注册。
  • Bean 生命周期核心扩展点：实例化（反射调构造器）→ 属性填充（依赖注入）→ Aware 接口回调 → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct / InitializingBean → BeanPostProcessor.postProcessAfterInitialization（AOP 动态代理 AbstractAutoProxyCreator 在此步生成 JDK 接口代理或 CGLIB 子类代理，Spring Boot 默认统一走 CGLIB）。（注：BeanFactoryPostProcessor 在更早的 BeanDefinition 加载完、实例化开始前介入修改元数据）。
  • Spring 三级缓存解决 Setter/字段循环依赖与双反证：
    • 三级结构：一级 singletonObjects（完整成品单例）、二级 earlySingletonObjects（提前曝光的半成品原始对象或早期代理对象）、三级 singletonFactories（存 ObjectFactory<?> 延迟工厂钩子 () -> getEarlyBeanReference(...)）。
    • 反证一：为什么不能去掉三级缓存只留一、二级？ 正常无循环依赖的 AOP Bean 规范是在初始化之后才通过 BeanPostProcessor 创建代理。若没有三级工厂延迟钩子，要么所有 Bean 不管有没有循环依赖都在刚实例化完就提前造代理（违背 Spring 生命周期设计规范），要么发生循环依赖时 B 注入的是 A 的原始裸对象、而 A 初始化完进一级缓存变成了代理对象，导致 B 持有的 A 没有事务/切面增强且与容器最终单例对象引用分裂（Spring 检测到引用不一致会直接抛 BeanCurrentlyInCreationException）。
    • 反证二：为什么不能去掉二级缓存只留一、三级？ 当出现多路循环依赖 A -> B -> A 且 A -> C -> A 且 A 需要 AOP 代理时，若没有二级缓存保存第一次调三级工厂生成的同一个早期代理对象，B 注入 A 时调一次 ObjectFactory.getObject() 造出代理 Proxy_A1，C 注入 A 时又调一次造出另一个代理 Proxy_A2，直接破坏 Singleton 单例唯一性语义。
    • 边界：构造器注入循环依赖（A 构造器要 B，B 构造器要 A）连第一步实例化空壳都完不成，无法放入三级缓存，必须在其中一个构造参数加 @Lazy 注入延迟代理破环。
  • @Transactional 高频失效场景与连接池死锁：
    1. 同类内部自调用（最易踩）：类内普通方法 entry() 直接调 this.saveWithTx()，绕过了外层 Spring CGLIB 代理对象，事务拦截器 TransactionInterceptor 根本没执行。
    2. 方法非 public：标准代理事务要求目标方法为 public。
    3. 异常被内部 try-catch 吞掉，或抛出受检异常（Checked Exception）却未显式配置 @Transactional(rollbackFor = Exception.class)（Spring 默认仅对 RuntimeException 和 Error 回滚）。
    4. 外层 @Transactional 内嵌 PROPAGATION_REQUIRES_NEW 的双连接死锁陷阱：外层事务挂起时并不会归还它已经持有的那条 HikariCP 数据库连接，内层 REQUIRES_NEW 必须向同一个连接池再申请第二条新连接。若连接池 max=20，突发 20 个并发请求同时进入外层事务把 20 条连接全拿光，随后全部走到内层申请第 2 条连接，20 个线程互相死等归还连接直至 connectionTimeout 集体雪崩。

3. 项目落地与系统设计权衡

  • 设计模式落地：NoteWeave 的 QA/Note/Wiki 检索模式与五段产物流水线（模板方法定「取材→规划→写作→校验→渲染」骨架，策略注册表通过构造函数注入 List<ArtifactStrategy> 转为不可变 EnumMap 并启动自检）完美实现开闭原则。
  • 制造业草稿三阶段拆解为什么用 TransactionTemplate：领单（~10ms）与写回（~15ms）中间夹着约 7.2s～8.8s 的大模型推理与规则校验。用编程式 TransactionTemplate 显式包住一、三两个毫秒级代码块，阶段二完全处于事务作用域之外，连接在阶段一结束瞬间立即归还给 HikariCP 连接池，单份草稿累计占用数据库连接仅 25ms，每机最多 5 个旁路线程即使同刻写回也稳保通知主链路至少 15 条连接可用。

4. 学生视角脱稿背诵与追问

【脱稿背诵】：「在制造业维修草稿和通知领单里，我全部采用编程式 TransactionTemplate 而不是声明式 @Transactional 注解。一是因为草稿流程要把『10ms 领单、7 秒多模型推理、15ms 校验写回』放在一段高内聚编排代码里精确切开，如果用 @Transactional 拆同类私有或内部方法自调用会绕过 CGLIB 代理导致事务失效。二是不能在外层套 @Transactional、内层套 REQUIRES_NEW，因为外层挂起期间并不会释放借走的 HikariCP 连接，不仅白占连接 7 秒多，一旦并发请求先把池子外层连接占满，所有线程进内层申请第二条连接就会发生连接池饥饿死锁。用 TransactionTemplate 显式设 READ COMMITTED 和 2 秒超时，阶段一提交瞬间连接就归还了，单张草稿总共只占连接 25 毫秒。」

1.5 Python 并发底座（GIL · asyncio · 混合服务化）

1. 痛点与本质定义

NoteWeave 采用 Spring Boot（有状态编排与并发锁）+ Python（无状态解析、模型调用与多模态 MCP） 双栈协作。面试官必拷问：Python 有 GIL，你们怎么扛并发？asyncio 协程里不小心调了一个同步函数会发生什么？

2. 底层机制与项目落地

  • GIL（Global Interpreter Lock）本质：CPython 内存管理采用非线程安全的引用计数（ob_refcnt），为避免每个对象加细粒度锁拖慢单线程性能，在解释器层加全局互斥锁，保证单进程同一时刻只有一个操作系统线程能执行 Python 字节码（默认每 5ms 请求让锁）。
    • 什么时候释锁：遇到网络 Socket 读写、磁盘文件 IO，以及 NumPy / PyTorch / OpenCV / faster-whisper 底层 C/C++ 算子计算时，会主动释放 GIL。但纯 Python CPU 循环（如复杂正则文本切分、纯 Python PDF 解析）多线程抢锁切换反而比单线程更慢。
  • asyncio 事件循环冻结灾难与四层混合并发架构：
    • asyncio 基于底层操作系统 epoll/kqueue 在单线程内通过 await 协作式切换成百上千个协程。一旦某个 async def 协程内部误调了同步阻塞调用（例如 requests.get()、time.sleep()、同步数据库驱动或耗时 500ms 的同步分词/PDF 光栅化），当前线程被卡住无法回到事件循环，同进程内所有其他正在推送的流式请求和心跳协程全部瞬间冻结断连。
    • NoteWeave 生产级混合并发解法：
      1. 多进程吃满多核：启动 Uvicorn --workers N 多进程，每个 Worker 拥有独立 GIL 与独立事件循环。
      2. 纯异步网络池复用：模型与公网抓取统一用进程级单例 httpx.AsyncClient 连接池（限制最大连接数与单域名连接数，连 3s/读 20s，防每次新建连接握手及短连接堆积大量 TIME_WAIT 耗尽临时端口），并用 asyncio.Semaphore 独立控制模型并发与搜索并发，多路并发用 asyncio.gather(..., return_exceptions=True) 防单路异常炸毁整组。
      3. 轻度同步库卸载：第三方无异步版本的轻量 SDK 用 await asyncio.to_thread(...) 卸载到后台 IO 线程池。
      4. 重 CPU 算力进程池隔离：15 页微批 PDF 光栅化 OCR 与视频抽帧 64 位 pHash 计算统一提交 ProcessPoolExecutor 独立子进程池执行，与 asyncio 事件循环物理隔离。

3. 学生视角脱稿背诵

【脱稿背诵】：「CPython 因为引用计数非线程安全引入了 GIL，单进程同一时刻只能有一个线程跑字节码，而 asyncio 是单线程事件循环靠 await 协作切换协程，一旦异步函数里混进 requests 同步调用或者重度 PDF 解析，整条事件循环就会被冻结，拖断同进程所有流式连接。所以在 NoteWeave 的 Python Worker 里，我用了四层混合架构：外层用多进程 Uvicorn 绕开单进程 GIL。网络层全局复用同一个 httpx.AsyncClient 连接池配 Semaphore 控制模型与搜索并发，避免频繁建连产生大量 TIME_WAIT。必须调的同步小库走 asyncio.to_thread。像 15 页微批扫描 PDF 渲染和关键帧 pHash 这类重 CPU 活，专门丢进 ProcessPoolExecutor 独立进程池，让主事件循环不被 CPU 密集任务卡住。」

1. 痛点与本质定义

2. 底层机制与源码细节（融合《Linux 网络 IO 学习与面试讲义》）

  • 一次网络读取的两阶段与 TCP 字节流本质：
    • fd（文件描述符）只是进程打开文件表里的整数索引（连接关闭后会复用，故异步任务写回不能只拿旧 fd 整数判身份，须绑连接对象与代际标识，见 close(2) ↗）。
    • 普通 Socket read/recv 分两逻辑阶段：① 等待内核协议栈接收缓冲区有数据可读。② 将数据从内核缓冲交付（复制）到用户态缓冲区并返回字节数（正数为本次读到字节、0 为对端关闭写方向 EOF、-1 且 errno == EAGAIN / EWOULDBLOCK 为非阻塞当前无数据可读，见 recv(2) ↗）。TCP 是无消息边界的字节流，应用必须维护接收缓冲与解析状态机处理粘包/半包。
  • 阻塞/非阻塞 vs 同步/异步 与 五种 IO 模型：
    • 阻塞 vs 非阻塞：关注当前暂时无法推进时，调用是挂起睡眠等待还是立即返回 EAGAIN。
    • 同步 vs 异步：关注收到通知后，是否还需要应用自己发起真正的读写系统调用。前四种（阻塞 IO、非阻塞轮询、IO 多路复用、信号驱动 SIGIO）收到就绪提示后仍需应用调 recv 取数据，均属同步 IO。第五种异步 IO（如 POSIX aio_read 或 io_uring 提交读写 SQE 收取完成 CQE，见 io_uring(7) ↗）先提交缓冲区与操作，收到通知时数据已读完直接消费结果。
  • select、poll 与 epoll 三代多路复用深度对比：

  • LT（水平触发）vs ET（边缘触发）与公平续跑：
    • LT（默认，Redis ae_epoll.c 即采用 LT）：只要内核缓冲区还有未读数据或发送缓冲有空间，后续 epoll_wait 会持续重复报告。注意：LT 下空闲连接通常一直可写，严禁无数据可发时长期注册 EPOLLOUT，否则每轮都会触发无用可写通知导致 CPU 100% 空转（应先直接尝试 send，遇 EAGAIN 再挂 EPOLLOUT，发空后立即移掉写兴趣）。
    • ET（EPOLLET）为什么必须配非阻塞循环读到 EAGAIN？（两步因果链）：① ET 不能依赖「缓冲区还剩半截数据」自动产生重复提醒，若一次通知只调一次 recv 留下残余字节，对端又在等服务端回包，双方就会永久死等卡住。② 因此必须循环读取排空（drain），但若用阻塞 Socket，把最后一点数据读空后的下一次 recv 会直接把整条事件循环线程挂死在这一个连接上，拖垮同线程上成千上万个其他就绪连接。所以必须设 O_NONBLOCK 读到返回 EAGAIN 为止。
    • 大流量饥饿防护：若某连接高速发包永远读不到 EAGAIN，不能无限独占事件循环——应设单轮字节预算（如 64KB），预算耗尽仍未见 EAGAIN 时将该连接放入用户态待处理就绪队列主动轮转续跑（队列非空时 epoll_wait 不能无限阻塞睡眠）。
  • 多线程惊群与连接所有权：多个 epoll 实例共享同一监听 Socket 可用 EPOLLEXCLUSIVE（仅 ADD 时指定，唤醒一个或多个）或 SO_REUSEPORT（内核级多独立监听队列分流）。多线程共享同一 epoll 时用 EPOLLONESHOT 交付一次后暂停报告，处理完再 MOD 重新激活（rearm），但业务状态最好固定归属同一 EventLoop（如 Netty 模型）串行维护。
  • SSE vs WebSocket 与慢客户端背压（Backpressure）：
    • 协议选型：AI 流式回答本质是「客户端一次提问 → 服务端持续单向推流」。WebSocket 是全双工独立协议，需 101 Switching Protocols 升级、自建应用层帧格式、心跳与网关粘性路由。SSE（Content-Type: text/event-stream）基于标准 HTTP 长连接，天然穿透企业防火墙（HTTP/2 多路复用下消除浏览器同域名 6 连接限制），且浏览器原生 EventSource 内置 id: 字段记录与断网自动携带 Last-Event-ID 请求头重连机制。
    • 为什么 NoteWeave 把提问拆成 POST + GET 两步：原生 EventSource 标准只支持发 GET 请求（无法带长 JSON 请求体且 URL 易超长泄露敏感上下文），故前端先 POST 创建幂等 Turn 拿到 turnId，再 GET 订阅事件流。Nginx 侧必配 X-Accel-Buffering: no 关闭代理缓冲防攒块，服务端每 15s 推 : heartbeat\n\n 注释帧防网关空闲超时掐断。
    • 慢客户端吃光内存与背压：非阻塞发送只保证线程不卡在 send()，但若上游模型每秒吐出数据远快于弱网客户端接收速度，未发数据若无限堆积在应用内存队列里，几千路慢连接就能把堆或堆外内存撑爆（如 Netty WriteBufferWaterMark 高低水位变不可写时若继续硬写照样 OOM）。NoteWeave 用 有界定长裁剪 Redis Stream（MAXLEN ~ 1000）+ MySQL 5s 滚动前缀检查点解耦生成与推送连接，生成端只管写有界 Stream，单路慢连接读落后超界直接切换检查点覆盖同步，从架构上封死了单连接内存无界膨胀。

3. 学生视角脱稿背诵与追问

【脱稿背诵】：「AI 流式问答是典型的单向推流，我选 SSE 而不是 WebSocket，是因为 SSE 直接复用标准 HTTP 协议免去协议升级成本，而且浏览器 EventSource 原生支持断线自动带 Last-Event-ID 重连。由于 EventSource 只支持 GET，我把接口拆成先 POST 创建带唯一键的幂等 Turn，再 GET 订阅流，配 Nginx 关闭代理缓冲和 15 秒注释心跳。往底层网络 IO 看，高并发长连接靠 epoll 加非阻塞 Socket 支撑：内核用红黑树管监听登记增删查、就绪链表交付活跃事件。如果开 ET 边缘触发，必须配非阻塞循环读到 EAGAIN 否则残留数据不二次通知会卡死，同时给大流量连接设单轮读取预算放用户态队列续跑防饥饿。另外非阻塞解决不了慢客户端积压，所以我没有把流绑在单机内存队列里，而是用 MAXLEN ~ 1000 定长裁剪的 Redis Stream 加 5 秒 数据库检查点做有界缓冲解耦。」

02二、关系型与多模向量数据库深度考点（MySQL 8 · PostgreSQL pgvector）

2.1 MySQL 存储架构、B+ 树 索引、聚簇回表与 Buffer Pool 冷热隔离

1. 痛点与本质定义

两段经历重度依赖 MySQL 8（制造业 8.0.36，NoteWeave 8.4）。面试常考：一条 SQL 怎么执行？为什么用 B+ 树 不用红黑树或哈希？聚簇索引和二级索引怎么配合？两千万行怎么算出来的？为什么制造业把 3 万条向量拆到独立 PostgreSQL 而不塞进 MySQL？

2. 底层机制与源码细节（融合《MySQL 学习与面试讲义》与 MySQL 8.4 Manual ↗）

  • 架构分层与 16KB 数据页：Server 层管连接、词法语法解析、基于成本的优化器（CBO）与执行器。InnoDB 引擎层按默认 16KB 页（Page）为单位与磁盘交互。与 MyISAM 相比，InnoDB 支持事务 ACID、支持 MVCC 多版本无锁快照读、支持行级锁与外键、数据按主键聚簇存储（MyISAM 仅支持表锁、无事务崩溃恢复、.MYD 数据与 .MYI 索引文件物理分离，仅无 WHERE 条件的全表 COUNT(*) 可直接读元数据计数）。
  • 为什么 InnoDB 选 B+ 树：
    1. 对比平衡二叉树 / 红黑树：二叉树每个节点最多 2 个分支，千万行树高达 20 多层，磁盘随机页读取太多。B+ 树是多路平衡查找树，非叶子节点不存完整行数据，只存分界键值和子页指针，单个 16KB 内部页扇出（Fan-out）可达上千，三层树即可承载千万级数据。
    2. 对比 B 树：B 树内部节点也存行数据，不仅大幅挤占内部页容量降低扇出（导致树变高），而且范围查询需在层间反复中序回溯。B+ 树所有数据均在叶子层，且同层叶子页通过双向链表顺序相连，等值定位起点后顺链表扫描即可高效完成范围查询与按索引排序。
    3. 对比 Hash 索引：哈希等值查找 O(1)，但无序，不支持范围查询（> / < / BETWEEN）、不支持 ORDER BY 消除排序、不支持最左前缀匹配。
  • 聚簇索引、二级索引、回表与覆盖索引：
    • 聚簇索引（Clustered Index）：叶子页直接存完整行记录（优先选显式 PRIMARY KEY → 第一个全列 NOT NULL 的 UNIQUE 索引 → 隐藏 6 字节 DB_ROW_ID）。主键不宜用无序长 UUID，否则一会让所有二级索引叶子变胖降低扇出，二会随机插入引发频繁页分裂（Page Split）与空间碎片。
    • 二级索引与回表：叶子页存「索引列值 + 主键 id」。若查询列包含索引外的字段（如 title），需拿主键再去聚簇索引查一次完整行即回表。若所需过滤列与返回列全在二级索引中（EXPLAIN Extra: Using index），即覆盖索引免回表（严谨补充边界：当二级索引页被并发新事务修改或记录带删除标记时，InnoDB 为判断 MVCC 可见性仍可能回聚簇记录检查 DB_TRX_ID）。
  • 三层 B+ 树容量推导：设内部页主键 BIGINT(8B) + 页号指针 6B = 14B，扣除页头页目录开销后单页扇出 F ≈ 1000\sim 1170。若单行宽约 1KB，叶子页存 L ≈ 15\sim 16 行，则三层树容量 N ≈ F² × L ≈ 1600万\sim 2200万 行（若窄表每页存 80 行则可达八千万行，故两千万只是特定行宽估算，绝非硬阈值）。
  • Buffer Pool 5:3 改进型 LRU 链表（防扫描污染）：InnoDB 将缓冲池链表按 5:3 拆为新生代热区（Young）与老生代冷区（Old）。新从磁盘读入的页先插在 Old 区头部（midpoint），只有当该页在 Old 区驻留时间超过 innodb_old_blocks_time（默认 1000ms / 1s）后再次被访问，才会晋升到 Young 热区头部（参考 InnoDB Buffer Pool ↗）。

3. 项目落地：为什么制造业把 3 万条手册切片物理拆到独立 PostgreSQL？

虽然 InnoDB 1s 冷区驻留能防住低频全表备份单次扫过，但制造业告警诊断旁路在高峰期会每隔几秒反复高频扫描几千条 4KB 向量切片，很快就会跨过 1s 门槛持续晋升到热区，把核心通知任务主表的热索引页挤出 Buffer Pool 拖慢通知领单。物理拆分到公司既有独立 PostgreSQL 16 实例后，不仅保护了 MySQL 核心缓冲池，两边也只靠单调递增的「知识发布批次号」松耦合关联，不需要跨库分布式事务。

4. 学生视角脱稿背诵

【脱稿背诵】：「InnoDB 默认按 16KB 页管理存储，用 B+ 树是因为非叶子节点只存键值和页指针，单页扇出上千，三层树就能装两千万左右行宽 1KB 的记录，而且叶子节点用双向链表串起来非常适合范围扫描和索引排序。另外 InnoDB 的 Buffer Pool 采用 5:3 新老生代 LRU 加 1 秒 老区驻留阈值来防偶发全表扫描污染，但在我实习的制造业平台里，AI 诊断旁路需要高频扫描几万条 4KB 的向量数据，超过 1 秒后照样会晋升热区把通知主表的热索引挤出去，这也是我们坚持把工业知识库物理拆到独立 PostgreSQL 只读实例、并且给 MySQL 历史通知单每晚归档 7 天前冷数据控在百万行以内的核心原因。」

2.2 联合索引列顺序证明、EXPLAIN 慢查询优化与 Online DDL（INSTANT 64 版本陷阱）

1. 痛点与本质定义

简历在制造业职责 1 明确点名：「基于『状态 + 优先级 + 到期时间』联合索引」。面试官大概率会追问：这三列的顺序能不能调换？如果写成 (status, next_run_at, priority) 会发生什么？深分页怎么优？百万行大表不停机加列有什么坑？

2. 底层机制与项目深度结合

  • 制造业 (status, priority, next_run_at) 三列联合索引顺序推导（源自 02_可靠通知、降噪流控与场景追问.md）：
    • 目标领单 SQL：在 status = 'PENDING' 且 next_run_at <= NOW() 的到期任务中，按 ORDER BY priority ASC, next_run_at ASC LIMIT 1 FOR UPDATE SKIP LOCKED 取出优先级最高、到期最早的一条。
    • 第 1 列放等值 status：表里 99% 以上是已完结历史记录，status = 'PENDING' 等值条件先一步把扫描区间急剧收敛到极小的待发送子集。
    • 为什么第 2 列必须放 priority 而不能放范围列 next_run_at？ 联合索引按列从左到右逐级排序。若建成 (status, next_run_at, priority)，固定 status='PENDING' 后，记录是按 next_run_at 排的，不同到期时间下的 priority 是乱序散落的——优化器为了找 priority 最小的那条，必须把所有到期行全扫出来做一次内存/磁盘额外排序（EXPLAIN 的 Extra 出现 Using filesort）。而建成 (status, priority, next_run_at) 后，由于 priority 只有 P0～P3 四个离散档位，待发送子集内天然先紧贴排完所有 P0（且 P0 内部按 next_run_at 升序排列），再排 P1。扫描时从 P0 最小时间看起，配合索引条件下推（ICP，Extra: Using index condition）在引擎层直接核验 next_run_at <= NOW()，命中首条未锁记录即可直接停止（无 Using filesort）。
  • 深分页优化（复合游标翻页 vs 延迟关联）：
    • LIMIT 100000, 20 慢在二级索引扫过 100,020 项并触发高达十万次无谓聚簇回表后全部丢弃。
    • 解法一（连续下拉：复合游标分页）：记住上一页末行的 (updated_at, id)，下一页查 updated_at < T OR (updated_at = T AND id < last_id) ORDER BY updated_at DESC, id DESC LIMIT 20（必须带唯一主键 id 打破同时间戳平局防漏行）。
    • 解法二（随机跳页：延迟关联 Deferred Join）：子查询只走二级覆盖索引扫出目标页的 20 个主键 id，外层再 INNER JOIN 原表仅回表 20 次拿宽字段。
  • 索引失效五大高频原因：① 左模糊 LIKE '%词'。② 索引列套函数或运算（如 DATE(updated_at) = '2026-11-01'，应改写为半开区间 updated_at >= '2026-11-01 00:00:00' AND updated_at < '2026-11-02 00:00:00' 以完整覆盖小数秒）。③ 隐式类型转换（如 varchar 列传数字不加引号，MySQL 将字符串列转浮点相当于对列套函数）或连表字符集/排序规则不一致（utf8mb4_0900_ai_ci vs utf8mb4_general_ci）。④ OR 连接了无索引列。⑤ 违背联合索引最左前缀或优化器评估回表比例过高主动走全表扫描。
  • MySQL 8 Online DDL 与 MDL 排他锁血案：
    • 三类算法：① ALGORITHM=INSTANT（MySQL 8.0.12+ 加普通列、8.0.29+ 支持任意位置加删列）：仅修改数据字典并在行记录头记 1B row_version，毫秒级完成——核心盲区考点：单表累计 INSTANT 加删列硬上限为 TOTAL_ROW_VERSIONS <= 64（查 information_schema.innodb_tables），一旦满 64 次且 DDL 未显式写死 ALGORITHM=INSTANT，MySQL 会静默退化为 INPLACE/COPY 重建百万行大表引发线上锁表事故，需在迫近上限前于低峰期跑 OPTIMIZE TABLE 清零计数。② ALGORITHM=INPLACE（加二级索引）：原地构建并回放期间 row log 增量。③ 改列类型等无法 Inplace 操作走 gh-ost 订阅 binlog 异步同步影子表再原子 RENAME。
    • MDL（Metadata Lock）排队堵死全库：即便 INSTANT 也需在首尾瞬间申请 MDL 排他写锁（X）。若此时表上恰好挂着一个未提交的慢查询或空闲长事务持有 MDL 共享读锁（S），DDL 的 MDL 写锁会排队等待，而 MDL 锁队列具有写锁优先级，排在该 DDL 后面的所有普通 SELECT / UPDATE 全部被连坐阻塞，瞬间打满连接池。故执行 DDL 前必查 information_schema.innodb_trx 清理长事务并设 lock_wait_timeout = 3。

3. 学生视角脱稿背诵

【脱稿背诵】：「在制造业通知任务表上，我建的是 (status, priority, next_run_at) 三列联合索引。列顺序是严格按查询成本推出来的：第一列 status 是等值过滤，直接筛掉九成九的历史完结单。第二列必须放 priority 而不是范围条件 next_run_at，因为如果把范围列放中间，后面的 priority 就没法利用索引有序性，EXPLAIN 会出现 Using filesort 把所有到期单全扫出来重排。把只有 P0 到 P3 四个值的 priority 放第二列后，每个优先级内部天然按到期时间升序排列，配合 ICP 索引条件下推，从 P0 顺扫命中第一条到期未锁行就能立刻返回。另外百万行表后期维护加列时，我们显式指定 ALGORITHM=INSTANT 毫秒级改元数据，但专门加了巡检核查 innodb_tables 的 TOTAL_ROW_VERSIONS 不超过 64 次硬上限防静默退化重建表，并且在低峰期先查杀未提交长事务防止 MDL 排他锁排队把普通读写全堵死。」

2.3 事务 ACID、隔离级别、MVCC（ReadView）与四类并发锁实战

1. 痛点与本质定义

简历中两段经历把数据库并发玩到了极致：NoteWeave 有「统一研究单元锁定顺序」「MySQL 批量复核权威状态」，制造业有「配合 SKIP LOCKED 领取与租约回收」「短事务领取、事务外模型调用、基于版本校验的短事务写回」。这部分是面试官深挖并发功底的核心战场。

2. 底层机制与源码细节

  • MVCC（Multi-Version Concurrency Control）三大组件：
    1. 聚簇索引隐藏列：DB_TRX_ID（6B，最后修改该行的事务 ID）、DB_ROLL_PTR（7B，回滚指针，指向 Undo Log 上一历史版本构成单向版本链，无主键时还有 6B DB_ROW_ID）。
    2. Undo Log 版本链：普通一致性快照读不加行锁，若当前记录版本不可见，顺 DB_ROLL_PTR 按需重构历史版本。长事务不提交会导致老 ReadView 一直存活，purge 线程无法清理旧 Undo 导致版本链膨胀拖慢查询。
    3. ReadView 四核心字段与可见性四步判断（参考 MySQL ReadView 源码 ↗）：
      • m_creator_trx_id（创建视图的当前事务 ID）、m_ids（创建视图瞬间活跃未提交的读写事务 ID 列表）、m_up_limit_id（活跃列表最小值，低水位）、m_low_limit_id（系统下一个待分配事务 ID，即当前最大事务 ID + 1，高水位）。
      • 对某行 trx_id：① == m_creator_trx_id（自己改的）→ 可见。② < m_up_limit_id（建视图前早已提交）→ 可见。③ >= m_low_limit_id（建视图后才开启的未来事务）→ 不可见。④ 落在 [m_up_limit_id, m_low_limit_id) 区间 → 查是否在 m_ids 中，在则当时未提交不可见，不在则已提交可见。
    • RC vs RR 核心区别：READ COMMITTED 每次执行普通 SELECT 都重新生成一个新的 ReadView（故能立刻看到别人刚提交的修改）。REPEATABLE READ 仅在该事务第一次执行普通 SELECT 时生成 ReadView 并后续全程复用（注意：BEGIN / START TRANSACTION 那一刻并未拍快照，除非显式写 START TRANSACTION WITH CONSISTENT SNAPSHOT）。
    • 快照读 vs 当前读与 RR 幻读边界：普通 SELECT 是快照读靠 ReadView。SELECT ... FOR SHARE、SELECT ... FOR UPDATE、INSERT / UPDATE / DELETE 全部是当前读，必须读取最新已提交版本并加锁。RR 下连续快照读不产生幻读，当前读靠 临键锁（Next-Key Lock = 记录锁 Record Lock + 前开间隙锁 Gap Lock） 锁住扫描区间禁止并发插入防幻读。但若先快照读没看到某行、别人插入提交后自己执行 UPDATE 当前读改了那行，后续再快照读就会因为 trx_id == m_creator_trx_id 突然看到这行（混合读写幻读现象），且两个事务读同一约束改不同行的写偏斜（Write Skew）在 RR 下仍会发生。

3. 项目落地：四大高含金量锁与并发控制场景（背熟直接拿高分）

  1. 场景一（制造业）：为什么 notify_task 领单短事务显式切 READ COMMITTED + FOR UPDATE SKIP LOCKED？
    • 防间隙锁卡死新告警插入：领单查询走非唯一联合索引 (status, priority, next_run_at) 范围扫描。若保持默认 RR，加锁读会对扫描到的索引区间加上 Gap Lock / Next-Key Lock，此时车间新上报一条告警要 INSERT 进 PENDING 对应时间间隙时会被领单事务无辜阻塞。显式切为 READ COMMITTED（配合 binlog_format=ROW 保证主从复制安全）后，InnoDB 退化为只锁命中的单行记录而不锁间隙。
    • 多实例免等待并行抢单：普通 FOR UPDATE 在双实例同时扫到队头第一条 P0 任务时，实例 B 会阻塞干等实例 A 提交。加上 MySQL 8 原生 SKIP LOCKED（参考 InnoDB Locking Reads ↗）后，实例 B 发现首行已被锁，不阻塞，立即跳过并锁下一条到期行。
    • 跨表死锁消除：领单已锁住子表 notify_task 行，复核父表 anomaly_round 是否已人工确认时，在 RC 下只做普通无锁快照读而不反锁父表。而人工确认先锁父表再按聚簇主键升序批量取消待发子单，避免形成「子等父、父等子」的死锁等待环。
  2. 场景二（NoteWeave 职责 1）：Table-as-State 并发写表统一锁序与 supremum 伪记录防护
    • 四表全局单向升序锁序（主记录写回 FOR SHARE 真并发）：所有写回短事务严格遵循「研究主记录（子任务写回只读 plan_version 加 FOR SHARE 共享锁使 8 路并发回调不互斥，仅低频 Replan 升版加 X 锁。token_seq 发号走独立微事务）→ 子任务 → 目标研究格（按聚簇主键升序排他锁）→ 引用资料主表（按聚簇主键升序走共享锁当前读，复核资料有效且匹配当前生效版本号）」，破坏死锁四大必要条件中的「循环等待」，消除 Error 1213 死锁。
    • 离散主键点查与页尾 supremum 间隙锁防护：单卡去重引用资料数很少，InnoDB 底层按主键升序执行离散唯一主键等值点查而非连续区间扫。但若模型幻觉编造了比当前最大资料 ID 还大的不存在编号直接进事务加共享锁，在可重复读（RR）下唯一主键未命中会锁住页内无穷大伪记录 supremum 的间隙锁，阻塞全系统新上传文档的自增主键插入。因此在事务外的第一层规则校验里先筛掉不存在的幻觉资料编号，配合软删除不物理删行，使事务内共享锁精确命中存在主键、退化为 LOCK_REC_NOT_GAP 单行锁。
  3. 场景三（制造业职责 4）：HITL 草稿为什么阶段一领单就递增 version，阶段三写回为什么要对父轮次加 FOR SHARE？
    • 防超时回收重派下的 ABA 覆盖：若领单不加 version，Worker 1 领走 version=1 后卡顿 95s。第 90s 守护线程将其超时重置回待生成，Worker 2 领走仍处于生成中（version 若还是 1），第 95s Worker 1 醒来执行 WHERE id=? AND version=1 就会误匹配成功覆盖状态。因此每次执行权转移（领单、90s 超时回收、人工接管编辑、批准）都原子 version + 1，拦截慢线程写回。
    • 父表 FOR SHARE 防关单竞态（与职责 1 通知领单的精准锁序对照）：模型在事务外生成草稿耗时约 7.2s，期间现场可能已经修好复机关闭了父异常轮次（子表自己的 version 感知不到父表变化）。阶段三写回短事务按「先父表后子表」顺序先对父表 anomaly_round 加 FOR SHARE 共享读锁做当前读确认轮次仍存活，防止读锁期间并发关单，再 CAS 写回子表草稿。切忌与职责 1 混淆：职责 1 通知领单先用 SKIP LOCKED 锁住子表，故严禁再反锁父表 FOR SHARE（防子→父与人工确认父→子逆序死锁）。而职责 3/4 诊断与草稿写回按「先父后子」同向加锁，不会形成死锁风险。

4. 学生视角脱稿背诵与追问

【脱稿背诵】：「我在两个项目里针对不同访问形态用了不同的隔离级别和锁策略。在制造业通知领单上，因为走的是非唯一联合索引范围扫描，如果用默认的 RR，加锁读会挂临键锁把间隙锁死，导致新进来的设备告警插入阻塞，所以我用 TransactionTemplate 显式切到 READ COMMITTED 配 ROW 格式 binlog，只锁命中单行不锁间隙，并加上 MySQL 8 的 FOR UPDATE SKIP LOCKED 让双实例遇到被锁行直接跳过、免等待并行抢单。而在 NoteWeave 并发写研究状态表时，我严格规定按『主记录 → 子任务 → 格子主键升序 → 资料主表 IN 共享锁』单向加锁破除循环等待，并且专门在事务外第一层规则剔除不存在的幻觉文档 ID，防止 RR 下唯一主键未命中锁住页尾 supremum 伪记录阻塞新文档上传，让锁退化成最轻的 LOCK_REC_NOT_GAP 单行锁。」

2.4 Redo / Undo / Binlog 两阶段提交、主从复制与主库权威复核

1. 痛点与本质定义

面试必考：为什么配了「双 1」掉电不丢已提交事务？Doublewrite Buffer 防什么？崩溃恢复怎么看 prepare 状态？NoteWeave 职责 2「MySQL 批量复核权威状态」为什么必须强制路由主库而不能走从库？

2. 底层机制与源码细节

  • WAL、双写缓冲与内部两阶段提交（2PC）：
    • WAL 与页断裂（Partial Page Write）防护：事务提交不必同步随机刷写 16KB 脏数据页，只需顺序写日志。但后台刷脏页时，InnoDB 页是 16KB 而 Linux 文件系统页是 4KB，刷到一半断电会导致磁盘页半新半旧损坏。而 Redo Log 采用物理逻辑日志（Physiological Logging：物理到页号，逻辑到页内修改操作），底页损坏则无法重放 Redo。因此刷脏前先顺序批量写入 Doublewrite Buffer（.dblwr） 备份完整页，恢复时若校验和损坏先用双写副本修好底页再重放 Redo（参考 InnoDB Doublewrite Buffer ↗）。
    • Redo Log 与 Binlog 两阶段提交及崩溃恢复：① InnoDB 写 Redo Log 置为 PREPARE 态（记录内部事务号 XID）。② Server 层写完整 Binlog（附同一 XID）。③ InnoDB 将 Redo 置为 COMMIT 态。崩溃重启恢复时，遇到处于 PREPARE 但未见 COMMIT 标记的事务，拿 XID 去有效 Binlog 中核对——存在完整 Binlog 事务则自动补齐提交，不存在则用 Undo Log 回滚，保证主库引擎与从库订阅的 Binlog 保持一致。
    • 双 1 持久化与三阶段组提交：innodb_flush_log_at_trx_commit = 1（每次提交 Redo 刷盘）+ sync_binlog = 1（每次提交组 Binlog 刷盘），底层通过 Flush -> Sync -> Commit 三阶段队列由每批 Leader 线程合并多次事务做单次 fsync，兼顾持久性与高并发吞吐。
  • 主从复制链路与主库复核的必要性：
    • 链路：主库写 Binlog → 从库 I/O receiver 线程拉取写本地 relay log → 从库 SQL applier（可多线程并行）重放修改。
    • 半同步复制边界：即便开启半同步（Semisync），主库等待从库返回的 ACK 仅代表从库已收到日志并刷入 relay log，并不代表 applier 线程已经在从库执行完该事务（且超时还会自动退回异步）。因此用户刚撤回一份机密资料（T+0 主库提交 status='REVOKED'），T+50ms 发起问答，从库仍可能停留在 ACTIVE 旧状态。
    • NoteWeave 落点：精排后的 Top-6 候选提取去重 doc_id（最多 6 个），通过 @MasterRoute 数据源路由显式直连 MySQL 主库做聚簇主键 IN (...) 批量点查（免回表，实测 20 QPS 下仅耗 1～2ms），并开启新快照（RC 或新短查询）核验 status='ACTIVE' 且切片携带的 proc_version == current_version，构筑撤回一致性的最终防线。

3. 学生视角脱稿背诵

【脱稿背诵】：「MySQL 单机提交不丢数据靠双 1 配置、两阶段提交和双写缓冲协同：提交时先写 Redo 进 PREPARE、再刷 Binlog、最后改 Redo 为 COMMIT，并靠组提交批量合并 fsync 摊薄磁盘开销。万一在二三步之间断电，重启时拿内部 XID 去 Binlog 核对，完整就提交、不完整就用 Undo 回滚。而后台异步刷 16KB 脏页靠 Doublewrite Buffer 解决 4KB 系统页撕裂导致 Redo 无法重放的问题。至于主从复制，哪怕开了半同步，从库回 ACK 也只是写进了 relay log 还没真正应用生效，所以在 NoteWeave 资料撤回链路最后一步，我对精排完的前 6 条候选去重资料 ID 强制路由直连 MySQL 主库走聚簇主键 IN 批量点查，只花 1 到 2 毫秒就能避开复制延迟，守住撤回后新提问不漏出已撤回切片的底线。」

2.5 PostgreSQL (pgvector) 工业多模检索与预过滤索引设计（B-Tree + GIN vs HNSW）

1. 痛点与本质定义

简历实习经历技术栈包含 PostgreSQL (pgvector)，职责 3 写到：「按设备型号、版本与片段级适用范围预过滤，经故障编码、全文与向量三路召回」。面试官极爱追问：为什么不用专门的 Milvus / ES？为什么 3 万条切片故意不建 HNSW 向量索引？3,000 条外部存储向量扫描怎么跑进 10ms 以内的？

2. 底层机制与项目容量账本（源自 03_工业RAG、HITL维修工单与场景追问.md）

  • 为什么向量检索怕「先全局 ANN 再后过滤（Post-filtering）」？
    • 工业合编手册里，老款通用型号的切片占大多数，某台特定改款机型（如 DX-560B 固件 v3.2）的合规切片可能只占全库的 5%～10%，且正文表述与相邻型号高度雷同。
    • 如果在全局 HNSW 图上先搜近邻 Top-20，再按机型和固件版本过滤，前 20 个名额经常被老型号切片挤占殆尽，过滤完变成 0 条或仅剩 1 条（召回坍塌 / 滤空问题）。而早期 pgvector 在高选择性过滤条件下若选错执行计划走图遍历，或后期迭代扫描跨度过大，延迟与召回稳定性反而不如精确位图过滤。
  • 四列复合 B-Tree + 三个 GIN 倒排索引 + 120MB 常驻内存精确余弦计算：
    1. 硬预过滤索引组合：标量范围建四列复合 B-Tree (device_category, batch_no, fw_min, fw_max)（首列设备大类等值先把 3 万条收窄到几千条，后三列在索引页内完成知识批次与固件上下界判定）。多值数组与全文建 3 个 GIN（Generalized Inverted Index）倒排索引——适用子型号数组 model_codes、关联故障码数组 fault_codes、zhparser 工业自定义词典 tsvector 分词列。
    2. BitmapAnd 不退化的执行路径：因 3 万切片阶段故意不建 HNSW 索引，PG 优化器稳定地选择 BitmapAnd(B-Tree, GIN) 位图按位与求交，筛剩 2,000～4,000 条合规切片。该位图仅几十 KB，远低于 PG 默认 4MB work_mem，全程保持精确行指针（Exact TIDs）而不会退化为 lossy 整页重扫，随后 Bitmap Heap Scan 精确计算余弦距离 <=> 取 Top-20（不引入近似图搜索的召回损失）。
    3. 为什么 TOAST 外部存储不慢且 <10ms？ 1024 维 float32 向量单条占 4KB，采用 pgvector 默认非压缩 STORAGE EXTERNAL 免去无收益的 LZ4 解压 CPU 开销。全库 30,000 × 4KB ≈ 120MB，整张向量 TOAST 表稳稳常驻在 PG shared_buffers 共享内存中，全程纯内存顺序/位图读取加 SIMD 指令内积运算，实测仅几毫秒。
    4. 连接池安全细节：独立 HikariCP 只读池 max=10，每次查询在只读事务块内执行 SET LOCAL statement_timeout = '800ms'——用 SET LOCAL 而非会话级 SET，保证事务结束归还连接时自动恢复默认超时，不会污染池中物理连接误杀后续查询。

3. 学生视角脱稿背诵与追问

【脱稿背诵】：「在制造业项目里，工业手册切片一共约 3 万条，我们复用了公司既有的 PostgreSQL 16 加 pgvector 和 zhparser。这里有个专门针对工业场景的设计：我们在 3 万条规模下故意没有建 HNSW 向量索引。因为同系列相邻改款机型的维修步骤长得很像但扭矩、液压参数不同，如果先在全局图上取近邻再过滤型号版本，名额很容易被老型号切片挤空。我们给设备大类、批次和固件上下界建了四列复合 B-Tree，给适用子型号数组、故障码数组和中文分词建了 GIN 倒排索引，让优化器稳定走 BitmapAnd 位图求交先硬筛出两三千条合规的切片（位图才几十 KB 远小于 4MB work_mem 不退化）。而 3 万条 1024 维 float32 向量用非压缩外部存储总共才 120MB，全部常驻 PG shared_buffers 内存免解压，直接算两三千次精确余弦距离不到 10 毫秒 就返回了，既不引入近似召回损失，又避免串用错型号参数。如果未来扩到几十万条，再开启 pgvector 0.8 的 HNSW 迭代过滤扫描（Iterative Index Scans）。」

3.1 Redis 高性能原理、线程模型与底层数据结构编码（SDS · listpack · dict · 跳表 · Bloom Filter）

1. 痛点与本质定义

两段经历把 Redis 的五大核心场景全部串了起来：并发槽位租约（ZSET）、通道令牌桶限流（Hash + Lua）、流式断线续读（Stream）、实时中断与失效广播（Pub/Sub）、防脏回填缓存与撤回墓碑（String / ZSET / Hash）。面试必从项目用法顺藤摸瓜问底层数据结构编码、单线程 vs IO 多线程、以及客户端选型。

2. 底层机制与源码细节（融合《Redis 学习与面试完整讲义》与 Redis 7.2 Docs ↗）

  • 为什么快与线程模型演进：纯内存访问 + 高效紧凑底层编码 + Linux epoll（默认 LT 模式，见 Redis ae_epoll.c ↗）非阻塞事件循环 + 核心命令执行主路径单线程串行（省去多线程锁竞争与上下文切换，但也意味着 KEYS *、超大 HGETALL、长循环 Lua 会阻塞后续所有命令）。Redis 6.0+ 引入可配置的网络 I/O 多线程分担 Socket 读写与协议解析，后台还有异步刷盘（BIO_AOF_FSYNC）和惰性释放内存（UNLINK BIO_LAZY_FREE）线程，故严谨表述为「常规命令执行主路径单线程，网络读写与后台清理可多线程」。
  • Java 客户端选型（Lettuce vs Jedis）：Spring Boot 默认用 Lettuce，底层基于 Netty NIO，单条物理连接天然线程安全，多线程共享多路复用发送短命令（阻塞命令如 BLPOP / XREAD BLOCK 或事务除外，需独立连接）。Jedis 基于阻塞 Socket，单连接非线程安全，必须配连接池。制造业中给 Lettuce 显式设 200ms 命令超时，防止主从切换期间挂住主线线程。
  • 核心底层编码必背细节：
    1. String 与 SDS（Simple Dynamic String）：相比 C 原生 \0 结尾字符串，SDS 显式记录已用长度 len 与分配容量 alloc，获取长度 O(1)、二进制安全（中间含 \0 不截断）、空间预分配防缓冲区溢出。三种编码：int（8B 长整型）、embstr（长度 <= 44 Bytes 时，16B redisObject 头 + 取消字节对齐 __attribute__((__packed__)) 的 3B sdshdr8 头 + 44B 内容 + 1B \0 恰好凑够 64 Bytes 单条 CPU 缓存行，只做一次连续内存分配，embstr 为只读编码，一旦 APPEND 修改立即转为 raw）、raw（> 44B，两次独立内存分配，见 Redis 7.2 object.c ↗）。
    2. List / Hash / ZSet 小对象紧凑编码 listpack 替代 ziplist：早期 ziplist 每个节点存前驱节点长度 prevlen（< 254B 占 1B，>= 254B 暴涨为 0xFE + 4B 共 5B），一旦首部插入一个 >= 254B 的元素，可能引发后续一连串处于 250～253B 边缘的节点连续扩容重分配即连锁更新（Cascade Update）。Redis 7.0+ 全面改用 listpack（见 antirez listpack 设计文档 ↗），每个节点只在自身尾部记录自己的长度 backlen（每字节最高位 MSB 作延续标志、尾部首字节 MSB=0 作反向定界符），既支持从尾向头反向遍历，又避免了跨节点连锁更新。List 大对象采用 quicklist（双向链表串多个 listpack 宏节点）。
    3. Hash 大对象 dict 与渐进式 Rehash：拉链法解决冲突，维护 ht[0] 与 ht[1] 两张哈希表及 rehashidx。扩容触发后（平时负载因子 >= 1，若正在跑 BGSAVE / BGREWRITEAOF 子进程，为减少 COW 写时复制内存翻倍，阈值提高到 >= 5），不一次性搬完，而在后续每次增删改查顺带搬 rehashidx 处一个桶：期间新插入一律只进 ht[1]，查/删/改先查 ht[0] 再查 ht[1]，避免漏查或重复。
    4. ZSet 大对象 dict + zskiplist（哈希表 + 跳表）与 double 53 位精度边界：
      • 为什么同时用两套结构？dict 支撑 ZSCORE 按成员 O(1) 查分值。跳表（Skiplist）按 (score, member 字典序) 有序排列并维护前向指针跨度 span，支撑 O(\log N + M) 范围查询 ZRANGE 与 O(\log N) 累加 span 算排名 ZRANK（两者共享成员 SDS 指针不双倍拷贝内容，相比红黑树，跳表范围遍历只需顺底层双向链表走，实现更简洁直观，见 Redis 7.2 t_zset.c ↗）。
      • 高频深水区：score 复合排序精度陷阱：ZSet 的 score 是 IEEE 754 64 位 double 浮点数，尾数有效精度仅 53 bit，能连续精确区分无精度丢失的最大整数范围是 [-2^53, 2^53]（约 9.007 × 10^(15)）。因此不能把两个任意 32 位整数直接拼成 64 位塞进 score，超出 2^(53) 后相邻整数会坍缩为同一个浮点数导致同分乱序。要做「积分优先、同分早到优先」混排时，必须用相对于活动起点的有界秒数差并验算 p(\max) · B + s(\max) ≤ 2^(53)。
    5. Bloom Filter（布隆过滤器）空间推导与工程禁区：m 位 bit 数组配 k 个独立哈希函数，对已正确同步集合无假阴性（判不存在则一定不存在），有假阳性（判存在可能误判），给定容量 n 与误判率 p 时 m ≈ -(n \ln p) / ((\ln 2)²)，k ≈ (m) / (n)\ln 2（如 1000 万元素、1% 误判率仅需约 11.43 MiB，k ≈ 7，见 Redis Bloom Filter ↗）。标准布隆不支持单元素清零删除（会连累共享位的其他元素产生假阴性）。NoteWeave 反例：向量化批次汇聚去重不能使用布隆过滤器——一旦某个真实批次撞上千分之一假阳性被误判为已处理跳过，文档主表已完成批次计数就会永远少 1，整份资料永久卡在中间态进不了 ES。

3. 学生视角脱稿背诵

【脱稿背诵】：「Redis 快在纯内存、紧凑编码、epoll 多路复用加核心命令单线程无锁竞争，6.0 以后引入的多线程只分担网络 IO 读写和协议解析，命令执行主线依然串行。底层编码上我重点关注三块：一是 SDS 长度不超过 44 字节走只读 embstr，利用取消字节对齐的 3 字节 sdshdr8 加 16 字节对象头和结尾符正好凑够 64 字节 CPU 缓存行。二是 Redis 7 用 listpack 把节点自身长度放尾部逆向定界，解决了老版 ziplist 超过 254 字节引发的级联更新。三是 ZSet 小规模走 listpack（比如 NoteWeave 工作区调研与产物独立 8 槽租约各有最多 8 个元素），超阈值转 dict 加跳表，但要注意它的 score 是 64 位 double，连续精确整数上限只有 2^(53)，不能盲目拼两个 32 位整数。」

3.2 Redis ZSET 租约、Fencing Token 与并发写回防护

1. 痛点与本质定义

简历在 NoteWeave 职责 1 明确写到：「以 Redis ZSET 租约管理槽位、Fencing Token 拒绝过期写回」。面试官必问：为什么不用 INCR / DECR 计数器或 Redisson 分布式锁？租约都有过期时间了，为什么还非要加 Fencing Token？

2. 底层机制与故障时序推演

  • 为什么 INCR / DECR 和普通分布式锁不够？
    1. INCR / DECR 崩溃漏减：工作区限 8 个并发槽，执行节点 INCR 占槽后若遭遇 kill -9 或容器 OOM 重启，来不及执行 DECR，槽位永久泄漏。而整个计数器设统一 TTL 又会把正在正常跑的其他任务计数一并清零。
    2. Redisson 看门狗 / Redlock 挡不住进程停顿覆盖写：分布式锁或租约只能管理「当前谁有资格领任务」，一旦持有者 A 遭遇长达几十秒的 Full GC STW 或网络分区导致锁/租约到期，执行者 B 合法接管并写完新结果。随后 A 醒来，它的代码并不会因为 Redis 里的键过期而自动终止，A 拿着旧上下文照样向 MySQL 发 UPDATE，直接把 B 的新结果覆盖掉（参考 Redis Distributed Locks ↗）。
  • NoteWeave「Redis 管准入数量 + MySQL Fencing Token 管写回正确性」双层闭环（源自 02_Table-as-State深度研究与追问.md 与 deep-research-design.md）：
    1. 三大独立 Redis ZSET 舱壁隔离（Lua 原子执行）：按快慢负载物理拆出调研专用 nw:slots:research:wsId（限 8 槽，饱和 DEEP 8×8 首波 8 行）与产物专用 nw:slots:artifact:wsId（限 8 槽，≤ 单机 32 池 25%），外加撤回墓碑 nw:tombstone:wsId（均不加 {wsId} Hash Tag 防 Cluster 分片倾斜）。member 为每次派发生成的唯一 lease_token，score 为到期毫秒时间戳。
      • 准入 Lua：调服务端 TIME 统一时钟 → ZREMRANGEBYSCORE key -inf now 剔除已崩溃/超时槽位 → ZCARD key < 8 则 ZADD key (now + 300000) lease_token 占槽成功（300s 过期）。
      • 续期顺序（防双租约脑裂与僵尸复活）：活跃执行者每 60s 心跳先更新 MySQL 任务运行租约，成功后再调 Lua，必须先验 ZSCORE key lease_token > now（确认自己还在且未过期）才用 ZADD XX 顺延 300s，不能无条件 ZADD 把已被踢掉的旧令牌重新塞回集合。
    2. MySQL 权威端单调 Fencing Token 与写回两支分流（主记录 FOR SHARE 并发 + 防 300s 槽位泄漏）：
      • 每次派发或超时重派都在独立微事务里原子递增 RESEARCH_MAIN.token_seq 签发单调代次 fencing_token 并写入子任务表。写回短事务对 RESEARCH_MAIN 降为共享锁 FOR SHARE（仅 Replan 升版加 X 锁），使 8 路并发回调完全不串行。
      • 写回短事务两支精准分流：
        • 分支 A（超时僵尸执行者）：当子任务已非 RUNNING 态，或传入令牌与子任务当前有效令牌不相等时，说明已被超时回收重派给新执行者——整事务回滚，且严禁调 ZREM 触碰 Redis 槽位（它自己的旧成员早已自然过期清理，乱碰会误伤别人）。
        • 分支 B（当值合法子任务逐格裁决与收口单次释槽）：当子任务确系运行中且令牌匹配：若研究已取消或波次等待窗口后计划已升版，不改旧格结论，结清子任务并立即单次调 ZREM 释放槽位。若计划未变则对本卡各格逐一裁决——单格已拆细归档仅跳过该格，单格引用资料撤回或重传升版仅将该格置为待重验（不扣减 3 次补查配额），其余满足传入令牌严格大于单元写入令牌水位的合规格子正常落库推进水位，事务末尾统一结清子任务并立即单次释放工作区槽位，消除 300s 槽位泄漏。

【脱稿背诵】：「我把并发治理拆成了『准入数量』和『写回正确性』两层。数量层用两把物理隔离的 Redis ZSET 分别管每个工作区 8 槽深度研究与 8 槽重型产物（快慢舱壁隔离、无 Hash Tag 防倾斜），成员是唯一 lease_token、分值是 now + 300 秒 到期时间戳，Lua 脚本调服务端 TIME 先清过期成员再判满准入，每 60 秒心跳先续 DB 租约再验未过期续期 Redis，解决了 INCR/DECR 实例崩溃漏减死占槽位的问题。但任何 Redis 租约或 Redisson 锁都防不住执行者长 GC 停顿醒来后覆盖写库，所以正确性层下沉到 MySQL 权威端，独立微事务单调递增签发 Fencing Token，写回短事务对主记录只加 FOR SHARE 共享锁让 8 路回调并发不串行（仅 Replan 加 X 锁），同时核验子任务令牌一致、计划版本未变且传入令牌严格大于格子最后写入水位。拦截拆两支：僵尸执行者回滚禁碰 Redis，当值执行者逐格裁决结清后单次 ZREM 释放槽位，消除 300 秒槽位泄漏。」

3.3 Redis + Lua 跨实例共享令牌桶限流与高可用降级

1. 痛点与本质定义

简历在制造业职责 2 明确写到：「基于 Redis + Lua 实现跨实例共享的通道级令牌桶限流」。面试必考：四种限流算法怎么对比？Lua 真的是数据库那种事务原子性吗？遇到下游 429 冷却期间键过期重置成满桶怎么防？Redis 哨兵主从切换或挂了怎么降级？

2. 底层机制与项目深度设计（源自 02_可靠通知、降噪流控与场景追问.md）

  • 四大限流算法系统设计对比：
    1. 固定窗口计数器（Fixed Window）：实现最轻，但存在致命窗口交界双倍突刺（前 1 分钟最后 1 秒打入 100 次、后 1 分钟第 1 秒又打入 100 次，2 秒内实际放行 200 次冲垮下游）。
    2. 滑动时间窗口（Sliding Window Log / Buckets）：ZSet 逐请求日志法精确控任意连续 T 秒上限，但高限额下内存开销与 ZREMRANGEBYSCORE 删除成本高，且仍允许在窗口第一毫秒瞬间把 100 个名额全用光，不平滑突发。
    3. 漏桶（Leaky Bucket）：请求先进队列，按恒定速率流出，能抹平毛刺，但不支持突发流量（车间平时安静，突然来 30 条告警也只能按慢速排队干等）。
    4. 令牌桶（Token Bucket，项目最终选择）：以恒定速率 r 向容量 B 的桶补令牌（T(new) = \min(B, T(old) + r · Δ t)），既严格卡住长期平均速率不超过运营商合同配额（短信 20/s、语音 2/s），又允许利用桶内积攒余量（桶容量短信 40、语音 4）毫秒级瞬发吸收车间短时告警突发。
  • Redis Lua 原子性的准确边界：Lua 脚本靠 Redis 单线程串行执行命令实现隔离性（脚本运行期间不会穿插其他客户端命令），但不具备关系型数据库的错误自动回滚（Rollback）语义——若脚本前半段执行了写命令、后半段因参数非法报错中断，前半段的修改会留在内存里（参考 Redis Lua Atomicity ↗）。因此脚本必须先校验所有参数合法性，最后再执行写操作，且通过 EVALSHA 传摘要省带宽、禁止无界循环。
  • 制造业生产级令牌桶三大关键细节：
    1. 单 Hash 同槽与服务端时钟防漂移：每个通道单 Hash 键存 tokens（余量）、last_ms（上次补桶毫秒）、cooldown_until（共享冷却截止时间），单键天然满足集群同槽。脚本内调 redis.call('TIME') 统一时钟并将偶发微回拨钳位为 0。
    2. 遇 429 清零余量 + 本机冷却前置跳过省 DB 写 + 保底长 TTL 配 volatile-ttl 防二次 429 突刺：收到网关 429 Retry-After 时，写入共享 cooldown_until 并同步把桶内剩余 tokens 清零（确保冷却结束从 0 平滑爬坡），同时在本机记录短暂通道冷却标记——Worker 在进入 MySQL 领单短事务前先查本机冷却标记，冷却期内直接跳过该通道领单，消除“领单→扣令牌失败→延期写回”的无效 DB 写放大。若冷却长达几十分钟、各实例跳过请求未调 Redis 刷新过期时间，短 TTL 流控键一旦在冷却结束前自然过期或被淘汰，冷却结束首秒会按「键不存在冷启动」瞬间重置出满桶 40 个突发令牌再次打爆网关。故每次写入刷保底长过期 max(24h, cooldown_remaining + 1h)，并将 Redis 内存淘汰策略配为 volatile-ttl，使其优先淘汰仅 5min TTL 的旁路子 BOM 缓存，不动长寿命流控键。
    3. Redis 故障 / Sentinel 切换降级：Redis 主从异步复制下 Sentinel 切主最坏仅丢失最后几毫秒扣减（误差不超过一桶 40 条，对流控可接受，不开 min-replicas-to-write 牺牲可用性）。Lettuce 设 200ms 硬超时，一旦超时或断连立即自动切回双实例本地 Guava RateLimiter 折半限流（双机各放短信 10/s、语音 1/s，全局合计仍严守 20/s 与 2/s 配额）。

3. 学生视角脱稿背诵

【脱稿背诵】：「运营商通道既要求长期均速不超标，又要能瞬发消化几十条突发停机告警，所以我选令牌桶而没选不支持突发的漏桶或有边界双倍突刺的固定窗口。实现上每个通道一个 Redis Hash 存余量、上次补桶毫秒和共享冷却截止时间，Lua 脚本里调服务端 TIME 原子补桶扣减，注意 Lua 只是单线程隔离执行、报错不回滚，所以要先验参再写。我还重点补了两个边界：一是收到网关 429 写冷却时间时同步把桶余量清零，并且设至少 24 小时 保底长过期配合 volatile-ttl 只淘汰 5 分钟的 BOM 短缓存，防止长冷却期丢键导致恢复瞬间重置满桶 40 条二次打爆网关。二是客户端配 200ms 超时，哨兵切换或断连期间自动降级为两台实例各自的本地 Guava 折半限流，全局总速率依然不超配额。」

3.4 Redis Stream、Pub/Sub 与 Last-Event-ID 流式断线续读

1. 痛点与本质定义

简历在 NoteWeave 职责 4 写到：「回答侧以幂等 Turn + Redis Stream 中转 SSE 解耦生成与连接，对 Stream 按条数裁剪，控制内存增长，支持基于 Last-Event-ID 的跨实例断线续读」。面试必问：为什么不用 Pub/Sub 或 List 中转？MAXLEN ~ 1000 裁剪怎么工作？重连时怎么比对 Last-Event-ID 才能做到既不乱序误判、又不静默漏字？

2. 底层机制与项目深度落地（源自 05_异步资料流式链路与Schema产物框架.md）

  • 三种 Redis 消息结构对比：
    • Pub/Sub：纯内存即发即弃（At-most-once），客户端断网哪怕 1 秒，期间广播的 Token 永久丢失无法补读——NoteWeave 仅用 Pub/Sub 发「用户点击停止生成」中断控制信号和「墓碑本地 1s 缓存失效广播」，不用它传回答正文。
    • List：弹出消费（LPOP/RPOP）会删元素，无法支撑同一用户在手机和电脑双端同时订阅同一路流，也不支持按任意事件 ID 游标定位续读（LRANGE 只能按下标扫）。
    • Redis Stream（基数树 Radix Tree 索引 listpack 宏节点）：消息追加保留有序 ID，支持多路客户端通过 XREAD BLOCK 独立按各自的游标位点追尾读取（前端续读无需建重型 Consumer Group，避免 PEL 待确认列表维护负担），且 XTRIM / XADD MAXLEN ~ 1000 近似裁剪只在整块 listpack 宏节点可整体摘除时才释放内存，达到近 O(1) 高效限容（参考 Redis XTRIM ↗）。
  • 断线续读三大工程细节：
    1. 50ms 微批聚合 + 显式 1 起始单调序号：生成端每 50ms 攒一个增量块执行 XADD sse:stream:turnId MAXLEN ~ 1000 <seq>-0 ...（不加 {} Hash Tag 防倾斜，且 Redis 协议规定 0-0 非法，显式从 1-0, 2-0... 单调递增），写吞吐降一个数量级且人眼依然丝滑，每次刷新 15min 过期。同时每 5 秒（约 100 个微批，远小于 1000 条保留窗口）将累计全文前缀与对应序号 cp_seq 刷入 MySQL 检查点。
    2. 严禁字符串字典序比对 ID，严防 XREAD 静默跳读漏字：浏览器断网重连自动带 Last-Event-ID: 9-0。若直接调 XREAD STREAMS key 9-0，万一断网太久 10-0 到 50-0 已被 MAXLEN 裁掉，Redis 会静默直接从现存最早的 51-0 开始返回，前端拼出来的文章中间就悄无声息缺了一大段。而如果先调 XINFO STREAM 拿当前首条 first-entry ID 跟 Last-Event-ID 做普通字符串比较，会出现 "9-0" > "10-0" 为真的字典序 Bug。
    3. 64 位整数拆解比对 + 三路分流无缝对齐：网关先拆出两边 - 号前的 64 位长整数 long 做数值比较：① 若游标仍在 Stream 保留窗口内，直接 XREAD 续推并在首帧返回时二次断言 frame_seq == cursor_seq + 1。② 若游标已被裁掉且后台生成已完结，直接查 MySQL 终态全文一次性下发。③ 若游标已被裁掉但后台仍在生成中，先取出最新 5 秒 检查点封装为专用 prefix_sync 事件让前端整体覆盖对齐到 cp_seq，随即无缝续接 Stream 中 > cp_seq 的尾部增量（5s 仅百条，必在千条窗口内），故障注入实测与终态全文逐字一致。

3. 学生视角脱稿背诵

【脱稿背诵】：「如果把流式生成直接绑在单机 HTTP 连接上，用户切 Wi-Fi 或网关滚动重启就会断流重算。我引入 Redis Stream 做生成与连接的中间缓冲：生成端按 50ms 微批用从 1-0 开始的单调序号写 Stream，配 MAXLEN ~ 1000 按整块 listpack 宏节点近似裁剪控内存，同时每 5 秒 往 MySQL 刷一次前缀检查点。用户点停止生成则走轻量的 Pub/Sub 广播切断上游流。重连带 Last-Event-ID 过来时有两个很容易踩的坑：一是如果直接调 XREAD 而旧位点已被裁掉，Redis 会静默从现存首条跳读导致中间漏字。二是查 XINFO STREAM 比首条 ID 时不能按字符串字典序比，否则 '9-0' 会大于 '10-0'。所以我拆出横杠前的 64 位整数比大小：窗口内直接续推并验首帧连续，超出窗口若还在生成中就先下发最新 5 秒检查点让前端整体覆盖前缀，再从检查点序号无缝接上 Stream 尾部。」

3.5 Cache-Aside 并发脏回填、Redis 墓碑、版本化 Key 与缓存治理全集

1. 痛点与本质定义

简历在 NoteWeave 职责 2 集中考察了分布式缓存最硬核的深水区：「针对资料撤销后的索引异步滞后与 Cache-Aside 并发脏回填，以 Redis 墓碑下推前置过滤、MySQL 批量复核权威状态及版本化 Key 隔离过期缓存写回，阻断最终一致窗口期的脏召回与旧值复活」。

2. 底层机制与故障时序推演（融合《Redis 讲义》第 2/5/6 章与 Meta Cache Consistency ↗）

  • 为什么经典读写双写、先删缓存、甚至「先改库再删缓存」仍有脏数据？
    1. 改库后直接改缓存：并发写事务 A（v11）和 B（v12），A 先提交 DB 但网络卡顿，B 后提交 DB 先写完缓存 v12，A 恢复把旧 v11 覆盖进缓存。
    2. 先删缓存再改库（最易错）：写请求 W 先删缓存尚未提交 DB，并发读请求 R 未命中读出 DB 旧值 100 回填缓存，W 再提交 120，缓存停留在脏值 100 直至过期。
    3. 标准 Cache-Aside（数据库事务提交后删缓存）的隐蔽慢读脏回填时序：初始缓存刚好失效为空，读请求 R 先未命中查到 DB 旧版 v3 后发生 GC/调度停顿 → 写请求 W 提交 DB 新版 v4 并成功执行 DEL 删缓存 → R 醒来把刚才手里的旧版 v3 重新 SET 回填进缓存（旧值复活）。延迟双删（sleep(500ms) 再删一次）无法证明慢读一定在 500ms 内结束，读写分布式锁又把高并发读拖成串行。
  • NoteWeave 三套精准破局方案（按数据特征量体裁衣）：
    1. Wiki 页缓存：单调版本指针（读写双端同段 Lua + SingleFlight）+ 不可变 版本化 Key：
      • 将数据拆成无 {} Hash Tag 的「版本指针键 wiki:ver:wsId:pageId（TTL 10min）」与「不可变版本正文键 wiki:page:wsId:pageId:v{N}（TTL 1h，配 volatile-lfu 淘汰）」。
      • 读写双端统一 Lua 单调高水位写：写侧先写好新版不可变键 :v4，再调 3 行 Lua（仅 newVer > curVer 才推高指针）。读未命中回源 DB 后回填指针也必须走同一段 Lua 单调写（严禁普通 SET），防止 10min 自然过期瞬间慢读回填旧 3 把写线程刚推高的 4 倒退覆写。热点页指针自然过期瞬间再配本地 SingleFlight 合并回源防击穿。
      • 慢读侧：即便慢读线程停顿醒来回填，指针回填因 3 < 4 被 Lua 拒写、正文也只落废弃旧键 :v3，新读按指针直取 :v4（仅从未存在的非法 ID 写 -1 防穿透。合法页下线升版写下线标记不覆写 -1）。
    2. Context 编译控制块（第 2 段会话约束与第 6 段长期记忆）：状态指纹自变 Key：
      • 键名直接对 (session_id, constraint_ver) 和 (user_id, scope, active_mem_ver_set) 做哈希指纹，状态一变自动切向新 Key，全程不执行主动 DEL，旧键靠 180s + 0～30s 随机抖动 TTL 自然回收（既防脏回填又防集体到期缓存雪崩）。
    3. 资料撤回跨存储一致性：防 ABA 升版 + 同 docId 分区建删保序 + Redis 墓碑（24h -> 60s 缩期 + 1,024 故障熔断水位）+ MySQL 主库复核：
      • 防 ABA 与同分区因果保序：撤回、重传或恢复启用一律递增分配全新 proc_version，并将阶段 4 建索引（UPSERT_INDEX）与撤回删索引（DELETE_INDEX）收口进同一个按 docId 分区的 ES 同步 Topic 严格 FIFO 串行消费，从根源消灭“删跑在迟到建索引之前”的幽灵切片（免去脆弱的 sleep 2s 盲等）。
      • 双端墓碑协同：撤回事务提交后写工作区墓碑 ZSET nw:tombstone:wsId（member = docId:oldVer，score = now + 24h 保底），顺带清本机缓存并经既有 Pub/Sub 广播失效各实例本地 1s Caffeine 缓存。ES 同步消费者调 delete_by_query，仅当返回 failures 列表为空、确认删净 < target_ver 旧切片后，才经 Lua 将墓碑到期时间缩至 min(oldScore, now + 60s)，精准覆盖 ES 1s refresh 与 index.gc_deletes=60s 物理回收窗口。
      • 1,024 故障/压测降级熔断水位：常态 ES 几秒删净缩期，单工作区有效墓碑仅个位数～几十条。1,024 是面向批量删库压测或 ES 消费积压演练的降级熔断水位——<= 1,024 双路下推 ES 预过滤保召回名额，> 1,024 告警并切 1s 本地 Caffeine 短缓存 + 扩窗召回 + 内存 HashSet 过滤（若主库复核剔除后结果被刚撤回长文挤空，立即绕过本地缓存重拉墓碑扩窗补检一次），最后经 MySQL 主库聚簇主键 IN 批量复核兜底。
  • 大 Key 排障、持久化与集群高频速记点：
    • 大 Key 治理（制造业实战故事）：初版将全厂上万备件塞入单个大 Hash 调 HGETALL 引发毛刺，通过 INFO commandstats、SLOWLOG 与从库 SCAN / --bigkeys 定位后，按「机台选配编码 + 功能部件单元」拆为二三十项小 Hash 改 HMGET 按需读，旧大 Key 用 UNLINK 后台异步释放内存，并前置本地 Caffeine（W-TinyLFU） 一级缓存（命中率 > 98%）。
    • 持久化与高可用：RDB（BGSAVE fork 期间主线程复制页表可能短暂微卡，共享物理页修改触发按页 COW 写时复制）+ Redis 7 Multipart AOF（拆分为 base 基线 RDB/AOF + incr 增量日志 + manifest 清单文件，everysec 正常约 1 秒窗口但磁盘阻塞会拉大）。Sentinel 区分主观下线 SDOWN、客观下线 ODOWN（达 quorum）与执行切主必须获 Sentinel 多数派投票授权。Redis Cluster 按 CRC16(key) mod 16384 分槽（{tag} 同槽但易引热点倾斜，永久迁完回 MOVED 刷路由，迁移中回 ASK 先发 ASKING 临时单次放行）。

3. 学生视角脱稿背诵

2. 底层机制与源码细节（融合《Kafka 学习与面试讲义》）

  • Kafka 为什么基于磁盘还能达到极高吞吐？（五大支柱 + 边界）：
    1. 分区日志顺序追加写：Partition 拆为多个 Segment（.log 数据文件 + .index 稀疏逻辑 offset 索引 + .timeindex 时间索引，通过二分定位最近稀疏锚点再顺序扫少量字节，省内存且免随机寻道）。
    2. 重度利用操作系统 Page Cache：Broker 自身 JVM Heap 不必设太大（留足机器内存给 OS 页缓存），生产写入页缓存后紧跟的实时消费者可直接从页缓存命中读取，省去物理读盘。
    3. sendfile 零拷贝（Zero-Copy）：传统读文件发网络需经历「磁盘 → 内核 Page Cache → 用户态缓冲区 → 内核 Socket 缓冲区 → 网卡」4 次拷贝与 4 次上下文切换。Linux sendfile(2) ↗ 配支持 Scatter-Gather DMA 的网卡，直接在内核态把 Page Cache 描述符交给网卡发送，省去用户态往返与 CPU 拷贝（必答边界：开启 SSL/TLS 加密时因需在用户态做加解密变换，无法走裸 sendfile 零拷贝路径）。
    4. 端到端批处理与批量压缩：Producer 按分区在 RecordAccumulator 攒批（batch.size + linger.ms=5）并整批 lz4 / zstd 压缩，Broker 原样落盘，Consumer 拉回才解压。
    5. Claim Check 传指针卸大载荷：大 PDF 原件、解析正文与向量块一律存 MinIO，Kafka 消息体仅传几百字节的 (docId, proc_version, minio_ref)，防爆 max.message.bytes 与复制带宽。
  • 副本复制、三道水位边界（LEO / HW / LSO）与端到端防丢：
    • LEO（Log End Offset）：某副本本地日志末尾的下一条待写位置。HW（High Watermark）：已满足复制提交条件的可见边界（普通 read_uncommitted 消费者最多读到 < HW）。LSO（Last Stable Offset）：开启事务隔离 isolation.level=read_committed 时的可见边界，取 min(HW, 最早未决事务起始 offset)（故若磁盘已有 offset 100 的消息，但 offset 98 挂着一笔未提交事务，read_committed 消费者就会被卡在 98 之前读不到 100）。
    • 为什么 acks=all + min.insync.replicas=2（RF=3）不是 Raft 任意多数派？ acks=all 等待的是当前 ISR（In-Sync Replicas）集合内所有副本复制确认，而 min.insync.replicas=2 是允许成功写入的最低同步副本门槛（若 3 副本都在 ISR 需等 3 份，挂 1 台剩 2 台在 ISR 等 2 份，挂 2 台只剩 Leader 1 台低于门槛则直接拒写保安全，配合 unclean.leader.election.enable=false 严禁落后非安全副本选主丢数据）。注意 acks=all 确认的是写入各副本内存/页缓存，不代表每条都同步执行了物理 fsync。
    • 幂等生产者边界：enable.idempotence=true（要求 acks=all 且 max.in.flight.requests.per.connection <= 5）靠 Broker 校验 (PID, Epoch, Partition Sequence Number)，既消除了单连接多在途批次重试乱序，又拦截了网络超时自动重传导致的 Broker 重复追加。但它管不了应用重启换新 PID 或业务层重新调 send()，下游消费端必须保留业务唯一键或外部版本号幂等（如 ES version_type=external_gte）。
  • 重平衡（Rebalance）、位点安全提交与长任务背压（NoteWeave 核心亮点）：
    • 两个完全不同的超时参数：session.timeout.ms 靠独立后台心跳线程维持，检测容器死机失联。max.poll.interval.ms（默认 300s）检测业务拉取线程两次调用 poll() 的间隔——哪怕后台心跳正常，只要单批消息处理超过 300s 没调下一次 poll()，协调器就会判定活锁将其踢出消费组触发重平衡（Kafka 4.x 支持 CooperativeStickyAssignor 增量撤销或新 group.protocol=consumer 服务端协调减少全组停顿，但被踢分区仍会被重派导致双写）。
    • NoteWeave 分钟级产物队列四步职责解耦闭环（为什么放弃 pause/resume + 内存连续位点）：
      1. Kafka 6 分区只做削峰与并行派发（毫秒安全提交 offset）：初版试过 max.poll.records=1 + pause/resume + 分区内内存连续位点集合，但单分区只要最早 1 单跑 6 分钟未完，位点就死卡 6 分钟，重启触发几十条重放风暴且代码脆弱。改造后消费线程不跑 2～6 分钟任务，毫秒级判 DB 幂等并检查工作区产物独立 8 槽（nw:slots:artifact:wsId，与调研 8 槽舱壁隔离）与本机 32 线程有界池余量。
      2. 抢槽入池或满槽转 DELAYED 均毫秒提交 offset：有槽且有空位则 DB 条件置 RUNNING(300s 租约 + exec_gen+1) 异步投递 32 线程池。单工作区满 8 槽或本机池满则条件置 DB DELAYED 放行后续其他工作区——两条分支都在毫秒内安全提交 Kafka offset，零 Rebalance、零 6 分钟位点空洞、没有观测到跨工作区队头阻塞。
      3. MySQL 权威运行租约 + exec_gen 兜底宕机：在途任务每 60s 心跳先刷 DB 租约再 Lua 续期 Redis 槽位。实例宕机停跳后后台 30s 扫描回收超时单递增 exec_gen 重派，写页与终态核验 exec_gen 防慢实例双写。
      4. 完单前「先 Lua 续租、再 DB 认领」原地接力（Relay）：工作线程跑完一单准备释放槽位前，若同工作区有 DELAYED 积压单，先调 Redis Lua（验 ZSCORE > now 并 ZADD XX）续期工作区租约，再通过数据库条件更新原子认领最早 1 单接力跑（影响 0 行立即 ZREM 释槽，最多连跑 1 次即主动让出槽位防饿死其他工作区）。
  • 消息积压排空公式：当消费完成率 \mu > 上游到达率 λ 时，排空存量积压 B 所需时间 T ≈ (B) / (\mu - λ)。普通消费组同组最大分区并行度受限于分区数（新建另一个消费组只会从头独立再算一遍，不能帮旧组分担积压，扩分区也不会自动搬走旧分区已积压的存量消息，且会改变 session_id 哈希映射打乱同会话增量摘要顺序，故摘要 Topic 积压优先提速单条模型吞吐，低峰期才受控扩分区）。

4.3 RabbitMQ 仲裁队列、双连接隔离、Outbox 与 稳定请求号对账（结合制造业平台）

1. 痛点与本质定义

简历在制造业职责 1 写到：「针对任务落库与 MQ 发布不一致及重复投递问题，采用 Outbox + 发布确认实现可恢复发布，结合消费确认、稳定请求号对账与业务幂等防重」。这是后端面试考察跨故障域最终一致性的标准模板。

2. 底层机制与全断点恢复闭环（源自 02_可靠通知、降噪流控与场景追问.md）

  • 为什么选本地消息表 Outbox 而不直接发 MQ 或上分布式事务？
    • 事务内发 MQ：网络抖动拖成秒级长事务耗尽 HikariCP 连接，且后续本地回滚撤不回已发出的消息。
    • 事务提交后直发 MQ：提交完瞬间进程崩溃或断网，消息永久丢失。
    • XA / Seata AT / TCC：强阻塞或业务侵入重，且外部运营商短信网关与第三方 CMMS 无法接入内部事务协调器。
    • 同库 Outbox 闭环：业务表（anomaly_round、notify_task，若是 P0 首报同事务一并预埋一张 +60s 独立语音兜底单）与 outbox 表在同一个 MySQL 毫秒级本地事务中原子提交。注册 Spring TransactionSynchronization.afterCommit 钩子异步快路径投递 RabbitMQ，漏发或断网未确认记录由每机 1s 守护线程（扫超 2s 宽限期记录，RC + SKIP LOCKED 认领 5s 短租约递增 corr_ver，指数退避）重投兜底。
  • RabbitMQ 三端防丢与生产级「双物理 TCP 连接隔离」暗牌：
    1. 生产端双确认：开启 publisher-confirm-type: correlated（带 outbox_id + corr_ver）确认到达 Exchange/Queue，同时开启 mandatory: true + ReturnsCallback 拦截 Exchange 存在但路由键无匹配队列导致的静默丢弃。只有收到 Confirm ACK 且未触发 Return 才将 Outbox 条件更新为 PUBLISHED（若队列设 x-max-length 必配 overflow=reject-publish，防默认 drop-head 静默删队头老消息却仍回 ACK）。
    2. Broker 端 Raft 仲裁队列（Quorum Queue）：持久化 topic 交换机绑定 3 节点 Quorum 仲裁队列，1 Leader + 2 Follower 基于 Raft 协议至少 2/3 多数派写入磁盘 WAL 才向生产者回 Confirm ACK，解决旧版经典镜像队列同步阻塞与网络分区脑裂丢消息问题。
    3. 消费端限流与手动确认：AcknowledgeMode.MANUAL + prefetch=20（限制未确认在途消息数防撑爆消费端内存）+ x-delivery-limit=5 超限自动路由进死信交换机 DLX / DLQ 告警。
    4. 关键工程细节：发布与消费拆两个独立 ConnectionFactory（双 TCP 连接）：RabbitMQ 任一节点内存超 vm_memory_high_watermark（默认 0.4）或磁盘低于阈值触发流控告警时，Broker 会按 TCP Connection 粒度暂停读取所有曾发过 Publish 帧的连接，而纯 Consume 连接不受阻。若应用读写共用默认单 Connection（多 Channel 复用），Broker 内存满了想靠消费者消费消息发回 ACK 腾内存，结果连消费端发 ACK 的 TCP 通道也被一起冻死，形成集群级连坐死锁。物理拆开生产与消费两个 ConnectionFactory 即可破局。
  • 为什么断网 90s 恢复重放 310 条 Outbox 事件不会重复发短信？（四层状态物理拆表）：
    • 系统将①异常轮次处置状态、②Outbox 发布状态、③notify_task 通知任务调度状态、④网关回执状态拆在四张独立表。断连 RabbitMQ 90s 期间，本机 1s 守护线程早已直接扫第三层 notify_task 表把紧急短信发完了。恢复后补发的 310 条第二层事件一侧帮车间大屏看板凭轮次版本号高水位补齐画面，另一侧通知消费者收到后仅置内存唤醒标志即 ACK，守护线程探活见第三层已无 PENDING 到期单直接休眠，不会重复发短信。
  • 外部网关超时未知：稳定请求号对账 与慢 GC 200 OK 不对称收敛：
    • 关闭 HttpClient 隐式自动重试。首次领单短事务生成雪花算法 request_no 冻结不变。
    • 慢 GC 租约过期后的不对称写回：若发送线程调网关途中遇超过 8s 租约的慢 GC，存活实例已递增 exec_gen 将任务收回转 待对账（RECONCILING）。原线程醒来分两路：① 若手里是超时/网络异常，因 WHERE status='SENDING' AND exec_gen=? 失配影响 0 行直接安全放弃。② 若原线程已拿到网关明确返回的 200 OK 与渠道流水号，则在同短事务按唯一 request_no 幂等插入回执表留证，并允许直接按 WHERE request_no=? AND status IN ('PENDING','SENDING','RECONCILING') 将主任务一步收敛为 已受理（ACCEPTED），省去盲等 30 秒。
    • 真正读超时结果未知：转 待对账 延后 30 秒（避开运营商网关内部异步落账延迟，立刻查会查不到误判重发）持原 request_no 调回查接口，已受理则补终态，确认未收到才持原 request_no 重投。5,200 条故障注入演练（4,890 实时 + 310 断网补发，5,150 一次受理 + 12 强杀接管 + 38 超时对账）两本账对齐，未观测到重复受理。

4.4 XXL-Job 分布式调度、优先级 + 老化调度 与 持久化延期

1. 痛点与本质定义

简历实习经历技术栈列有 XXL-Job，职责 2 写到：「MQ 与扫描入口统一按优先级 + 老化调度，结合持久化延期分批消化积压」。面试必问：既然有了 RabbitMQ 和本机守护线程，为什么还要用 XXL-Job？XXL-Job 底层怎么防集群重复触发、时间轮怎么转？为什么不用 RabbitMQ 优先级队列或延迟插件？

2. 底层机制与三级触发体系权衡

  • XXL-Job 核心底层机制（源自 01_项目总览）：
    1. 集群防重悲观锁：多个 Admin 调度中心实例通过数据库表 SELECT * FROM xxl_job_lock WHERE lock_name = 'schedule_lock' FOR UPDATE 争抢排他行锁，同一时刻仅一个节点执行预读扫描，防止多 Admin 重复下发。
    2. 5s 预读 + 60 槽秒级内存时间轮：ScheduleThread 每次预读未来 5000ms（PRE_READ_MS） 内即将触发的任务：已过期的按过期策略处理，即将到期的按触发秒数 triggerTime / 1000 % 60 推入内存 ConcurrentHashMap<Integer, List<Integer>> 60 槽时间轮，由独立 RingThread 按秒刻度精准摘槽投快/慢触发线程池 RPC 调执行器，把数据库锁竞争与精确触发时刻解耦。
    3. 路由与阻塞策略：跨班升级采用 SHARDING_BROADCAST（分片广播），双实例分别拿到 shardIndex = 0, 1 与 shardTotal = 2，在 SQL 中按 MOD(factory_id, shardTotal) = shardIndex 水平分工扫不同厂区。阻塞处理策略配 SERIAL_EXECUTION（单机串行） 配合数据库条件更新幂等。
  • 制造业三级时间触发职责严格划分（不混用）：
    1. 毫秒级实时一对多扇出 → RabbitMQ：新告警同时唤醒通知模块与车间看板。
    2. 秒级高可靠状态推进与防饥饿老化 → 应用内本机 ScheduledExecutorService 守护线程：
      • 为什么不把 8s 租约回收和到期催办交给 XXL-Job？因为 XXL-Job Admin 是中心化外部依赖且 RPC 有开销，一旦调度中心抖动或网络隔离，紧急告警接管不能停。本机 scheduleWithFixedDelay(1s)（上一轮跑完再等 1s，防任务超时堆积）直连数据库最稳。
      • 10s 分段老化与封顶 P1 设计：两分钟涌入 3,000 条 P3 断网补报单时，取消 MQ 消费者直调网关（RabbitMQ 3.12 仲裁队列不支持消息优先级，且就算经典优先级队列，已被 prefetch 预取到客户端内存的消息也无法被后来的 P0 插队，拿不到令牌发 nack requeue 还会在 Broker 与客户端之间死循环空转耗光 CPU）。统一收归数据库按 (status, priority, next_run_at) 领单，拿不到令牌就用 Lua 返回的等待毫秒加随机微抖动（防下一秒集体惊群抢桶）推迟 next_run_at 落库做持久化延期。同时本机另一守护线程每 10 秒沿 (status, next_aging_at) 索引 RC + SKIP LOCKED 取出最多 200 个等待满 10 分钟 且低于 P1 的主键，按聚簇主键升序批量提一档优先级——严格封顶 P1 不升 P0，既保证低优补报几十分钟内有序排空不饿死，又永远给最新爆发的真实 P0 停机告警留出最高优先超车道。
    3. 班次边界与全局重批处理 → XXL-Job（仅管 4 件事）：① 早晚 08:00 / 20:00 跨班交接升级（为什么跨班升级不用 MQ 延迟消息？因为延迟消息发出去就定死了，车间一旦临时调整排班表无法在队列里批量改期或取消，且需在八点整对所有未物理关轮的故障统一结算取消上班遗留单、生成接班员 SHIFT_ESCALATE 单并给未关 P0 重新预埋新班次 +60s 语音单）。② 夜间通道账单全量对账核销。③ 凌晨 7 天 前历史冷单归档。④ 凌晨工业知识库新批次构建发布。

3. 学生视角脱稿背诵

【脱稿背诵】：「我在系统设计上把时间触发按特征切成了三层：毫秒级事件扇出走 RabbitMQ。秒级到期领单、8 秒 租约回收和每 10 秒 一次的低优分段老化放在每台实例本地的 ScheduledExecutorService 固定延迟守护线程里，这样哪怕 MQ 和调度中心全挂了，核心告警照样能发能接管。而 XXL-Job 专门负责早晚八点跨班升级、夜间账单对账、凌晨冷单归档和知识批次发布这四类全局批处理。底层上 XXL-Job 靠数据库 schedule_lock 排他行锁防多中心重复触发，预读未来 5 秒 任务推入 60 槽秒级内存时间轮保精度，跨班升级用分片广播按厂区取模并行处理。至于两分钟 3,000 条补报洪峰，因为 RabbitMQ 3.12 仲裁队列不支持优先级、且预取到本地的消息无法被新 P0 插队，所以我把调度权收归数据库：无令牌时加随机抖动推迟 next_run_at 做持久化延期不空转，守护线程每 10 秒用 SKIP LOCKED 按主键升序把等满 10 分钟的低优单提一档、但严格封顶到 P1，既不饿死低优单，又把最高优先权留给刚发生的 P0 停机事故。」

5.1 Elasticsearch 底层倒排原理、近实时（NRT）链路与外部版本幂等

1. 痛点与本质定义

简历在 NoteWeave 技术栈与职责 2/4 深度使用了 Elasticsearch：18 万切片混合检索、定制分析器、批量 bulk 建索引，以及最核心的考题——「为什么资料在 MySQL 已经删了，ES 里还能被搜出来？为什么不能每次删资料都直接调 refresh=true 强刷？」

2. 底层机制与源码细节（源自 03_QA_Note_Wiki知识链路与撤销一致性.md 与 Elasticsearch Doc Values ↗）

  • Lucene 倒排索引三大核心结构（为什么上亿文档毫秒级检索且不撑爆内存？）：
    1. Posting List（倒排表）：记录包含某词项的所有文档 ID 列表及词频、偏移位置。对递增整数 ID 采用 Frame of Reference（FOR）差值分块压缩省磁盘。多条件布尔过滤（filter）在内存合并时自动转为 Roaring Bitmap（咆哮位图：高 16 位分桶，稀疏桶用有序 short[] 数组、稠密桶用 65536 bit 位图、连续桶用游程编码 RLE） 做极速位运算求交。
    2. Term Dictionary（词典）与 Term Index（词典索引 FST）：排序后的全量词典太大放磁盘，内存中只驻留基于 FST（Finite State Transducer，有限状态转换器） 构建的前缀+后缀双重共享有向无环图索引，体积压至原词典的几十分之一，定位磁盘词典块后再顺序读倒排表。
    3. Doc Values（列式正排存储）：倒排解决「由词找文档」，而排序、分组聚合或脚本过滤需要「由文档找字段值」，Lucene 在建索引时同步生成磁盘列式存储 Doc Values 交 OS Page Cache 缓存。
  • ES 写入、近实时可见与软删除回收全链路（撤回滞后的根本原因）：
    1. Index（内存缓冲 + translog）：文档写入先进入内存 Indexing Buffer（此时不可被搜索），同时追加写 translog 保障崩溃可恢复。
    2. Refresh（默认每 1s 一次 → 近实时可见）：每隔 1s 将内存缓冲生成一个新的不可变 Lucene 段（Immutable Segment） 写入操作系统 Page Cache 并打开供搜索，清空内存缓冲。为什么不能每次删改都传 ?refresh=true？ 高并发下每次请求强刷会产生海量几 KB 的微型碎段，耗尽文件句柄并触发后台疯狂段合并打满磁盘 IO，且跨 MySQL 与 ES 同步双写遇到异常无法回滚。
    3. Flush（刷盘切 translog）：定期或 translog 满阈值时执行 fsync 将 Page Cache 中的段刷入物理磁盘、写入 commit point 并截断旧 translog。
    4. 删除与更新本质（.del / .liv 位图 + 60s 回收窗口）：因为 Lucene 段不可变，执行 delete_by_query 并不会立刻去磁盘抹掉文档字节，而是在段旁边的 .liv（Live Docs）位图中将该文档标记为已删除，且默认保留 index.gc_deletes = 60s 供在途搜索快照与历史版本校验，直到后台 Merge（段合并） 把多个小段合并成大段时才真正物理剔除废文档。这正是 NoteWeave 在 delete_by_query 确认 failures 为空后，仍让 Redis 墓碑保留 60s 的底层依据。
  • NoteWeave 工程实践三大细节：
    • 索引别名不停机重建：业务代码永远只读写工作区逻辑别名（Alias）。当需要修改分词器或字段 Mapping 时，后台新建 idx_v2 重灌数据，再用原子 _aliases API 一键切走旧 idx_v1，线上不停机切换。
    • bulk 批量与外部版本号 external_gte 幂等：建索引每批 500 条或 5MB（过大易引发协调节点内存抖动），写入显式带 version = proc_version 且 version_type = external_gte——既允许同版本 Kafka 重试批次幂等覆盖，又在引擎层直接拒绝迟到的旧版本慢任务覆盖新切片。
    • 深分页对比：ES 默认拒查 from + size > 10,000（协调节点需向每个分片拉取 from+size 条做全局归并排序，复杂度成倍放大）。scroll 会冻结历史快照耗内存仅适离线导出。在线深翻页统一用 search_after + PIT（Point in Time） 轻量级一致性视图配唯一排序键游标推进。

3. 学生视角脱稿背诵

【脱稿背诵】：「Elasticsearch 底层基于不可变的 Lucene 段：词典索引靠 FST 前后缀共享把内存压到极小，倒排表靠差值压缩和 Roaring Bitmap 咆哮位图做极速布尔求交。写入时文档先进内存缓冲和 translog，默认每 1 秒 refresh 生成新段进操作系统页缓存才可被搜到。而删除文档只是在 .liv 位图打删除标记，默认还有 index.gc_deletes=60s 的保留窗口，直到后台段合并才物理清掉。如果删资料时同步强调 refresh=true，不仅跨库没法回滚，还会刷出大量微型碎段把磁盘 IO 打爆。所以我才设计了先写 24 小时 Redis 墓碑拦截、等后台 delete_by_query 确认 failures 为空后再把墓碑缩期到 60 秒 覆盖刷段窗口的异步闭环，写新版本时再配 version_type=external_gte 拒绝迟到旧写。」

5.2 Hybrid RAG 漏斗工程：BM25 / BM25F + HNSW 向量 + RRF 融合 + Rerank

1. 痛点与本质定义

简历两段项目均以 Hybrid RAG 为核心亮点：NoteWeave 用 「BM25 + Vector 双路召回、RRF 融合与 Rerank」（单轮 Recall@10 从 0.66 提至 0.87，MRR 从 0.51 提至 0.78），制造业用 「故障编码、全文与向量三路召回、RRF 融合与重排」（防穿越 Hit@6 达 85%）。面试必考每一层的算法数学直觉与参数定法。

2. 底层机制与算法公式精讲

  • 为什么纯稠密向量不够，必须上混合检索？
    • 稠密向量模型（bge-m3 1024 维双塔 Bi-Encoder）把整段文本压缩进固定维度连续向量，擅长抓「主轴转起来发烫异响 ≈ 电主轴温升异常振动」这类跨措辞语义泛化，但有致命信息瓶颈：极易混淆仅差一位数字的工业报警码（E2041 vs E2014）、错误码（ERR_4031）、精确软件版本号或生僻专有名词。
    • NoteWeave 定制分词 BM25：英文与符号配 word_delimiter_graph（索引端加 flatten_graph）将 ERR_4031 拆为 ERR、4031 并保留原词，中文用 cjk_bigram 二元切词（NoteWeave 单轮专有名词题 Recall@10 直接从纯向量的 0.48 飙升至 0.93）。制造业则扩展为 故障码 GIN 数组精确路 + zhparser 工业词典全文路 + 向量路 三路互补。
    • BM25 打分三要素与 BM25F：相比传统 TF-IDF 词频无限线性增长，BM25 引入 ① 词频饱和度参数 k_1（默认 1.2，词重复出现多次后收益递减收敛上界）、② 文档长度归一化 b（默认 0.75，惩罚啰嗦长文档偶然撞词）、③ 逆文档频率 IDF（越稀有的专有词权重越高）。NoteWeave Wiki 检索采用的 BM25F 则进一步对「页面标题、摘要、正文」赋予递减字段权重（标题命中远重于正文顺带提及）。
  • HNSW（Hierarchical Navigable Small World）分层小世界图参数调优：
    • 检索过程：借鉴跳表思想构建多层近邻图，顶层极其稀疏做大步跳跃导航，逐层贪心向距离 Query 向量最近的邻居收敛，到底层第 0 层做精细近邻搜索。
    • NoteWeave 三个核心参数：m = 16（每个节点双向连接的最大邻居数，越大召回越高但内存与建图开销线性涨）、ef_construction = 100（建图插入节点时动态维护的候选列表大小，决定图拓扑质量）、查询期 k = 50, num_candidates = 100（每个分片搜索时保留的动态候选池，取 2×k 兼顾召回与延迟）。带墓碑过滤时必须把 must_not 塞进 knn.filter 走图遍历期预过滤（Pre-filtering），边走图边跳过废节点凑够 50 个有效近邻，否则后过滤会被废切片占空名额。
  • RRF（Reciprocal Rank Fusion，倒数秩融合）公式与为什么不用分数加权？
    • 标准公式：

      RRF_Score(d) = Σ(r ∈ R) (1) / (k + rank_r(d))
      其中 R 为各召回路，rank_r(d) 为文档 d 在第 r 路中的正整数名次（从 1 开始），平滑常数取业界验证稳健值 k = 60（抑制单路排第 1 的极端孤证霸榜，奖励在多路均排前列的高共识候选）。

    • 为什么不用线性加权 α·BM25 + (1-α)·Cosine 或 Min-Max 归一化？ 因为 分数量纲与分布形态完全异构：BM25 分数区间为 [0, +∈fty) 无上界，一旦撞上罕见高 IDF 词某条分数可能飙到 30 多分，做 Min-Max 会把其余正常的 8 分、9 分全部压扁到 0.2 以下。而 bge-m3 余弦相似度往往挤在 [0.65, 0.85] 极窄区间。RRF 只看序数名次不看绝对分值，免调参、对异常离群高分免疫（代码实现时按切片 ID 去重累加各路贡献）。
  • Rerank 交叉编码器（Cross-Encoder vs Bi-Encoder 漏斗分工）：
    • 粗召回双塔 Bi-Encoder 将 Query 与切片独立编码成单个向量再算余弦，切片向量可离线预计算建索引，毫秒级扫几十万条，但丢失了词与词之间的细粒度注意力交互。
    • 精排模型（bge-reranker-v2-m3）采用 Cross-Encoder：将 [CLS] Query [SEP] Chunk [SEP] 拼接在一起送入 Transformer 全层自注意力，让问题里的限定词与原文每个字逐层交叉比对，精度极高。但代价是无法离线预计算索引，每次查询必须实时跑 N 次前向推理，耗时与候选数严格线性正比。因此采用「双路各 50（或三路各 20）→ RRF(k=60) 合并去重截断 Top-30 → Cross-Encoder 精排取 Top-6 进上下文预算」的黄金三级漏斗，20 QPS 下端到端检索+精排 P95 ≈ 180ms。

3. 学生视角脱稿背诵

【脱稿背诵】：「两个项目我都搭了『多路粗召回 → RRF 融合 → 交叉编码器 Rerank』的三级漏斗。粗召回阶段双塔向量能离线建图算语义泛化，但对报错码、故障码和生僻专有名词很钝，所以我配了定制分词的 BM25（工业场景还单独加了一路故障码 GIN 数组精确匹配）。多路合并没用线性分数加权，是因为 BM25 无上界而余弦相似度挤在窄区间，极端高分做归一化会把正常候选压扁，改用 k=60 的 RRF 倒数秩融合只看排名不看绝对分值，既免调权重又天然奖励多路共识候选。融合出前 30 条再交给 bge-reranker-v2-m3 交叉编码器把问题和切片拼起来跑全注意力精排取前 6 条，在 NoteWeave 单轮评测里把 Recall@10 从纯向量的 0.66 拉到了 0.87、MRR 从 0.51 拉到了 0.78。」

2. 系统设计权衡（共用一套索引底座，按策略模式分叉组装）

  • 章节树结构化切片底座（优于定长硬切与昂贵语义切分）：
    • 固定字符硬切会把跨页表格、代码块和章首适用前提拦腰斩断（制造业手册更会导致子块丢失小节标题上的适用机型与固件版本限定）。全量调 Embedding 算句间相似度做语义切分入库太贵太慢。

  • QA / Note / Wiki 三种证据粒度为什么分叉？
    1. QA（精准点状事实问答）：重多源高精对比，走双路 50 → RRF 30 → Rerank 6，且把最高分证据排在证据区最前面防长文注意力衰减。
    2. Note（长文精读归纳：两级资料定位 + 前后各 2 块连续窗口）：精读往往聚焦某篇资料某一大节，若直接在全库碎切片里搜，前 6 条散落在五篇不同文章里拼不成连贯推理（按文档切片分求和又偏向长文、取最高分易被偶发词带偏）。故入库额外建「资料摘要」与「小节标题+首段」轻量索引项，先锁定最相关的 1～2 份资料与目标小节，再顺 MySQL (doc_id, section_path, seq_no) 联合索引把命中切片前后各扩 2 块拼成连续原文窗口并附上章首前提。
    3. Wiki（长期知识沉淀：BM25F + 有界一跳扩展 + 段落级来源回链，为什么不上 GraphRAG？）：
      • 检索用 BM25F 选 Top-3 种子页，顺「共享来源资料 / 显式主题引用」有向边最多扩展一跳、上限 6 页控住 Token 预算。
      • 为什么拒用重型 GraphRAG？ ① 全量让大模型抽三元组实体关系建图并做社区聚类摘要，Token 入库成本高出几个数量级。② 最致命的是无法低成本精准撤回：一旦用户删掉某份原始资料，很难反推知识图谱里哪些融合边和社区摘要该同步擦除。而我们的有界页面结构在每个 Wiki 段落精确挂载来源 (doc_id, chunk_id) 回链，删资料时顺回链直接定位受影响页面做毫秒级/秒级局部重算并推高版本指针即可。

6.1 Table-as-State 深度研究、Plan / Replan、分层 Verifier 与工业 HITL 边界

1. 痛点与本质定义

简历在 NoteWeave 职责 1 提出核心架构 「以 Table-as-State 为核心的 Deep Research Agent」，而在制造业职责 3/4 则采用 「隔离式单步受控流水线 + HITL 人工在环」。面试官必问：Agent 常见编排范式各自有什么缺陷？Table-as-State 怎么克服的？为什么跟 LangGraph 不一样？为什么制造业不用自主 Agent？

2. 系统设计深度对比与工程机制（源自 02_Table-as-State深度研究与追问.md 与 deep-research-design.md）

  • 主流 Agent 编排范式演进对比：
    1. 自由 ReAct（Reasoning + Acting 循环）：边想边调工具把所有 Observation 不断往一个消息列表里塞——步数一多（10+ 步），上下文急剧膨胀稀释注意力，极易漏查研究维度、目标漂移或在查不到的死胡同里原地打转。
    2. 静态 Plan-and-Execute：开局一次性列死线性步骤列表，执行途中发现某篇博客没写具体 JDK 版本号或某概念需拆细时，缺乏精准定位哪个单元缺证据并局部改词补查的机制。
    3. Reflexion：靠模型自我反思追加文字教训，反思文本仍堆在上下文里且同模型「自己审自己」极易顺着错误推理自我说服（Sycophancy 附和偏差）。
    4. NoteWeave Table-as-State（六阶段单一主链 + 显式数据库状态表）：
      • 克制智能体边界与前置探路定档：仅划分 1 个主控 Lead Agent + N 个同构 Research Subagent（按任务卡切换探路、深挖、反证三种模式，其余环节均为确定性流水线步骤）。开局先派 1～4 路并行探路（无原文支撑候选直接过滤，按独立主域名数与工作区命中客观预排），主控一次合并建表后锁定 QUICK(1×4) / STANDARD(6×6) / DEEP(8×8，活跃格≤48) 档位落入 MySQL，每格是带独立验收口径的最小可验证单元。
      • 按对象分包独立上下文取证与状态解耦：同一研究对象的待查字段打包成单张深挖卡（≤5 列共享长文阅读、逐列独立抽取，超 5 列或来源跨度大拆为 ≤2 张卡），在独立短窗口内跑 8～12 步循环（连续 2 步无新独立来源早停），原文片段与偏移量旁路直写不可变证据库（同场网页快照按网址共享），销毁本地搜索窗口后仅回传轻量候选、适用前提与最多 2 条线索。物理分离执行状态与研究状态，限流或租约超时按原卡重派（≤2 次）不扣减补查配额。
      • 剥离推理的双层异构 Verifier 与独立反证：第一层确定性规则快筛证据存在、偏移量逐字匹配、工作区资料生效版本与量纲换算。第二层物理剥离取证推理过程，仅将「验收口径 + 候选结论 + 原文片段」送入异构家族轻量模型（如 GLM-4-9B，区别于主模型 Qwen2.5-72B）核验支持度与适用前提——异前提无交集分档并存，同前提结论相悖则下一波注入已用文档与主域名黑名单派 1 次独立反证搜寻第三方权威源（独立于 3 次补查配额），仍分歧定为证据冲突并列披露。
      • 波次等待窗口、缺口 Replan 与拆格判环：每波设 3/5 分钟等待窗口不等慢长尾，主控仅对缺口格改词补查（单格 ≤3 次，整场 ≤5 轮，跳过近似旧词），达独立主域名门槛的表外线索受控加行或扩列（≤2 次），粒度过粗归档父格新建待核实子格（不直接复制通过态），新增依赖边先过 Kahn 入度拓扑排序，残余子图跑三色 DFS 揪出环边拦截。
      • 成文前反查与无工具比较降级成文：全档位跑必答点规则反查，DEEP 档另生成几百 Token 论证提纲暴露跨行支撑缺口（最多补查 1 轮后冻结状态表并复用提纲）。成文步骤物理禁用一切检索与联网工具，跨行结论至少引 2 个已采纳格，比较级表述须覆盖全部参比行否则降级分行陈述，随后核对数字、版本号、日期精度不超原文并由轻量模型校验正负极性。
      • 公网不可信网页四层安全防线：① 网页正文包进带边界声明的数据围栏（仅作资料不作指令）。② 锁死搜索引擎返回的原始 URL 白名单禁拼接参数防数据外带。③ 拦截 127.0.0.0/8、10.0.0.0/8、169.254.169.254 云元数据等内网地址防 SSRF，并在实际建连前二次校验 DNS 解析 IP 防 DNS Rebinding（重绑定攻击）。④ 取证子任务仅持只读检索工具无写副作用 + 异构 Verifier 终审。
    5. 对比 LangGraph 状态图：LangGraph 擅长管节点跳转控制流，但它的全局 State 是单个大对象（靠 Annotated reducer 合并并发分支输出），多执行者跨进程并发修改不同格子并拦截超时慢节点迟到写回仍需自己造锁。拆成 MySQL 单格行记录可直接利用行锁与 Fencing Token 独立并发提交。
  • 为什么制造业平台不用自主多轮 Agent 而坚持固定流水线 + HITL？
    • 工业拆修涉及强电柜高压电击、液压蓄能器残压喷射与 ERP 库房领料扣账，安全上不能容错，且自部署模型的总并发配额仅 10 路。做成开放 ReAct 循环不仅把耗时拉长到三四十秒吃光并发配额，还曾出现漏写断电验电挂锁（LOTO）与混用 DX-560B 不同功能部件轴承（主轴前端 70 系列角接触球轴承 vs 进给丝杠 TAC 系列推力支撑轴承）及不同产线选配主轴（BT40 vs HSK-A63）的坏例。因此坚持单步受控生成 + Java 策略链硬校验 LOTO 与选配部件子 BOM（不过带报错自动重修 1 次）+ 班组长 HITL 事前一键审批冻结快照后再异步提单 CMMS，一次审批通过率达 80.9%（93/115）。

3. 学生视角脱稿背诵

【脱稿背诵】：「多轮检索如果直接跑自由 ReAct，几十篇网页堆在一条对话历史里极易上下文膨胀漏查维度。静态 Plan-and-Execute 在开放课题下又容易盲拆且没法回头纠偏。所以在 NoteWeave 里我设计了以 Table-as-State 为核心的六阶段闭环：先多视角前置探路摸清对象，一次定档在 MySQL 里建最多 8 行乘 8 列的『研究对象 × 待验证字段』状态表。再按对象分包（单卡不超过 5 列）在独立上下文并行取证并将原文片段外置进证据库。候选回来先过 Java 偏移量、资料版本和量纲核验，再剥离推理过程交给异构家族的 GLM-4-9B 做双层 Verifier，缺口格局部改词 Replan（拆格跑 Kahn 加三色 DFS 判环），遇到同前提冲突就注入已用域名黑名单派独立反证，最后经提纲反查后拔掉所有工具按表成文并核对数字日期精度，把 20 道冻结研究题离线评测的有效单元完成率从 67%（94/140） 提到了 83%（120/145）。反过来在制造业实习项目里，因为拆修关乎高压电安全且自部署模型只有 10 路并发配额，我们坚决不用开放多轮 Agent，而是走固定单步流水线加 LOTO 安全前提、选配子 BOM 硬规则校验和班组长 HITL 事前审批，这就是我理解的 Harness Engineering——根据场景容错率给概率模型套上恰当强度的确定性护栏。」

6.2 Context Engineering、Prefix KV Cache 物理原理、长期 Memory 与 信息缺口门控

1. 痛点与本质定义

简历在 NoteWeave 职责 3 与开源贡献 TencentDB Agent Memory 双重聚焦上下文与记忆治理：一边是 「分层编译 Topic-aware Window、会话持续约束与增量摘要……经『候选提取—门控晋升』沉淀长期 Memory，限定于表达参数控制并与资料 Evidence 事实层隔离（Token 降 34%、事实通过率 92%）」。另一边是 MemoryProxy 的 「信息缺口门控替代关键词触发 + 五段固定前缀装配」。

2. 底层机制与系统设计精髓（源自 04_Context编译与长期Memory治理.md 与 TencentDB 精炼全册）

  • Prefix KV Cache（前缀缓存）物理机制——串联三段经历的核心性能铁律：
    • 自回归大模型（Decoder-only）受单向因果掩码（Causal Mask）约束，第 t 个 Token 的 Key/Value 状态严格依赖前 0 … t-1 个 Token 的精确序列。推理引擎（如 vLLM Automatic Prefix Caching 基于 PagedAttention 物理块，每块 16/32 Token）对每个块计算包含前序所有块哈希的级联块哈希（Block Hash）。
    • 一字节击穿灾难：只要提示词在最前面第 100 个 Token 处塞了一个每轮跳动的当前秒级时间戳、或者逐轮动态更换了置顶工具卡/摘要，从第 100 个 Token 往后的整段几千乃至几万 Token 历史与源码 KV Cache 全部哈希失配作废，被迫重新跑极其耗算力的 O(N²) Prefill。
    • 三段经历统一的置顶防击穿架构：
      1. NoteWeave 七段编译（总预算 16,384 Token）：将 [1] 静态系统指令（1,200）+ [2] 会话持续约束（200）+ [3] 不可变话题摘要（1,500） 合计 2,900 Token 死死钉在最前面，且未覆盖消息攒够 4～6 条步长（连续 2～3 轮问答） 才经 Kafka 异步升版摘要，窗口期内缺口按 (session_id, msg_seq) 补拉原文放在动态第 4 段（3,800）——保证连续 2～3 轮追问期间前 3 段逐字节恒定。两级 [#序号] Provenance 定位回放（1,500）、向资料倾斜的当轮重检 Evidence（5,400）、长期记忆表达块（200）与当前问题依次排在动态尾部区。
      2. TencentDB MemoryProxy 五段固定装配：早期每轮自动检索记忆塞进前缀直接打碎几万字代码缓存而下线。我改造后固定 [1] 共享协议 + [2] 信息缺口门控 + [3] 会话级能力裁剪工具卡 三段静态置顶（进程内按 模板版本 + 会话能力签名 缓存），动态目录置底，宁可只做会话级静态压缩 27.02%，也不做逐轮 Query 动态抽 1～2 张工具卡（省几百字却击穿后面几万字源码 KV Cache，因小失大）。
      3. 制造业静态 Schema 置顶：保持全局固定静态 JSON Schema（不把每单动态变化的候选切片 ID 写进 Schema enum），常驻命中 vLLM 服务端受限解码有限状态机（FSM）编译缓存。
  • NoteWeave 不新增串行调用的 Guided Decoding 流式 JSON {i,r,d,s} 路由与长期 Memory 四道门控：
    • 受限解码固定键序 JSON：改写小模型输入压薄为最近 4 轮短摘与话题标题行，走 Guided Decoding / FSM 约束解码流式输出极简固定键序 JSON {"i":...,"r":...,"d":...,"s":"..."}（i 意图 780 轮准确率 726/780 ≈ 93%，误判不检索仅 4/612 轮），设 64 字符/400ms 超时护栏，避免纯文本格式漂移，超时自动退回资料问答 + 高 IDF 词覆盖与话题均值余弦规则退路。
    • 为什么自动记忆会污染事实，怎么隔离？ 若把对话中临时讨论的猜测或旧版文档数字自动存进跨会话记忆，下周资料更新后旧记忆就会像幽灵一样覆盖新事实。因此严守「事实每轮从资料重检 Evidence，跨会话长期记忆只存程序性表达规范」：仅用数据围栏包裹用户本人消息抽取 8 个正交表达槽位（语言/篇幅/风格/约束/结构/表格/术语规范/交互），主表建 (user_id, slot, scope) 唯一约束（全局用非空哨兵 'GLOBAL' 替代 NULL，规避 MySQL 唯一索引允许多个 NULL 的大坑）。因单用户生效记忆最多仅 8 条（<250 字），不另建记忆向量库而直接全量送 7B 做跨槽语义冲突检测。经① Beta(α, β) 后验平滑置信度、② EMA 指数移动平均效用、③ 风险分 <0.70、④ 剔除单轮临时要求四道门控无冲突才升 ACTIVE，任何负反馈或效用跌破 <0.40 直接合并降级回 PENDING_CONFIRM（待确认） 移出自动注入池。
  • TencentDB 读取侧「全局三步信息缺口门控」：
    • 为什么不用关键词（87.14% 误调用）、不用向量相似度路由（分不清「主题相关」与「窗口缺证据」）、也不挂前置 7B 路由小模型（看不全几万字本地代码与多步同轮新 Observation，全传又多一跳长文 Prefill 延迟）？
    • 复用握有完整上下文的主模型执行三步判断：① 判窗口充分性（自包含编码或已在对话/L3 画像/前序返回中出现则拒识，同时钉死两条防漏调硬边界：L2 路径摘要不等于场景正文，Skill 名称简述不等于流程正文）。② 按证据类型优先级路由家族（事实约定走 Memory、步骤模板走 Skill、跨文件调用图谱走 Knowledge）。③ 最小跳步够用即停。有效负例误调用率从 87.14% (122/140) 暴降至 31.94% (46/144)（坦诚正例发出率 ECR 由 96.08% 回落至 77.88% 的召回换精度权衡）。

【脱稿背诵】：「做长会话和编码 Agent 上下文工程时，最容易踩的两个坑是『打碎 Prefix KV Cache』和『记忆污染事实』。因为因果掩码要求从第 0 个 Token 起字节一致才能复用块级哈希缓存，我在 NoteWeave 七段编译里把静态指令、会话约束和不可变摘要前 3 段 2,900 Token 置顶，攒够 4 到 6 条消息才异步升版摘要、滞后差额用原文补在动态第 4 段，让同话题连续两三轮追问前缀逐字节不变。在 TencentDB 里也是同样道理，固定前三段静态协议和会话级裁剪工具卡，不做逐轮换卡免得击穿后面几万字源码缓存。至于记忆治理，两个项目正好一写一读互补：NoteWeave 是写入侧门控，坚持事实每轮重检资料，长期记忆只从数据围栏用户消息里抽 8 个表达槽位，过 Beta 置信度和 EMA 效用等四道门控才晋升、负反馈降回 PENDING_CONFIRM，平均输入 Token 降了 34%（9,860 -> 6,510），250 个检查点事实通过率从全量回放截断的 89% 提到 92%。TencentDB 则是读取侧信息缺口门控，复用主模型先判窗口缺不缺证据并卡死『目录摘要不等于正文』两条防漏调边界，不增加网络延迟把误调用从 87.14% 压到了 31.94%。」

6.3 Structured Output、MCP、SKILL.md 五段流水线与运行时契约工具卡

1. 痛点与本质定义

简历密集出现了四大结构化与工具协议关键词：Structured Output、MCP、SKILL.md + Schema、运行时契约生成工具卡。面试官常把 Function Calling、MCP、Skills、A2A 放在一起考正交分层。

2. 底层机制与工程落地细节

  • Structured Output（受限解码 Guided / Constrained Decoding）底层原理与能力边界：
    • 怎么让输出语法稳定合法？ 不同于只在提示词里求模型「请输出 JSON」，推理引擎（如 vLLM 集成 outlines / xgrammar）将 JSON Schema 离线编译为上下文无关文法（CFG）或有限状态机（FSM / Pushdown Automaton）。在自回归每一步 Decode 生成下一个 Token 前，根据当前状态机所处位置动态算出允许接续的合法词表子集掩码（Token Mask），将所有破坏括号闭合、缺必填字段或类型错乱的非法 Token 的 logits 直接置为 -∈fty（概率归零）。
    • 两大工程边界：① 只管语法结构合法，不管内容事实真假——模型仍可能在合法的 JSON 字段里填一个编造的页码或漏掉安全断电步骤，所以必须配「前置证据门控 + 后置确定性代码校验（偏移量/页码/压力扭矩正则/LOTO/子 BOM）+ 局部带错重修 1 次」。② 保持全局固定静态 Schema 以复用服务端 FSM 编译缓存，同时客户端显式检查 finish_reason != 'length' 拦截超长截断半截 JSON。
  • 四大 Agent 协议正交分层全景：
    1. Function Calling：模型层单步原语——模型把自然语言意图转成结构化函数名与参数 JSON，工具怎么注册和执行耦合在单个宿主应用进程内。
    2. MCP（Model Context Protocol）：宿主应用（Host/Client）连接外部工具与数据源（Server）的标准化进程间/跨网协议，基于 JSON-RPC 2.0 暴露 tools/list、tools/call、resources、prompts。本地进程通信走 stdio，远程通信已从早期难过企业网关的双通道 HTTP + SSE 演进为单端点按需升级流式并支持断线续传的 Streamable HTTP。
      • NoteWeave MCP 落地细节：严守全项目仅封装 2 个重依赖多模态工具——① faster-whisper 语音转写工具。② 视频关键帧抽取与板书多模态理解工具（读取真实显示时间戳 PTS，在 ProcessPoolExecutor 中计算 64 位 DCT 感知哈希 pHash，相邻帧汉明距离 < 10 判为重复画面滤除编码噪点，入库全片稀疏抽帧与讲义生成局部时间窗高分辨率补抽复用同一工具的不同档位参数）。传输大视频不走 JSON Base64 塞爆报文，而是传 15 分钟有效期的 MinIO 只读 GET / 单次受限目录 PUT 预签名 URL。启动时校验工具描述哈希防 MCP 工具描述投毒（Tool Poisoning）。
    3. SKILL.md（渐进式规程包）+ 五段流水线：首轮仅向模型暴露轻量目录简述，命中任务才加载完整 SKILL.md 写作规范与 JSON Schema 渲染契约。NoteWeave 用模板方法模式固定「取材（冻结下单时资料 proc_version）→ 规划（每页独占论点素材）→ 写作（逐页受限解码防一次直出 20 页尾部注意力退化截断）→ 代码校验（超宽/字数/引用核验，单页异常仅局部重修该页 1 次）→ 策略渲染（python-pptx / XeLaTeX）」五段骨架，新增产物类型仅需加一份契约目录与渲染策略类。
    4. TencentDB 低侵入 Shell + curl + 三层运行时契约工具卡编译器（对比 MCP）：因产品要求不改 Codex CLI / Claude Code 一行代码、不让用户本地装 MCP（只需改一行 API Base URL 指向 MemoryProxy），故借宿主原生自带的 Shell 发 curl 调 Bridge 网关（安全鉴权由服务端网关按会话令牌强校验，只读会话乱拼写接口直接返 403）。为解决无原生 Schema 易拼错参数断链，设计「底层 Runtime Contract 对齐源码路径与必禁参 → 中层 Strategy IR 写明成对适用/避开边界、相邻工具区分及同次业务成功响应的 Skill ID + 版本号 + 路径 强绑定 → 顶层 Capability Pruning 会话级裁剪」三层编译器，配 7 文件 183 项单测（含故意删改限制词必报错的负向断言），将工具说明从 3,518.0 压至 2,567.5 Token（-27.02%），条件首步命中率从 27.55%（27/98） 提至 74.07%（60/81）（全量正例口径同步从 26.47% [27/102] 提至 57.69% [60/104]）。
    5. A2A（Agent-to-Agent Protocol）：面向跨团队/跨组织黑盒自治 Agent 对等协作，通过 Agent Card 发现能力并围绕长耗时状态机 Task 交换 Artifact 产物（与面向确定性工具调用的 MCP 互补）。

3. 学生视角脱稿背诵

【脱稿背诵】：「这几个协议处于不同层级：Function Calling 是模型输出函数参数的单步原语，工具耦合在单应用里。MCP 用 JSON-RPC 2.0 统一了宿主与外部工具服务的通信，我在 NoteWeave 里把吃显存和依赖 FFmpeg 的 faster-whisper 转写与 pHash 关键帧理解拆成独立 Streamable HTTP MCP 服务，传 15 分钟 MinIO 预签名链接免传大字节流，让研究和产物两个模块直接共享。而产物内部用 SKILL.md 管怎么写好、用静态 JSON Schema 受限解码屏蔽非法词表保证每页结构能被 python-pptx 和 XeLaTeX 稳定渲染，遇到超字数只单页重修 1 次。到了开源项目 TencentDB 里，因为透明代理要求用户不装插件只改一行 Base URL 接入第三方 CLI，没法挂 MCP，我就设计了运行时契约、策略表示、能力裁剪三层编译器配 183 项单测生成 Shell + curl 工具卡，强绑定同一次有效响应的版本号和附件路径，把 Token 压了 27.02%，条件首步命中率从 27.55% 拉到 74.07%，全量正例口径也同步从 26.47% 拉到了 57.69%（命中题数从 27 涨到 60）。」

6.4 Agent Evaluation 评测方法论、LLM 推理底座（GQA · FlashAttention）与微调边界

1. 痛点与本质定义

简历三段经历都给出了定量评估指标，尤其开源贡献构建了 39 个仓库、1,140 条正负样本基准与受控对照框架。面试官必深挖：怎么防过拟合和刷分？为什么不用 LLM-as-a-Judge？为什么 Complete 翻倍但 Strict 涨得少？为什么模型并发配额只有 10 路、怎么拆？为什么不上 SFT 微调？

2. 评测防作弊体系与底层推理基础

  • 三段经历四大评测防作弊硬核设计：
    1. 防时间穿越与同源泄漏（制造业 Hit@6: 85%）：初版随机切分 180 道有解题跑出 165/180 (91.7%) 虚高，排查发现混入了故障发生之后才补录的事后完修案例及同一异常轮次的衍生题。重做按工单发生时刻可见知识批次截断 + 按独立异常轮次簇分组隔离后，剔除 12 道穿越题拿到真实 153/180 = 85.0%（另 20 道超纲无解题在生成前全部被门控拦下）。同时用 2×2 四格表对平 153 道 Hit@6（148 放行 + 5 擦边附注拦下）与 156 张放行诊断卡（148 + 8 基础 SOP 放行），371/390 = 95.1% 获工程师逐条核验支撑。线上用两条同构产线、甲乙两班组 4 周按周交叉轮换 + CMMS 硬节点时间戳取中位数（20.5 -> 13.2min，-35.6%）抵消人与设备偏差。
    2. 防少拆格刷分与裁判同源偏见（NoteWeave 离线评测 67% -> 83%）：离线评测有效单元完成率以活跃规划格子（不含不适用豁免格）为分母（94/140 -> 120/145），为防止主控建表时故意少建难查的列刷高比例，强制统计对比题点名实体覆盖率，并用异构模型家族评 3 次取多数投票逐项核对每题预埋的 3 个必答要点。
    3. 资产先行反推 + 逐字节正负 Pair + 双口径恒等式自证（TencentDB test1k）：
      • 基于 39 个真实仓库固定 Commit，先从真实代码与提交历史提炼记忆/技能资产，再反推构造 464 组逐字节相同的用户 Query 正负配对（正例窗口缺答案必须调，配对负例窗口已贴出答案严禁调，外加 109 条同主题外队干扰 + 103 条纯通用编码 = 676 负例，合计 1,140 条），冻结前过 3 项防泄题扫描，并采用确定性工具调用轨迹漏斗规则判分（检验真实 Shell 执行记录、HTTP 状态码与跨步参数绑定，拒绝噪声大的 LLM-as-a-Judge 看回答文本打分）。
      • 主动坦诚双口径防缩分母质疑：前 250 条受控对照有效样本（Baseline 242 = 102正 + 140负，V4 248 = 104正 + 144负），汇报简历上的已发出条件首步命中率 TSR_cond: 27.55% (27/98) -> 74.07% (60/81) 时，同步给出全量有效正例口径 TSR_all: 26.47% (27/102) -> 57.69% (60/104)，二者满足恒等式 TSR_all = ECR × TSR_cond，堂堂正正证明真实验证命中数从 27 条翻倍涨到了 60 条，绝非靠压低 ECR 缩分母刷出来的。
      • 高阶加分拆解：为什么 Complete 从 25.49% (26/102) 翻倍到 55.77% (58/104)，而一步不多调的 Strict 仅从 15.69% 到 19.23%？ 通过恒等式 Overcall = ECR - Strict 拆成两半看：未完链盲目乱试（ECR - Complete）从 72/102 (70.59%) 暴砍超三分之二降至 23/104 (22.12%)。而完链后求稳多查一步（Complete - Strict）从 10/26 变为 38/58——这是典型的难度迁移（Simpson 效应）：Baseline 完成的 26 道大多是简单的 1 跳直读题，而 V4 新救活的 +32 道全是复杂的 2 跳/3 跳跨工具链路，编码模型在改代码前习惯保守再发一次确认查询，这也直接驱动了下一步在 Bridge 网关层做等价检索幂等短路与返回头增加 sufficiency=complete 停止信号。
  • LLM 推理底座通用知识（不绑定具体机器）：
    • GQA（Grouped-Query Attention，分组查询注意力）让多个 Query 头共享一组 KV 头，把 KV Cache 显存压到传统多头 MHA 的几分之一，兼顾多头表达力与低显存，优于全共享单头的 MQA。
    • 单 Token KV Cache 的手算公式（K 和 V 各一份乘 2）：

      2 × 层数 × KV头数 × 头维 × 每元素字节数

    • 底层算子与调度加速：RoPE 旋转位置编码通过复数平面旋转使注意力内积仅依赖相对距离。Prefill 算力受限、Decode 显存带宽受限，FlashAttention 将 Q/K/V 分块加载进 GPU 高速片上 SRAM 配合 Online Softmax 一趟算完，免去读写 O(N²) 巨型 HBM 注意力矩阵。Continuous Batching（Iteration-level 连续批处理） 在每个生成步踢出已输出 EOS 完结的请求并立刻补入新排队请求，配合 PagedAttention 按非连续页块管理显存消除内外碎片。
  • 什么时候选 RAG vs LoRA SFT vs DPO / GRPO？
    • 高频动态事实、资料可见范围隔离、秒级撤回与原文页码溯源 → 必选 RAG（微调记不住精确故障码扭矩且撤回资料无法从权重里擦除）。
    • 固化特定垂直输出格式、领域黑话或私有 DSL → 选 LoRA SFT：冻结原权重 W_0，旁路训练低秩矩阵 Δ W = (α) / (r) B A（r ≪ d）——必考初始化细节：矩阵 A 用高斯随机初始化、矩阵 B 用全 0 初始化（保证训练第 0 步 Δ W = B A = 0 不破坏预训练底座，若两边全 0 则梯度死锁为 0 无法更新），上线前离线合并 W' = W_0 + (α) / (r) B A 实现合并后不增加推理延迟。
    • 对齐偏好与多步工具决策强化 → 选 DPO 或 GRPO：有成对正负偏好样本用 DPO 闭式隐式奖励直接优化免训奖励模型。像我们有确定性单测或工具轨迹判分器时用 GRPO，同题采样一组轨迹按组内均值标准差归一化算优势，省去与主模型同规模的 Critic 价值网络省近半显存。

3. 学生视角脱稿背诵

【脱稿背诵】：「做 Agent 优化如果先改提示词再找几个例子试，很容易拆东墙补西墙，所以我三段项目全是评测先行。比如开源项目构建 test1k 时，我基于 39 个仓库固定提交反推造了 464 组逐字节相同提问的正负 Pair，专门考模型能不能区分『主题相关』和『窗口真缺证据』，并用确定性轨迹规则判分替代不稳定的 LLM 裁判。汇报首步命中率从 27.55% 提到 74.07% 时我也主动同步报全量口径 26.47% -> 57.69% 自证没靠缩分母刷分，还通过拆解 Overcall 发现未完链乱调已经暴降三分之二，剩下的多调主要源于多跳难题救活后的求稳复查。在模型并发上，实习项目自部署的 32B 模型由内网模型网关给我们划了 10 路并发配额，我没有去猜硬件，而是按诊断 4 路、草稿 6 路拆分线程池和信号量，线程数对齐配额，超出配额只丢唤醒信号，任务留在库里排队。」

6.5 全简历核心评估指标、统计概念与手算公式总表（面试一问就答）

面试官听到 Recall@10、MRR、nDCG@10、Hit@6、P95、微平均、TSR_cond / TSR_all、pp、利特尔定律、Beta / EMA、Cluster Bootstrap 时常会顺口插问「这个指标怎么定义的、公式怎么写、跟旁边那个有什么区别」——一表彻底打通：

指标 / 公式名称所属项目核心含义与精确计算公式手算小例 / 为什么选它（与相邻指标区别）
Recall@K（如 Recall@10）NoteWeave（0.66→0.87）前 K 条结果召回了多少比例的全部标准相关证据：`Recall@K = \Top-K 命中相关集\/ \全部标准相关集\`（跨题取均值）某题共有 4 条标准证据，前 10 命中 3 条则 0.75。只看找得全不全，不关心排第 1 还是第 10
MRR（平均倒数排名）NoteWeave（0.51→0.78）只看第一条正确证据排在第几位：`MRR = (1 / \Q\) × Σ (1 / rank_first_i)`首位命中 1.0、第 2 位 0.5、第 5 位 0.2、未中 0。最能检验 Cross-Encoder 重排把最关键证据顶到最前排的效果
nDCG@K（如 nDCG@10）NoteWeave（0.57→0.80）同时衡量分级相关性与位置折损：DCG@K = Σ (2^{rel_i} - 1) / log2(i + 1)，nDCG@K = DCG@K / IDCG@K越靠后按 log2(i+1) 衰减折损，除以理想排序 IDCG@K 归一到 [0, 1]，全面刻画排序质量
Hit@K（如 Hit@6）制造业（153/180 = 85.0%）二值命中率：前 K 条至少命中 1 条核心标准切片的题数 / 总有解题数工业诊断只要把关键故障规程召进 Top-6 即可生成正确诊断卡，故看二值 Hit@6 而非全集召回
微平均 vs 宏平均NoteWeave 职责 1（67%→83%）微平均：Σ 各题有效格 / Σ 各题活跃格 = 120 / 145 = 83%；宏平均：先算每题完成率再平均按格子等权计分，防止 4 格简单题与 20 格复杂题权重相同导致虚高
