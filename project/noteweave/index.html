01研究状态落表：Table-as-State 与两层验证

开放式研究容易漂移、证据不足时编结论、中断后只能整段重来。把研究状态收成一张表，状态中心是“格子”，而不是一段越写越长的笔记。

规划阶段把问题定成表：行是研究对象，列是待核验字段，每一格是一个研究单元，独立保存候选、证据链和判定。执行按格派发、验证按格进行，失败只对缺口格局部重规划；冲突证据保留双方，反证次数有上限。Host 是权威状态的唯一写者，Worker 无状态，只做检索与抽取、交回候选；每一波结束写检查点，恢复时只重新领取未验证的格。

验证分两层。格子验证先规则短路：没有证据卡判“证据不足”，只有反驳证据判“矛盾”，这两种不调模型；其余交模型判；模型不可用时，只有支持证据的格也只判证据不足，绝不判已验证。引用核验在报告生成后逐条结论进行：引文片段必须落在当时的读取窗口内、证据必须属于这一格、数字和日期逐项比对、否定极性一致，这些确定性检查都过了才让模型判蕴含；模型没跑时按词项覆盖度兜底，数字日期或极性不符直接不过。证据不足是业务结果，如实写进报告。

方案对比

方案怎么做在哪出问题代价结论
Scratchpad / ReAct 长循环模型每轮自己决定搜什么，把过程写进同一段笔记状态无法结构化查询（问不出哪几格已有原文证据）；中断只能重来；错误在笔记里自我强化建模成本几乎为零，但笔记越长越贵只用作单格内临时推理
STORM 类（多视角 → 大纲 → 成文）多视角提问拓宽问题面，整理大纲后按章节写只重做某对象的某一字段不自然；完成率难定义成“已验证格 ÷ 应完成格”面向维基式长文借鉴“规划前拓宽问题面”
Planner + 多个子 Agent主 Agent 定计划，子 Agent 并行搜索后交回综合子 Agent 各写各的发现，没有格子级 CAS / fencing 时后到覆盖先到并行快，但合并协议要自己补用“按格拆子任务”对齐并行
Table-as-State 采用每格独立候选、证据、判定；Host 唯一写者；局部重规划；检查点计划拆错则表就错，必须显式修表；叙事综述不适合硬塞成表表结构与状态机更复杂采用

研究要能量化完成率、能中断后续跑、能拒绝晚到写回，这三件事都要求状态是可查询的格子。放弃的是开放网页上的浏览深度，这一点不与产品级 Deep Research 比。叙事题为主时加重文章化路径，等待人工成为耗时大头时再引入工作流引擎管等待，格子账本仍留在库里。

简历数字定义（公式）不代表什么

02长任务所有权：数据库租约 + fencing 与检查点恢复

研究、产物生成、转写都远超请求超时。Worker 挂掉或长 GC 停顿后醒来时，必须保证旧持有者的结果写不进去。

Worker 领取子任务时，Host 在任务行上写持有者、到期时间、租约代际和 fencing 令牌，领取本身是一条条件更新；Worker 周期性心跳续租，结束时提交带代际和载荷摘要的完成回执。Host 用一条条件更新校验代际和令牌，通过才在同一事务里合并格子状态；租约过期即可被接管，接管使代际加一，旧持有者晚到的回执影响 0 行。外部回调同样校验阶段和代际，超时已判失败并重试后，晚到的回调不会把状态改乱。

方案对比

方案怎么做在哪出问题代价结论
Redis 分布式锁带过期的锁 key + 续期锁与业务库不是同一真源：锁已易主，旧持有者仍会回调写库；续锁失败、时钟漂移、误删锁都说不清所有权要额外做锁与业务状态对账不选
数据库行级租约 + fencing 采用任务行上写持有者、到期、代际、令牌；回执带代际，条件更新校验比 Redis 慢一点；心跳间隔太接近租约时长时，数据库抖动会误判过期要写心跳和过期扫描，表多几列采用
Kafka 分区独占同一 key 进同一分区串行处理格子大多可并行，串行浪费并发；大任务堵住同分区小任务；重平衡会停顿扩容受分区数限制只用于顺序流水
工作流引擎活动心跳引擎管心跳、超时重试引擎状态与格子账本两套真源，宕机后要对账多一套编排运维跨天等待多时再换

完成回执要改的是 MySQL 里的账本，互斥和提交放在同一个库，fencing 才是一条条件更新的事。领取 QPS 大到单库条件更新成为瓶颈时，按工作区分库，或领取改用 Redis、提交仍走数据库 fencing 校验，所有权真源不变。

03异步资料流水线：Outbox 派发、重试与死信

大文件同步处理会阻塞请求，长链路失败难定位。上传后的处理拆成解析、切片、向量化、索引四个阶段，阶段之间只传资料快照 ID。

资料版本落库时，在同一本地事务写入一条任务 Outbox。派发器每秒轮询，领取是条件 UPDATE 并写租约持有者；发往 Kafka 成功后置“已发送”时再校验持有者，两个实例抢同一行只有一个能落“已发送”。普通派发租约 1 分钟；产物任务的派发租约 70 分钟，用来盖住 Worker 一小时的执行超时，进度回调续租。派发最多 5 次，退避为 min(60, 2ⁿ) 秒再加至多 20% 抖动，避免一批记录同时重试；次数耗尽置死信并触发业务死信处理。

消费侧只挡瞬时故障：2 次指数退避重试（约 1 秒、约 2 秒，加抖动）后进入原主题名加 .DLT 的死信主题，任务恢复器把任务标失败，不阻塞分区后面的消息；业务重试交给任务层。每个阶段按“资料快照 ID + 阶段”幂等去重，所以派发器“发送成功、标记前崩溃”造成的重复投递会被吞掉。大批向量化期间，消费者最大拉取间隔取配置值与流水线预算上界的较大值，避免被判定为假死而反复重平衡；静态成员 ID 让重启不触发整组再平衡。

故障处理结果
业务事务提交后进程崩溃Outbox 行已同事务落库，下次轮询发出不丢任务
发送后、置“已发送”前崩溃租约过期重领再发至少一次投递，消费端幂等
两个派发实例抢同一行条件 UPDATE 领取，置“已发送”时校验持有者只有一个成功
Kafka 暂时不可用回到待发送，按退避重试恢复后自动补发
回调型 Worker 收到消息却不回调租约过期再派；次数耗尽由扫描器置死信不会永远卡在“处理中”
状态被并发修改条件 UPDATE 影响 0 行，返回非法转移不回退、不覆盖

方案对比

方案怎么做在哪出问题代价结论
提交后直接发 Kafka事务提交后在代码里调一次发送提交后、发送前进程被杀，资料永远停在“已上传”，且日志没有任何报错代码最短不选
与业务不同事务的消息表单独待发表，定时扫出发业务成功、消息行失败（或相反）的窗口仍在看起来专业，本质是直发不选
Transactional Outbox 采用业务状态与投递意图同事务；派发器带租约发送，重试，耗尽进死信至少一次投递，下游必须幂等多一张表和轮询扫描采用
CDC 读 binlog连接器从日志抽变更转成消息连接器积压或 schema 变更未同步时下游看到旧字段多一套连接器运维扫描压力大时再换

资料版本一旦落库，解析任务绝不能丢；Kafka 事务管不到 MySQL，XA 过重。Outbox 扫描 QPS 持续高于业务写入，或派发延迟从秒级漂到分钟级时，把轮询换成 CDC——CDC 也是 Outbox，只是换了“谁发现新行”，表结构和消费端幂等键都不改。

指标口径

简历数字定义（公式）不代表什么
128 MB单文件上传的配置上限；大文件分片上传后进入上述异步流水线是配置上限，不是吞吐

04按任务选检索：问答、精读、Wiki 三条链路

一条向量 TopK 无法同时满足查事实、通读长文和跨资料整合，三种任务的证据形态不同。

链路适合检索方式证据形态
问答快速查事实BM25 + 向量两路召回 → 加权 RRF → Rerank零散片段
精读长文档连续阅读先定读哪几份资料，再在同一快照里锚定命中处，按原文顺序扩连续窗口连续窗口
Wiki跨资料整合知识页 BM25F + 链接传播 + 图遍历知识页 + 来源回链

问答的两路召回按名次融合：每路贡献 w / (k + rank)，k = 60，向量路权重 0.7、关键词路 0.3（口语提问更多）；中文 BM25 用相邻两字切词，避免单字匹配的噪声。精读在超预算时缩减远处续读，而不是静默删掉锚点附近的原文；相邻窗口保留少量重叠，句子不被拦腰截断；整理出的草稿要人工确认才写回资料。三条链路共用证据预算和工作区 / 快照范围校验。

方案对比

方案怎么做在哪出问题代价结论
只向量查询和切片向量化，按相似度取 TopK编号、接口名、公式符号召回漂移，含公式的段落可能排到二十名开外几乎放弃精确匹配不选
只 BM25倒排 + 词法打分用户换种说法就零召回（“注意力机制” vs “模型怎么决定看哪些词”）语义近似能力弱不选
分数加权融合两路分数归一化后加权相加量纲不同，min-max 对极值敏感：一个罕见词的极高分会把另一路好结果整体压沉；换批查询就要重调需要持续标注校准标注量撑不起
加权 RRF + Rerank 采用按名次融合，路权重区分口语 / 专名，再 Rerank丢掉分数幅度；只有一路能命中的专名题吃亏k 与权重是经验值采用

资料里既有专名也有口语，单路都有盲区；小规模回归集撑不起分数加权的稳定校准，按名次融合不要求分数可比。攒到几千条相关性标注后，再换学习式排序或交叉编码器直接打分。

方案对比

方案怎么做在哪出问题代价结论
精读直接复用 TopK 拼片段取最相关的若干切片换一个笔记 Prompt片段之间有空洞，模型会脑补；跨资料拼接丢掉版本归属，限定条件串资料零额外链路不选
资料级召回 + 连续窗口 采用先定资料，再锚定并按原文顺序扩窗锚点选错时整段通顺的跑题原文更难被察觉多一套资料召回与窗口逻辑，Token 更贵采用

用户要的是读懂一段，而不是相关碎片的拼盘。跨十几份资料做主题综述成为主场景时，再在资料级召回之上加一层综述编排。

05长会话上下文：话题窗口 + 增量摘要

全量回放的 Token 随轮次线性上涨，旧话题还会串进当前回答；固定最近 N 轮又会把早先的约束过早丢掉。

对话按话题切分：每个话题保留最近的原文窗口，更早的内容用该话题的增量摘要覆盖。摘要任务与窗口规划使用同一条边界，已落库的切分不回溯修改，保证不存在“既不在窗口、也不在摘要里”的空洞；摘要只覆盖窗口以外的内容，最近原文始终保留。切分用词项覆盖度和向量余弦各占一半的融合分，只有落在不确定区间的边界才调模型判断，不是每条消息都调。显式要求的数字不依赖摘要“记住”。

方案对比

方案怎么做在哪出问题代价结论
全量回放历史消息全部拼进 PromptToken 线性涨；论文 A 的数据集名被带进论文 B 的回答长会话不可持续只适合短会话
固定最近 N 轮只保留尾部若干轮原文开头约定（如“全部用英文术语”）滑出窗口后被遗忘用“忘”换省钱不选
每次全量重摘要整个历史反复压成一条反复摘要漂移，细节丢失难控摘要成本高不选
话题窗口 + 增量摘要 采用当前话题留原文，关闭话题进摘要话题切错会丢历史；摘要可能压掉数字和限定语切分与摘要链路 + 关键事实回归检查采用

多话题长会话既要压 Token 又要留住后面还会用到的事实，所以 −34% 必须和 92% 一起看。跨会话引用很久以前的内容成为常态时，再加一层长期记忆检索；回放集上切分错误率升高时，把切分全面交给模型并接受更高成本。

指标口径

简历数字定义（公式）不代表什么
−34%降幅 = 1 − Context 编译后平均每轮输入 Token ÷ 全量回放平均每轮输入 Token；同一批长会话离线回放，同一 Token 估算器，只算对话历史不含输出和摘要成本，不是线上省下的钱
92%关键事实检查通过率 = 压缩上下文下答对的关键事实检查数 ÷ 检查总数（数字、截止日期、限定条件等后续会用到的事实）；先关键词规则、再人工判定不是整体回答正确率

06长期 Memory：候选门控与偏好 / 证据分层

自动抽取的记忆可能是误判，一旦生效就会长期污染回答。记忆只控制语气、结构和要避免的写法；事实与引用始终来自资料证据。

对话中抽出来的只是候选。每条候选的证据可信度用 Beta 后验累积：先验按来源区分（用户明说偏高、产物反馈中性、模型推断偏低），每次新的支持或反对证据都更新分布。自动生效要同时满足四道门：后验均值 ≥ 0.70（可信）、后验方差 ≤ 0.04（证据够多够稳）、预期效用 ≥ 0.60、风险 < 0.70；否则进入待确认。风险由类别基础分、作用范围和冲突项相加，冲突检查没跑成也按有冲突计。冲突不靠正反关键词，而是把记忆归到语义槽位（如“输出格式”），同槽位不同取值就算冲突。生效后按与当前问题的相关度注入，使用后的效果反馈再变成新证据更新后验。

方案对比

方案怎么做在哪出问题代价结论
抽到就写入模型抽出偏好立刻生效一次误判长期污染后续回答实现最简单不选
按来源给固定可信度每个来源一个固定分数分不清“说过一次”和“反复确认五次”；效用写入后从不更新简单可解释早期方案，已替换
Beta 后验 + 四道门 + 人工确认 采用均值管可信、方差管证据量，再加效用和风险；不过门进待确认先验与阈值是初始值，未经大样本校准要维护证据更新与槽位冲突采用
记忆参与事实回答把记忆当作可引用的知识事实被记忆污染，错误难以追溯到资料—不选：只控制表达

写错记忆的代价比少记一条更大，所以宁可多进待确认。偏好与资料证据分层后，记忆错了最多影响表达方式，不会改变答案里的事实与引用。
